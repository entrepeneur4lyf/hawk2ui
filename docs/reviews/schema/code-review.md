# Code Review — hawk2ui-schema

**Reviewed at:** `5a042c51` · 2026-05-28 · **Remediated at:** `e7918972` · 2026-05-28
**Scope:** `src/{lib,product}.rs` (2 src files, ~480 LoC; in-source `#[cfg(test)]` only, no `tests/` dir)
**Purpose:** Shared typed schema records for `Hawk2UI` products — host targets, surface kinds, product capabilities, the `ProductModel` conformance record, and a central JSON-Schema *catalog* that aggregates the generated schemas of the build/plugin/plugin-adapters/platform boundaries, with schema generation + document validation.
**Note:** The two actionable findings (#1 validation honesty, #3 deserialize duplicates) were **remediated** at `e7918972` — see the Remediation section. The crate was already Tier-1 clean (no High findings); the remaining items are deferred coherence/cosmetic notes.

## Summary

JSON-Schema generation **and validation are genuinely real, not modeled** — this is the crate's headline capability and it holds. `product_model_json_schema` calls `schemars::schema_for!(ProductModel)` (real draft-2020-12 schema with `$defs`, `oneOf`/`const` enums, and `"additionalProperties": false` from `#[serde(deny_unknown_fields)]` — verified by dumping the output). `validate_product_model_json` compiles that schema with `jsonschema::Validator::new` and calls `validator.validate(value)`, which **actually rejects** invalid documents: a type-mismatched (`"identity": 123`) and an unknown-field (`"unexpected": true`) document both return `is_valid == false` (verified empirically). `schema_catalog()` aggregates nine real schemas from five crates; every entry carries `additionalProperties: false` and `$defs` (verified). No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME/HACK markers, no `unsafe`.

The substantive weaknesses are not stubs but *coherence and validation-completeness* gaps: (1) `ProductCapability` (a closed enum) and the manifest's capability vocabulary (free-form strings such as `"native-windowing"`) are **two unreconciled models with no bridge** — a manifest capability is never checked against the product capability set; (2) `validate_product_model_json` performs **only structural validation** and never invokes the crate's own semantic invariant (`validate_required_surfaces`), so a structurally-valid but semantically-incomplete model (empty surfaces/targets) passes; (3) the `with_*` builders dedup, but `Deserialize` does **not**, so duplicates survive the untrusted deserialize boundary and bypass the builder invariant. No correctness blocker; no High-severity defect. The crate is materially cleaner than its `hawk2ui-a11y`/`hawk2ui-assets` siblings.

## Remediation (2026-05-28 · `e7918972`)

`hawk2ui-schema` was already Tier-1 clean (real `schemars`/`jsonschema`, no High findings). Closed the validation-honesty Medium and the deserialize-integrity Low so the JSON gate matches the in-process builder.

- **#1 — structural-only validation (FIXED).** `validate_product_model_json` previously ran *only* `jsonschema` structural validation, so a structurally-valid but semantically-incomplete model (e.g. no `PluginEditor` surface) passed the public gate. It now also deserializes the validated document and runs `validate_required_surfaces` (the Hawk2UI product is dual-surface by architecture), failing with `schema.product.surface.missing`. Verified safe: the function has **zero production callers** (only the in-crate test, whose complete model still passes); the doc now describes the full structural + semantic contract.
- **#3 — duplicate-bypass on the deserialize path (FIXED).** The `with_*` builders dedup but `Deserialize` does not, so duplicate enum members survived the untrusted JSON boundary and bypassed the builder's set invariant. The gate now rejects them (`schema.product.duplicate-member`) via `enforce_no_duplicate_members`. Tests added for both the incomplete-surface and duplicate-member rejections.

**Not addressed here** (deferred): #2 / #4 — `ProductCapability` (closed enum) is unreconciled with the manifest's free-string capability vocabulary, and there is no surface↔target↔capability coherence check. A manifest-string → `ProductCapability` bridge (plus coherence rules) is a small **feature** that depends on the intended capability vocabulary, not a contained fix. Low cosmetics (#5 `RawManifest` schema method placement, #7 `{:?}` error flattening) left as-is.

## Completeness & implementation gaps

1. **Structural schema validation does not enforce the crate's own semantic invariant** (`lib.rs:60` `validate_product_model_json` vs `product.rs:112` `validate_required_surfaces`). The JSON-validation entry point runs *only* `jsonschema` structural validation. The semantic rule that a production model must advertise both `DesktopWindow` and `PluginEditor` lives in a separate `pub` method that the JSON path never calls. Verified: `validate_product_model_json({…,"surface_kinds":[],"host_targets":[],"capabilities":[]})` returns `Ok`, while `validate_required_surfaces()` on the same model returns `Err(MissingSurface(DesktopWindow))`. So an externally-supplied product document can be "schema-valid" yet violate the model's documented production contract — the two validation surfaces disagree, and the structural one is the public/JSON-facing one. → Either fold the surface/target requirements into validation (a `validate_product_model_json` that also runs the semantic checks) or document that schema-validity is structural-only.
2. **`host_targets` and `capabilities` have no semantic validation at all** (`product.rs`). `validate_required_surfaces` checks only `surface_kinds`. A model with **zero** `host_targets` (no platform to run on) or an empty `capabilities` list passes every validation the crate offers. There is no surface↔target↔capability coherence check (e.g. a `PluginEditor` surface implying `PluginHost` target / `PluginEditorEmbedding` capability). The model is a flat bag of three independent vectors with one cross-cutting rule on one of them.
3. **`ProductCapability` is effectively orphaned and disconnected from the manifest capability model** (`product.rs:30`). The only workspace consumer of `ProductCapability` outside this crate is the `hawk2ui-core` facade *test* (`crates/hawk2ui-core/src/lib.rs`), which merely re-exports and equality-checks a variant. Meanwhile the actual manifest capability surface (`hawk2ui_build::HawkManifest::capabilities: Vec<String>`, validated only as non-empty/space-free in `manifest.rs:243`) uses free-form kebab strings — `"native-windowing"`, `"plugin-editor"`, `"sealed-artifacts"` (see `examples/*/manifest.hawk.toml`). There is **no `From`/`TryFrom`/lookup** mapping manifest strings to `ProductCapability` (verified by grep across the workspace). So the crate ships a closed, typed capability enum that nothing reconciles against the open string vocabulary that real manifests carry: a manifest capability typo (`"natve-windowing"`) is never validated against the product model's known set, and the product model cannot be derived from or checked against a manifest. This is the "manifest/product-model coherence" the model is nominally for, left unwired.

## Code quality & smells

- **`with_*` builders dedup but `Deserialize` does not — round-trip is not idempotent** (`product.rs:70`/`79`/`88`). `with_host_target`/`with_surface_kind`/`with_capability` each guard with `if !…contains(&x)`, so the *builder* enforces set semantics (verified: double-add yields `len == 1`). But the fields are plain `Vec<_>` deriving `Deserialize`, so a JSON document with `"host_targets":["LinuxWayland","LinuxWayland"]` deserializes to `len == 2` (verified) and **passes** `validate_product_model_json`. The "no duplicates" invariant the builder advertises is silently violated on the deserialize path — which is the untrusted boundary. Downstream `supports_surface`/`has_capability` still work (they use `contains`), but any code that iterates or counts these vectors sees duplicates. → Use a set type, or dedup/reject duplicates in validation, or drop the builder dedup so the two paths agree.
- **Catalog registers the *raw* manifest schema via a method on the *validated* type, with a doc that reads as if it were `HawkManifest`** (`lib.rs:79–84`). `schema_catalog` calls `hawk2ui_build::HawkManifest::json_schema()`, but that method emits `schemars::schema_for!(RawManifest)` — schema `title == "RawManifest"`, with optional `identity`/`source` and `capabilities` shaped as `CapabilityDeclaration{keys}` (verified). The catalog *id* `hawk2ui.raw-manifest` is therefore **accurate** (it genuinely is the raw wire schema), and this is the correct schema to validate untrusted manifest documents against. The smell is purely cosmetic and lives out-of-crate: a schema-generating method named/placed on `HawkManifest` (the post-validation type) that actually describes `RawManifest`. Low; mention only.
- **`schema_error` formats with `{error:?}` (Debug), losing structured detail** (`lib.rs:181`). For the five external boundaries it wraps (e.g. `ManifestError`, `PackageDiagnostic`), the catalog collapses a structured error into a `Debug` string inside a `SchemaValidationError`. The owning crates have richer diagnostic types; the catalog flattens them. Minor — these are generation-time failures that should never fire in production — but the lost structure is a smell.
- **No accessor/`From` parity between the two error types.** `SchemaValidationError` exposes `rule()`/`message()` and a `From<…> for Diagnostic`; `ProductModelError` exposes neither accessor and only the `From`. Asymmetric but not wrong.

## Documentation

- Strong: crate-level `//!` on both modules, every public type/field/method documented, and `# Errors` sections on all four fallible public fns (`product_model_json_schema`, `validate_product_model_json`, `schema_catalog`, `schema_catalog_json`). No undocumented public items.
- Minor: nothing documents that `validate_product_model_json` is **structural-only** and does not enforce `validate_required_surfaces` (gap #1) — a reader reasonably assumes "validate" means the full contract. The `ProductModel` doc ("Product conformance model … capabilities") does not flag that `ProductCapability` is disconnected from manifest capabilities (gap #3).

## Testing

- Reasonable for the happy path: `schema_catalog_contains_all_production_schema_entries` asserts all nine catalog ids are present and the catalog serializes with `schema_version == "1.0.0"`; `product_model_generates_and_validates_json_schema` does a **real** positive + negative pass (valid model validates; unknown-field document is rejected with `schema.product.invalid`) and checks the error→`Diagnostic` bridge; `product_model_reports_missing_required_surfaces` covers the semantic `MissingSurface` path and its `Diagnostic`/`RelatedContext`.
- Gaps: **no test asserts the deserialize-duplicate behavior** (masks the round-trip smell — a test that round-trips a deduped builder model and asserts vector lengths are preserved would expose it). **No test covers the structural-vs-semantic gap** (#1): nothing asserts that an empty-surfaces document passes `validate_product_model_json` while failing `validate_required_surfaces`. No test that a structurally-malformed value (wrong type, missing required field) is rejected by `validate_product_model_json` (only the unknown-field rejection is exercised). No round-trip serialize→deserialize equality test for `ProductModel`/`SchemaCatalog`. No test that the per-owner external schemas (`raw-manifest`, `sealed-artifact`, …) actually *validate* a representative document — the catalog test only checks ids/shape, not that the aggregated schemas function.

## Security

The trust boundary here is **untrusted JSON documents** validated against generated schemas, and (via the catalog) the schemas of the manifest/artifact/plugin/package boundaries that originate from project authors. `#![forbid(unsafe_code)]` holds; there is no `unsafe`.

- **Validation genuinely rejects — confirmed, not assumed.** The generated `ProductModel` schema carries `"additionalProperties": false` (from `deny_unknown_fields`) and typed `oneOf`/`const` enums; `jsonschema::Validator::validate` rejects both unknown-field and type-mismatched documents (verified empirically). All nine catalog schemas likewise emit `additionalProperties: false`, and the raw-manifest schema rejects unknown top-level keys and wrong-typed sections (verified). This is a real structural gate, not a model.
- **Validation gap — structural pass ≠ semantic validity (Medium).** As in gap #1: `validate_product_model_json` does *not* run `validate_required_surfaces` or any target/capability check. A schema-valid document can advertise no surfaces, no host targets, and no capabilities and still pass the public validation entry point. For a record whose entire purpose is conformance, "passed validation" understates the actual contract — a consumer that trusts `validate_product_model_json` as the gate admits incomplete/incoherent models. This is the schema-validation-bypass-by-incompleteness this section is meant to surface.
- **Duplicate-bypass on the deserialize path (Low).** The builder's set invariant is not re-checked on `Deserialize`; duplicate enum members in untrusted JSON survive (verified). Not a memory-safety issue, but a deserialized model can carry state the in-process constructor would reject — a mild integrity mismatch on the untrusted boundary.
- **No unbounded-recursion / nesting-DoS profile in this crate — verified absence.** Unlike `hawk2ui-a11y` (a self-recursive `A11yNode` tree deriving `Deserialize` → stack-overflow DoS), this crate's `Deserialize`-able types (`ProductModel`, `SchemaCatalog{Entry}`) are **flat** — fixed-depth structs over `Vec<enum>`/`String`. The only arbitrarily-nested field is `SchemaCatalogEntry.schema: serde_json::Value`, but that is *produced* internally by `schemars` (trusted), not parsed from an untrusted document on any path in this crate. So there is no attacker-controlled nesting depth here. (A consumer that deserialized an externally-supplied `SchemaCatalog` would inherit `serde_json`'s own recursion limit on the embedded `Value`; that is `serde_json`'s bound, not a defect of this crate.) `jsonschema::Validator::new`/`validate` over self-generated, internally-`$ref`'d schemas is not a recursion vector.
- **`jsonschema` configured with `default-features = false` — a genuine security positive** (`Cargo.toml:25`). jsonschema 0.46's default features (`resolve-http` → reqwest/rustls, `resolve-file`) enable remote and local-file `$ref` retrieval — an SSRF / arbitrary-file-read surface if a schema or document could reference external URIs/paths. Disabling them is the correct hardening for self-generated, internally-`$ref`-only schemas: there is no network or filesystem `$ref` resolution at validate time. Good and deliberate.
- **No panic-on-parse / panic-as-DoS.** Every fallible path returns `Result` (schema generation, compilation, and validation all map errors to `SchemaValidationError`); there is no `unwrap`/`expect`/indexing in non-test code. Schema-generation failures (which would only fire on a serde/schemars bug, not on input) are surfaced as errors, not panics.
