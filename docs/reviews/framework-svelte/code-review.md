# Code Review — hawk2ui-framework-svelte

**Reviewed at:** `5a042c51` · 2026-05-28 · no uncommitted changes in this crate at review time
**Scope:** `src/lib.rs` + `tests/svelte_integration.rs` + `Cargo.toml` (1 src file ~680 LoC / 1 test file ~410 LoC)
**Purpose:** Svelte 5 authoring integration — turn a Svelte component (author file + source, or an explicit native-compiler `FrameworkNativeProgram`) into typed `Hawk2UI` authoring records (`ElementNode`, refs, style/asset refs, event/lifecycle bindings) and, via `compile_to_runtime*`, bridge those records into a real `RuntimeViewTree` through `hawk2ui_authoring::NativeRuntimeBridge` (with optional compiled styles / theme).
**Note:** Codex is concurrently committing hardening/remediation work; HEAD drifts (git HEAD is `5fecf2c4`). Findings reflect the SHA above and may overlap with in-progress fixes.

## Summary

The **runtime path is genuinely implemented, not a stub.** `compile_to_runtime` / `_with_styles` / `_with_theme` build a `NativeAuthoringRuntime`, call `finish()` (real duplicate-key + asset-path validation), and hand the artifact to `NativeRuntimeBridge::bridge_artifact*`, which does real work upstream (layout style, hex-color parsing with rejection, token/theme style resolution, runtime tree assembly, `mount-element:`/`bind-event:` operation keys). Tests render through `RuntimeSceneBridge` + `SkiaRendererBackend` and assert visible pixels and themed fill colors. The `from_native_program` boundary is also real: it forwards an explicitly-compiled `FrameworkNativeProgram` and reuses the shared bridge. `#![forbid(unsafe_code)]` holds; no `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME markers.

The substantive weaknesses concentrate in the **`compile()` source path, which is not a Svelte compiler — it is a set of `str::find`/`contains` substring scans.** I traced the producer side of the explicit-compiler boundary to confirm this is not merely a thin Rust wrapper over a real TS compiler: it is not. The shipped TS entrypoint `compileHawkSvelte` (`packages/hawk2ui-svelte/src/index.ts:14`) is **the same kind of substring scanner** (`readAttribute` = `indexOf('name="')`, the same asset denylist, the same `on:` loop) and its keyed-child extraction `keyedChildIds` **returns the hardcoded literal `["title","cta"]`** whenever the source contains `(item.id)` (`index.ts:67`). So **no real Svelte 5 compiler exists in this codebase** — neither in this Rust crate nor in the TS package that feeds the `from_native_program` boundary — and the relabeled-vDOM risk from the brief is confirmed at both layers. Specific consequences for this crate: (1) **nothing reflects Svelte 5's runes/reactivity model** — no `$state`/`$derived`/`$effect`, no reconciler/renderer/operation-keys surface, no `fine_grained_updates` (sibling Solid emits at least a canned one). (2) **The Svelte adapter diverges from React/Vue by dropping protocol validation:** `svelte_artifact_from_native_program` is infallible and never calls `FrameworkNativeProgram::custom_renderer_operation_keys`, where React and Vue both call it and return `Result`. (3) the adapter consumes a **non-Svelte directive** (`use:ref="…"`) for refs — used consistently in the shipped `App.svelte` *and* the TS package, so it is a project-wide fabricated convention, not a test artifact — and **hardcodes lifecycle/keyed/text values** that look derived but are constants. None of these block the happy path; they are fidelity, correctness-of-derivation, and duplication defects. There is **no `Deserialize` on any public type**, so (unlike `hawk2ui-a11y`) there is no deserialization attack surface.

## Completeness & implementation gaps

1. **No Svelte 5 reactivity / compiler model — `compile()` is substring scanning** (`lib.rs:226` `SvelteIntegration::compile`, helpers `lib.rs:558`–`664`). Everything is derived by `extract_attribute` (first `name="…"` match), `source.contains("on:press")`, `source.find("<hawk-text")`, and `source.contains("(item.id)")`. There is no parse of `<script>`, no runes, no `$state`/`$derived`/`$effect`, no `{#if}`/`{#await}`, no reactive statements, and no emitted reactivity record. Svelte 5's defining model (compiler + signals) is **absent**, not "modeled with record types" — it is simply not represented. **The TS producer is no better:** I traced the `from_native_program` boundary's real-world feeder to `packages/hawk2ui-svelte/src/index.ts` and confirmed `compileHawkSvelte` is itself a substring scanner whose `keyedChildIds` returns the hardcoded literal `["title","cta"]` on seeing `(item.id)` (`index.ts:67`), so there is **no real Svelte compiler anywhere in the repo** to delegate to. The crate doc (`//! Svelte 5 integration`) and `framework_version_requirement() -> ">=5"` (`lib.rs:130`) advertise a Svelte-5-specific integration that neither layer embodies. Sibling `hawk2ui-framework-solid` at least emits a `fine_grained_updates` record (`solid/src/lib.rs:178`, `:313`); Svelte emits no analogous reactivity surface at all. → Either real parse/representation of runes/reactivity, or down-scope the doc/claim to "static template record extraction."
2. **`svelte_artifact_from_native_program` drops the custom-renderer protocol that React/Vue validate** (`lib.rs:471`). It returns `SvelteCompiledArtifact` **infallibly** and never invokes `native_program.custom_renderer_operation_keys(...)`. React (`react/src/lib.rs:479`–`489`) and Vue (`vue/src/lib.rs:475`–`482`) both call `custom_renderer_operation_keys("react"/"vue")`, surface the result (`reconciler_operations` / `renderer_operations`), and propagate `CustomRendererError`. The upstream API is real and fallible (`hawk2ui-authoring/src/adapter.rs:212` `custom_renderer_operation_keys`, which runs `emit_node_operations` + a `Commit` through `CustomRendererProtocol::apply` validation). So for the explicit-compiler boundary, **Svelte skips a validation + output that two of its three siblings perform** — a behavioral divergence, and a missing public surface. (Solid also omits it, so this is a 2-vs-2 split, not a lone outlier — but Svelte is on the weaker side.)
3. **Lifecycle handler labels are hardcoded constants, not derived** (`lib.rs:309`). The source path always sets `lifecycle_handlers: vec!["mounted:onMount".into(), "unmounted:onDestroy".into()]` regardless of whether `on:mount`/`on:destroy` actually appear in the source. A component with neither still reports both lifecycle labels; a component that only has `on:destroy` still reports `mounted:onMount`. The adjacent `events` vector *is* gated on `contains("on:mount")`/`contains("on:destroy")`, so `lifecycle_handlers()` and `events()` can disagree for the same input. This is the "records canned intent" pattern. (React `react/src/lib.rs:317` and Vue `vue/src/lib.rs:313` hardcode the same way — shared defect — but Svelte's `onMount`/`onDestroy` labels are at least Svelte-named.)
4. **Refs use a fabricated `use:ref="…"` directive that is not Svelte syntax** (`lib.rs:300`). `extract_attribute(&source.source, "use:ref")` matches a literal `use:ref="value"`. Real Svelte 5 has no `use:ref="x"` form — `use:` is an action directive (`use:action`) taking no string value, and element references are `bind:this={x}`. This is a **project-wide fabricated convention, not a test artifact:** the shipped example `examples/frameworks/svelte-basic/src/App.svelte:6` uses `use:ref="root_ref"`, the TS package reads the same `use:ref` attribute (`packages/hawk2ui-svelte/src/index.ts:30`), and the unit test (`tests/svelte_integration.rs:23`) mirrors it. So the ref-extraction is wired end-to-end to a syntax Svelte authors cannot actually write in real Svelte. Additionally, because `extract_attribute` only returns the **first** match, at most one ref is ever extracted regardless of how many elements declare one (same single-match limitation as React `"ref"` and Vue `"ref"`).
5. **`compile()` accepts essentially any input and returns `Ok` with a synthesized root** (`lib.rs:226`). Absent one of the three negative triggers (`data-asset` with `://`/`/`/`..`; an `on:` event outside the `press`/`mount`/`destroy` allowlist; a literal `<Broken`), the function always succeeds — even for empty, whitespace, or non-Svelte input — defaulting `id` to `"root"` (`lib.rs:270`). There is no positive check that the input is a Svelte component or even contains a recognized root element. "Compiles" therefore means "did not trip a denylist," not "is a valid Svelte component."
6. **Keyed-children detection is heuristic and order-fragile** (`lib.rs:599` `keyed_children`, `:642` `declared_item_ids`). Keyed children are harvested only if the source contains the exact bytes `(item.id)`, then IDs are scraped by scanning for `id:` followed by a quote anywhere in the source (`declared_item_ids`) — it does not associate `{#each}` blocks with their bodies, so any `id: '…'` literal in `<script>` (e.g. an unrelated object) is treated as a keyed child. The static `<hawk-text id="…">` IDs are then unioned in (`static_hawk_text_ids`). This yields plausible output for the fixture but is not a structural extraction.

## Code quality & smells

- **Near-total copy-paste across the four sibling adapters.** `extract_attribute`, `extract_number_attribute`, `style_refs_from_attribute`, `static_hawk_text_ids`, `static_hawk_text_content`, `declared_item_ids`, `push_unique`, `framework_program_events`, `lifecycle_event_kind`, `lifecycle_handler_label`, and the three `*_with_defaults` native-artifact builders are **byte-for-byte (or near) identical** to `react/src/lib.rs`, `solid/src/lib.rs`, and `vue/src/lib.rs` (e.g. compare `svelte/src/lib.rs:558`–`670` against `solid/src/lib.rs:569`–`669`). The default visual props (`background "#080a0e"`, child `font_size 18`, `color "#ffffff"`, `width 160`, `height 32`) are duplicated as literals in every crate (`lib.rs:428`,`:444`–`459`). This is a maintenance hazard: the four copies have **already silently diverged** — Vue's `static_hawk_text_ids`/`static_hawk_text_content` grew `:id=`/`v-bind:id=` guards (`vue/src/lib.rs:628`,`:645`) that the Svelte/React/Solid copies lack, and there is no shared test to keep them in lock-step. (For Svelte the matching dynamic form is `id={item.id}` — no `id="` — so `extract_attribute` simply returns `None` and a dynamic `<hawk-text id={item.id}>` contributes no static id; the crate relies on the `(item.id)` + `declared_item_ids` path instead, which is exactly the fragile heuristic in #6. The duplication means any future correctness fix to one framework's scraper must be hand-ported to three others.) → Extract a shared `hawk2ui-framework-core` (or put the heuristics behind `hawk2ui-authoring`) and parameterize per-framework token sets.
- **`extract_attribute` is a naive scanner with cross-attribute false positives** (`lib.rs:558`). `format!("{name}=\"")` + `find` means `extract_attribute(src, "id")` matches the first occurrence of the substring `id="` *anywhere* — e.g. `valid="x"` contains `id="`, so a `valid="…"` attribute would be mistaken for the `id`. For the root `id`, the first element (or attribute) whose text contains `id="` wins. No attribute-boundary or tag-scope awareness. (The shared TS `readAttribute`, `index.ts:53`, has the identical flaw.)
- **`framework()`/`framework_version_requirement()` return hardcoded `&'static str`** (`lib.rs:124`,`:130`) — fine as constants, but `">=5"` is never checked against anything; it is advertised metadata with no enforcement.
- **`SvelteComponentSource::from_native_program` discards `source`** (`lib.rs:44`) — sets `source: String::new()`. Expected (the native-program path bypasses scanning), but it means the two constructors produce structurally different objects that the same `compile()` treats divergently; worth a doc note.
- **No dead code or unreachable arms**; the `RuntimeDrawCommand` match in tests correctly handles all variants (`tests/svelte_integration.rs:347`).

## Testing

- Good breadth on the happy path and the parts that are real: lifecycle/keyed/events/refs/styles/assets/source-map mapping (`svelte_5_compile_maps_…`), the explicit native-compiler boundary (`…accepts_explicit_native_compiler_boundary…`), full runtime bridge + child order + metadata + operation keys (`…compile_to_runtime_uses_native_bridge_contract`), static-text preservation, **real Skia pixel rendering** (`…renders_visible_skia_pixels`), and compiled-style + theme background application (`…with_styles…`, `…with_theme…`). The style/theme/pixel tests genuinely exercise the upstream bridge and are not false-confidence.
- **False-confidence on the Svelte-specific layer:** `svelte_5_compile_maps_…` asserts `lifecycle_handlers() == ["mounted:onMount","unmounted:onDestroy"]` — but those are **hardcoded** (gap #3), so the assertion passes for *any* input and tests nothing about lifecycle derivation. The same test asserts `refs() == ["root_ref"]` using the fabricated `use:ref="root_ref"` syntax (gap #4) — it locks in non-Svelte behavior rather than validating Svelte refs.
- **Untested divergence / negatives:** no test that a component **without** `on:mount`/`on:destroy` does *not* report those lifecycle labels (would expose #3); no test of the `events()` vs `lifecycle_handlers()` disagreement; no test that `compile()` rejects non-Svelte input (it doesn't — #5); no assertion that `from_native_program` validates the renderer protocol (it doesn't — #2, and no Svelte-side test of `custom_renderer_operation_keys`, unlike React/Vue which surface `reconciler_operations`/`renderer_operations`). The `svelte_smoke_app_declares_public_package_entrypoint` test reads `packages/hawk2ui-svelte` + `examples/...` from disk and only `contains`-checks strings — it asserts file presence, not behavior.
- Cross-framework conformance (`hawk2ui-framework-conformance`) *does* include `FrameworkKind::Svelte`, but its `svelte_snapshot()` (`conformance/src/lib.rs:468`) builds via `from_native_program(framework_native_program(...))` — i.e. it feeds the **same** hand-built `FrameworkNativeProgram` to all five frameworks and then asserts equivalence. So the equivalence harness exercises the shared `hawk2ui-authoring` bridge, **not** Svelte's source-scanning `compile()` path, and it hardcodes `state_updates: vec!["state:items"]` for every framework (`conformance/src/lib.rs:491`) — the Svelte adapter contributes no state records of its own.

## Security

The trust boundary is **Svelte component source + props/IDs from app/author code** (and the `FrameworkNativeProgram` produced by an external native compiler). **There is no `Deserialize`/`Serialize` on any public type in this crate**, so — unlike `hawk2ui-a11y` — there is no deserialization attack surface here. `#![forbid(unsafe_code)]` holds; no `unsafe`.

- **Asset-path validation is a denylist, not an allowlist** (`lib.rs:240`). `compile()` rejects `data-asset` values containing `://`, starting with `/`, or containing `..`. This catches the obvious traversal/absolute/URL cases (and the conformance + unit tests cover `https://` and `../`), but it is a substring denylist over a single first-match attribute: a Windows-style `\`-separated path, a percent-encoded `..` (`%2e%2e`), or a second `data-asset` occurrence (only the first is checked, `extract_attribute` returns first match) is not validated. The path is then forwarded verbatim into an `AssetRef` (`lib.rs:304`) and downstream into the runtime metadata. The actual file read happens in `hawk2ui-assets` (out of scope), but this is the gate that's supposed to constrain it. **Low** (mirrors the React/Vue/Solid siblings' identical gate). → Prefer an allowlist of workspace-relative path shapes.
- **Unbounded recursion in the upstream bridge over an attacker-shaped tree — but bounded on the Svelte input** (`hawk2ui-authoring/src/runtime_bridge.rs:317` `bridge_child`, and `native.rs:520`–`551` `collect_mounts`/`collect_events` recursion). These recurse over the authoring child tree with no depth cap. From the **source-scanning** path the tree is at most root + a flat list of `keyed_children` (depth 2), so Svelte's own `compile()` cannot drive deep nesting. From the **`from_native_program`** path, depth is whatever the external native compiler emitted (`FrameworkNativeProgram` nests `FrameworkNativeNode`); a hostile/buggy native program with deeply nested children could overflow the stack during `to_native_authoring_artifact` → bridge. This is an upstream concern surfaced through this crate's `compile_to_runtime`. **Low / verify** for this crate (no `Deserialize` entry point here; depth is gated by whoever constructs the `FrameworkNativeProgram`).
- **Substring scanners allocate per call but are bounded by input length** (`unsupported_svelte_events` `lib.rs:579`, `declared_item_ids`, `static_hawk_text_ids`). The `unsupported_svelte_events` loop advances `rest` past each consumed slice and terminates even when a matched event is empty (`event_len == 0` leaves `rest` at the char after `on:`, which no longer contains that `on:`), so there is **no infinite loop**. Verified — not a DoS. Allocation is O(input).
- **`compile()`-as-pass-through (gap #5)** is a correctness/trust issue more than a security one: arbitrary non-Svelte text yields a successful `root` artifact. Combined with the denylist-only asset check, the crate's notion of "valid" is permissive. No panic/DoS.
- **Good:** the runtime bridge rejects non-finite/negative/zero layout numbers and malformed `#rrggbb` colors with structured errors before rendering (`runtime_bridge.rs:509`,`:559`), and `NativeAuthoringRuntime::finish()` rejects duplicate keyed children and invalid asset paths — these are exercised by the conformance failure matrix for Svelte (`svelte.runtime-bridge.failed`, `svelte.asset.path-invalid`, `svelte.event.unsupported`).
