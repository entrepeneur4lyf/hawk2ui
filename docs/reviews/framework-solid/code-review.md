## Summary

This crate is **genuinely implemented, not a stub.** The runtime path does real work: `render_to_runtime` builds a `NativeAuthoringRuntime`, calls `runtime.finish()` (real validation/finalization in `hawk2ui-authoring`), and feeds the artifact to `NativeRuntimeBridge::bridge_artifact{,_with_styles,_with_theme}`, producing a real `RuntimeViewTree` — the integration tests then drive `RuntimeSceneBridge` to emit actual `RuntimeDrawCommand::{Text,Fill}` values (verified against `to_native_authoring_artifact`/`bridge_artifact`/`keyed_child_order` in `hawk2ui-authoring`, all of which are real impls). The native-program boundary (`from_native_program` → `solid_artifact_from_native_program`) reads genuine `FrameworkNativeProgram` records. No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME markers, no `unwrap`/`expect`/`panic!` in `src`.

The substantive weaknesses are all about **fidelity of the extracted records**, not the bridge: (1) `fine_grained_updates` — the crate's headline Solid-reactivity surface — is a **hardcoded 3-element literal** emitted identically in both code paths and never derived from signals/effects in the source; (2) the source scanner **hardcodes handler and ref names** (`"handlePress"`, `"root_ref"`) instead of extracting them, so any real component that names them differently gets silently-wrong bindings; (3) `lifecycle_handlers` is emitted **unconditionally** and is internally inconsistent with the *conditionally* built `events`; and (4) massive **copy-paste duplication** across the four sibling adapters that has **already drifted** (Vue gained `:id=` guards the others lack). No correctness blocker on the happy path / test fixtures; the defects are record-fidelity gaps that the fixture-pinned tests actively mask. Security posture is **cleaner than its reviewed siblings** (no Serde, no recursion, no panics) — there is no High here.

## Completeness & implementation gaps

1. **`fine_grained_updates` is a canned literal, not a reactivity model** (`lib.rs:313-317` in `render`; `lib.rs:504-508` in `solid_artifact_from_native_program`). Both paths emit the *identical* hardcoded vector `["signal:items", "for-each:keyed", "effect:root-props"]` regardless of source content. Nothing scans the source for `createSignal`/`createEffect`/`createMemo`, counts them, or names them; a component with three signals named `a`/`b`/`c`, or with no `<For>`, or with no effects, still reports exactly `signal:items`, `for-each:keyed`, `effect:root-props`. This is the crate's distinguishing Solid feature (fine-grained reactivity), and it is **decorative**: it records intent and returns canned values. Crucially, the upstream model cannot supply it either — `FrameworkNativeProgram` (the explicit-compiler boundary) carries **no signal/effect/memo concept at all**, so even given real native compiler output the value is still the literal. The accessor doc ("Returns fine-grained update records") overstates what is computed. → Either derive these from the source/native program, or document them as a fixed reactivity-capability descriptor rather than per-component update records.
2. **Handler names are hardcoded, not extracted** (`lib.rs:273-296`, mirrored at `lib.rs:438-450`). Event bindings are gated on substring presence but the `HandlerRef` is a literal: `onPointerDown` → `HandlerRef::new("handlePress")`; `onMount` → `"onMount"`; `onCleanup` → `"onCleanup"`. A real component `onPointerDown={doThing}` still binds to `handlePress`. The binding is therefore correct only for sources that happen to use the fixture's handler names — the event *plumbing* is real (it reaches `NativeAuthoringElement::with_event`), but the *handler identity* is fabricated.
3. **Refs are hardcoded to the fixture string** (`lib.rs:301-305`). `refs` is `vec!["root_ref".into()]` *iff* the source contains the exact literal `ref={root_ref}`, else empty. **Divergence:** Svelte extracts the actual ref via `extract_attribute(source, "use:ref")` and Vue via `extract_attribute(source, "ref")`; Solid alone pins the fixture token `root_ref` and cannot represent any other ref name. A Solid `ref={myEl}` produces *no* ref record.
4. **`lifecycle_handlers` is unconditional and inconsistent with `events`** (`lib.rs:312`). It is always `["mounted:onMount", "unmounted:onCleanup"]`, independent of whether the source contains `onMount`/`onCleanup`. Meanwhile `events` (`lib.rs:283-296`) adds the matching lifecycle `EventBinding`s only *conditionally*. So a source with only `onMount` yields `events` containing just `Mounted`, but `lifecycle_handlers` still claims both `mounted:onMount` and `unmounted:onCleanup` — two views of the same fact that disagree. (The native-program path at `lib.rs:498-503` derives this correctly from `native_program.root().lifecycle()`; only the source-scan path is canned.)
5. **No Solid-specific operation/protocol surface — divergence from React and Vue.** React computes `reconciler_operations` through a **real, fallible** `CustomRendererProtocol` (`react_protocol_operations`, which `apply`s `CreateNode`/`AppendChild`/`Commit` and can error), and Vue derives `renderer_operations` from `native_program.custom_renderer_operation_keys("vue")`. Solid's analogous "reactivity" surface (`fine_grained_updates`) computes nothing, validates nothing, and cannot fail — it is the literal in (1). This is the concrete place the Solid adapter diverges in behavior from its siblings: it claims a framework-distinct model but does not implement one.

## Code quality & smells

- **Near-total duplication across the four framework adapters, already drifting.** `extract_attribute`, `extract_number_attribute`, `style_refs_from_attribute`, `static_hawk_text_ids`, `static_hawk_text_content`, `declared_item_ids`, `push_unique`, `lifecycle_event_kind`, `lifecycle_handler_label`, `framework_program_events`, `bridge_error`, and the `native_artifact_from_*_with_defaults` body are byte-for-byte (modulo the framework name) identical across react/solid/svelte/vue. This is not theoretical debt: the copies have **already diverged** — Vue's `static_hawk_text_ids`/`static_hawk_text_content` added `:id=` / `v-bind:id=` guards (`framework-vue/src/lib.rs:628-633, 645-647`) that solid/react/svelte lack, so the "same" helper now behaves differently per crate. A shared helper crate (or a generic adapter parameterized over the per-framework event/attr vocabulary) would remove ~400 LoC of lockstep maintenance and the drift hazard.
- **Naive substring scanning of source.** `extract_attribute` (`lib.rs:569-575`) only matches double-quoted `name="…"`; JSX commonly uses expression attributes (`id={x}`, `class={cn(…)}`) which are silently missed — note the test fixture itself uses `id={item.id}` for children (handled by the separate `<For>`/`id:` path) but the *root* `id` extraction would miss `id={...}`. `component.source.contains("onPointerDown")` (`lib.rs:273`) fires on the string anywhere, including comments or unrelated text. `static_hawk_text_ids` slices on `split('>')` / `find('>')`, which breaks if an attribute value contains `>`. These are acceptable for the controlled fixtures but fragile for real author source.
- **Misleading accessor doc.** `fine_grained_updates()` doc "Returns fine-grained update records" (`lib.rs:177`) describes a per-component computation that does not occur (gap #1) — same class of misleading doc the assets review flagged for `sanitized()`/`load_font`.
- **`SolidRenderedArtifact.native_program` is stored but only read by the artifact constructor**, never via a public accessor; it is plumbing for `native_artifact_from_solid_with_defaults`. Fine, but undocumented dead-looking state on a `pub` struct.
- **`SolidRenderedArtifact` is `pub` with no public constructor** other than via `SolidIntegration::render`; all fields private. Consistent with siblings — noted, not a defect.

## Security

This crate's trust boundary is **untrusted Solid author source** (a `String`) plus an optional caller-supplied `FrameworkNativeProgram`. Its security posture is **materially cleaner than the reviewed siblings (`hawk2ui-a11y`, `hawk2ui-assets`)** — none of their High/Medium structural risks apply here, and that is worth stating explicitly rather than importing them by pattern:

- **No `unsafe`.** `#![forbid(unsafe_code)]` holds.
- **No deserialization attack surface.** Unlike `hawk2ui-a11y` (whose `Deserialize`-able tree drives its High recursion-DoS finding), none of this crate's public types derive `Serialize`/`Deserialize`. Input arrives only as a `String` or a typed `FrameworkNativeProgram` constructed in-process.
- **No unbounded recursion / stack-overflow vector.** Every source scanner (`static_hawk_text_ids`, `static_hawk_text_content`, `declared_item_ids`, `unsupported_solid_events`) is an iterative `while let Some(index) = rest.find(...)` loop that always advances `rest` past the match, so it terminates in O(len). The tree built for the bridge is shallow by construction — a single root plus one level of keyed text children — so there is no attacker-controlled depth. Contrast a11y's recursive `find`/`collect_*` over nested children.
- **No panic-as-DoS.** No `unwrap`/`expect`/`panic!`/indexing-by-computed-index in `src`; all slicing is on `find`-derived byte offsets of ASCII delimiters (`"`, `>`, `<hawk-text`), and `len_utf8()` is used correctly for the quote characters in `declared_item_ids`, so no UTF-8 boundary panic. `extract_number_attribute` uses `.parse().ok()` (no panic).
- **Input validation is substring-based and advisory, not canonicalizing (Low).** The asset-path guard (`lib.rs:240-248`) rejects `://`, leading `/`, and `..`; the event denylist (`unsupported_solid_events`, `lib.rs:590-596`) rejects four DOM events. These are simple `contains` checks with no normalization, so they are best-effort: e.g. an asset reference smuggled through an unquoted/expression attribute is not seen by `extract_attribute` at all, and the path guard never runs on it. Because the output is typed records consumed by in-workspace tooling (not a filesystem read or shell exec in this crate), the blast radius is "wrong/unvalidated record," not code execution. Defense-in-depth: validate the resolved record at the authoring/asset boundary rather than via source-substring heuristics.
- **Unbounded source iteration is bounded by input length.** All scans are linear in the source string the caller supplies; there is no amplification.

**Net:** the only security-relevant note is the Low advisory-validation point. There is no High or Medium security finding in this crate; "lower-risk than its reviewed siblings" is the honest characterization.
