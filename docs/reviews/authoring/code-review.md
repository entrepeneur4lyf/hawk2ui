# Code Review — hawk2ui-authoring

**Reviewed at:** `5a042c51` · 2026-05-28 · in-flight tree (Codex committing concurrently)
**Scope:** `src/{lib,element,component,events,state,compile,adapter,native,runtime_bridge}.rs` + `tests/{authoring_records,native_authoring_runtime}.rs` (9 src files ~2.4k LoC / 2 test files ~950 LoC)
**Purpose:** Typed authoring layer — element/component/event/state records, a line-based source compiler, framework renderer-adapter contracts, a direct native authoring runtime, and the bridge that lowers native authoring records into runtime/layout/render records.
**Note:** Codex is concurrently committing hardening/remediation work; HEAD drifts (live HEAD was `6a018b23` at read time). Findings reflect the stamped SHA above and may overlap with in-progress fixes.

## Summary

This crate is **genuinely implemented for one of its three record families and record-only for the other two.** The headline real path — `NativeAuthoringElement` → `NativeRuntimeBridge` → `RuntimeViewTree`/`LayoutStyle`/`RuntimeVisual` — is the real thing: `runtime_bridge.rs` constructs actual `hawk2ui_runtime`/`hawk2ui_layout`/`hawk2ui_render`/`hawk2ui_style` records, resolves compiled style refs + theme tokens, parses hex colors, and validates numeric domains; the test suite renders it to **visible Skia pixels** (`native_runtime_bridge_renders_authoring_artifact_to_visible_skia_pixels`) and asserts pixel values. That is not a stub. Documentation is thorough, `#![forbid(unsafe_code)]` holds, and there are **zero** `todo!`/`unimplemented!`/`unreachable!`/`panic!`/`unwrap`/`expect` in `src/` and no `TODO`/`FIXME`/`HACK`.

The substantive weakness is that the other two pipelines never lower. (1) The string compiler `compile_authoring_source` emits `ComponentInstance`s into an `AuthoringArtifact` that **nothing bridges to runtime** — even the workspace "source to render" conformance test reads only the component's id+name and hand-fabricates the scene. (2) `CustomSurfaceDeclaration` and `NodeOperation::{MountComponent, DeclareSurface}` are **constructed nowhere outside their own definitions/tests** and never emit operations; `RuntimeVisual::CustomSurface` is never produced — custom draw surfaces (the crate's stated plugin-editor use case) do not lower. Secondary: framework adapters model their output as `Vec<String>` operation keys rather than typed operations, `parse_event` covers only 4 of ~20 event kinds, and tree traversal is unbounded recursion. No correctness blocker on the native-element happy path.

## Completeness & implementation gaps

1. **String-compiled components never lower to runtime** (`compile.rs::compile_authoring_source` → `AuthoringArtifact`). The compiler is real (line-based parse, diagnostics, child/event records), but its output type `AuthoringArtifact { components: Vec<ComponentInstance>, … }` has **no conversion to `NativeAuthoringArtifact`**, and `NativeRuntimeBridge` accepts only `NativeAuthoringArtifact`. The only consumers of `AuthoringArtifact::components()` are this crate's own test and `hawk2ui-conformance/tests/source_to_render.rs:37`, and the latter reads only `component.id()` + `component.component_name()` and **hand-builds** the `SceneGraph`/`LayerStack` with literal values — the component's text children and `pointer.press` binding are discarded. So the `.hawk` source → rendered UI path does not exist end-to-end; only the programmatic `NativeAuthoringElement` builder path does. Material because the crate's purpose is "build UIs from … a manifest."
2. **Custom surfaces do not lower** (`component.rs::CustomSurfaceDeclaration`, `runtime_bridge.rs::visual`). `CustomSurfaceDeclaration` is constructed only in a test; it has no stable-key/operation emission and no bridge. `visual()` matches only `Text` and `View|Button`; `ElementKind` has no surface variant, and `RuntimeVisual::CustomSurface`/`RuntimeCustomSurfaceVisual` is **never** constructed in the crate (the sole `RuntimeDrawCommand::CustomSurface` reference is a test match arm falling through to `=> {}` at `native_authoring_runtime.rs:446`). For a framework whose plugin editors center on custom draw surfaces (oscilloscope/scope-surface in the tests), this is a real gap.
3. **`NodeOperation::{MountComponent, DeclareSurface}` are inert** (`adapter.rs:250,252`). Both variants appear only in the enum definition and `stable_key`; nothing ever constructs or applies them. The real protocol emitter `emit_node_operations` only ever produces `CreateNode`/`SetProp`/`SetStyleRef`/`SetAssetRef`/`SetRef`/`BindEvent`/`BindLifecycle`/`AppendChild`/`Commit`. So two of four `NodeOperation` cases are dead surface area.
4. **`parse_event` covers 4 of ~20 event kinds** (`compile.rs::parse_event`). Only `pointer.{press,release,move,drag}` parse; keyboard/focus/input/resize/lifecycle/custom-component/plugin-parameter — all of which have stable keys in `events.rs` and are exercised by `event_records_cover_native_event_domains` — return `None` and are rejected as `authoring.event.unsupported`. The source compiler can bind only pointer events even though the record model and adapters support the full set.
5. **`EnterErrorBoundary` is never emitted by the real emitter** (`adapter.rs::emit_node_operations`). A `NativeLifecycleEvent::ErrorBoundary` lifecycle handler is lowered to `BindLifecycle{…error-boundary…}`, not `EnterErrorBoundary`. `EnterErrorBoundary` is reachable only by a caller hand-applying it to `CustomRendererProtocol` (as a test does). Not wrong, but the dedicated operation is effectively decorative for the crate's own lowering.
6. **Framework adapters model output as `Vec<String>`, not typed operations** (`adapter.rs::CustomRendererProtocol`, `RecordingNativeRendererAdapter`, `native.rs::operation_keys`). The protocol does **real** validation (duplicate-node, reference-before-create, parent/child existence — see `validate_operation`) but then discards the typed op and stores only `operation.stable_key()`. `RecordingNativeRendererAdapter::apply` does **no** validation at all — it pushes a stable key unconditionally. These are deterministic conformance stand-ins; they coexist with the real `runtime_bridge` lowering, so this is "modeled output," not a stubbed pipeline — but a consumer cannot recover the operations, only their string keys.

## Code quality & smells

- **Stable-key construction is duplicated across three sites** with no shared source of truth: `NodeOperation::stable_key`, `CustomRendererOperation::stable_key` (`adapter.rs`), and the inline `format!("bind-event:…")` / `format!("lifecycle:…")` / `format!("mount-element:…")` strings in `native.rs::{collect_events, collect_lifecycle, collect_mounts}`. The `bind-event:{target}:{key}` and `lifecycle:…` formats must stay byte-identical across files for conformance keys to line up (the tests pin exact strings), but nothing enforces it.
- **`narrow_number` narrows f64→f32 via `value.to_string().parse::<f32>()`** (`runtime_bridge.rs:521`). A string round-trip to narrow is unusual (`value as f32` would be the idiom) and allocates per number; it is guarded on both sides (`is_finite` before and after), so it is correct, just costly and surprising. Low.
- **`ChildList::ordered` documents `# Errors` but cannot fail** (`element.rs`), returning `Result<_, DuplicateChildKeyError>` only to share a call shape with `keyed`. Self-documented in the doc comment; very minor.
- **`NativeRuntimeBridge::bridge_element*` variants always leave `operation_keys` empty** while `bridge_artifact*` populates them from the artifact (`runtime_bridge.rs:148-170` vs `32-88`). An element-only bridge silently yields no operation keys; a caller relying on `operation_keys()` gets different behavior depending on which entrypoint was used. Mild API inconsistency.
- **`framework_node_to_native_element` hardcodes a root background `#080a0e`** when `include_default_visual_props` is set (`adapter.rs:669`). A magic color constant baked into the adapter rather than sourced from style/tokens; matches a test expectation but is a leaky default.
- **`finish()` re-sorts events with a tie-only key** (`native.rs:440`): `events.sort_by_key(|e| matches!(e.event(), EventKind::Lifecycle(_)))` (stable sort pushing lifecycle events after non-lifecycle). Combined with the deliberate two-phase `collect_lifecycle_for(Mounted)` … `collect_lifecycle_for(rest)` ordering, the resulting order is tested and correct, but the intent is non-obvious and fragile.

## Documentation

- Strong: crate-level `//!`, every public type/fn/enum-variant documented, `# Errors` sections on all fallible public fns. No undocumented public items found.
- Minor: the recursive traversals (`bridge_child`, `validate_element`, `collect_*`, `emit_node_operations`, `framework_node_to_native_element`) carry no note about depth/stack expectations (relevant given the DoS below).
- Minor: `parse_event`'s pointer-only support is undocumented at `compile_authoring_source`, so the source grammar's limits are invisible to authors.

## Testing

- Good breadth on the real path: native authoring finalize + deterministic op-keys, nested lifecycle collection, duplicate-key + invalid-asset-path diagnostics, runtime bridge happy path, compiled-style + theme-token application, three structured error paths (`invalid-number` for NaN width / zero `font_size` / zero styled `font-size`), and a full **Skia pixel** render assertion. The custom-renderer protocol's duplicate-node and missing-child rejections are tested.
- **False-confidence risk:** `adapter_contract_records_equivalent_operations_for_framework_labels` iterates five framework labels and asserts the same two operation keys for each — but `RecordingNativeRendererAdapter::apply` ignores the label and does no validation, so this proves only that string formatting is label-independent, not any per-framework behavior.
- Gaps (no coverage): the disconnected component pipeline (#1) and custom-surface non-lowering (#2) are unblocked by any test that would surface them; `parse_event`'s rejection of non-pointer events (#4) is untested; `NodeOperation::{MountComponent, DeclareSurface}` (#3) have no test applying them through any adapter; deep-recursion / stack-depth behavior (Security) is untested; the `bridge_element*` empty-`operation_keys` divergence is untested.

## Cross-cutting conventions (workspace-wide; noted once, not a per-crate defect)

- `crate_name()` plus the `exposes_crate_identity` marker test — recurs in every crate; not a defect here.
- `#![forbid(unsafe_code)]` at crate root. Holds.
- Domain error → `hawk2ui_api::Diagnostic` conversion: present and idiomatic for `AuthoringDiagnostic` (`From<AuthoringDiagnostic> for Diagnostic`). **Deviation worth one line:** the other error types (`CustomRendererError`, `AdapterError`, `NativeAuthoringError`, `NativeRuntimeBridgeError`, `DuplicateChildKeyError`) expose `rule()`/`message()` (Diagnostic-shaped) but do **not** implement `From<_> for Diagnostic` (nor `Display`/`std::error::Error`), so they cannot be funneled into the shared diagnostic stream the way `AuthoringDiagnostic` can. Minor inconsistency, not a correctness issue.

## Security

- **Unbounded recursion → stack-overflow DoS over authoring/adapter trees** (`runtime_bridge.rs::bridge_child`; `native.rs::{validate_element, collect_lifecycle, collect_mounts, collect_events}`; `adapter.rs::{emit_node_operations, framework_node_to_native_element}`). All recurse over `children` with no depth bound. **Trust boundary:** unlike `hawk2ui-a11y`, **no type in this crate derives `Deserialize`/`Serialize`**, so there is no untrusted-snapshot deserialization vector. The reachable hostile input is (a) a deeply-nested tree built through the public `FrameworkNativeNode`/`NativeAuthoringElement` builders at the framework-adapter boundary (a framework compiler emitting attacker-influenced component trees), and (b) the `compile_authoring_source(&str)` source — which is **flat/line-based and cannot nest**, so the string path is safe. Net: real, but narrower than a11y and not deserialization-driven → **Medium**, not High. Mitigation: depth-bounded or iterative traversal with a cap.
- **Good input validation at the lowering boundary** (`runtime_bridge.rs`, `native.rs`). Numeric props are domain-checked (`narrow_number`: finite + non-negative/positive) before they reach layout; colors must be `#rrggbb`; styled font-size must be a positive finite `LengthPx`; asset paths are rejected if they contain `://`, start with `/`, or contain `..` (`validate_element` — a genuine path-traversal/SSRF guard for workspace-relative assets). Errors are structured, not panics.
- **No panics on fallible paths.** Every failure is a typed `Result`; the only `expect`/`unwrap` calls live in tests. Panics-as-DoS is not a concern in `src/`.
- **No `unsafe`.** `#![forbid(unsafe_code)]` enforced.
- **String pass-through is unbounded but non-injecting.** Handler refs, prop values, ids, and asset names are forwarded verbatim into records and stable keys without length bounds; not an injection vector (they become struct fields / formatted keys), but pairs with the recursion theme as an allocation-growth surface on hostile input.
