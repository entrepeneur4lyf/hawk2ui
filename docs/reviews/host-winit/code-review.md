## Summary

This crate is **genuinely implemented, not a stub**, and the two backends are cleanly separated:

- **Real winit path** (`runtime.rs::RuntimeApplication`): creates a native `Window` via `event_loop.create_window`, builds a `softbuffer::Context`/`Surface`, and on each `RedrawRequested` runs Skia (`SoftwareFrameRenderer::render_frame`/`render_scene_frame`), copies the resulting `0x00RRGGBB` pixels into `surface.buffer_mut()`, and calls `window.pre_present_notify()` then `buffer.present()`. The Skia→softbuffer wiring is **real and coherent** — the pixel format (`render` produces packed `RGB` `u32`, softbuffer expects exactly that), `copy_from_slice`, and `present()` line up. This is not record-only.
- **Headless double** (`lib.rs::WinitDesktopAdapter` + `WinitEventTranslator`): an event-recording adapter that implements `DesktopHostAdapter` by pushing `DesktopHostEvent`s into a `Vec`, and a translator that maps native `winit::WindowEvent`s into host events. This is the legitimate CI-testable surface (real windowing cannot run headless) — not a fake masquerading as the whole crate.
- **Test doubles** (`tests/winit_adapter.rs::Fake{Clipboard,Dialog}Backend`) implement the `WinitClipboardBackend`/`WinitDialogBackend` traits; the production backends (`ArboardClipboardBackend`, `RfdDialogBackend`) call the real OS APIs.

Error handling in the event loop is sound: every fallible op returns `Result<_, WinitHostError>`, and `handle_window_event` routes any error to `fail()` → `event_loop.exit()` — the loop **fails closed**, it does not panic-abort. No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME markers. Crucially, the trust boundary into this crate (`DesktopWindowConfig`, `DesktopDialogRequest`) is `Deserialize`-able but **validated**, and the rendered `RuntimeViewTree` is **not** `Deserialize` (built only through a validating API), so the unbounded-recursion-DoS that is `hawk2ui-a11y`'s headline finding does **not** transfer here.

The substantive weaknesses are integration gaps, not core-path defects: (1) the **development error overlay is fully built and tested but never wired into the live runtime** — `with_error_overlay` is called only in tests, and the CLI that produces overlays (`to_desktop_overlay`) has no path to inject one into `WinitDesktopRuntime`; (2) **`DesktopRuntimeEvent` is inert** — defined, exported, and tested but consulted by no code; (3) **`clear_text` writes an empty string instead of releasing the clipboard**; plus several Low smells (Debug-formatted key identity, a dead redraw branch, a latent `copy_from_slice` panic point).

## Completeness & implementation gaps

1. **Development error overlay is built + tested but unreachable in the live runtime** (`software_frame.rs::SoftwareFrameRenderer::with_error_overlay` / `DesktopErrorOverlay`). The overlay rendering is real and well-tested (two tests assert visible warning pixels over both the default scene and a runtime scene). But `with_error_overlay` has **zero non-test callers in the workspace**. `WinitDesktopRuntime` exposes no way to set an overlay: `RuntimeApplication::new` constructs the renderer with overlay `None` (via `self.renderer.clone()` of a default `SoftwareFrameRenderer`), and `RuntimeApplication::apply_reload` rebuilds the renderer as `SoftwareFrameRenderer::new().with_assets(...)` — which would **drop** any overlay even if one existed. The CLI dev loop *does* produce overlays (`hawk2ui-cli/src/dev_loop.rs:445` `to_desktop_overlay`), but the executor only ever hands a `WinitDesktopRuntimeConfig` to `run_dev_blocking`/`run_blocking` (`hawk2ui-cli/src/executor.rs:530,637`) — the overlay has no channel into the running surface. Worse for intent: on a reload-validation failure, `run_dev_blocking`'s `user_event` calls `self.fail()` → `event_loop.exit()`, i.e. it tears the window down at exactly the moment a dev overlay was presumably meant to display the build error and keep the window alive. Feature implemented, not connected. → Add an overlay slot to `WinitDesktopRuntimeConfig`/`RuntimeApplication` and preserve it across `apply_reload`, and present (not exit) on recoverable dev errors.
2. **`DesktopRuntimeEvent` is inert (record-only API)** (`runtime.rs:336`). The enum and its `requires_full_repaint` predicate are defined, re-exported from `lib.rs`, and exercised by `runtime_events_request_repaint_after_resize` — but **no code constructs or consults a `DesktopRuntimeEvent`**. The real repaint policy in `handle_window_event` is driven entirely by per-`WindowEvent` match arms plus `translated.requires_redraw`; `present_frame` never asks `requires_full_repaint`. So this type is dead/record-only and its test is false-confidence (it asserts the predicate's truth table, not that the runtime uses it). → Either route redraw decisions through `DesktopRuntimeEvent` (making it load-bearing) or delete it.
3. **`ArboardClipboardBackend::clear_text` does not clear the clipboard** (`lib.rs:277`). It calls `self.write_text(String::new())`, leaving the app owning an empty string rather than releasing ownership; the bridge then reports `Cleared`. `arboard::Clipboard` exposes a real `clear()` (confirmed in arboard 3.6), so the "Clear" semantic is misrepresented. → Call `clipboard.clear()`.

## Code quality & smells

- **Keyboard identity is a Debug string** (`lib.rs:560`). `KeyboardInput::new(format!("{:?}", event.logical_key), …)` uses `Debug` formatting of `winit::keyboard::Key` as the semantic key label. `Debug` output is not a stable API across winit versions and is not intended for identity/matching; downstream consumers keying on this string are fragile to a winit bump. → Map to a stable explicit label (as `mouse_button_label` already does for buttons).
- **Dead redraw branch in the input arm** (`runtime.rs:710`). The arm for `Focused | KeyboardInput | Ime | Cursor* | Mouse* | DroppedFile | HoveredFile | … | ModifiersChanged` guards `if translated.requires_redraw { self.request_redraw(); }`, but `WinitEventTranslator::translate` only sets `.redraw()` for `Resized`, `ScaleFactorChanged`, and `RedrawRequested` — all handled in *separate* match arms above. So this condition can never be true; the branch is unreachable. Harmless, but misleading. → Drop the guard.
- **Redundant double surface resize** (`runtime.rs:691` vs `593`). On `WindowEvent::Resized`, `handle_window_event` calls `resize_surface`, which resizes the softbuffer surface; then the subsequent `RedrawRequested` → `present_frame` resizes it **again** to `window.inner_size()` before rendering. The `present_frame` resize is the authoritative one (it feeds the buffer that is actually presented), so the `Resized`-arm resize is redundant work, not a correctness bug. → Drop the eager resize or make `present_frame` trust the prior resize.
- **`WinitEventTranslator.metrics` is carried but the renderer ignores it** (`runtime.rs`). `present_frame` computes the viewport and scale from `window.inner_size()`/`window.scale_factor()` fresh on every frame, never from `event_translator.metrics()`. The translator's metrics feed only `RuntimeLifecycle` counters (`record_translated_event`). This is benign (the live window is the right source of truth) but means the translator holds state the render path does not consult — a mild smell, and a place where a future reader could wrongly assume metrics flow translator→renderer.
- **`run_blocking` vs `run_dev_blocking` duplicate the event-loop bootstrap and the two `ApplicationHandler` impls duplicate every handler body** (`runtime.rs:388,419` and the two `impl ApplicationHandler[...] for RuntimeApplication` blocks). The handler bodies all delegate to the shared `handle_*` methods, so divergence risk is contained, but the boilerplate is sizable. `run_blocking` correctly resolves to the `ApplicationHandler<()>` impl (no user-event type), so reloads are simply unreachable there by construction — fine, but worth a doc note.
- **`compact_f32`/`compact_f64`** (`lib.rs:680,691) format scroll deltas into strings for `PointerInput` labels like `"wheel-lines:1:-2"`. Encoding numeric scroll magnitude into a free-form string (then presumably re-parsed downstream) is stringly-typed; a structured pointer-delta would be cleaner. Low.

## Security

The trust boundaries are **untrusted clipboard contents**, **file-dialog paths**, and **`Deserialize`-able host config/requests** (`DesktopWindowConfig`, `DesktopDialogRequest`, both `#[derive(Deserialize)]` in `hawk2ui-host`). `#![forbid(unsafe_code)]` holds; there is **no `unsafe`** anywhere in the crate — appropriate to flag as clean.

- **Good: file-dialog input validation is real and reasonably tight** (`lib.rs::validate_dialog_*`). `validate_dialog_file_name` rejects empty, `/`, `\`, and `\0` — blocking a path being smuggled through the save-file *name* field. `validate_dialog_filters` rejects empty names/extensions, leading dots, separators, and NUL in extensions. Titles/messages are non-empty-checked. These run in `WinitDialogBridge::handle_request` before any `rfd` call. **Note (Low):** the `directory: Option<PathBuf>` for open/save is passed to `rfd::FileDialog::set_directory` **unvalidated** — an attacker-supplied (e.g. deserialized) `DesktopDialogRequest` could point the picker's starting directory anywhere on the filesystem. This is only a starting hint (the user still confirms via the native picker, and `rfd` does not auto-read it), so it is **not** path-traversal/TOCTOU in the file-read sense, but the directory is the one dialog field with no validation while the file-name field is strictly validated — an inconsistency worth a bound (e.g. require existing/absolute, or canonicalize). **Low.**
- **No untrusted-input recursion DoS** (contrast with `hawk2ui-a11y`). The rendered `RuntimeViewTree` is `#[derive(Clone, Debug, PartialEq)]` only — **not** `Deserialize` — and is stored as a flat `Vec<RuntimeViewEntry>` built solely through the validating `with_child` API, so there is no deeply-nested-deserialized-tree stack-overflow vector through this crate. The `Deserialize`-able inputs that *do* reach it (`DesktopWindowConfig` metrics+title, `DesktopDialogRequest`) are scalar/bounded and validated. Clean.
- **Event loop fails closed, not via panic** (`runtime.rs::handle_window_event`/`fail`). Every fallible op in the loop returns `Result`; errors set `last_error` and call `event_loop.exit()`. There is no `unwrap`/`expect`/`panic!` on the present/resize/render path. `elapsed_ms` uses `unwrap_or(u64::MAX)` (saturating, not panicking). So a transient surface/render failure terminates the loop with a diagnostic rather than aborting the process — no panic-as-DoS in the event loop.
- **Latent `copy_from_slice` length-panic point** (`runtime.rs:635`). `buffer.copy_from_slice(frame.pixels())` panics if the Skia frame's pixel count ever diverges from the softbuffer buffer length. Currently safe — both are derived from the same `window.inner_size()` and `present_frame` resizes the surface to match immediately before — so dimensions are threaded consistently. But it is the one place in the loop where a dimension-tracking bug would become an immediate panic rather than a clean `WinitHostError`. → A length check returning `desktop.surface.*` error would make the loop's fail-closed property total. **Low / robustness.**
- **Clipboard contents are passed verbatim** between `arboard` and host events (`SurfaceClipboardRequest::Write(text)`), with no length bound. arboard/the OS tolerate arbitrary text (not an injection vector here), but there is no cap on read/written text size — a slow memory-pressure consideration, not an exploit. **Low.**
- **Detached reload thread can outlive the loop** (`runtime.rs:434`). `run_dev_blocking` spawns a thread that blocks on `for reload in reloads` (the `Receiver`); if the event loop exits first, that thread lingers blocked on `recv` until the sender side is dropped. Minor resource/lifecycle note, not a leak of OS handles. **Low.** Surface resources themselves are correctly released in `exiting` (`self.surface/context/window = None`).
- **Frame allocation is bounded by window dimensions, with overflow guards.** `SoftwareFrame::new`, `render_frame`, and `surface_to_frame` use `checked_mul`/`try_from` to reject pixel-count, row-byte, and byte-count overflow before allocating, and `i32::try_from` guards the Skia raster size. No unbounded allocation from these paths.
