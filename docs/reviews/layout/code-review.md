# Code Review — hawk2ui-layout

**Reviewed at:** `5a042c51` · 2026-05-28 · **Remediated at:** `e7918972` · 2026-05-28
**Scope:** `src/{lib,compute,tree,text,scene,plugin}.rs` + `tests/layout_behavior.rs` (6 src files ~2.3k LoC / 1 test file ~700 LoC)
**Purpose:** Layout tree records + style model, a text-measurement bridge feeding Taffy leaf sizing, plugin-editor size/region constraints, and scene-geometry attachment (render/hit-test/clip/a11y) for `Hawk2UI`. Built on `taffy` 0.10 (flexbox + grid) over `hawk2ui-text`.
**Note:** The two Medium findings (#1 silent-empty, #2 parent-relative coordinates) were **remediated** at `e7918972` — see the Remediation section. The crate is Tier-1 (no High findings); the remaining items are deferred Low/Low-Med quality notes.

## Summary

This crate is **genuinely implemented, not a stub, and it really computes layout with Taffy** — this was the central question and the answer is unambiguous. `LayoutTree::try_compute_layout_inner` (`compute.rs:137`) constructs a real `TaffyTree<TextMeasureInput>`, builds the node graph via `build_taffy_node`, calls `taffy.compute_layout_with_measure(...)` (real flexbox/grid solving), and reads geometry back with `taffy.layout(taffy_id)`. **Both flexbox and grid are wired**: `taffy_style` sets `Display::Grid` when a grid style is present and `apply_grid_style` (`compute.rs:334`) maps template/auto tracks (`fr`/`min_content`/`max_content`/`px`/`auto`), `grid_auto_flow`, and row/column line+span placements into Taffy. The tests assert solver outputs, not canned values (`right.x == 115.0` = 10 padding + 100 width + 5 gap; grid `content.x == 90`, `content.width == 100`), and `grid_layout_computes_template_tracks_gaps_spans_and_auto_flow` confirms grid is exercised end-to-end. The **text bridge is real on both ends**: `HawkTextMeasurer` (`text.rs:194`) delegates to `hawk2ui_text::TextBackend::layout`, and the measurer is fed into Taffy's measure closure through `new_leaf_with_context` + `measure_text_leaf` (`compute.rs:226`, `compute.rs:245`). No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME/HACK markers, and **no `serde` anywhere** — there is no `Deserialize`-able layout tree, so (unlike `hawk2ui-a11y`) there is no deserialization attack surface.

The substantive weaknesses are: (1) the **ergonomic non-`try_` `compute_layout` swallows every error and returns an empty layout** indistinguishable from a real empty result; (2) **`ComputedGeometry` exposes Taffy's parent-relative coordinates verbatim** — undocumented as parent-relative and propagated unchanged into render/hit-test/a11y bounds, so any consumer treating them as absolute mis-places every nested node; (3) the **`compute_layout`/`try_compute_layout` paths pass `None` for the measurer, silently collapsing any text-measured node to zero content size**; (4) **`GeneratedParameterLayout::dense_panel` is validated metadata that emits no layout nodes** — the name overpromises a generated layout; (5) **linear-scan tree access (O(n²)) on a per-frame hot path**; and (6) **flexbox is a deliberate subset** (no wrap, no reverse, single shared gap). There is **no High-severity finding**: the recursion DoS that was High in `hawk2ui-a11y` is materially lower here because trees are cycle-free by construction and never deserialized.

## Remediation (2026-05-28 · `e7918972`)

`hawk2ui-layout` is Tier-1 (real Taffy flexbox + grid, real text bridge; no High findings). The two Mediums are intentional behaviors that were undocumented — clarified the load-bearing contracts and pinned the coordinate space with a test.

- **#2 — parent-relative coordinates (FIXED: documented + pinned).** `ComputedGeometry.x/y` are Taffy's parent-relative coordinates (relative to the parent's border box), propagated verbatim into `SceneGeometry`/render/hit-test/a11y. The field docs now state this explicitly and warn that treating them as absolute mis-places every nested node. Added `computed_geometry_is_parent_relative_not_absolute`, which nests a child under an offset parent and asserts the grandchild's coordinate is its parent-relative offset `(20,20)`, not the absolute `(30,30)` — pinning the contract so any future switch to absolute accumulation must change the test deliberately. (Pipeline-wide absolute-position accumulation is a cross-crate coordinate decision, deferred.)
- **#1 / #3 — silent-empty and zero-text contracts (FIXED: documented).** `compute_layout` now documents that it returns an empty `LayoutOutput` on *any* failure (indistinguishable from a real empty tree → use `try_compute_layout` to detect failure) and that text-measured leaves collapse to zero without a measurer. `try_compute_layout` documents the same zero-text behavior and points to `try_compute_layout_with_text_measurer`.

**Not addressed here** (deferred, all Low/Low-Med, no untrusted-input vector): #4 recursion depth cap (mitigated — no `serde`, cycle-free by construction; a defense-in-depth cap is deferred), #5 O(n²) tree access (a `HashMap` index — perf refactor), #6 `GeneratedParameterLayout` naming, #7 `clamp_host_size` swallow, #8 flex subset (no wrap/reverse, shared gap, `flex_shrink` default 0), #9 dead `_label`, #10 unconsumed plugin regions, #11 no `Diagnostic` bridge.

## Completeness & implementation gaps

1. **`compute_layout` swallows all errors → silent empty layout** (`compute.rs:110`). The non-fallible convenience wrapper is `self.try_compute_layout(viewport).unwrap_or_else(|_| LayoutOutput::new(Vec::new(), Vec::new()))`. Any failure — invalid viewport, `InvalidStyle` (e.g. a NaN dimension), missing root, or a Taffy/`ComputeFailed` error — is discarded and returned as an **empty `LayoutOutput`**, which is indistinguishable from a legitimately empty tree. This is the API most consumers reach for (the tests use it pervasively; `hawk2ui-runtime`/`hawk2ui-host-*` are consumers). A frame whose tree silently fails to lay out renders nothing with no diagnostic. The `#[must_use]` doc says nothing about the empty-on-error contract. → Either document this explicitly or have hosts call `try_compute_layout`. This is the strongest correctness finding.
2. **`ComputedGeometry` carries Taffy's *parent-relative* coordinates, undocumented, and propagates them verbatim into render/hit-test/a11y** (`compute.rs:188`, `scene.rs:21`). `try_compute_layout_inner` copies `layout.location.x`/`.y` straight into `ComputedGeometry.x`/`.y` (`compute.rs:189`). In Taffy 0.10 `Layout.location` is **relative to the parent's border box** (confirmed against Taffy docs: `content_box_x` = "content-box top-left relative to parent's border box"), not absolute. `SceneGeometry::from_computed` (`scene.rs:21`) then copies that same value into `render`, `hit_test`, and (via the attachment) the a11y bounds **unchanged**. `ComputedGeometry`'s docs say only "X coordinate" / "Y coordinate" with no mention of the frame. A render/hit-test/a11y consumer that assumes absolute coordinates will mis-place **every nested node** by its ancestors' offsets. The crate provides no absolute-position accumulation and no documentation of the contract. The tests never expose this because every test child is a direct child of a root positioned at the origin (so relative == absolute: `left.x == 10`, `right.x == 115`, grid `content.x == 90` are all parent-relative under a root at 0,0). → Document the coordinate space explicitly, or have the read-back accumulate absolute positions; add a nested-under-offset-parent test.
3. **`compute_layout`/`try_compute_layout` collapse text-measured leaves to zero** (`compute.rs:121`, `compute.rs:252`). Both call `try_compute_layout_inner(viewport, None)`. In `measure_text_leaf`, `let (Some(input), Some(measurer)) = (context, measurer) else { return Size::ZERO; }` — with `measurer == None`, **every node carrying `text_measurement` measures to `Size::ZERO`**. So a tree built with text leaves but laid out through the non-measurer entry points produces zero-sized text content with no error. Only `try_compute_layout_with_text_measurer` feeds a real measurer. This is an easy footgun: `with_text_measurement` attaches input that is then silently ignored unless the caller picks the right compute method. → Document the requirement, or treat "text node present but no measurer" as an error/warning.
4. **`GeneratedParameterLayout::dense_panel` is record-only metadata, not a generated layout** (`plugin.rs:183`). It stores `id`, `parameters`, and a clamped `columns`, and computes `rows()` via `div_ceil`. It produces **no `LayoutNode`s, no geometry, no Taffy nodes** — nothing in the crate turns it into a panel. The name and the builder verb (`with_generated_parameters`) advertise layout generation that does not occur in-crate; the only behavior is validation + `rows()` arithmetic. This is the one fair naming/altitude smell in the plugin module (not a stub — it is real validated metadata — but the name overpromises). → Either rename to reflect "parameter panel descriptor" or have it emit a sub-tree.
5. **`GraphRegion` / `AnalyzerRegion` are validated, ID-retrievable geometry with no in-crate consumer** (`plugin.rs:104`, `plugin.rs:138`). They are validated by `validate_region` and fetched by ID (`graph_region`/`analyzer_region`), but nothing in this crate uses their `x/y/width/height` to drive layout. This is plausibly legitimate ("the plugin exposes named regions for the host to position custom surfaces"), so it is **not** flagged as a stub — but it should be confirmed that a downstream consumer (host/render) actually reads these; otherwise they are inert records. Verify against `hawk2ui-host-baseview`/`hawk2ui-render-skia`.

## Code quality & smells

- **O(n²) tree access on the layout hot path** (`tree.rs:839` `entry`, `tree.rs:845` `find_index`, `tree.rs:829` `node`). All node lookups are linear scans of the `nodes: Vec<TreeEntry>`. `validate()` (`tree.rs:791`) calls `find_index` inside a nested loop over every child of every node → O(n²); `with_child` calls `find_index` twice per insertion → O(n²) to build a tree; and the geometry read-back loop in `try_compute_layout_inner` calls `self.node(&layout_id)` per node → another O(n²) over the just-built `ids`. Layout reruns on every resize/DPI change, so this is a per-frame cost. For small editor trees it is fine; for large desktop trees it is a latent scaling cost. → A `HashMap<LayoutNodeId, usize>` index would remove it.
- **Flexbox is a deliberate subset** (`tree.rs`/`compute.rs`). No `flex-wrap` (Taffy default `NoWrap` is never overridden), no `Row-Reverse`/`Column-Reverse` (`FlexDirection` has only `Row`/`Column`, `compute.rs:313`), and `gap` is a single `LayoutValue` applied to **both** axes (`compute.rs:307`-`310`) rather than independent row/column gaps. Grid, by contrast, is fairly complete. This is a scoping choice, not a bug, but the crate cannot express wrapped flex rows or asymmetric gaps. Worth documenting as a known limitation.
- **`flex_shrink` defaults to `0.0`** (`tree.rs:438` `base()`). CSS/Taffy default flex-shrink is `1.0`; here flex items do not shrink unless `with_flex_shrink` is called. Combined with `flex_grow` default `0.0`, the default flex item is rigid. Intentional and internally consistent, but it diverges from CSS expectations and is undocumented on the builder.
- **`validate_size`'s `_label` parameter is dead** (`plugin.rs:430`). Every caller passes a descriptive label (`"default"`, `"min"`, `"max"`, `"host"`) but the function ignores it and emits a single fixed `plugin-layout.size.invalid` message. The label is threaded through but never reaches the diagnostic, so callers cannot tell *which* size failed from the error. Minor — either use it in the message or drop the parameter.
- **Geometry validation rejects the whole tree on one bad node, reporting only an ID string** (`compute.rs:195`). When `is_valid_computed_geometry` fails, the error is `ComputeFailed(layout_id)` — a bare ID with no indication it was a geometry-finiteness failure vs. the "node missing" case at `compute.rs:181` which produces the *same* shape. The two distinct failure modes are indistinguishable to a caller parsing the error string.
- **`PluginEditorSurfaceMetrics` round-trips DPI but `physical_size` silently saturates** (`plugin.rs:419` `scaled_physical_dimension`). Non-finite or overflowing products clamp to `0` / `u32::MAX`. This is defensible defensive code, but a `0×0` physical surface from a non-finite logical size is a silent degenerate result rather than an error (validation upstream should prevent it, but `PluginEditorSurfaceMetrics::new` is public and unchecked).

## Documentation

- Strong baseline: crate-level `//!` on every module, every public type/method documented, and `# Errors` sections present on all fallible entry points (`with_child`, `validate`, `try_compute_layout`, `try_compute_layout_with_text_measurer`, `try_clamp_host_size`, `try_negotiate_host_resize`, the `LayoutTextMeasurer` trait). No undocumented public items found.
- **Misleading/incomplete in the spots tied to the gaps above:** `compute_layout` does not document that it returns an **empty** layout on *any* error (gap #1); `ComputedGeometry.x`/`.y` are documented only as "X/Y coordinate" with no mention that they are **parent-relative** (gap #2) — a load-bearing omission for a record consumed by render/hit-test/a11y; neither `compute_layout` nor `with_text_measurement` documents that text leaves measure to **zero** without a measurer (gap #3); and `GeneratedParameterLayout`'s docs ("Generated parameter layout" / "dense parameter panel layout") imply node generation that does not happen (gap #4). The `flex_shrink`/`flex_grow`/`gap` defaults and the flex-subset limitations are undocumented.

## Testing

- Good breadth on the happy paths: parent/child structure, style→record conversion, ID/style/viewport rejection (NaN size, zero viewport, NaN flex factor), flex row layout with padding+gap (real solver math), scroll-clip + absolute tracking, min/max clamping, flex grow/align/basis/inset, **grid template/gap/span/auto-flow**, the `TestTextMeasurer` intrinsic/wrap/truncate cases, `TextMeasureKey` invalidation, the **production `HawkTextMeasurer`** against a real `TextBackend` (incl. bidi/emoji input), text-into-Taffy via the measurer, plugin clamp + DPI negotiation + invalid-size/region/parameter rejection, and scene attachment (render/hit/clip/a11y/surface) + recomputation.
- **False-confidence gaps (parallel to a11y/assets):**
  - **No test ever observes the empty-on-error fallback** (gap #1). Every `compute_layout` call in the suite uses a *valid* tree, so the silent-empty path is invisible; error behavior is only checked through `try_compute_layout`. A test feeding an invalid tree to `compute_layout` and asserting the empty result (and ideally that `try_` errors) would expose the contract.
  - **No test disambiguates the parent-relative coordinate frame** (gap #2). Every test child is a direct child of a root at the origin, so parent-relative and absolute coordinates coincide; a child nested under a parent at a non-zero offset would reveal whether `ComputedGeometry.x/y` are relative (they are) and is the test that would have surfaced the undocumented contract.
  - **No test for the zero-measurer text path** (gap #3). `layout_tree_feeds_text_measurements_into_taffy` always supplies a measurer; nothing checks what `compute_layout` does to a text-measured node (it would silently zero it).
  - **No deep-tree / recursion-depth test** (see Security) and no test that a region/generated-parameter record is actually consumed by layout (would surface gaps #4/#5).
- The `HawkTextMeasurer` assertions are loose (`<= 160.0`, `>= 38.0`, `>= 1`) — appropriate for a real shaping backend whose exact metrics are font-dependent, but they would not catch a measurer that returned a plausible-but-wrong size.

## Cross-cutting conventions (workspace-wide; noted where this crate deviates)

- `crate_name()` + `exposes_crate_identity` follow the workspace pattern.
- **Deviation (Low):** this crate does **not** carry a `*_workspace_filter_marker` test (which `hawk2ui-a11y` includes for the conformance filter gates). Like `hawk2ui-assets`, it is invisible to any gate that enumerates per-crate markers.
- **Deviation (Low):** the crate's error types (`LayoutTreeError`, `TextMeasureError`, `PluginLayoutError`) have **no `From` bridge to `hawk2ui_api::Diagnostic`**, and the crate does **not depend on `hawk2ui-api`** at all (deps are only `hawk2ui-text` + `taffy`). `TextMeasureError`/`PluginLayoutError` carry a `rule()`+`message()` shape that mirrors `Diagnostic` but cannot fold into the unified diagnostic stream without a caller-side adapter. Same pattern as `hawk2ui-assets`.

## Security

The trust boundary here is **in-process, programmatically-built layout trees** (via `LayoutTree::new` + `with_child`) plus **`f32` dimensions** from those builders and from plugin hosts. There is **no `serde`**, so — in sharp contrast to `hawk2ui-a11y` — there is **no `Deserialize`-able tree from untrusted input**. `#![forbid(unsafe_code)]` holds; there is no `unsafe`.

- **Unbounded recursion over the layout tree (Low–Medium, *not* High).** `build_taffy_node` (`compute.rs:208`) recurses over `children_of`, and Taffy's own `compute_layout_with_measure` recurses through the built tree. Depth is bounded only by the depth of the in-process tree. **Why this is lower than a11y's High:** (a) there is no `Deserialize`, so an attacker cannot inject a deep tree directly; (b) the tree is **cycle-free by construction** — `LayoutTree` fields are private, the only constructors are `new` + `with_child`, `with_child` rejects duplicate IDs and only ever appends a *new* node as a child of an *existing* one, so parent→child edges always point to strictly-newer nodes and cannot form a cycle (the recursion therefore terminates). The residual risk is a pathological but legitimately-constructed deep tree (e.g. thousands of nested nodes from a generated UI) overflowing the stack during build or solve. → A depth cap in `validate()`/`build_taffy_node`, or an iterative build, would harden it for defense-in-depth. There is no test exercising deep nesting.
- **Good f32 NaN/Inf/negative validation at the boundaries.** `validate_viewport` (`compute.rs:466`) rejects non-finite/non-positive viewports; `validate_value`/`validate_sizing`/`validate_edges` (`tree.rs:920`) reject non-finite values and enforce non-negativity except where negatives are legitimate (margin/inset); `validate_layout_style` rejects non-finite/negative `flex_grow`/`flex_shrink`; and **the computed geometry is re-validated** post-solve via `is_valid_computed_geometry` (`compute.rs:478`, finite + non-negative width/height) before it is emitted, so a Taffy result that somehow produced NaN/negative sizes is rejected rather than propagated to render/hit-test. Plugin sizes are validated by `validate_size` (finite + positive) and DPI by `try_negotiate_host_resize` (finite + > 0), and `scaled_physical_dimension` saturates rather than panicking on overflow. This is thorough and is the crate's strongest security property.
- **Plugin size constraints are actually enforced** (not record-only). `try_clamp_host_size` (`plugin.rs:322`) validates then `clamp`s host width/height into `[min,max]`, and `validate` rejects inverted ranges (`min > max`). `clamp_host_size`/`clamp`-based negotiation genuinely bound the accepted editor size. Note the **non-fallible `clamp_host_size` (`plugin.rs:312`) swallows validation errors and falls back to `default_size`** — same swallow pattern as `compute_layout` (gap #1); on invalid constraints it silently returns the default rather than surfacing the error.
- **Unbounded memory is not a notable vector here.** The crate holds no long-lived growing collections (no event log / no manifest map like a11y/assets); trees are transient per-compute. The only growth is proportional to caller-supplied tree size.
- **No panics-as-DoS in `src`.** The only `unwrap`-family calls are `unwrap_or`/`unwrap_or_else`/`Option::unwrap_or` (`plugin.rs`, `compute.rs`) — none can panic. No `expect`, no `panic!`, no indexing that can go out of bounds on attacker-influenced input (the one index, `self.nodes[parent_index]` in `with_child` at `tree.rs:777`, uses an index just obtained from `find_index` on the same `&self`).
