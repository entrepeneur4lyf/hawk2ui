# Code Review — hawk2ui-security-model

**Reviewed at:** `5a042c51` · 2026-05-28 · **Remediated at:** `e7918972` — security-model's own sources are unmodified in the provided git status; the workspace tree carries uncommitted changes elsewhere, including `crates/hawk2ui-build/src/artifact.rs` (the file the Ed25519 trust trace below depends on), so the dependency was read at working-tree state, not at the stamped SHA.
**Scope:** `src/lib.rs` + `tests/threat_model.rs` (1 src file ~747 LoC / 1 test file ~474 LoC) plus the validated registry data under `security/*.toml`
**Purpose:** The security-critical registry crate: a machine-readable threat-model registry, a capability allow/deny rejection registry, a source/asset attack-fixture registry, a sandbox runtime-authority policy with diagnostic redaction, and package **trust validation** for sealed release artifacts (schema/hash/signature/verification-report gates), bridging failures to `hawk2ui_api::Diagnostic`.
**Note:** The three trust-layer logic defects (#1 stale threat registry, #2 inert redaction, #3 forgeable `Verified`) were **remediated** at `e7918972` — see the Remediation section. The findings text below reflects the original review at `5a042c51`; the remaining open item is #4 (no enforcement wiring), surfaced as a bucket-(c) capability decision.

## Summary

The crate is a **mix of one genuinely-real capability and several declarative/inert ones**, and the split matters because this is the trust layer. The **package signature trust path is real** and is the strongest thing here: `PackageTrustRecord::from_trusted_sealed_artifact` (`lib.rs:480`) delegates to `hawk2ui_build`'s `SealedArtifact::verify_trusted_signature` → `ArtifactSignatureVerifier::verify`, which is genuine Ed25519 (`VerifyingKey::from_bytes` + `verifying_key.verify(payload, sig)` over a domain-separated `signature_payload_bytes()`, with algorithm check and trusted-key lookup by `key_id`). That constructor only emits `PackageSignatureStatus::Verified` on a cryptographically valid signature, and the metadata-only `from_sealed_artifact` (`lib.rs:463`) correctly never emits `Verified`. The registry parsers (`ThreatModel`/`CapabilityRejections`/`AttackFixtures`) do real TOML deserialization plus structural validation (duplicate-ID detection, required-field non-emptiness, and — for capabilities — an allow-AND-deny completeness check). No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME/HACK markers.

The security-relevant weaknesses cluster in three places. (1) **The threat registry has already gone stale**: each threat names a `required_test`, `validate()` only checks the string is non-empty, and **3 of the 8 referenced test names do not exist anywhere in the workspace** — the registry's central "every threat is covered by a test" promise is unenforced and already violated. (2) **`redact_diagnostic` (`lib.rs:398`) is inert security logic** — it is the *enforcing mitigation* for the Critical `secret-exposure` threat, yet it matches one secret prefix (`sk_`) and one hardcoded literal eval payload, i.e. it is written to pass its own test rather than to redact. (3) **`PackageTrustValidator::validate` keys on a forgeable field**: `PackageTrustRecord` has all-public fields and `validate()` (`lib.rs:561`) treats `signature_status == Verified` as proof, even though that variant can be hand-constructed without any crypto. Finally, **nothing in the workspace consumes this crate** — no crate depends on it and the public API has zero callers outside this crate's own tests, so the model is self-tested, not wired to a release gate.

## Remediation (2026-05-28 · `e7918972`)

Fixed the three trust-layer **logic** defects (#1, #2, #3) — broken logic in existing code, fixed regardless of the crate's (currently absent) consumers, since these are exactly the false-assurance controls a future caller would wire up trusting they work.

- **#1 — stale threat registry (FIXED).** Corrected the 3 phantom `required_test` references in `security/threat-model.toml` to tests that **genuinely cover** each threat: `malicious-source` → `source_asset_fixtures_map_each_attack_to_diagnostic`, `malicious-plugin-host-data` → `capability_rejections_cover_all_capabilities` (checks the `plugin-metadata` capability), `untrusted-user-data` → `runtime_authority_denies_unsafe_operations` (asserts `UndeclaredHostApi` is denied). Added an enforcement test (`security_threat_registry_required_tests_exist`) that reads this test file's source and fails if any threat's `required_test` is not a real `fn` here — the "every threat is test-covered" promise can no longer silently drift. (All `required_test`s are in-crate; a cross-crate reference would correctly fail this check.)
- **#2 — inert `redact_diagnostic` (FIXED, with an honesty label).** Replaced the `sk_`-prefix-plus-one-literal matcher with a structured, punctuation/quote-aware redactor: a token-run scan over a denylist of well-known credential prefixes (Stripe `sk_`/`pk_`/`rk_`, GitHub `gh*_`, AWS `AKIA`/`ASIA`, Slack `xox*-`), opaque tokens following a `Bearer`/`Authorization` keyword, and `eval(...)` / `Function(...)` payloads — preserving surrounding text instead of the old lossy whitespace-collapse. It is **explicitly documented as best-effort, not exhaustive, and not a sole control** (a denylist is evadable by construction); new formats must be added to `SECRET_PREFIXES`. Tests cover quoted/punctuation-adjacent secrets, all five prefix families, `Bearer` tokens, and alternate eval payloads.
- **#3 — forgeable `Verified` (FIXED).** `PackageSignatureStatus::Verified` now carries a `VerifiedSignature` witness whose only field is private, so it is **unconstructable outside this crate** — `Verified` can be produced only by `from_trusted_sealed_artifact` after a real Ed25519 check, and `validate()` therefore tests an *established fact*, not a caller-asserted claim. The forgery test and the missing-report test now build records through the crypto path (a `signed_trust_record` helper); the schema/hash rejection tests use `Missing` (they fail before the signature check anyway).

**Surfaced for the bucket-(c) batch (needs a consumer to exist):** #4 — **no enforcement wiring.** Nothing in the workspace calls `PackageTrustValidator` / `RuntimeAuthorityPolicy` / the registries; they are validated in-crate but applied at no real release/runtime gate. Wiring them into build/packaging/runtime (vs. documenting this as a contract-fixture registry consumers must independently honor) is an architecture decision, not a contained fix.

**Not addressed here** (deferred Low items, unchanged from below): #5 `RuntimeAuthorityPolicy` deny-all-only constructor; #6 remaining tautological tests (the new enforcement + diverse-redaction tests replace the worst offenders); #7 missing `deny_unknown_fields` on registry structs + unchecked fixture-path existence; #8 missing `Diagnostic` bridges for the three registry error enums + duplication.

## Completeness & implementation gaps

1. **Threat registry references phantom tests; the coverage link is unenforced and already broken** (`ThreatModel::validate`, `lib.rs:91`; `Threat::require_field`, `lib.rs:44`). Each `Threat` carries `required_test`, the documented purpose of which is to bind a threat to "the required test or fixture identifier." But `validate()` only calls `require_field("required_test", …)`, which checks `value.trim().is_empty()` — it never checks the named test **exists**. Cross-referencing the 8 rows in `security/threat-model.toml` against actual test names across the **whole workspace**: 5 match (`package_trust_rejects_tampered_artifact`, `package_trust_rejects_missing_verification_report`, `runtime_authority_redacts_secret_payloads`, and the `source_asset_fixtures_map_each_attack_to_diagnostic` / `capability_rejections_cover_all_capabilities` it points at indirectly), but **3 reference tests that do not exist anywhere**:
   - `malicious-source` → `source_asset_fixtures_reject_unsupported_style` (no such test; the real one is `source_asset_fixtures_map_each_attack_to_diagnostic`)
   - `malicious-plugin-host-data` → `capability_rejections_cover_plugin_metadata` (no such test)
   - `untrusted-user-data` → `runtime_authority_denies_undeclared_host_api` (no such test)
   This is the canonical **"documented threat with no enforcing check"** failure, and it is not hypothetical — the registry has *already* drifted: three Critical/High threats point at green-looking test IDs that were renamed or never written, and nothing catches it. → `validate()` (or a workspace conformance test) must assert each `required_test` resolves to a real, present test; otherwise the registry is decorative. **High.**
2. **No enforcement wiring — the model is self-contained and self-tested** (whole crate). Grepping the workspace: **no crate depends on `hawk2ui-security-model`** (only the workspace-root `Cargo.toml` member list references it), and there are **zero callers** of `PackageTrustValidator`, `from_trusted_sealed_artifact`, `from_sealed_artifact`, `RuntimeAuthorityPolicy`, `ThreatModel::parse`, `CapabilityRejections::parse`, or `AttackFixtures::parse` outside this crate's own `tests/threat_model.rs`. The only consumer of the registries is the test file reading `security/*.toml` via `include_str!`. So the crate's guarantees — package trust gating, sandbox-authority denial, secret redaction — are **validated in-crate but not applied at any real release/runtime enforcement point.** Whether that is acceptable depends on intent (a conformance fixture vs. a runtime gate), but per the crate description ("package trust validation") and the threat mitigations ("Reject … before runtime", "redact diagnostic output"), the validation is currently **descriptive, not wired to enforcement.** → Either wire `PackageTrustValidator`/`RuntimeAuthorityPolicy`/`redact_diagnostic` into the build/packaging/runtime path, or document that this crate is a contract-fixture registry that other crates must independently honor. **Medium.**
3. **`redact_diagnostic` does not redact — it pattern-matches two literals** (`RuntimeAuthorityPolicy::redact_diagnostic`, `lib.rs:398`; `redact_token`, `lib.rs:408`). Body: split on whitespace, map each token through `redact_token` (which redacts **only** tokens with the `sk_` prefix), re-join, then `.replace("Function('return secrets')", "[redacted-source]")` (one exact literal). This is the **enforcing mitigation** for the Critical `secret-exposure` threat ("redact diagnostic output, … reject plaintext secret leakage"), but it misses: `pk_`/`rk_` Stripe keys, AWS `AKIA…`, GitHub `ghp_`/`gho_`, `Bearer …` tokens, anything quoted or punctuation-adjacent (`"sk_live_…"` starts with `"`, so `starts_with("sk_")` fails), and every eval payload that is not byte-for-byte `Function('return secrets')` (`eval(...)`, `new Function(...)`, different argument). It is implemented to pass `runtime_authority_redacts_secret_payloads`, which feeds exactly those two literals. The lossy `split_whitespace().join(" ")` also silently rewrites the diagnostic (collapses runs of whitespace, drops leading/trailing) as a side effect. **In a security crate this is inert security logic, not a smell.** **High.**
4. **`PackageTrustValidator::validate` trusts a forgeable claim** (`lib.rs:561`). `PackageTrustRecord` has **all public fields**, and `validate()` accepts the record when `record.signature_status == PackageSignatureStatus::Verified`. Nothing forces a record through the crypto path: `package_trust_accepts_complete_verified_record` (test, `tests/threat_model.rs:264`) hand-builds `signature_status: Verified` with zero signature material and passes. Real trust exists *only* because the honest path (`from_trusted_sealed_artifact`) is the one that gates `Verified` on Ed25519 verification — but the type system does not require callers to use it, and any code (or a future caller) constructing a `PackageTrustRecord` directly can assert `Verified` for free. → Make `PackageSignatureStatus::Verified` constructor-gated (e.g. private field / sealed builder) so `validate()` checks an *established* fact, not a claim. **Medium.**
5. **`RuntimeAuthorityPolicy` is a constant dressed as a configurable policy** (`lib.rs:368`). The struct stores `denied: BTreeSet<RuntimeOperation>`, implying configurability, but the only constructor is `sandboxed()` (`lib.rs:375`), which inserts all six variants; there is no allow path, no capability-scoped relaxation, no builder. `is_denied` therefore returns `true` for every defined operation under the only constructible policy. The `BTreeSet` field and the "policy" naming over-state what exists (a hardcoded deny-all). Not wrong, but the data model promises flexibility the API does not provide. **Low.**

## Code quality & smells

- **`Severity` only models High/Critical** (`lib.rs:21`). The threat-model enum has no Low/Medium/Info, and `security_threat_registry_covers_required_domains` (test) asserts every row is `High | Critical` — which is *type-guaranteed* since those are the only variants (see Testing). Fine as a "release-blocking only" registry, but the enum name is broader than its contents and the invariant test is tautological.
- **`Raw*` deserialization structs omit `#[serde(deny_unknown_fields)]`** (`RawThreatModel` `lib.rs:63`, `RawCapabilityRejections` `lib.rs:172`, `RawAttackFixtures` `lib.rs:290`; same for the row structs `Threat`/`CapabilityCase`/`AttackFixture`). The sibling `hawk2ui-build` applies `deny_unknown_fields` on its artifact types (e.g. `BuildMetadata`, `ArtifactSignatureVerificationKey`). Here, unknown/typo'd keys in `security/*.toml` are silently ignored — a misspelled `requied_test` would deserialize as an empty `required_test` and only be caught by the (non-emptiness-only) `require_field`, or not at all if defaults applied. Input is trusted-in-repo so the deserialization risk is low; flagged as a hardening deviation. **Low.**
- **Three near-identical `require_field` + `validate` + `Raw*` + `*Error` quartets** (`Threat`/`CapabilityCase`/`AttackFixture`). Each registry repeats the same shape: a `Raw*` wrapper, a `parse` that maps `toml::from_str` error to a `Parse(String)`, a per-row `require_field` returning a registry-specific `MissingRequiredField { id, field }`, and a `validate` doing duplicate-ID detection via `BTreeSet`. Mechanical duplication; a shared helper/trait would remove ~60 LoC and three parallel error enums. Cosmetic. **Low.**
- **`toml` parse errors are stringified** (`Parse(String)` in all three errors, `lib.rs:77`/`186`/`304`). `.map_err(|error| …::Parse(error.to_string()))` discards the structured `toml::de::Error` (span/line info). For repo-internal fixtures this is acceptable, but it loses the location context that would make a malformed-registry failure actionable.
- **`from_artifact_parts` silently coalesces two different hash provenances** (`lib.rs:495`). `compiled_asset_hashes` is the sorted-deduped union of `asset_manifest[].hash` and `compiled_assets[].source_hash`; `compiled_script_hashes` picks `compiled_source` hash when non-empty else `source_hash`. The trust record cannot later distinguish "asset manifest hash" from "compiled asset source hash," nor "compiled" from "source" script hash. By design (the validator only checks non-emptiness + format), but the asymmetry is undocumented and means the record proves *some* hash exists per slot, not *which*.

## Security

This is the trust layer, so the central question is whether "trust validation" and "source/asset validation" *establish* security properties or merely *assert structure*. The verdict is mixed and important to state precisely. `#![forbid(unsafe_code)]` holds; there is no `unsafe` and no memory-safety surface.

- **Package signature trust IS real (the load-bearing positive finding).** `from_trusted_sealed_artifact` (`lib.rs:480`) → `SealedArtifact::verify_trusted_signature` → `ArtifactSignatureVerifier::verify` (`hawk2ui-build/src/artifact.rs:157`) performs genuine Ed25519: it enforces `RequireVerifiedSignature` policy, checks the algorithm is `ed25519-sha256-v1`, finds a **trusted key by `key_id`** in the keyring (rejecting untrusted keys), decodes the hex public key and signature, builds a `VerifyingKey`, and calls `verifying_key.verify(&artifact.signature_payload_bytes(), &signature)` over a **domain-separated** payload (magic prefix + stable payload-without-signature). `Verified` is emitted only on cryptographic success. This is real identity/signature validation, not structure assertion — **say so explicitly.** The metadata-only `from_sealed_artifact` correctly downgrades to `Missing`/`Invalid` and never forges `Verified`. *Caveat:* `hawk2ui-build/src/artifact.rs` is **modified in the working tree** (uncommitted per the provided git status), so this trace was read at working-tree state, not at the stamped `5a042c51`; given Codex is mid-flight on exactly these files, re-confirm `ArtifactSignatureVerifier::verify` against HEAD before relying on it.
- **…but `validate()` checks a forgeable claim, not the established fact** (gap #4, `lib.rs:561`). Because `PackageTrustRecord.signature_status` is a public field and `Verified` is a freely-constructible variant, `PackageTrustValidator::validate` only verifies that *someone asserted* `Verified`. The crypto guarantee lives entirely in *which constructor was used*, and the type system does not force that choice. A direct struct literal (as the happy-path test does) bypasses crypto. The trust boundary is sound **only if every producer is disciplined enough to use `from_trusted_sealed_artifact`** — an un-enforced convention. → Gate `Verified` behind the verifying constructor. **Medium.**
- **The threat registry has gone stale, by construction** (gap #1). `required_test` is the registry's mechanism for guaranteeing every documented threat is backed by an enforcing test, but it is validated for non-emptiness only and **3 of 8 references already point at non-existent tests** (`source_asset_fixtures_reject_unsupported_style`, `capability_rejections_cover_plugin_metadata`, `runtime_authority_denies_undeclared_host_api` — zero workspace matches). This is exactly the "documented threat with no enforcing check" risk, and it is *realized*, not theoretical: a reader of `threat-model.toml` would believe `malicious-source`, `malicious-plugin-host-data`, and `untrusted-user-data` are test-covered when their named tests do not exist. **High.**
- **`redact_diagnostic` is the enforcing mitigation for a Critical threat and is inert** (gap #3, `lib.rs:398`). It is the named control for `secret-exposure` ("redact diagnostic output"), but it redacts one prefix (`sk_`) and one literal eval string. A real diagnostic carrying `pk_live_…`, `AKIA…`, `ghp_…`, a `Bearer` token, a quoted `"sk_…"`, or any eval payload other than the exact literal **leaks verbatim**. Substring/whitespace matching with no awareness of quoting or token shape is fragile in the same way a denylist is — easy to evade, here trivially so since it is written to its own test. → Replace with structured redaction (regex/entropy over known secret formats; reject rather than substring-rewrite executable payloads). The real-world leak is currently **latent** because nothing consumes this crate (gap #2): the weak redactor is also unwired, so it cannot leak until something routes diagnostics through it — but it must be fixed *before* that wiring lands, not after. **High.**
- **Deserialize of registry input is structurally lax but low-risk** (`Raw*` structs lack `deny_unknown_fields`, `lib.rs:63`/`172`/`290`). The TOML registries are trusted, in-repo, and loaded via `include_str!`, so this is not an untrusted-input attack surface today. The hardening gap is that unknown/misspelled keys are silently ignored (a typo'd `required_test` becomes an empty-string field caught only by non-emptiness), and the validators check only presence/uniqueness/format — never that referenced `fixture`/`path`/`required_test` targets exist. Advisory, not enforced. **Low.**
- **Capability rejection registry validates symmetry, not authority** (`CapabilityRejections::validate`, `lib.rs:205`). The strongest check here is `has_allow_and_deny` requiring every capability to have both an allow and a deny case — a useful fixture-completeness invariant. But it validates only that *fixtures exist for both verdicts*; it does not evaluate any policy, parse any fixture, or deny anything at runtime. It is a coverage matrix over declared cases, not an enforcement mechanism — fine as a contract registry, but not "source validation" in the parsing/sanitizing sense. Pair with gap #2 (nothing consumes it).
- **Good:** the Ed25519 path (above); the package-hash format check `is_supported_hash` (`lib.rs:632`) is real (requires `sha256:`/`blake3:` prefix + exactly 64 ASCII-hex chars, rejecting `md5:`, wrong-length, and non-hex — exercised by `package_trust_rejects_malformed_hashes`); duplicate-ID detection across all three registries is real; the trust validator fails closed on every missing/empty/invalid field and on `Missing`/`Invalid` signature status.
