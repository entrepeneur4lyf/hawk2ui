# Code Review — hawk2ui-render-skia

**Reviewed at:** `5a042c51` · 2026-05-28 · **Remediated (contained subset):** 2026-05-29
**Scope:** `src/lib.rs` + `tests/skia_backend.rs` (1 src file ~2418 LoC / 1 test file ~740 LoC) + `Cargo.toml`
**Purpose:** Concrete Skia (`skia-safe` 0.97, CPU raster) implementation of the `RendererBackend` trait from `hawk2ui-render` — surface lifecycle, real rasterization (fills, strokes, paths, rounded rects, gradients, shadows/glows, text, image/vector assets, opacity groups, layer caching), runtime-scene replay, custom audio-meter surfaces, and a CPU-readable `0x00RRGGBB` frame snapshot.
**Note:** Findings reflect the SHA above. The contained security finding (#4, unbounded surface allocation) was **remediated** 2026-05-29 — see the Remediation section. The effects-pipeline items (#1/#5) are **bucket-(c)** (a design decision spanning style→runtime→render), and the vector-color (#2) / text-reshaping (#3) fidelity gaps are deferred as scoped work.

## Summary

This crate is a **genuine `skia-safe` rasterizer, not a recording/intent backend.** Every draw path issues real Skia `Canvas` calls against an allocated `surfaces::raster_n32_premul` surface: `draw_rect`/`draw_round_rect`/`draw_path`/`draw_line` (fills, strokes, rounded rects, vector paths, custom surfaces), `draw_str` (text), `draw_image_rect`/`draw_image` (images and cached layers), `gradient::shaders::linear_gradient` (real shader), `MaskFilter::blur` (real shadow/glow blur), `save_layer_alpha_f`/`restore` (real opacity compositing), `image_snapshot_with_bounds` (layer cache capture), and `read_pixels` (frame readback into the `0x00RRGGBB` snapshot other crates depend on). The `commands: Vec<String>` log coexists with these real draws as an audit/conformance trail — it is **not** inert recording. Tests assert genuine pixel changes via `frame_snapshot`/`pixel_at`, and the opacity test verifies an actual blended red value (`120..=136`), confirming real compositing. No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME markers. GPU is honestly declared `Unsupported` (a scoped capability, not a stub-panic). Input validation is thorough (finite/range checks on geometry, blur, opacity, DPI, transform, text placement; integer-overflow guards on surface and snapshot sizing). The effect-string parser is fully bounds-checked and non-panicking.

The substantive weaknesses are about **integration wiring and fidelity, not stubbing**: (1) `apply_layer_effect` — the trait's only effect channel and the very surface the brief flagged — has **no production caller** and parses a positional string grammar (`shadow-rect`/`glow-rect`) that **does not match** the grammar the framework's `export_paint_commands` actually emits (`draw-shadow`/`draw-glow`/`draw-gradient`), so shadow/glow/gradient/rounded-rect are reachable only by direct API or hand-written test strings; (2) compiled-vector rendering is **lossy** — usvg-lowered SVG is reduced to `<path>` `d=` strings filled **opaque white**, discarding all fill/stroke/gradient color and every non-path element; (3) `render_text_layout` **re-shapes** each line through a Skia system-font lookup rather than replaying the glyph runs `hawk2ui-text`/parley already measured, so measured metrics and rendered glyphs can diverge; (4) the parity test compares only the curated command log (RecordingBackend draws no pixels), and the effect tests are self-referential. No correctness blocker on the desktop happy path; the gaps are in effect integration, vector color fidelity, and measure/render shaper agreement.

## Remediation (2026-05-29) — contained subset

Fixed the one contained, decision-independent security finding; the rest are either the effects-pipeline design decision (bucket-(c)) or meatier fidelity work, recorded honestly.

- **#4 — unbounded surface allocation (FIXED, Medium / memory-exhaustion).** `create_raster_surface` — the single allocation primitive behind both `create_surface*` and `resize_surface` — now rejects any **physical (DPI-scaled)** dimension above `MAX_SURFACE_DIMENSION` (16384, covers an 8K display at 2x) with `skia.surface.too-large`, **before** `surfaces::raster_n32_premul`. Capping the surface transitively bounds `capture_frame_snapshot`'s ~2x readback. Enforced on the **scaled** dimension (not just logical) because `validate_dpi_scale` has no upper bound, so a modest logical size at a large DPI was equally unbounded. Test: `skia_backend_rejects_oversized_surface_allocation` (oversized create + over-cap DPI-scaled resize both rejected; an in-bounds surface still allocates) — failed before (oversized create returned `Ok`), passes after.

**Surfaced / deferred (NOT fixed — not contained):**
- **#1 + #5 — the effects pipeline (bucket-(c)).** `apply_layer_effect` has no production caller and parses a grammar (`shadow-rect`/`glow-rect`) that `export_paint_commands` never emits (`draw-shadow`/`draw-glow`/`draw-gradient`); the wired scene path (`RuntimeVisual`) can't express shadow/glow/gradient/rounded-rect at all. Routing paint commands into the backend / extending `RuntimeVisual` is a design decision spanning style→runtime→render (the same effects-pipeline item flagged in the `style` and `render` reviews) — surfaced for decision, not unilaterally wired.
- **#2 — vector color fidelity (Medium, deferred).** Compiled vectors render opaque white (the ad-hoc SVG scan drops usvg fill/stroke). The clean fix carries structured path records across the asset boundary (or parses fill/stroke from the lowered SVG) — a fidelity feature, scoped separately.
- **#3 — text re-shaping (Medium, deferred).** `render_text_layout` re-shapes via a system-font lookup rather than replaying parley's measured glyph runs; the fix is glyph-run replay (a real fidelity change in render-skia + the text boundary).
- **Low items unchanged:** #6 self-referential effect/parity tests (tied to #1), #7 `apply_layer_effect` log pop/re-push coupling, #8 trait-level white `stroke`/`draw_path` + opacity-group depth not asserted zero at `end_frame`, #9 audit-`Vec` growth + no `*_workspace_filter_marker` test.

## Completeness & implementation gaps

1. **`apply_layer_effect` is wired to nothing in production and parses a grammar the framework never emits** (`lib.rs:1762` `apply_layer_effect`, `lib.rs:2063` `parse_layer_effect`). The trait method (`hawk2ui-render/backend.rs:224`) is the out-of-band channel for gradient/shadow/glow that the sibling `hawk2ui-render` review flagged. This backend's parser accepts exactly two shapes: `shadow-rect:x,y,w,h:dx,dy:blur:r,g,b,a` and `glow-rect:x,y,w,h:blur:r,g,b,a`; anything else → `skia.effect.unsupported`. But the framework's paint-command exporter (`hawk2ui-render/export.rs:155` `command_key`) emits an entirely **different** vocabulary — `draw-shadow:{key}:{blur}`, `draw-glow:{key}:{radius}`, `draw-gradient:{key}:linear`, `draw-fill:…`, `draw-rounded-rect:…`. **No code anywhere in the workspace bridges `export_paint_commands`/`PaintCommand` to `apply_layer_effect`** (verified: the only callers of `apply_layer_effect` are this crate's test and `hawk2ui-render`'s own test). Consequences: (a) the parser will reject every string the real exporter produces; (b) **gradient and rounded-rect have no representation in the effect grammar at all** even though `draw_linear_gradient`/`draw_rounded_rect` exist as methods; (c) the rich effect surface is dead relative to the framework — exercised only by synthetic strings hand-written to fit the parser. This is the "records intent / not actually wired" pattern sitting on the exact surface the brief asked to verify: the parsing itself is sound, but it parses a format nothing feeds it.
2. **The wired scene path cannot express shadow/glow/gradient/rounded-rect at all.** The runtime path that *is* connected — `draw_runtime_scene_frame` → `draw_runtime_command` (`lib.rs:1312`) — switches over `RuntimeDrawCommand`, whose source `RuntimeVisual` (`hawk2ui-runtime/view.rs:165`) has only `None`/`Fill`/`Text`/`ImageAsset`/`VectorAsset`/`CustomSurface`. So in the integrated rendering path, none of the shadow/glow/gradient/rounded-rect/opacity-group machinery is ever invoked. Those methods are real and correct, but currently reachable only through direct public-API calls, not through scene replay or paint-command export. → Either route paint commands into the backend or document these as direct-call-only primitives.
3. **Compiled-vector rendering discards all color and non-path geometry** (`lib.rs:1885` `extract_svg_path_data` → `lib.rs:739` `register_vector_paths`). `register_compiled_asset` for `Vector` runs a naive `svg.split("<path")` + substring `d="…"` extractor, then `register_vector_paths` fills **every** path with hardcoded opaque white (`Color::rgba(255,255,255,255)`). usvg's `Tree::to_string` (the assets crate's lowered output, `hawk2ui-assets/lib.rs:603`) emits `fill=`/`stroke=`/gradient paint on each `<path>` and may emit `<image>`/`<text>`/nested groups — **all of it is dropped**. A multicolor logo renders as a white silhouette. The extractor is also fragile: it keys on the literal substring `<path` and a quoted `d=` attribute, so namespaced/space-variant serializations or `d` appearing after other attributes with unusual quoting can mis-extract. → Parse fill/stroke from the lowered SVG (or carry structured path records across the asset boundary) instead of forcing white.
4. **`render_text_layout` re-shapes already-shaped text through a system-font lookup** (`lib.rs:1491`). It receives a `TextLayout` that `hawk2ui-text`/parley already shaped (bidi, clusters, line breaking), then for each line calls Skia `draw_str(line.text(), …)` using `FontMgr::legacy_make_typeface(Some(layout.resolved_family()), normal)` — a system font resolved **by family name**, which may not be the face the text stack measured with, at a font size reconstructed as `font_size_from_layout = baseline_px()/0.8` (a magic constant, `lib.rs:2014`). Only per-line text + baseline survive; per-cluster advances, bidi runs, and font-fallback selections are thrown away and re-derived by Skia's own shaper. This is not "fake widths," but it is a **measure/render shaper divergence**: the renderer can lay glyphs differently from what layout measured, producing overflow or misalignment, and silently loses bidi/shaping fidelity that the upstream pipeline computed. (`draw_text_at`/`draw_text`/`render_text_at` similarly always use the single `default_typeface` and ignore family entirely.)
5. **`stroke` and `draw_path` ignore the requested color; `stroke` ignores everything but width** (`lib.rs:1647` `stroke`, `lib.rs:1664` `draw_path`). Both hardcode opaque white. `stroke` takes a `Stroke` (width only in this trait) and `draw_path` takes only a path string, so there is no color parameter to honor — but the effect is that trait-level strokes/paths are always white regardless of scene intent, with color expressible only through the higher-level `draw_filled_path`. Consistent with the trait signature; worth noting as a fidelity limit.

## Code quality & smells

- **Command-log massaging in `apply_layer_effect`** (`lib.rs:1774`, `1784`). After delegating to `draw_shadow_rect`/`draw_glow_rect` (which push their own `shadow-rect:`/`glow-rect:` command), it does `self.commands.pop()` then pushes `effect:{effect}` to mirror `RecordingBackend`'s log. The pop assumes the delegate pushed exactly one trailing command and that no diagnostic-only early-return path leaves the stack in a different shape — latently fragile coupling between two methods' logging.
- **`extract_svg_path_data` / `extract_svg_attribute` are an ad-hoc SVG scanner** (`lib.rs:1885`–`1905`). Substring `split("<path")` with manual quote handling re-implements a sliver of XML parsing where the crate already depends (transitively) on usvg via assets; brittle and color-blind (see gap #3).
- **`require_surface` vs `surface_mut` duplicate the missing-surface check** with slightly different diagnostic messages ("surface does not exist" in both, but `require_surface` routes through `fail` while `surface_mut` inlines the push). Minor redundancy across the lifecycle helpers (`lib.rs:1410`, `1418`, `1444`).
- **Opacity-group depth is backend-global and not frame-scoped** (`lib.rs:497` `opacity_group_depth`, `end_frame` `lib.rs:1589`). `end_frame` does not assert the depth is zero, so an unbalanced `begin_opacity_group` without `end_opacity_group` leaks a live `save_layer` across the frame boundary (and into the next frame's surface state). Reachable only via the explicit API (scene replay never opens groups, per gap #2), so low impact today.
- **Per-draw `image_assets.get(...).cloned()` / `vector_assets.get(...).cloned()`** (`lib.rs:843`, `1160`, `1192`, `1702`). `skia_safe::Image` clone is a refcount bump (cheap) but `SkiaVectorAsset` clone deep-copies the `Vec<SkiaVectorPathRecord>` (each holds a `Path`) on every `draw_vector`/`draw_vector_rect` to satisfy the borrow checker against `with_active_surface`. A hot path for vector-heavy frames.
- **`SkiaCapabilitySupport`/`SkiaRendererCapabilities` is a large parallel capability struct** that largely mirrors `BackendCapabilities`; only `cpu_raster`/`gpu`/`paths`/`clips`/`effects`/`dirty_regions` add detail beyond the trait-level caps. Reasonable, but the two capability surfaces must be kept in sync by hand.

## Documentation

- Strong: crate-level `//!`, every public type/method documented, and `# Errors` sections on all fallible public fns (surface lifecycle, draws, cache ops, text, runtime replay, custom surface). No undocumented public items found.
- Misleading relative to the gaps: `register_compiled_asset`/`register_vector_paths` docs do not mention that vector color is discarded and fills are forced white (gap #3). `draw_text_layout`'s doc ("draws a shaped text layout") does not disclose that the layout is **re-shaped** by Skia rather than glyph-run-replayed (gap #4). The `apply_layer_effect` doc inherits the trait's generic contract and gives no hint that only two positional grammars are accepted or that the grammar differs from the exporter's (gap #1).

## Testing

- Genuinely good for a renderer: tests read back real pixels via `frame_snapshot`/`pixel_at`/`count_changed_pixels` and assert visible changes for fills, transforms (affine), placed text, images, vectors, gradient (start≠end pixel), shadow, glow, rounded rect, custom meter surface, layer-cache replay-then-invalidate, and opacity blending (the `120..=136` red check is a real composite assertion). Lifecycle/error coverage is solid (`skia.frame.missing`, `skia.surface.duplicate`, `skia.surface.invalid-size`, `skia.geometry.invalid`, `skia.transform.invalid`, `skia.frame.active`, `skia.cache.invalid`). This crate is materially better tested than the a11y/assets siblings.
- **False-confidence: the RecordingBackend parity test compares only the command log, never pixels** (`skia_backend_matches_recording_backend_for_core_frame_commands`). `RecordingBackend` (`hawk2ui-render/backend.rs:266`) issues no Skia/canvas calls — it only records strings — so the assertion `skia.command_keys()[1..] == recording.command_keys()` proves the two backends agree on their *audit log*, not that Skia rendered anything matching the intended scene. The `[1..]` slice silently drops Skia's extra leading `register-image:hero` command, a brittle index coupling.
- **False-confidence: the effect tests are self-referential** (`apply_layer_effect_executes_supported_structured_effects`). They hand-write strings in exactly the `shadow-rect:`/`glow-rect:` grammar the parser expects and assert pixels change. Because no production component emits that grammar (gap #1), the test validates the parser against itself, not against the framework's real `export_paint_commands` output — so the integration break in gap #1 is invisible to the suite.
- Coverage gaps: no test feeds the exporter's actual `draw-shadow`/`draw-gradient` strings to `apply_layer_effect` (would expose gap #1); no test asserts vector **color** is preserved (would expose gap #3); no test compares `draw_text_layout` glyph placement against the measured `TextLayout` metrics (would expose gap #4); no test for `skia.effect.unsupported`, `skia.vector.invalid-utf8`, `skia.image.decode-failed`, surface/snapshot overflow guards, or unbalanced-opacity-across-frame.

## Security

The trust boundary here is **draw parameters and asset bytes flowing into Skia**, plus the `apply_layer_effect` string. `#![forbid(unsafe_code)]` holds; there is no `unsafe`, and no public type derives `Deserialize` (no serde attack surface in this crate, unlike a11y).

- **Unbounded surface allocation → memory exhaustion (Medium).** `validate_surface_size` (`lib.rs:1907`) and `validate_dpi_scale` only reject zero / non-finite / non-positive — there is **no upper bound** on width/height. `create_surface`/`resize_surface`/`create_surface_with_config` therefore allocate a raster surface sized by attacker-/caller-influenced dimensions (bounded only by `i32::try_from` and Skia's own allocator returning `None`). A large but i32-valid request (e.g. 30000×30000 at high DPI) allocates hundreds of MB of N32 pixels; `capture_frame_snapshot` (`lib.rs:2225`) then allocates **~2× more** transiently — a `vec![0u8; byte_len]` readback buffer *plus* a `Vec<u32>` of the same pixel count. Integer overflow itself is correctly guarded (`i32::try_from`, `checked_mul`, the `pixel-count-overflow`/`byte-count-overflow`/`size-overflow` rules), so this is exhaustion, not unsafety. Parallels the assets decode-bomb. → Enforce a max surface dimension/pixel budget derived from a limits struct before allocation.
- **`apply_layer_effect` parser: fragile-by-coupling but not a panic/DoS surface (Low).** The positional, colon/comma-delimited grammar is an untyped string contract (the design smell called out in gap #1), but `parse_layer_effect` and its helpers are **fully bounds-checked and non-panicking**: `parse_f32_list` verifies exact length before any `values[i]` index, `parse_color` checks `len()==4`, `parse_u8`/`parse_f32` return `Result`, and the top-level `match fields.as_slice()` falls through to a clean `skia.effect.unsupported` error. Malformed/oversized/hostile strings yield errors, not panics or unbounded work. This is a correctly-hardened parser of a poorly-typed protocol — credit the hardening; the defect is the protocol's existence and its mismatch with the exporter, not memory safety.
- **NaN/Inf geometry and colors are rejected at the boundary (good).** `validate_geometry` (finite + positive dims), `validate_blur`, `validate_opacity` (0..=1), `validate_transform`, `validate_text_placement`, and `validate_dpi_scale` all reject non-finite input before it reaches Skia, closing the obvious NaN-into-rasterizer vectors. Color channels are `u8`, so no out-of-range color.
- **Asset decode delegates to Skia/`image` (bounded by upstream).** `register_image_asset` feeds bytes to `Image::from_encoded` then falls back to `image::load_from_memory` (`decode_raster_image`, `lib.rs:2211`). Decode-bomb resistance is inherited from those libraries and from the assets crate's pre-sanitization; this crate adds `i32::try_from` dimension guards but no pixel cap of its own. Lower priority than the assets-crate decode path since registration is normally fed already-sanitized `compiled_bytes`.
- **No unbounded recursion.** Unlike a11y/assets there is no self-recursive traversal here; the SVG extractor and runtime-command loop are flat iterations.
- **Minor unbounded growth:** `commands`, `diagnostics`, `dirty_regions`, and `cache_invalidation_keys` `Vec`s grow for the backend's lifetime with no drain (audit logs). `surfaces`/`image_assets`/`vector_assets`/`layer_caches` `BTreeMap`s grow with distinct IDs. Slow memory growth on a long-lived backend; parallels a11y's `events` and assets' `manifest`. **Low.**
