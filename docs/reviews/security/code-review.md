# Code Review — hawk2ui-security

**Reviewed at:** `5a042c51` · 2026-05-28 · working tree clean at review time
**Scope:** `src/lib.rs`, `src/source.rs`, `src/sandbox.rs`, `src/assets.rs`, `src/secrets.rs`, `src/trust.rs`, `src/diagnostic.rs` + `tests/security_policy.rs` (7 src files ~690 LoC / 1 test file ~250 LoC)
**Purpose:** *Intended* to provide the security policy, build-time source validation, script-sandbox policy, asset policy, secret redaction, and trust-boundary classification for Hawk2UI. **As implemented, the crate is a library of diagnostic/record constructors: it names security decisions and formats their diagnostics, but performs no validation, scanning, parsing, hashing, or interception of its own.**
**Note (READ FIRST):** Codex is **actively committing security/hardening work and this crate is a prime target right now** (git HEAD is `5fecf2c4`, ahead of the reviewed `5a042c51`). The headline finding below — that this crate has **zero production consumers** — is exactly the kind of gap concurrent work may be closing as you read this (Codex may be wiring these policies into `hawk2ui-build`/`hawk2ui-script`). **Several findings may already be addressed or in-progress.** Re-verify every "unwired"/"record-only" claim against current HEAD before acting.

## Summary

This crate is **not stubbed and contains no broken code** — there is no `todo!`/`unimplemented!`/`unreachable!`, no placeholder panic, no TODO/FIXME/HACK marker, and every public constructor is complete and correct for what it does. The defect is **architectural, not unfinished**: each "policy" type (`SourceValidationPolicy`, `ScriptSandboxPolicy`, `AssetSecurityPolicy`) is a zero-sized unit struct whose only methods (`reject`, `deny`, `image_record`, `vector_record`) **package a decision the caller already supplies** into a `SecurityDiagnostic` and a record struct. None of them inspects source text, parses a manifest, intercepts a script operation, decodes or hashes an asset, or scans for secrets. The values they "verify" — `AssetHashVerification::Verified { hash }`, `AssetSecurityRule::Oversized { actual_bytes, max_bytes }`, `VectorSafetyStatus::Safe` — are caller-asserted; the crate compares nothing.

The decisive finding is that **no crate in the workspace depends on `hawk2ui-security` and nothing imports it.** A workspace-wide search for `use hawk2ui_security` returns exactly one hit: this crate's own `tests/security_policy.rs`. `hawk2ui-security-model` — the one crate whose name made it look like a consumer — depends on `hawk2ui-api` and `hawk2ui-build`, **not** on `hawk2ui-security` (confirmed in its `Cargo.toml`), and imports none of its symbols. The only `hawk2ui-security =` reference anywhere is the crate's own `name =` line. So every policy here is **unwired**: it cannot enforce anything because nothing calls it.

The real enforcement the crate's name and docs imply lives **in other crates that do not reference this one**: build-time source/manifest validation and path-traversal defense are in `hawk2ui-build` (`manifest.rs::validate`, `workspace.rs:196 validate_workspace_relative_path`); real asset decode/sanitize/SHA-256 is in `hawk2ui-build/src/assets.rs` (see the `hawk2ui-assets` review); the script sandbox over the boa engine is in `hawk2ui-script` (`HostCallPolicy::deny_all()`); capability-scoped secret handles are in `hawk2ui-platform` (`PlatformSecretHandle`). This crate therefore **does not close** the gaps the sibling reviews found (the `hawk2ui-script` "no execution limits / unreachable `HostCallPolicy`" gap, the `hawk2ui-assets` "SVG denylist + font trust" gap) — it only provides a vocabulary that *names* some of them (`script.string-to-code.denied`, `asset.vector.unsafe`) without participating in their enforcement. The substantive risk is **false assurance and dead code on a security-critical surface**, not an exploitable runtime bypass (because no runtime path depends on it).

## Completeness & implementation gaps

1. **The entire crate is unwired — zero consumers** (`lib.rs` public surface). `grep "use hawk2ui_security"` across the workspace matches only `tests/security_policy.rs`. No production crate constructs a `SourceValidationRecord`, `ScriptSandboxDenial`, `AssetSecurityRejection`, `SecretVerificationReport`, or `TrustRecord`. For a crate described as "the security policy … for Hawk2UI," this is the headline gap: the policies exist but are not on any enforcement path. This is the "records intent, does no real work" pattern at crate scale — and worse than the assets crate's `cache_generation`, because there nothing computes the verdict *and* nothing consumes it. → Either wire these into `hawk2ui-build`/`hawk2ui-script` as the authoritative diagnostic vocabulary, or fold the types into the crates that actually enforce. **(Verify against HEAD — Codex may be wiring this now.)**
2. **Source validation performs no validation** (`source.rs:69` `SourceValidationPolicy::reject`). The only entry point takes a `SourceValidationRule` *the caller already chose* plus a path and returns a record. There is no parser, no syntax check, no manifest read, no asset-existence probe — the eight `SourceValidationRule` variants (`UnsupportedScriptSyntax`, `UnsafeVectorContent`, `MissingAsset`, `MalformedManifest`, …) are a label enum, not a decision procedure. The real equivalents live in `hawk2ui-build` (`manifest.rs:229 validate`, `manifest.rs:347 validate_manifest_schema`, `workspace.rs:196`) and emit `ManifestError`/`BuildWorkspaceError`, never this crate's rules. So `SourceValidationRule` is a parallel, never-emitted vocabulary.
3. **Script sandbox performs no sandboxing** (`sandbox.rs:73` `ScriptSandboxPolicy::deny`). Same shape: caller passes the `ScriptSandboxOperation` it has already decided to deny; the method formats a denial. Nothing here observes a script, intercepts `eval`, gates a host call, or talks to the boa engine. The actual sandbox is `hawk2ui-script`'s `ScriptBackend::new(HostCallPolicy::deny_all(), …)` (used in `hawk2ui-cli/src/executor.rs:1336` and the script tests) — which does not import this crate. The sibling `hawk2ui-script` review found that crate has *no execution limits* and a Rust-side `HostCallPolicy` unreachable from JS; **this crate does nothing to address that** — `ScriptSandboxOperation::StringToCode` is a diagnostic label, not an `eval` interceptor.
4. **Asset hash "verification" computes no hash; size "limit" compares nothing** (`assets.rs:40` `AssetHashVerification`, `assets.rs:63` `AssetSecurityRule`). `AssetHashVerification::verified(hash)` wraps a caller string; `Mismatch { expected, actual }` and `Oversized { actual_bytes, max_bytes }` carry caller-supplied numbers. There is no `Sha256`, no byte comparison, no length check anywhere in the crate (contrast `hawk2ui-build/src/assets.rs`, which performs a real SHA-256 and real size/pixel checks). `AssetSecurityPolicy::image_record`/`vector_record` simply stamp an `AssetImageMetadataStatus`/`VectorSafetyStatus` the caller passes in — `VectorSafetyStatus::Safe` is an assertion the crate never tests. These "gates" record verdicts reached elsewhere (or nowhere).
5. **Secret scanning is not implemented; redaction is real but narrow** (`secrets.rs`). `SecretScanFinding`/`ShippedArtifactSecretCheck`/`SecretVerificationReport` are containers you hand pre-found findings to (`with_source_scan`, `with_artifact_check`); nothing in the crate scans a source tree or an artifact for secrets. `SecretValue::is_absent_from` (`secrets.rs:30`) *is* real logic — `!text.contains(&self.value)` — but it only detects a **verbatim** substring: an encoded, split, partially-printed, or transformed secret passes as "absent," and an empty `value` makes `is_absent_from` always return `false` (over-reporting). The `Debug` redaction (`secrets.rs:35`) is correct and genuinely prevents accidental `{:?}` leakage.

## Code quality & smells

- **`SecretValue` stores plaintext, derives `Clone`, and never scrubs memory** (`secrets.rs:6`). For a type whose whole purpose is secret hygiene, this is the notable smell: the raw value lives in a `String`, `#[derive(Clone)]` lets copies proliferate freely, and there is no `Zeroize`/`Drop` wipe — the plaintext lingers in the allocator after drop. The `Debug` guard prevents *formatting* leaks but not in-memory exposure. → Wrap in a zeroizing type or at minimum drop `Clone` and scrub on `Drop`.
- **`SecretValue`/`is_absent_from` is duplicated by `hawk2ui-platform::PlatformSecretHandle`** (`secrets.rs:24`-`33` vs `crates/hawk2ui-platform/src/secrets.rs:38`-`47`). Two crates carry byte-identical `redacted()` (`format!("[REDACTED:{}]", …)`) and `is_absent_from` (`!text.contains(&self.value)`) implementations, with the same plaintext-`String` + `Debug`-tuple-redaction pattern — and **neither crate depends on the other**. This is divergent duplication of a security primitive with no single source of truth; given that `hawk2ui-platform`'s handle is reachable from the platform secret API and this one is reachable from nothing, this crate's `SecretValue` reads as the **dead twin**.
- **Diagnostic-label string assembly is repeated five times** (`source.rs:58`, `sandbox.rs:62`, `assets.rs:121`, `trust.rs:80`, plus the `serialize_text` builder in `secrets.rs:155`). Each `diagnostic_label` is a bespoke `format!` with a different prefix (`source.`, `sandbox.`, `asset.`, `trust.`). Minor, but a shared helper or trait would prevent prefix/format drift across a stable-diagnostic surface.
- **`AssetHashVerification::Mismatch` and `AssetSecurityRule::HashMismatch` are redundant** (`assets.rs:31`, `assets.rs:79`). Two near-identical `{ expected, actual }` shapes for the same concept (one as an accepted-record status, one as a rejection rule). The accepted-record `Mismatch` variant is curious: a record of *acceptance* that can encode a hash *mismatch* is contradictory and has no consumer to resolve the ambiguity.
- **`#[must_use]` on builders that are also commonly chained-and-dropped** (`secrets.rs:134`/`141`/`148` `with_*`). Correct convention, no issue — noted only to confirm it is applied consistently.

## Documentation

- Strong surface docs: crate-level `//!`, and **every** public type, variant, field, and method carries a doc comment. No undocumented public items.
- **The docs overstate capability and there are no `# Errors` sections — because nothing is fallible.** No method in this crate returns `Result`, so the absence of `# Errors` is *correct*. But the crate-level `//!` ("source validation, script sandbox, asset policy") and method docs ("Produces a rejection record", "Produces a denial record") read as though the crate *decides* rejections/denials, when it only *formats* decisions handed to it. A reader would reasonably assume `SourceValidationPolicy` validates source and `ScriptSandboxPolicy` sandboxes scripts; neither does. This is misleading-by-omission on a security-critical crate — the docs should state that these types are a diagnostic vocabulary, and that enforcement lives in `hawk2ui-build`/`hawk2ui-script`/`hawk2ui-platform`.
- `is_absent_from`'s doc ("Returns true when text does not contain the raw secret value") is literally accurate but omits its verbatim-substring limitation and the empty-value edge case (gap #5).

## Testing

- Breadth looks reassuring — eight trust boundaries, eight source rules, six sandbox operations, four asset rejections, secret redaction — but the suite tests **only record/diagnostic formatting**, never enforcement.
- **False-confidence test names (the central testing risk).** `source_validation_rejects_all_build_time_security_rules` (`security_policy.rs:51`) and `script_sandbox_denies_all_direct_privileged_operations` (`security_policy.rs:108`) read as enforcement suites — "rejects all rules", "denies all operations" — but each loop asserts only that `reject(rule, path)`/`deny(op, subject)` copies the rule into `.diagnostic.rule`, sets the message, and produces the expected `diagnostic_label` string. **Nothing is validated and nothing is denied** — the input *is* the rule under test. A `SourceValidationRule::UnsafeVectorContent` is never derived from an actual unsafe vector; it is handed in. These tests give a security reviewer false assurance that "all build-time rules are enforced" / "all privileged operations are denied," when they verify string templating over a fixed vocabulary. The names should not contain "rejects"/"denies".
- **`asset_security_records_image_vector_and_hash_status`** (`security_policy.rs:155`) asserts `VectorSafetyStatus::Safe` and `AssetHashVerification::verified("hash-a")` round-trip into the record — i.e. it asserts the crate stores the safety verdict and hash the test itself supplied. No safety check, no hash computation is exercised (none exists).
- **`secret_redaction_hides_values_…`** (`security_policy.rs:229`) is the one genuinely valuable test: it confirms `{:?}` and `serialize_text()` never emit the raw value and always emit `[REDACTED:…]`. This tests real behavior. It does **not** cover `is_absent_from` at all (no assertion on it), nor the empty-value or encoded-secret edge cases.
- Coverage gaps that matter only if these types ever become load-bearing: no test distinguishes a real unsafe vector from a safe one, a real oversize from within-limit, a real hash match from mismatch — because the crate cannot make those distinctions.

## Security

The crate's stated job is to be Hawk2UI's security policy layer. The threat-by-threat assessment below evaluates **whether each policy actually enforces its stated defense.** The recurring answer is *no — the policy is unwired and record-only* — which on a security-critical crate is itself the primary finding. `#![forbid(unsafe_code)]` holds; there is no `unsafe`.

- **No untrusted-deserialization surface (this is fine, stated for completeness).** The task asks specifically about `Deserialize` of untrusted policy input. **There is no `serde`/`Deserialize` anywhere in this crate** (no `serde` dependency in `Cargo.toml`; no derive on any type). So there is no deserialization attack surface here. (Untrusted TOML/JSON deserialization *does* exist — in `hawk2ui-build`'s manifest parsing and `hawk2ui-security-model`'s threat/capability registries — but not in this crate.)

- **Source-validation bypass — N/A here because there is no validator (Threat: malicious/malformed source admitted at build).** `source.rs` does **no parsing and no substring matching** — so the "substring vs real parsing / denylist fragility" critique from the sibling reviews does **not** apply to this crate; there is nothing to bypass because nothing validates. The actual build-time gate is `hawk2ui-build`: `manifest.rs:229 Manifest::validate` (capability shape checks, e.g. `capability.contains(' ')` at `manifest.rs:244`), `manifest.rs:347 validate_manifest_schema` (JSON-Schema validation), and crucially `workspace.rs:196 validate_workspace_relative_path` — which **does** perform real path-traversal defense (rejects absolute paths and `..`/prefix components, then `canonicalize()` + `starts_with(root)` at `workspace.rs:186`-`190`). **That is the authoritative source/path gate, and it is real — but it lives in `hawk2ui-build`, which does not reference this crate.** This crate's `SourceValidationRule` neither participates in nor strengthens it. **Enforcement: real, but elsewhere; this crate: inert.** Risk to *this crate*: false assurance. **High** (because the crate advertises source validation it does not perform).

- **Script-sandbox completeness vs the actual boa engine (Threat: untrusted script escaping the sandbox — `eval`, host APIs, fs/net/process/native).** `ScriptSandboxPolicy::deny` (`sandbox.rs:73`) **never touches the boa engine.** `ScriptSandboxOperation::StringToCode`/`UndeclaredHostApi`/`DirectFilesystem`/… are diagnostic labels; the method formats a denial for an operation the caller already decided to deny. The real sandbox is `hawk2ui-script`'s `ScriptBackend` + `HostCallPolicy::deny_all()` — and the sibling `hawk2ui-script` review found that backend has **no execution/time/memory limits** and a Rust-side `HostCallPolicy` **unreachable from JS**. **This crate does not close either gap** (it does not gate `eval`, cap execution, or wire host-call policy into boa); it only names some of the operations. Treating the presence of `ScriptSandboxOperation::StringToCode` as evidence that string-to-code is blocked would be a dangerous misread. **Enforcement: none here. High** (false assurance on the highest-stakes boundary; would be Critical if any consumer relied on it for protection — none does).

- **Asset-policy enforcement; allowlist/denylist gaps (Threat: oversized/malformed/unsafe-vector/hash-mismatched assets).** `AssetSecurityPolicy` (`assets.rs:127`) records verdicts; it **computes no hash, compares no size, and validates no vector.** There is no allowlist or denylist *in this crate at all* — so the `hawk2ui-assets` SVG-denylist/font-trust gaps are neither present nor closed here. The real asset gate is `hawk2ui-build/src/assets.rs` (real decode, SHA-256, size/pixel limits — see the assets review). This crate's `AssetHashVerification::Verified`/`Oversized` are caller-asserted. **Enforcement: none here. High** (asset *security policy* that enforces no asset security).

- **Advisory-vs-enforced gates — the crux (Threat: a gate that is computed but not applied).** The task flags "computed but not applied = critical." This crate is a step **beyond** advisory: its verdicts are **not even computed** — they are caller-supplied and packaged, and then **consumed by nobody** (zero importers). So the realized severity is not an exploitable bypass of a live gate (nothing live depends on it); it is **dead code + false assurance** on a security-critical surface. I lead this at **High** with that framing. It would be **Critical** *iff* the architecture intends this crate as the enforcement layer and a consumer relies on it — the discriminator "does any runtime path rely on this for protection?" currently answers **no**, which is why it is High, not Critical. **This is the single most important thing to re-verify against current HEAD: if Codex is mid-wiring these policies into `hawk2ui-build`/`hawk2ui-script`, the picture changes materially.**

- **Secret redaction (Threat: secret material leaking into logs/diagnostics/artifacts).** Mixed. **Real:** `Debug` for `SecretValue` (`secrets.rs:35`) emits only `[REDACTED:name]`, so `{:?}` cannot leak the value — genuinely good, and tested. `is_absent_from` (`secrets.rs:30`) is real logic. **Weak:** it is verbatim-substring-only — an encoded/split/partially-rendered secret passes the "absent" check, so as a leak detector it is fragile (same substring-fragility class the task warns about, applied to redaction rather than denylisting); empty `value` makes it always report "present" (false positive). **Hygiene gap:** plaintext `String` + `Clone` + no `Zeroize`/`Drop` scrub (see Code quality) leaves secret copies in memory. The scanning side (`SecretScanFinding`, `ShippedArtifactSecretCheck`) **does no scanning** — it stores findings produced elsewhere. **Enforcement: partial (formatting-leak prevention real; detection narrow; in-memory hygiene absent). Medium.**

- **Panics-as-DoS.** None. No `unwrap`/`expect`/`panic!`/indexing/`todo!`/`unreachable!` on any path; all constructors are infallible and allocate bounded `String`s. `serialize_text` (`secrets.rs:155`) builds an unbounded `String` from the report's vectors, but those vectors are caller-populated and not attacker-streamed within this crate — not a DoS vector here. **No finding.**

- **Trust-boundary records are descriptive only** (`trust.rs`). `TrustBoundary`/`TrustRecord` classify and label (e.g. `trust.secret:api-key@manifest`) but enforce no policy between boundaries (no "UserData must not reach Secret" check). Documentation/telemetry value only; no enforcement claimed in code, though the crate docs imply a "security policy." **Low.**
