## Summary

This is a **policy / decision layer, not the syscall layer** — and reading it correctly hinges on that. Every domain type is a *record* (`NetworkRequestRecord`, `FilesystemAccess`, `AudioPlaybackRequest`, …) describing an *authorized* operation; the privileged op itself (the actual socket connect, `read`/`write`, keychain fetch, SQL execution) is performed by a host that is **not present in this workspace**. The only in-workspace consumer, `hawk2ui-schema`, uses just the schema-generation surface (`CapabilityRecord::json_schema`/`CapabilityTable::json_schema`); nothing here yet wires `FilesystemPolicy::resolve` into real IO or a secret value into a real operation. So the crate's job is to **return the correct decision**, and the security review is (1) are the decisions sound, and (2) where the crate *itself* touches privilege (it probes the real filesystem via `canonicalize`/`exists`), is that done safely.

On that bar the crate is **genuinely implemented, not a stub**: no `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME/HACK markers, no `unwrap`/`expect` in `src/`. `CapabilityTable::ensure_allowed` is a correct deny-by-default gate (requires runtime-availability **and** not-denied **and** explicitly-allowed **and** context-applicable), and **nine of ten** capability-gated domains (`network`, `clipboard`, `ai`, `mcp`, `audio`, `notifications`, `shortcuts`, `localization`, `dialogs`) call `ensure_allowed` **first**, before any allowlist/manifest check — the gate is enforced, not advisory. Network host matching is notably careful (scheme-restricted, exact-set, IDNA-canonicalized on both sides, userinfo/port/fragment rejected). The substantive weaknesses, in defect-confidence order, are: (1) `resolve_scoped_path` has a **silent unchecked fallback** when the grant root can't be canonicalized, dropping the scope-containment guarantee its own `filesystem.path.escape` diagnostic promises — an *observable* in-crate defect; (2) the **secret handle is inert/record-only** — it stores a caller-supplied plaintext value with no accessor and no backing store, so it neither fetches nor releases a secret; (3) the **filesystem domain is the one capability not threaded through the table** — `FilesystemPolicy::resolve` takes a `FilesystemGrant` and *no* `PlatformContext`, which is plausibly a deliberate grant-as-capability model but means a `filesystem.read` capability marked `plugin: false` **cannot** be context-restricted through this crate; the same is true of `database` storage. No correctness blocker on the happy path; the defects are in a path-scope escape-hatch, secret confinement, and capability-model coverage.

## Completeness & implementation gaps

1. **`resolve_scoped_path` silently skips the containment check when the root is not canonicalizable** (`filesystem.rs:200`). If `root.canonicalize()` returns `None` (root does not yet exist, or is inaccessible), the function returns `root.join(relative_path)` verbatim with **no `starts_with` scope check** — the only branch that does enforce containment is the `Some` arm (lines 203–206). `validate_relative_path` has already stripped `..`/absolute/`\`/`:`, so there is no *lexical* escape, but the function's own failure mode (`filesystem.path.escape` → `None`) is documented as "escapes its scope," and on this branch that invariant is simply not evaluated. Any symlink inside an uncanonicalizable root tree is therefore unresolved and unchecked. This is the one *observable* in-crate scope-confinement defect. → Resolve/normalize and apply the containment check on both branches, or reject when the root cannot be canonicalized.
2. **Secret handle is inert/record-only** (`secrets.rs:30`). `PlatformSecretHandle { key, value }` holds the raw secret as a `String`, but there is **no accessor** to read it back: the only uses are `redacted()` (returns `[REDACTED:key]`) and `is_absent_from(text)`. The caller of `read(manifest, key, value)` already supplies `value`, so the handle round-trips a secret the caller already holds and never hands it back. As a confinement primitive this is inert — it neither fetches the secret (no keychain/keyring/env integration) nor releases it. It is a *redaction wrapper*, not a secret store. The crate doc ("secrets … access") oversells it. → Either add a controlled `expose`/`zeroize`-on-drop accessor and a real backing store, or rename to reflect that this only wraps a value the caller owns for redaction. (Plaintext-at-rest/no-zeroize is a secondary, lower concern; see Security.)
3. **Filesystem is the one capability not threaded through the table — context-restriction is inexpressible** (`filesystem.rs`, whole module). `PlatformOperation` declares `FilesystemRead`/`FilesystemWrite` and the tests build `CapabilityRecord::new("filesystem.read").allow(FilesystemRead).plugin(false)` — but **no function in the crate calls `ensure_allowed` for a filesystem operation.** `FilesystemPolicy::resolve`/`resolve_user_selected` take a `FilesystemGrant` and crucially **no `PlatformContext`**. This is plausibly a deliberate *grant-as-capability* model (the grant object *is* the minted permission, as in object-capability systems) — but the concrete consequence is sharp: **a `filesystem.read` capability whose record sets `plugin: false` cannot prevent a plugin from resolving a grant**, because the resolver never sees the context or the table. The `desktop_applicable`/`plugin_applicable`/`runtime_availability` flags are therefore inert for filesystem within this crate; they bind only if a host *also* calls `ensure_allowed` before minting the grant. → **Verify against the host integration contract.** If grants are minted only after a host-side `ensure_allowed`, this is by-design; if grants can be constructed directly (they can — `FilesystemGrant::new`/`user_selected_file` are public and ungated), context confinement is unenforceable here. Document which.
4. **`DatabasePolicy::validate_storage_path` validates path scope but carries no capability/context** (`database.rs:73`). It delegates to `FilesystemPolicy::resolve` (inheriting gap #1 and #3) and maps any failure to `database.storage.unsafe`; `PlatformOperation::DatabaseQuery`/`DatabaseMigration` are never routed through `ensure_allowed`, and `validate_migrations` is pure ordering/ID validation. Same grant-as-capability caveat as filesystem — only structural validation here, no context-aware decision.

## Code quality & smells

- **`is_declared` / `is_stable_id` duplicated verbatim across five modules** (`ai.rs:101`, `mcp.rs:101`, `audio.rs:84`, `notifications.rs:84`, and a near-identical `is_declared_locale`/`is_valid_locale` in `localization.rs:84`, plus `is_valid_migration_id` in `database.rs:88`, `is_valid_secret_key` in `secrets.rs:106`, `is_stable_id`-style accelerator check in `shortcuts.rs:88`). Eight copies of "non-empty ASCII-alnum + `[-_.]`" allowlist validation. Should be one shared `is_stable_id` helper (the locale and accelerator variants differ only in the punctuation set). Divergence risk: a future tightening of one copy silently leaves the others permissive.
- **The per-domain policy structs are near-identical boilerplate** (`AiPolicy`/`McpPolicy`/`AudioPolicy`/`NotificationPolicy`/`ShortcutPolicy`/`LocalizationPolicy`). Each is `ensure_allowed` → `is_declared(allowlist, value)` → build a one/two-field record. Six copies of the same shape with different field names. A small generic ("gate + single-allowlist domain") would remove ~250 LoC and centralize the gate-then-allowlist ordering that is currently re-implemented (and must stay correct) in each.
- **`canonical_or_original` swallows canonicalization failure** (`filesystem.rs:238`). `resolve_user_selected` returns the *original* string when `canonicalize` fails, so the "resolved" path it advertises may be non-canonical (and thus not the path containment was reasoned about). Combined with `same_user_selected_path`'s string-equality fast path (line 230), an exact byte-match grant succeeds without canonicalization at all — a relative or `..`-containing requested path is rejected earlier by `is_valid_scope_root`, but the asymmetry (validate-then-maybe-canonicalize-then-maybe-not) is a smell on a security path.
- **`CapabilityTable::new` last-writer-loses is correct but subtle** (`capability.rs:281`). `or_insert` keeps the *first* declaration for a duplicate `manifest_key` (the test `capability_table_preserves_first_duplicate_declaration` pins this). Reasonable, but undocumented on the public constructor — a caller appending a stricter record expecting it to win gets the looser first one.
- **`PlatformDiagnostic`/`*Denied` types do not bridge to `hawk2ui_api::Diagnostic`** (whole crate). Like `hawk2ui-assets`, this crate defines its own diagnostic type and does not depend on `hawk2ui-api`; there is no `From` into the unified diagnostic stream. (See Cross-cutting.)

## Documentation

- Strong: crate-level `//!`, every public type and method documented, `# Errors` sections on all fallible entry points. No undocumented public items.
- Misleading in two places tied to the gaps: the crate description ("capability-scoped … filesystem … and database access") implies the capability table gates filesystem/database with context, which within this crate it does not (gaps #3/#5); and the `secrets` module presents `PlatformSecretHandle` as secret *access* when it only wraps a caller-supplied value for redaction (gap #2). `FilesystemPolicy::resolve`'s `# Errors` ("when the path escapes scope") is not upheld on the uncanonicalizable-root branch (gap #1).

## Security

This crate is the **capability-confinement boundary**, so each domain's trust boundary and gate placement are stated below. The cross-cutting deserialization surface is real: `capability.rs`'s `PlatformOperation`, `PlatformContext`, `RuntimeAvailability`, `CapabilitySchema`, `CapabilityRecord`, `CapabilityTable`, `PlatformDiagnostic`, and `CapabilityDenied` all derive `Deserialize` (with `#[serde(deny_unknown_fields)]` on the structs) — i.e., **the capability policy itself can be deserialized from untrusted input** (a manifest file, a plugin bundle). The per-domain manifests (`NetworkManifest`, `PlatformSecretManifest`, etc.) do **not** derive `Deserialize`, so the attack surface is the capability table, not the manifests.

- **Capability gate — enforced (good).** `CapabilityTable::ensure_allowed` (`capability.rs:291`) is deny-by-default and checks, in order: existence, plugin-applicability, desktop-applicability, then `runtime_availability == Runtime` **&&** `!denied.contains(op)` **&&** `allowed.contains(op)`. Deny wins over allow; `BuildOnly`/`Unavailable` are refused. For `network`/`clipboard`/`ai`/`mcp`/`audio`/`notifications`/`shortcuts`/`localization`/`dialogs`, `ensure_allowed` is the **first** statement of the policy function, before any manifest/allowlist check — the gate is enforced before the (record-producing) op, **not advisory**. This is correct.
- **Filesystem — uncanonicalizable-root branch drops scope containment (observable defect)** (`filesystem.rs`). Trust boundary: a host-supplied `relative_path` resolved against a `FilesystemGrant`. Path scoping is mostly sound: `validate_relative_path` rejects empty, `\0`, `\`, `:`, absolute, and any `..`/`RootDir`/`Prefix` component; `is_valid_scope_root` requires an absolute, `..`-free root. **But** `resolve_scoped_path` (`filesystem.rs:197`) **drops the containment check on the uncanonicalizable-root branch** (gap #1): when `root.canonicalize()` fails it returns `root.join(path)` unchecked, so symlink resolution and `starts_with` are skipped — lexical escape is blocked upstream by `validate_relative_path`, so this is **Medium**, not High, but the documented `filesystem.path.escape` invariant is genuinely not upheld on that branch. **TOCTOU is inherent to the design:** `resolve` returns a *path string*, then the host opens it later; `canonicalize_existing_prefix` (`filesystem.rs:209`) canonicalizes the existing prefix and re-appends the missing leaf components — but a symlink swapped in at a `missing` position (or at the leaf) between resolve and the host's `open` escapes the scope. A record layer cannot close this; it must hand the host an `O_NOFOLLOW`/`openat`-relative recipe or an opened fd, not a string. Flag as a documented host obligation. **Medium.**
- **Filesystem — capability/context gate is absent in this crate (verify against host contract)** (`filesystem.rs`). No `ensure_allowed` is called for `FilesystemRead`/`FilesystemWrite`, and `resolve` takes no `PlatformContext` (gap #3). This is the task's "capability check absent" shape rather than an *advisory* (computed-but-unenforced) check — there is no computed-then-ignored decision; there is simply no decision. The plain reading is a deliberate grant-as-capability model, so it is **not** asserted as a confirmed defect. The concrete, expressible gap: a `filesystem.read` capability marked `plugin: false` cannot restrict a plugin through this crate, and `FilesystemGrant::new`/`user_selected_file` are public+ungated, so a grant can be constructed without any table consultation. **Medium / verify:** by-design iff the host mints grants only after a host-side `ensure_allowed`.
- **Network — allowlist enforced, host matching careful** (`network.rs`). Trust boundary: a host-supplied `url`. `ensure_allowed` runs first. `parse_host` (`network.rs:118`) restricts the scheme to `http`/`https` (no `file:`/`data:`/`ftp:` bypass), and **rejects** any URL carrying userinfo, password, fragment, or a non-default port — closing the `https://allowed@evil/` and `https://evil#allowed` confusion classes. Host comparison is **exact-set membership** (no wildcards — so no `*.evil.com`-style over-match), and both the request host and the allowed hosts are run through `Url::parse` and lowercased/trailing-dot-trimmed, so **IDN/punycode and case are normalized symmetrically** (the test pins `BÜCHER.example` → `xn--bcher-kva.example` on both sides). `canonical_allowed_host` rejects allowlist entries containing `/ \ @ ? # :` or whitespace, so a port/path can't be smuggled into an allow entry. Residual: the request URL's **path and query are not validated** — acceptable because the gate is host-only by design, but it means the allowlist authorizes a *host*, not a *URL prefix*; a host that must be reachable only on certain paths cannot be expressed. **Low / by-design.** Overall the strongest part of the crate.
- **Clipboard — gated; read/write distinguished** (`clipboard.rs`). `ensure_allowed` runs first (after rejecting non-clipboard operations), then plugin opt-in (`plugin_allowed`) is required *in addition* to the table's `plugin_applicable`, then supported-type. Both read and write are gated by the corresponding `ClipboardRead`/`ClipboardWrite` operation. Enforced, not advisory. Good.
- **Secrets — inert/record-only handle; correct redaction; constant-time N/A** (`secrets.rs`). Trust boundary: a declared secret value the caller already holds. **Positives:** `Debug` is overridden to print `[REDACTED:key]` (`secrets.rs:49`), so the value cannot leak through `{:?}` / `dbg!` / structured logging; the type derives no `Serialize`, so it cannot leak through serde; `read` rejects undeclared and structurally invalid keys. **Primary issue (gap #2):** the handle is **record-only** — the value is write-only (no accessor) with no backing store, so it neither fetches nor releases a secret; it is a redaction wrapper, not the "secret access" the crate advertises. **Secondary:** the value is held as a plaintext `String` with **no zeroize-on-drop** (it lingers in freed heap) — **Low**. **Constant-time comparison is N/A here:** there is **no secret-equality / authentication comparison** anywhere in the crate (the task's constant-time concern targets exactly such comparisons). The only reader, `is_absent_from` (`secrets.rs:44`), is a `!text.contains(&self.value)` leak-detection helper, not an equality check; its non-constant-time substring scan is at most a weak signal over attacker-influenced `text` and not a credible auth side-channel. **Medium overall**, anchored on the record-only inertness, not on timing.
- **Database — no SQL surface here; injection N/A** (`database.rs`). `DatabasePolicy` does **not** build, accept, or execute any SQL — it validates migration *ordering*/*ID shape* and delegates storage-path checks to `FilesystemPolicy`. So there is no raw-SQL injection vector *in this crate* (the host's executor is out of scope). Migration IDs are constrained to ASCII-alnum + `[-_.]`. The only security-relevant gap is the inherited un-gated capability (gap #2) and the inherited filesystem path-scope caveats. Good that no SQL is string-built here.
- **Deserialize of untrusted policy** (`capability.rs`). The capability table is `Deserialize` + `deny_unknown_fields`. `deny_unknown_fields` blocks field-injection/typo-smuggling — good. Residual considerations: `allowed_operations`/`denied_operations` are unbounded `Vec`s and `records` is an unbounded `BTreeMap`, so a hostile policy blob is an **unbounded-allocation** vector at deserialize time (bounded only by serde's input). Deny-precedence in `ensure_allowed` means a deserialized policy cannot *grant* more than the union it declares, and an empty/garbage table fails closed (`capability.missing`) — so a malformed policy denies rather than escalates, which is the safe failure mode.
- **Panics-as-DoS:** none found — no `unwrap`/`expect`/indexing-panic/`panic!` in `src/`. `migrations.windows(2)` is safe on any length. No recursion anywhere (contrast `hawk2ui-a11y`'s tree recursion), so no stack-overflow vector.
- **Unbounded growth:** `CapabilityTable.records` and every manifest's `Vec` allowlist grow with input but are caller-constructed per check (no long-lived accumulator like a11y's `events` or assets' `manifest`), so this is a deserialize-time concern (above), not a runtime leak.
