# Code Review — hawk2ui-script

**Reviewed at:** `5a042c51` · 2026-05-28 · **Remediated at:** `e7918972` · 2026-05-28
**Scope:** `src/lib.rs` + `tests/script_backend.rs` + `Cargo.toml` (1 src file ~815 LoC / 1 test file ~220 LoC)
**Purpose:** Production script backend — JavaScript execution via `boa_engine` 0.21 and TypeScript→JavaScript compilation via `oxc_*` 0.133 (parser → semantic → transformer → codegen), with a host-call policy gate, deterministic promise/timer projection into Boa jobs, and source-size limits.
**Note:** This is a **security-critical** crate (it executes untrusted JS/TS). The resource-limit, parse-depth, and panic findings (#1–#3, #10) were **remediated** at `e7918972` — see the Remediation section. The findings text below reflects the original review at `5a042c51`; the remaining items (#4–#9) are unaddressed quality/design notes.

## Summary

The two headline capabilities are **genuinely implemented, not stubbed.** JavaScript execution is real: `evaluate_javascript` (`lib.rs:618`) builds a `boa_engine::Context::default()` and calls `context.eval(Source::from_bytes(source))` then `context.run_jobs()` — confirmed real evaluation by tests asserting `[1,2,3].map(...).reduce(...) === 12`. The TypeScript path is real: `compile_typescript` (`lib.rs:568`) runs `oxc_parser::Parser::parse` → `oxc_semantic::SemanticBuilder::build` → `oxc_transformer::Transformer::build_with_scoping` → `oxc_codegen::Codegen::build`, with each stage's `errors` checked and surfaced as a diagnostic; the test confirms interfaces/generics/`as` assertions are stripped and the result evaluates. No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME markers. `#![forbid(unsafe_code)]` holds; `ScriptBackendError` → `Diagnostic` via `From` per convention.

The defects are concentrated in the trust boundary, which is exactly where they matter most for a script engine: **there is no runtime resource bound of any kind** on the Boa context — no CPU/loop-iteration budget, no wall-clock timeout, no memory cap. The crate's "limits" bound only source/compiled **byte length**, not execution. A one-line untrusted module (`while(true){}` or `new Array(1e9)`) hangs or OOMs the host/DAW thread, and `interrupt()` cannot stop it because it is checked only *before* evaluation. Worse, **deeply-nested source overflows the native stack at parse time** — both `oxc_parser` and boa's parser are unguarded recursive descent (verified: no depth limit, no `stacker`), and the only defense is the 1 MiB byte cap, which does not bound nesting depth — so ~1 MiB of `[[[[…` aborts the process *before* any runtime limit could apply, an **uncatchable** crash. Other adversarial-input **panics from boa/oxc are also not caught** (`Err` is handled, unwinding is not). Separately, the `HostCallPolicy` gate is a **Rust-side API gate that is unreachable from JavaScript**, so it provides no sandboxing of script behavior, and `host_calls` is write-only dead state.

## Remediation (2026-05-28 · `e7918972`)

Hardened the trust boundary; the two High findings (#1 runtime resource bound, #2 parse-time stack overflow) plus the related #3 (uncaught panics) and #10 (duplicated default constants) are **fixed**, with tests.

- **#1 — runtime resource bound (FIXED).** `ScriptExecutionLimits` gained a tunable `max_loop_iterations` (default 10,000,000); `apply_runtime_limits` sets boa's `set_loop_iteration_limit` on every untrusted context, so `while (true) {}` now terminates with a recoverable `script.eval.failed` instead of hanging the thread (test `script_backend_bounds_runaway_loops`). boa's recursion (512) and stack-size (10240) limits were already bounded by its own defaults. *Residual:* a true memory ceiling and wall-clock preemption of a finite-but-heavy run still need OS-level isolation — the worker thread (below) is the hook for a future watchdog/timeout.
- **#2 — parse-time native stack overflow (FIXED).** Two layers: (a) `enforce_nesting_depth` rejects source whose bracket-nesting depth exceeds a tunable `max_nesting_depth` (default 256) *before* either parser, via a saturating depth scan that cannot be bypassed (tests `…rejects_deeply_nested_javascript/typescript_before_parsing`); (b) all untrusted parsing/eval now runs on a dedicated worker thread with a known 16 MiB stack (`run_on_worker` / `SCRIPT_WORKER_STACK_BYTES`), so the depth bound is calibrated against a *known* stack rather than whatever (possibly small) stack the host/DAW invokes us on. **Empirically validated:** 100-deep nesting aborts the process when parsed on a default 2 MiB thread, but parses cleanly on the worker (test `script_backend_parses_deep_nesting_on_the_worker_thread_stack`). A native stack overflow remains uncatchable — prevention (the depth bound), not recovery, is the defense.
- **#3 — uncaught boa/oxc panics (FIXED).** Joining the worker thread converts a catchable panic into a `script.*.panicked` diagnostic instead of unwinding through the host (this replaced a planned `catch_unwind`).
- **#10 — duplicated default-limit constants (FIXED).** `ScriptBackend::new` now uses `ScriptExecutionLimits::DEFAULT` (single source of truth), and the misleading `ScriptExecutionLimits` doc (which implied *execution* limits) was rewritten to describe the actual byte/CPU/depth bounds.

**Severity recalibration (verify-against-source).** The original High rating on #1/#2 assumed *untrusted-runtime* input. Tracing the actual callers: the eval path **is** wired in production — `hawk2ui-cli`'s desktop runtime config runs the compiled entry script through `execute_module` (`entry_script_mount_app_model` / `entry_script_visible_title`, `executor.rs:1488`/`1516`), and `hawk2ui-build` compiles module source through `compile_module_source` → `compile_typescript`. But **both run author-controlled source** — the app's own compiled entry script / build sources — so today a runaway loop or deep-nesting crash is the *author crashing their own app or build* (a robustness failure), not an untrusted-input breach. The crate's designed-for *untrusted* third-party execution is not yet connected (`hawk2ui-runtime`'s script execution is record-only — its own finding). So the **live** exposure is author-source robustness on the `run-desktop` path; the untrusted-runtime **High** applies once that path is wired. This hardening serves both: a buggy author entry script now fails gracefully instead of hanging the desktop app, *and* the untrusted path is pre-armed. *(An earlier draft of this note wrongly claimed the eval path had no production caller — a truncated `tilth_deps` listing missed the CLI caller; corrected after a `gitnexus`/source trace.)*

**Not addressed here** (deferred quality/design items, unchanged from below): #4 `HostCallPolicy` unreachable-from-JS (a host-binding *design* decision — whether the engine should expose host calls to scripts at all), #5 inert `delay_ms` timer ordering, #6 dead `host_calls` state, #7 unreachable timer branch, #8 `SourceType`-from-filename. These are correctness/clarity, not the security priority, and several hinge on product decisions.

## Completeness & implementation gaps

1. **`host_calls` is write-only dead state** (`lib.rs:301`, `lib.rs:514`). `call_host` pushes every `HostCall` into `self.host_calls`, but the field is **never read** — there is no getter and no internal consumer (confirmed by grep: the only references are the `Vec::new()` init and the `.push`). Contrast `executed_modules`/`timers`/`promises`, which all have accessors. Either expose it (audit log) or drop it. Mirrors the "records intent, never read" dead-state pattern flagged in the sibling reviews.
2. **`TimerRecord.delay_ms` is inert for ordering/scheduling** (`lib.rs:209`, `lib.rs:668`). `delay_ms` is stored but never used to schedule or order anything. `execute_module_with_host_jobs` flushes timers by **label, in insertion order** (`for timer in timers { __hawk2uiFlushTimer(label) }`), regardless of delay. A 0 ms timer registered after a 1000 ms timer still fires second. "Deterministic timer … scheduling" (doc at `lib.rs:172`) overstates what is modeled: it is ordered flush, not delay-based scheduling.
3. **`schedule_timer`'s `script.timer.unavailable` branch is unreachable** (`lib.rs:473`). The guard is `if !self.timer_policy.deterministic`, but `TimerPolicy` has exactly one constructor — `deterministic()` (`lib.rs:174`) — which always sets `deterministic: true`, and the field is private. There is no way to construct a non-deterministic policy, so the error path is dead. Either add a non-deterministic constructor or remove the branch + the diagnostic.
4. **`interrupt()` cannot interrupt a running script** (`lib.rs:519`, checked at `lib.rs:542`). It sets `self.interrupted = Some(reason)`, which is read **only** by `ensure_running()` — invoked at the *start* of `execute_module`/`execute_module_with_host_jobs`/`schedule_timer`. Once `context.eval` is executing, nothing polls this flag (Boa is not given an interrupt handler), so a long/infinite script in flight runs to completion. The method models cooperative cancellation between calls, not preemption of a hung evaluation. See Security #1.
5. **`PromiseId`/`TimerId` are opaque with no accessor and `Ord`-only utility.** Returned to callers but cannot be introspected (no `.get()`), and `promise_state`/timers are the only ways to observe state. Minor; likely intentional handle opacity.

## Code quality & smells

- **`SourceType::from_path(...).unwrap_or_else(|_| SourceType::ts())`** (`lib.rs:571`). For a `ScriptModuleKind::TypeScript` module whose `id` ends in `.js`/`.mjs`/`.cjs`, `from_path` returns a **JavaScript** `SourceType`, so TS-specific syntax in that module is parsed as JS and a valid TS input fails with a parse error keyed on the module *name*, not its declared kind. The declared `kind` (which is `TypeScript` here by construction) should drive `SourceType`, not the filename. Filename-derived `.d.ts`/`.tsx` detection is a reasonable bonus, but the fallback-to-`ts()` only triggers on a path with no extension; a `.js` id silently downgrades.
- **`format_oxc_diagnostics` uses `{error:?}` Debug formatting** (`lib.rs:609`). oxc diagnostics implement `Display` (miette-style, with spans/labels); rendering them via `{:?}` produces verbose, less-readable internal structure in the user-facing diagnostic message. Prefer `Display`.
- **Two parallel "limits" representations.** `ScriptBackend::new` (`lib.rs:320`) hand-inlines the struct literal `ScriptExecutionLimits { max_source_bytes: 1_048_576, max_compiled_source_bytes: 4_194_304 }` instead of calling `ScriptExecutionLimits::default()` (`lib.rs:131`), which holds the identical constants. Two sources of truth for the same defaults; they can drift.
- **`structured_value_js_literal` for numbers uses `value.to_string()`** (`lib.rs:752`). Round-tripping an `f64` through Rust's `to_string` into a JS numeric literal is generally lossless for finite values (and non-finite is rejected), but it is a fragile coupling between Rust float formatting and JS number parsing; `{:?}`/`ryu`-style shortest round-trip would be more defensible. Low.
- **`module_id` is stored on `ScriptExecution` (`lib.rs:89`) but has no accessor.** The struct exposes only `value()`; the module id captured at `lib.rs:351`/`380` is unreadable by callers.

## Documentation

- Strong: crate-level `//!`, every public type/method documented, and `# Errors` sections on all fallible entry points (`execute_module`, `execute_module_with_host_jobs`, `compile_module_source`, `resolve_promise`, `schedule_timer`, `call_host`). No undocumented public items.
- **Misleading vs. behavior in two places:** the `ScriptExecutionLimits` doc ("limits enforced before script source is handed to the JavaScript engine", `lib.rs:101`) is accurate but easy to read as *execution* limits — there are **none** at runtime (Security #1). And `TimerPolicy::deterministic` ("plugin-safe scheduling", `lib.rs:172`) implies delay-aware scheduling that is not implemented (gap #2). Neither doc warns that `delay_ms` is recorded-but-unused or that there is no CPU/memory bound.

## Testing

- Good breadth for the happy paths: JS arithmetic + array higher-order methods (real Boa), TS with interfaces/generics/assertions (real oxc), compile-without-eval, promise/timer/host-call records, host-promise + timer projection into Boa jobs settling `__hawk2uiResult` to `"ready:timer"`, teardown clearing state, interrupt/teardown/denied-call rejection, error→`Diagnostic`, and both source-size limit paths.
- **False-confidence re: sandboxing.** `script_backend_denies_host_calls_interrupts_and_tears_down_safely` calls `call_host("fs.read", "/etc/passwd")` from **Rust** and asserts denial. This reads as a sandbox test but proves nothing about script confinement: JavaScript running in the Boa context never had an `fs.read` binding in the first place (the policy gate is not reachable from JS — Security #4). The test models a Rust-side API denial, not a script-escape defense.
- **Coverage gaps (the security-relevant ones are unexercised):** no test that an infinite loop / large allocation is bounded (because nothing bounds it — Security #1); no test that adversarial source cannot panic the engine (Security #2); no test of the TS error paths (`script.typescript.parse-failed`, `…semantic-failed`, `…transform-failed`); no test of `structured_value_from_js` rejecting `Object`/`BigInt`/`Symbol` results (`script.value.unsupported`), the non-finite-number rejection (`script.value.invalid-number`), or non-UTF-8 strings; no test of the unreachable `script.timer.unavailable` branch (because it is dead — gap #3); no test that `delay_ms` affects ordering (it doesn't — gap #2).

## Security

The trust boundary is **untrusted script source** (JS and TS), executed in-process. The crate makes one strong, correct architectural choice — a host-less engine with no native JS→Rust bridge — and then leaves the resource-exhaustion and crash-resistance protections (CPU/memory bound, parse-depth bound, panic containment) unimplemented, which is where the real risk concentrates.

**What is sound (stated explicitly to preempt false positives):**

- **No native host bridge is exposed to JavaScript.** boa is a pure ECMAScript engine: `Context::default()` provides language built-ins but **no** `require`, filesystem, network, process, or environment access. The *only* JS-facing host surface is the `host_job_prelude` (`lib.rs:697`), which installs a **frozen** `globalThis.hawk2ui = Object.freeze({ promise, onTimer })`. Both methods are pure-JS shims over two `Map`s (`__hawk2uiResolvedPromises`, `__hawk2uiTimerCallbacks`) pre-seeded by Rust; neither calls back into Rust. So script cannot reach the host through `hawk2ui`. This is real and appropriately minimal.
- **Prototype pollution is contained, not global.** Every `execute_module*` call builds a **fresh** `Context::default()` (`lib.rs:619`, `lib.rs:640`); a script that mutates `Object.prototype` poisons only its own throwaway context, which is dropped at function return. Not a cross-execution issue.
- **The `format!`-into-`eval` prelude path is not a script-controlled injection sink.** `execute_module_with_host_jobs` builds JS strings by interpolating promise/timer **labels** through `js_string_literal` and `eval`-ing them (`lib.rs:651`, `lib.rs:672`). This looks like an injection vector, but the labels originate from **Rust callers** (`create_promise`/`schedule_timer` arguments), never from the executing script — the script-facing `hawk2ui.promise(label)`/`onTimer(label,…)` shims only touch JS-side `Map`s and never reach the Rust interpolation. `js_string_literal` (`lib.rs:761`) escapes quotes/backslash/control chars; it does not escape U+2028/U+2029, but those are valid in string literals on an ES2019+ engine and the input is host-trusted, so this is benign. Stated to close the loop, not a finding.
- **Source size is bounded on both edges** (`enforce_source_limit`, `lib.rs:553`): raw input ≤ 1 MiB and compiled JS ≤ 4 MiB by default, checked before evaluation. This bounds the oxc parse/transform workload (so TS-compilation DoS is constrained — Low) and the eval input. The compiled-size check is *after* oxc runs, but the 1 MiB raw cap upstream limits oxc's input.
- **`structured_value_from_js` (`lib.rs:781`) is total over `JsVariant`** — every arm returns `Ok`/`Err`, no panic, and rejects `Object`/`BigInt`/`Symbol` and non-UTF-8 strings cleanly. Boa `Err` results from `eval`/`run_jobs` are mapped to diagnostics, not unwrapped.

**What is unsafe — ranked:**

1. **No runtime resource bound: CPU/infinite-loop and memory are unbounded → host/DAW hang or OOM (High).** The crate uses `Context::default()` and **never** calls `set_runtime_limits` / `runtime_limits_mut`. I verified boa 0.21's `RuntimeLimits` defaults (`boa_engine-0.21.1/src/vm/runtime_limits.rs`): `loop_iteration = u64::MAX` — i.e. **loops are unlimited by default**, enforced per-iteration only if a limit is set (`vm/opcode/iteration/loop_ops.rs`). So an untrusted module containing `while (true) {}` runs **forever on the calling thread**; in an audio-plugin editor this can wedge the host/DAW. There is **no memory cap at all** in `RuntimeLimits` (no heap-size field), so `const a = []; while(true) a.push(a)` or exponential string-doubling drives unbounded allocation until the process OOMs. boa exposes no wall-clock timeout, and `context.eval` is **synchronous and blocking** with no interrupt handler installed — so `ScriptBackend::interrupt()` (which only sets a flag read at `ensure_running`, `lib.rs:542`) cannot stop a script already in `eval`. **Mitigation:** set `runtime_limits_mut().set_loop_iteration_limit(...)` and run untrusted evaluation on a dedicated thread with a watchdog/timeout and a hard memory ceiling (RuntimeLimits alone does not bound wall-clock or memory). This is the crate's headline security gap.
2. **Parse-time native stack overflow on deeply-nested source → uncatchable process abort (High).** Both parsers run *before* any boa `RuntimeLimits` apply, and I verified neither bounds nesting depth: `oxc_parser` 0.133 has no recursion/depth guard and no `stacker` dependency (its only "list" handling is `parse_delimited_list` for comma sequences), and `boa_parser` 0.21 returned **zero** matches for any depth/recursion/limit/`stacker` keyword — both are plain recursive descent on the native thread stack. The crate's *only* depth-relevant defense is the 1 MiB raw-byte cap (`lib.rs:553`), which bounds *length* but **not** nesting depth: ~1 MiB of `[[[[…` / `((((…` / `{a:{a:{a:…` is hundreds of thousands of recursion frames and overflows the native stack during `Parser::parse` (TS path, `lib.rs:572`) or `context.eval` parsing (JS path, `lib.rs:620`/`660`). A stack overflow trips the guard page → `SIGSEGV`/abort, which is **not** unwindable, so `catch_unwind` cannot recover it — the host/DAW process dies. This is the same class the sibling `hawk2ui-a11y` review rated its headline High (unbounded recursion → stack-overflow DoS), here reaching *both* the JS and TS paths. **Mitigation:** enforce a maximum nesting-depth (token-balance pre-scan or a parser with a depth cap) before parsing, and/or parse untrusted source on a dedicated worker thread with a bounded stack so an overflow is contained to that thread rather than aborting the host.
3. **Other boa/oxc panics on adversarial input are uncaught → host crash (DoS) (Medium).** Distinct from the overflow in #2 (which is *not* a panic and cannot be caught): `context.eval`/`context.run_jobs` and the oxc pipeline (`SemanticBuilder::build`, `Transformer::build_with_scoping`, `Codegen::build`, `lib.rs:581`–`606`) are guarded for their `Result::Err` channels but not for unwinding. boa/oxc carry `debug_assert!`s and `panic!` paths reachable on some pathological inputs; nothing wraps execution in `std::panic::catch_unwind`, so a *catchable* internal panic takes down the host thread rather than yielding a diagnostic. No concrete trigger is demonstrated here (hence Medium, not High). **Mitigation:** evaluate untrusted source inside `catch_unwind` (on the worker thread from #1/#2) and convert a caught panic into a `ScriptBackendError`.
4. **TypeScript→JavaScript output is fed to the engine unvalidated, but this is not an escalation (Low).** `compile_typescript` returns codegen output that flows straight into `evaluate_javascript`. There is no post-transform validation, but because the JS context is itself host-less (point above), TS-transform "injection" gains nothing a JS module could not do directly by being written as JS — same hostless sandbox. The compiled-size cap (`lib.rs:407`) bounds output volume. Worth noting only because the task asks; not a privilege boundary.
5. **`HostCallPolicy` is a Rust-side gate that is unreachable from JavaScript — it does not sandbox script behavior (Medium).** `deny_all`/`allow` (`lib.rs:146`/`154`) gate the **Rust** method `call_host` (`lib.rs:500`); JavaScript executing in the Boa context has no way to invoke `call_host`, and the policy is never consulted during `eval`. So the policy governs only what *Rust callers* of this API may do, not what *scripts* may do. Combined with #1/#2, the practical sandbox today is "whatever boa's pure-ECMAScript surface allows, unbounded in time and memory." The naming and the `fs.read`/`/etc/passwd` test strongly imply script-confinement that is not provided. **Mitigation:** if scripts are meant to reach host bindings, expose a permission-checked native function into the context and route it through `HostCallPolicy`; today the gate is effectively inert w.r.t. the script trust boundary.
6. **`eval`/`Function`/dynamic `import`/`globalThis` are reachable from script (Low, defense-in-depth).** `Context::default()` leaves `eval`, the `Function` constructor, and `globalThis` available, so a script can build and run further code at runtime. Because the context is host-less, this is **not** a host-escape — it only runs more in-engine JS — so it is low severity. But it widens the dynamic-code surface (and interacts with #1: dynamically-generated infinite loops). If the threat model wants statically-analyzable scripts, delete `eval`/`Function` from the global object after context construction.
7. **No bound on number of contexts / accumulated state.** Each execution allocates a fresh `Context` (good for isolation) but there is no rate limit; `executed_modules`, `host_calls` (dead), `promises`, `timers` grow with calls and are drained only by `teardown`. Slow memory-growth vector for a long-lived backend driven by many calls. **Low.**
