# Code Review — hawk2ui-framework-conformance

**Reviewed at:** `5a042c51` · 2026-05-28 · working tree clean at review time
**Scope:** `src/lib.rs` + `tests/framework_conformance.rs` (1 src file ~1100 LoC / 1 test file ~150 LoC)
**Purpose:** Cross-framework conformance harness for the Native / Svelte / React / Vue / Solid adapters. Runs each adapter against a shared semantic fixture and asserts (a) every framework normalizes to the same native record contract, (b) invalid fixtures produce source-mapped diagnostics, (c) reference frameworks bridge through the runtime and render visible pixels via Skia, and (d) invalid contracts are rejected with the expected rules.
**Note:** Codex is concurrently committing hardening/remediation work; HEAD drifts (git HEAD is `5fecf2c4`). Findings reflect the SHA above and may overlap with in-progress fixes.

## Summary

This crate is **not a stub** — it wires real adapters into real downstream machinery: `run_diagnostic_matrix` and `run_failure_matrix` feed each adapter raw author source via `*::new(file, source)` and exercise its genuine string-lowering (`extract_attribute`, `keyed_children(source)`, `unsupported_*_events`), producing real source-mapped diagnostics and rejection rules; `run_runtime_matrix` performs a real `NativeRuntimeBridge` bridge, a real `RuntimeSceneBridge` layout, real `SkiaRendererBackend` draw calls, and a real per-pixel diff (`count_changed_pixels`). No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME markers. `#![forbid(unsafe_code)]` holds and there is no `Deserialize`/serde surface at all.

The central weakness is the one most dangerous for a conformance crate: **the headline equivalence path (`run_all` / `is_equivalent`) is tautological.** All four framework `*_snapshot()` helpers build their input with `*ComponentSource::from_native_program(...)`, which sets `source: String::new()` and stores a pre-built `FrameworkNativeProgram`. On that path each adapter's `render`/`compile` **short-circuits** to `*_artifact_from_native_program(...)`, which merely *projects* fields straight off the shared program (`root().id()`, `keyed_child_order()`, `refs()`, `style_refs()`, `asset_refs()`, lifecycle). Because `run_all` hands **the same** `framework_native_program()` output to all four adapters, `is_equivalent()` compares fields that are identical **by construction** — the per-framework source lowering that is the crate's entire reason to exist is never run here. A regression that makes one adapter's real lowering diverge would pass `run_all` untouched. Secondary: `state_updates` is a hardcoded constant in all five snapshots, so the "state" parity advertised in the test name is vacuous.

## Completeness & implementation gaps

1. **Equivalence is asserted over fields that are identical by construction** (`lib.rs:345` `run_all`; `lib.rs:155` `is_equivalent`; `native_snapshot`/`svelte_snapshot`/`react_snapshot`/`vue_snapshot`/`solid_snapshot`, `lib.rs:413`–`574`). Each framework snapshot is produced from `from_native_program(...)`, which forces the adapter down `*_artifact_from_native_program` (e.g. `hawk2ui-framework-react/src/lib.rs:479`) — a field-by-field copy of the *shared* `FrameworkNativeProgram`. The four frameworks therefore cannot differ on `root_id`/`keyed_children`/`refs`/`style_refs`/`asset_paths`/`event_keys` unless `hawk2ui-authoring`'s own projection is non-deterministic. `is_equivalent` thus validates the authoring-layer projection, **not** that React vs Vue vs Svelte vs Solid lower equivalently from their own representations. The actual per-framework lowering (`extract_attribute`/`keyed_children(source)`/`on:press` vs `onPointerDown` vs `v-for` grep) is bypassed on this path. → To be a real conformance check, each snapshot must originate from framework-native *source* (the `::new(file, source)` path), so divergent lowering can be caught.
2. **`state_updates` is a hardcoded constant, never derived** (`lib.rs:464`, `:491`, `:518`, `:545`, `:572`). Every snapshot sets `state_updates: vec!["state:items".into()]`. No adapter computes state updates (the string `"state:items"` exists only in this crate). So the `state_updates` column of `is_equivalent`, and the "...state..." claim in the test name `framework_conformance_outputs_equivalent_records_for_lifecycle_state_events_refs_keyed_children_styles_and_assets`, assert nothing about any framework. → Derive it from the artifacts or drop the field and the name claim.
3. **`frames_presented` is a hardcoded `1`** (`lib.rs:759`). It is not read back from the backend; the runtime test asserts only `frames_presented() > 0` (`tests/framework_conformance.rs:72`), which is therefore vacuous. The surrounding render work *is* real, but this particular field is canned. → Return the backend's actual present count or document the field as a fixed marker.
4. **The runtime matrix is a smoke test run five times, not a conformance comparison** (`run_runtime_matrix`, `lib.rs:378`). Unlike `run_all`, `FrameworkRuntimeReport` exposes no `is_equivalent`; each `runtime_evidence_*` is checked independently. Combined with finding #1 (all four frameworks bridge the *same* program), this is the same end-to-end smoke path exercised once per framework. It proves the bridge+Skia pipeline works, but proves nothing *cross-framework*. Worth labeling as a per-framework runtime smoke rather than a parity check. (The `operation_keys` it asserts — `mount-element:root`, `bind-event:root:pointer.press` — are genuinely derived via `custom_renderer_operation_keys`, so that part is real.)

## Code quality & smells

- **Unguarded `diagnostics()[0]` indexing in every diagnostic/failure helper** (`lib.rs:588`, `:604`, `:620`, `:636`, `:927`, `:943`, `:959`, `:975`, `:991`, `:1007`, `:1023`, `:1039`, `:1055`, `:1071`). Each reads `error.diagnostics()[0].rule.as_str()`. If an adapter ever returns an `Err` with an empty diagnostics vector (e.g. a bridge/finalization failure routed through the same error type), this panics instead of surfacing a message. The `run_*` signatures return `Result<_, String>`, so the intent is no-panic; the `[0]` violates it. → Use `.first().ok_or(...)?` and fold a "missing diagnostic" into the returned `String`.
- **Five near-identical `*_snapshot` and `*_invalid_layout_failure`/`*_unsupported_event_failure` helpers** (`lib.rs:413`–`574`, `:947`–`1073`). Heavy duplication; each differs only in adapter type, asset name, and unmount handler. A small trait or macro over the four framework integrations would remove ~300 LoC and make coverage asymmetries (below) visible by absence.
- **`comparable()` clones the entire snapshot to drop one field** (`lib.rs:107`). `ConformanceSnapshot` and `ComparableSnapshot` are identical except `framework`; `is_equivalent` clones every `Vec<String>` per snapshot to compare. Functionally fine at fixture scale; a derived `PartialEq` that ignores `framework`, or comparing field tuples by reference, avoids the allocation and the parallel struct.
- **`from_native_program` path leaves the adapter `source` empty and unused.** Not a defect in the adapters, but it is the mechanism that makes the conformance harness skip real lowering (finding #1); the harness chose the one constructor that bypasses what it claims to test.

## Testing

- **Real coverage:** `framework_conformance_diagnostics_point_to_author_source_files` and `framework_conformance_failure_matrix_rejects_invalid_contracts` drive real broken source through each adapter and assert real source files + rule strings — these are the genuine conformance assertions in the crate. The runtime test confirms `changed_pixels > 0` from an actual Skia rasterization (real).
- **False-confidence (mirrors finding #1):** `framework_conformance_outputs_equivalent_records_...` asserts `is_equivalent()` and per-snapshot field equality, but every snapshot is projected from the same `FrameworkNativeProgram`; the assertions hold by construction and cannot detect a per-framework lowering regression. The test name implies far more than is verified.
- **Vacuous assertions:** `frames_presented() > 0` (against a hardcoded `1`, finding #3) and the `state_updates` equality (against a hardcoded constant, finding #2).
- **Coverage asymmetry across the four frameworks** (crate's stated purpose is parity):
  - *Diagnostic matrix:* one rule (`asset.path-invalid`) across Svelte/React/Vue/Solid; Native is absent (it has no author-source language, so it is not comparable on this axis — worth stating, not necessarily fixing).
  - *Failure matrix:* Svelte has an `invalid-asset-path` case (`lib.rs:931`) that React/Vue/Solid **lack**; Native has only `duplicate-keyed-child`. So the four "framework" adapters are not exercised by the same failure set.
  - The `invalid-layout-number` fixtures (`lib.rs:947`,`:979`,`:1011`,`:1043`) are framework-native syntax (`{#each}` / `.map` / `v-for` / `<For>` plus `data-font-size="0"`), so each adapter **does** run its real iteration-construct parsing and `extract_number_attribute` before bridging — that part is genuine per-framework coverage. What is **shared** is the rejection *decision*: all four resolve to `*.runtime-bridge.failed`, a single `NativeRuntimeBridge` validation re-wrapped with a per-framework prefix. So the rule asserted is the same shared rule four times; the `unsupported-event` cases (`*.event.unsupported`) are where per-framework event-matching is tested most directly.
- **No negative test for `is_equivalent`** (no fixture where one framework is made to diverge and the harness is shown to catch it) — which is exactly the test that would expose finding #1.

## Cross-cutting conventions (workspace-wide; noted once)

- `crate_name()` plus the `exposes_crate_identity` and `framework_conformance_workspace_filter_marker` tests follow the workspace pattern.
- `#![forbid(unsafe_code)]` at crate root. **Deviation (informational):** unlike most domain crates, this crate has no error type of its own and no `hawk2ui_api::Diagnostic` bridge — all `run_*` methods return `Result<_, String>` via `format!("{error:?}")`. Acceptable for a test harness (errors are assertion fuel, not a public diagnostic surface), but it means adapter errors are flattened to `Debug` strings here.

## Security

The attack surface is **near zero**, and notably smaller than `hawk2ui-a11y`/`hawk2ui-assets`: this crate derives **no** `Deserialize`/serde on any type, takes **no** external/untrusted input (all fixtures are hardcoded string literals and hand-built programs), and the only allocation/iteration bound is the fixed `220×120` surface in `count_changed_pixels` (`lib.rs:875`) and `RuntimeSceneBridge::new(Viewport::new(220.0, 120.0))` (`lib.rs:730`). There is no recursion over attacker-influenced structure within this crate, no `unsafe`, and no parsing of runtime input. As an internal harness, it is not a production trust boundary.

- **The real security-relevant issue is false assurance, not a runtime vector.** A conformance harness is a safety net: its value is catching a regression that makes one adapter's lowering diverge — including one that mishandles or under-rejects malicious author source (path traversal, `://` schemes, unsupported event handlers). The diagnostic/failure matrices *do* test some of that rejection behavior with real source, which is good. But the **equivalence guarantee (`run_all`/`is_equivalent`) provides no such protection**: because it feeds every adapter the same pre-lowered `FrameworkNativeProgram` and compares fields that are identical by construction (finding #1), an adapter whose source-handling silently diverged — accepting a path the others reject, or lowering keys/events differently — would still pass `run_all`. The crate's marquee assertion therefore advertises cross-framework correctness it does not verify. **This is the central risk the harness is supposed to mitigate and currently does not.**
- **Latent panics-as-robustness-bug (not DoS):** the `diagnostics()[0]` indexing (Code quality) would panic a test rather than report, on an empty-diagnostics `Err`. In-process only; no external trigger. **Low.**
- **Good:** no `unsafe`; no deserialization; deterministic, fully-bounded fixtures; the parts that *are* exercised (diagnostics, failure rules, runtime bridge + Skia pixel diff) do real work against real adapter code paths.
