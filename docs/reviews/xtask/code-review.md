## Remediation (2026-05-29) — contained subset

Fixed the two false-assurance gates on `release-check`; surfaced the broader validate-reality finding as a release-process decision. Verified: `cargo test -p xtask` (23 passed) + `cargo clippy --all-targets -- -D warnings` clean.

New test `rejects_changelog_missing_required_sections`; the real `CHANGELOG.md` still parses (it carries all seven).

Full per-member version validation via `cargo metadata` is the fuller form of #1, surfaced here.
- **Low, deferred:** #4 module-wide `#![allow(dead_code)]` still covers the remaining test-only `contains`/`release_blockers` helpers (wiring `has_section` in #3 removed one dead item; narrowing the allow needs those moved to `#[cfg(test)]`); #5 self-referential version test (now complemented by the real-version test); #6 duplicated validator structs + `run_script` duplicated across `main.rs`/`release.rs`; #7 `include_str!` compile-time embedding (verified non-issue — rustc dep-info rebuilds on edit); #8 no module/item docs on `release.rs`.

## Summary

`main.rs` is **genuinely implemented and well-tested**: arg parsing is exhaustive (exact-arity matching, unknown-command / missing-command / too-many-args all produce usage text), subprocess dispatch checks `status.success()` and propagates failure as `Err` → `exit(2)`. No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME markers anywhere in the crate. `check`/`check-fast` are thin, correct `bash <script>` wrappers and the scripts do real `cargo fmt/clippy/test/bench/doc/deny` work.

The substantive weakness is concentrated in `release.rs`, and it is the crate's headline capability: **`release-check` does not validate the repository — it validates five policy *documents* that are baked into the binary at compile time.** Every validator (`validate_repository_version_policy`, `..._package_targets`, `..._changelog`, `..._release_criteria`, `..._dependency_policy`) does `include_str!("../../release/<file>")` → `toml::from_str` / line-scan → shape checks (non-empty fields, unique IDs, enum membership). The parsing and shape-checking is *real* (it will fail on a malformed or duplicate-id policy file, and the version equality / git-dependency-blocker rules are genuine cross-field invariants). But **nothing reads live workspace state**: no `Cargo.toml`, no `CARGO_PKG_VERSION`, no `cargo metadata`, no filesystem read (`grep` for `fs::`/`Cargo.toml`/`CARGO_PKG`/`env!` in `xtask/src/` returns nothing). The most consequential instance: `VersionPolicy::validate` asserts `crate_version == package_version == manual_version` where **all three are string fields in the same `version-policy.toml`** (all `"0.1.0"`) — it never compares them to any crate's actual version. So a crate bumped to `0.2.0` while `version-policy.toml` stays `0.1.0` **passes the version gate**. This is "records intent, does no real work against reality" sitting on the crate's headline gate — the same shape the `hawk2ui-assets` anchor review rates **High** (its inert, self-referential "cache invalidation" #1), so I rate it High here too; the only thing pulling against that is xtask's low exposure as a dev/CI tool (see Security), and I am consciously **holding it at High** because the defect is on the release-readiness gate itself. (`compatibility_notes_required` is a second tautology of the same kind: `VersionPolicy::validate` asserts the file's boolean is `true`, not that compatibility notes actually exist.)

A second issue: the changelog gate is the weakest of all. `Changelog::parse` enforces only a `# Changelog` title plus two substrings; the required-sections check (`has_section`) is **test-only and never runs in production** (`#![allow(dead_code)]` exists precisely to silence it and the other test-only helpers). (Note: `include_str!` embeds the policy files at compile time, but this is **not** a stale-validation hazard on the supported path — verified empirically: editing `release/version-policy.toml` content and running the documented `cargo run -p xtask -- release-check` rebuilds xtask and validates the new content, because rustc dep-info tracks `include_str!` inputs. See #3.)

## Completeness & implementation gaps

1. **Version policy is tautological w.r.t. the repository** (`release.rs:175` `VersionPolicy::validate`). The three "version domains" it cross-checks (`crate_version`, `package_version`, `manual_version`) are sibling fields *inside* `version-policy.toml`; `require_matching_version` compares them to each other, not to any real artifact. `workspace.package` has no `version` key, and each crate hardcodes `version = "0.1.0"` in its own `Cargo.toml` (34 crates use `version.workspace = true`-style inheritance for other fields but **not** version). Result: the gate is green as long as the operator keeps the three strings in one file equal, regardless of what the crates actually ship. The headline `--version-only` check therefore cannot catch the exact drift it appears to guard. `compatibility_notes_required` (`release.rs:197`) is the same anti-pattern in miniature: it errors if the file's bool is `false`, i.e. it asserts the policy *declares* notes required — never that any compatibility note exists. → Read the real workspace version (parse root/member `Cargo.toml`, or `env!("CARGO_PKG_VERSION")` for crates compiled in) and compare *that* against the policy.
2. **All five validators check document shape, not repository compliance** (`release.rs:34`–`62`). `validate_repository_package_targets` confirms `package-targets.toml` is well-formed (unique ids, non-empty `kind`/`platform`/`command`/`evidence`) but never checks that the referenced build commands exist, that `release_gate` targets actually build, or that evidence files under `target/release-evidence/` are present. `validate_repository_release_criteria` / `validate_repository_dependency_policy` likewise validate the TOML, not the world. The crate-level claim is "release-readiness validation"; the delivered behavior is "release-*policy-file* lint." Only `run_full_release_check` → `run_script("scripts/check.sh")` exercises the real toolchain. → Either narrow the docs to "policy-file validation," or make the gates assert against live state (evidence-file existence, `cargo metadata` versions, `cargo deny` exit).
3. **`include_str!` embeds policy at compile time — design smell, not a correctness hazard on the supported path** (`release.rs:35,41,47,53,59`). I initially flagged this as stale-validation but **verified otherwise**: cargo's rustc dep-info tracks `include_str!` inputs, so editing `release/version-policy.toml` content and running the documented invocation (`cargo run -p xtask -- release-check`, which is exactly what `scripts/release-check.sh` and `release/checklist.md` call) **recompiles xtask and validates the new content** — a mutation to `package_version` was correctly caught as `MismatchedVersion`. The only way to validate stale content is to run a pre-built binary directly, which is not a supported path. Remaining smell: a run-time `std::fs::read_to_string` (relative to `CARGO_MANIFEST_DIR`/repo root) would be clearer than compile-time embedding and would remove the rebuild dependency, but the current approach is correct as invoked. **Low / design note.**
4. **Changelog Full-mode gate does not enforce required sections** (`release.rs:410` `Changelog::parse`). Production parsing rejects only (a) missing `# Changelog` title and (b) `has_verification_evidence` — a substring test for `"Verification Evidence:"` **and** `"target/release-evidence/"` anywhere in the file. The Added/Changed/Fixed/Security/Compatibility/Migration/Known-Limitations requirement lives only in the test `repository_changelog_has_required_release_sections` via `has_section`, which is **never called by `parse`**. So `--changelog-only` passes on a changelog that has the title + the two magic substrings but is otherwise empty of the mandated sections. The substring check is also trivially gameable (a comment or prose line containing both strings satisfies it). → Call `has_section` from `parse` (and/or check section presence against the policy) so the gate matches the documented requirement.
5. **`#![allow(dead_code)]` blankets the whole module to hide test-only API** (`release.rs:1`). `ReleaseCriteria::contains`/`release_blockers`, `PackageTargets::contains`/`release_blockers`, `DependencyPolicy::contains`/`release_blockers`, and `Changelog::has_section` have **zero production call sites** (verified via caller search + regex over `xtask/src`); they exist solely so the in-module tests can probe parsed structures. A crate-wide `allow(dead_code)` is a blunt instrument that will also mask *future* genuinely-dead code. → Move these to a `#[cfg(test)]` helper impl, or `#[allow(dead_code)]` the specific items, and drop the module-wide allow.

## Code quality & smells

- **Five near-identical validator structs** (`ReleaseCriteria`, `PackageTargets`, `DependencyPolicy`, plus `VersionPolicy`) repeat the same `parse → toml::from_str → validate → require_field (trim().is_empty()) → dedupe-ids-via-HashSet → typed Error enum` shape (`release.rs:82`, `250`, `320`, `167`). `require_field`/`require_policy_field` are duplicated three times verbatim with only the error-enum variant differing. A shared `require_non_empty` helper or a small trait would remove ~80 lines of near-copy and the matching test boilerplate. Not a bug, but high-duplication for a 2-file crate.
- **`run_script` is duplicated between the two files** (`main.rs:81` in `run_command` vs `release.rs:64` `run_script`) — identical `Command::new("bash").arg(script).status()` + `success()` + formatted-error logic. One should call the other. Minor drift risk if one is hardened (e.g., to capture stderr) and the other is not.
- **Possible re-entrancy via `scripts/check.sh`** (`release.rs:31`). Full `release-check` runs `scripts/check.sh`, which runs `cargo test --workspace` — and the workspace includes `xtask`, whose tests `include_str!` and parse all the policy files again. Not infinite recursion (the tests don't shell back out), but Full release-check transitively recompiles+tests xtask, so the policy files are validated twice by two mechanisms. Worth being aware of; not a defect.
- **`run_command`'s `let Some(script) = (…) else { return Ok(()) }`** (`main.rs:73`) is a convoluted way to special-case `ReleaseCheck` (which `return`s inside the match arm). The `else` branch is unreachable — both non-release arms yield `Some`. A plain `match` with three arms would be clearer; the current shape reads as if an `Ok(())` fall-through is possible when it is not.
- **`ReleaseCheckMode` is `pub(crate)` and re-exported into `main.rs`'s public-ish parse API** while every other release type is private. Fine for a binary crate, but the `#[derive(PartialEq, Eq)]` on it exists only for the `main.rs` parse tests — consistent, low concern.

## Documentation

- `main.rs` has a crate-level `//!`. `release.rs` has **no module doc** and **no doc comments on any item** — none of the validator types, the `parse`/`validate` methods, or the error enums are documented. For a release-gate module whose semantics are subtle (what each check actually asserts), the absence of `//!`/`///` is a real gap: a reader cannot tell from the code that "version policy" means "three strings in one file agree" without tracing it. (The crate is a binary, so missing-docs lints don't fire, but the pedantic bar elsewhere in the workspace makes this conspicuous.)
- No `# Errors` sections anywhere; again binary-crate-excusable, but the `Result<_, String>` public-ish `parse` fns would benefit.

## Testing

- **Strong, real arg-parsing coverage** (`main.rs` tests): all four `release-check` forms, both `check`/`check-fast`, unknown command, missing command, extra args — each asserting the exact usage string. This is genuine and valuable.
- **`release.rs` tests are mostly real positive/negative coverage of the parsers**: duplicate-id rejection (criteria, targets), missing-evidence rejection, version-mismatch rejection, missing-verification-evidence rejection. These exercise the actual `validate` logic and would catch a malformed policy file. Good.
- **False-confidence / mislabeled tests:**
  - `repository_version_policy_declares_all_version_domains` (`release.rs:553`) asserts the *parsed values* equal `"0.1.0"` — it pins the policy file's contents to itself, reinforcing the illusion (gap #1) that this constitutes a version check against the repo. It tests the document, not version correctness.
  - `repository_changelog_has_required_release_sections` (`release.rs:683`) exercises `has_section` — but `has_section` is **never run in production** (gap #4). The test gives confidence that section-checking *works*, while the actual `--changelog-only` gate doesn't perform it. The test masks the fact that the section requirement is unenforced at runtime.
  - `repository_*_cover_required_*` (criteria/targets/dependency) assert that today's policy files contain a hardcoded list of ids/names. These are change-detectors for the policy files, not validators of release readiness — fine as regression guards, but they read as "the release gate checks for X" when the gate does no such thing.
- **Coverage gaps:** no test for `run_full_release_check` ordering / short-circuit behavior; no test that a *failing* sub-validator aborts Full mode; no test of `run_script` failure propagation (the subprocess path in both files is untested — only the pure parsers are). The `dead_code` helpers (`contains`, `release_blockers`) are tested but unused in prod — inverted coverage.

## Cross-cutting conventions (workspace-wide; noted once)

- `#![forbid(unsafe_code)]` holds in `main.rs`; `release.rs` has no inner attribute but inherits the workspace `unsafe_code = "forbid"` lint — no `unsafe` anywhere. (Per review scope, not reported as a finding.)
- `exposes_binary_identity` (`main.rs:170`) is the xtask analogue of the workspace `crate_name()` identity test — conventional, not reported.
- xtask does **not** use the `hawk2ui_api::Diagnostic` convention — expected and fine for a standalone binary with no dependency on `hawk2ui-api`; its `Result<_, String>` + typed internal error enums are appropriate here.
- **Deviation (Low):** `release.rs:1` `#![allow(dead_code)]` is a module-wide suppression (gap #5) — out of step with the workspace's pedantic-clippy posture; prefer item-scoped or `#[cfg(test)]`.

## Security

xtask is a **dev/CI tool** with low external exposure: it takes no network input, reads only repo-local files, and its only untrusted-input surface is `argv` (which is operator-controlled). The genuine security-relevant concern here is **correctness-as-security of the release gate** — a gate that passes when it shouldn't grants false release-readiness assurance.

- **Command injection: none.** Every subprocess is `Command::new("bash").arg(<hardcoded literal>)` — `"scripts/check.sh"`, `"scripts/check-fast.sh"`, `"scripts/check.sh"` (`main.rs:74-76`, `release.rs:31`). No user/argv/file-derived string is ever passed to the shell; the `command`/`upgrade_gate` strings parsed out of the policy TOMLs are validated for non-emptiness and then **never executed** by xtask (they're documentation of what humans/CI should run). No `sh -c`, no string interpolation into a shell. Clean.
- **Path handling: minimal and safe.** Script paths are fixed relative literals resolved against CWD by `bash`; policy/changelog paths are compile-time `include_str!` constants. No path traversal surface, no attacker-controlled paths.
- **Release gate can pass when it shouldn't (false-assurance) — the real risk.** Per gaps #1, #2, #4: `--version-only` passes despite real crate↔policy version drift (it only self-compares fields in one file, and `compatibility_notes_required` self-asserts a boolean); the validators check policy-document shape rather than repository compliance (no evidence-file / build-target / live-version assertions, gap #2); `--changelog-only` does not enforce the mandated sections (gap #4) and its evidence check is a gameable substring match. A release operator running `release-check` and seeing green can reasonably (and wrongly) believe versions are aligned, the changelog is complete, and package targets are satisfied. For a tool whose purpose is to *block* unsafe releases, this is the central finding — the version-gate instance is **High** (parallel to the assets anchor's inert-headline-feature #1; held at High despite low tool exposure because it sits on the release gate). Full mode still runs the real `check.sh`, which catches some toolchain/test drift — but not version or changelog drift.
- **Panics: none in the production path.** `main` routes all errors through `Result` → `eprintln!` → `exit(2)`; no `unwrap`/`expect`/indexing-panic in non-test code. `toml::from_str` errors are caught and stringified. `unwrap`/`expect` appear only in `#[cfg(test)]`. A malformed policy file yields a clean error exit, not a crash. Good.
