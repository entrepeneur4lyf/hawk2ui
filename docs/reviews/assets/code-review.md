# Code Review — hawk2ui-assets

**Reviewed at:** `5a042c51` · 2026-05-28 · working tree clean at review time
**Scope:** `src/lib.rs` + `tests/asset_backend.rs` (1 src file ~620 LoC / 1 test file ~120 LoC)
**Purpose:** Production asset decoding, validation, lowering, hashing, and cache invalidation — image decode + lossless-WebP sanitize, SVG validate + usvg lowering, font load, SHA-256 hashing, per-asset cache-generation tracking, and export to `hawk2ui_render::CompiledAsset`.
**Note:** Codex is concurrently committing hardening/remediation work; HEAD drifts (git HEAD is `5fecf2c4`). Findings reflect the SHA above and may overlap with in-progress fixes.

## Summary

This crate is **genuinely implemented, not a stub**. The decode/sanitize/hash pipeline does real work: `compile_image` calls `image::load_from_memory` (real decode) then re-encodes to lossless WebP via `WebPEncoder::new_lossless` (real metadata-stripping sanitize); `compile_vector` runs a substring denylist, parses with `usvg::Tree::from_data` (real SVG parse), counts paths, and re-serializes via `Tree::to_string` (real lowering); `AssetHash::sha256_bytes` is a real `Sha256` digest; `load_font` feeds bytes to `fontdb::Database::load_font_data`. No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME markers.

The substantive weaknesses are: (1) **`cache_generation` increments unconditionally** — the hash-change guard is dead code and the stored hash is never read for any decision, so the crate's headline "cache invalidation" feature does not actually key on content; (2) **fonts are stamped `sanitized: true` with zero validation** — `load_font` accepts arbitrary non-font bytes and never errors; (3) a **decode bomb runs before the pixel limit is checked** (`verify_pixels` is post-decode), so the crate's 16M-pixel cap is post-hoc rejection, not a decode guard; (4) the **SVG denylist is both load-bearing for file-read safety and over-broad**, rejecting common-but-benign SVG constructs (`url(#…)` gradients, `<use>` symbols). No correctness blocker on the happy path; the defects are in cache-invalidation correctness, the font trust boundary, and decode robustness.

## Completeness & implementation gaps

1. **`cache_generation` is inert as an invalidation signal** (`lib.rs:480` `AssetBackend::cache_generation`). The body is:
   ```rust
   if generation.hash != hash { generation.hash = hash.to_string(); }
   generation.generation = generation.generation.saturating_add(1);   // outside the `if`
   ```
   The increment is **unconditional**. Recompiling the *same* `id` with the *same* bytes still bumps the generation (1 → 2 → 3…). The `if generation.hash != hash` block updates the stored hash but never gates the increment, and the stored `hash` field is **never read to make any decision** — it is dead state. So the feature named in the crate docs ("cache invalidation") does not key on content change at all; identical recompiles churn the generation, and a content change is indistinguishable from a no-op recompile. This is the "records intent, does no real work" pattern, sitting directly on the crate's headline capability. → Gate the increment on `generation.hash != hash` (bump only on real content change) or document that generation == compile count, not content version.
2. **`compiled_hash` is computed and exposed but internally inert.** Every `compile_*` path computes `AssetHash::sha256_bytes(&compiled_bytes)` and stores it (`AssetRecord::compiled_hash()` exposes it), but its only would-be internal consumer is the dead guard in (1) — and that guard is fed the *source* `expected_hash`, not the compiled hash. Nothing in the crate compares compiled hashes across recompiles, so sanitization-output stability is never used for invalidation.
3. **`load_font` performs no font validation yet stamps `sanitized: true`** (`lib.rs:404`). It stores the bytes verbatim and calls `font_database.load_font_data(bytes.to_vec())`, which returns `()`. Confirmed against fontdb 0.23: `load_font_data` → `load_font_source` parses faces and, on parse failure, only `log::warn!`s and **drops** the face (`ids.unwrap_or_default()`); the dropped IDs are discarded by `load_font_data` anyway. So **arbitrary non-font bytes succeed as a `Font` asset** — the test loads `b"font-v1"` (7 bytes, not a font) and it "compiles." Images earn `sanitized: true` by re-encoding and vectors by denylist+normalize; fonts get `sanitized: true` for free. The flag is then propagated to the renderer via `to_render_asset` → `with_sanitized(self.sanitized)`, advertising a guarantee that was never enforced. The `# Errors` doc ("limits or hash verification fails") is accurate only because no validation exists. → Reject unparseable fonts (check the returned face IDs are non-empty) and/or stop claiming `sanitized` for fonts.
4. **Pixel limit is enforced after the full decode** (`compile_image`, `lib.rs:324`). `verify_bytes` (input size) runs first, but `verify_pixels` runs only after `image::load_from_memory` has decoded the whole image into a pixel buffer. The crate's `max_pixels` (16M) therefore never prevents the allocation it is meant to bound — it only rejects the already-decoded result. See Security for the decode-bomb consequence.

## Code quality & smells

- **Over-broad SVG denylist with false positives** (`validate_vector`, `lib.rs:542`). The blocklist rejects `url(`, `<use`, `href=`, and `xlink:href`. These are pervasive in legitimate SVG: gradient/pattern/clip fills reference paint servers as `fill="url(#grad)"`, and `<use>` is the standard symbol-reuse mechanism. Any such asset is rejected with `asset.vector.unsafe-content`. Worse, the **same denylist is re-run on the normalized output** (`validate_vector(&compiled_payload)` at `lib.rs:380`): usvg legitimately emits `url(#…)` references for resolved gradients/clips, so even an input that somehow passed could be rejected on its own lowered form — a self-inflicted failure. (The denylist is also a security control; see Security for the bypass-fragility angle.)
- **`hex_nibble` masks an index that can never overflow but reads as fragile** (`lib.rs:537`). `HEX[usize::from(value & 0x0f)]` — the `& 0x0f` keeps it in `0..16`, and the caller already masks. Safe, but the double-mask plus raw index (vs. a lookup that cannot panic by construction) is a smell in a `#![forbid(unsafe_code)]` crate that otherwise avoids panicking paths.
- **`AssetGeneration.hash` is write-only dead state** (`lib.rs:497`). Stored and updated but never read (see gap #1). Remove it or make it load-bearing.
- **`to_render_asset` discards `compiled_hash`, `metadata_stripped`, and `vector_lowering`** (`lib.rs:193`). The render record is keyed on the *source* `hash` (`CompiledAsset` carries no payload and no compiled-hash field), and `metadata_stripped`/`path_count` never cross the boundary. This is by design of `CompiledAsset` (reference-by-hash, payload stays in the assets manifest) rather than a bug, but it is an undocumented asymmetry: a consumer cannot tell from the render asset which hash (source vs sanitized) identifies the bytes the renderer will load.
- **`AssetHash::new` accepts any string unchecked** (`lib.rs:68`). Used in tests as `AssetHash::new("sha256:bad")`; a public constructor that bypasses the `sha256:` format and digest. Minor — it is the intended escape hatch for expected-hash inputs — but there is no validation that the string is a well-formed digest.

## Documentation

- Strong: crate-level `//!`, every public type and method documented, and `# Errors` sections on all three fallible entry points (`compile_image`, `compile_vector`, `load_font`). No undocumented public items.
- Misleading in two places tied to the gaps above: `load_font`'s `# Errors` implies validation it does not perform (gap #3), and nothing documents that `cache_generation` is a compile counter rather than a content-version (gap #1). The `sanitized()` accessor doc ("whether the asset was sanitized") is true for images/vectors but vacuous for fonts.

## Testing

- Reasonable breadth for the happy paths: image decode + dimensions + cache_generation==1 + render export; size-limit and hash-mismatch rejection; vector safe-compile + path count + lowered-output assertions + unsafe-content rejection; font load + manifest dedupe.
- **False-confidence test (mirrors the cache bug):** `asset_backend_loads_fonts_and_tracks_cache_invalidation` loads `font-v1` then `font-v2` — **different** bytes/hashes — and asserts `second.cache_generation() > first.cache_generation()`. This passes whether the increment is content-driven or unconditional, so it does **not** test invalidation; it masks gap #1. A test that recompiles **identical** bytes and asserts the generation does *not* advance would expose the defect. The test name overstates the guarantee.
- **Untested font trust boundary:** the same test feeds non-font bytes and treats success as correct — actively asserting the broken behavior in gap #3 rather than catching it. No test exercises a real/invalid font distinction.
- Coverage gaps: no test for the pixel-limit path (`asset.limit.pixels-exceeded`), the WebP encode-failure path (`asset.image.encode-failed`), invalid-UTF-8 vectors (`asset.vector.invalid-utf8`), SVG parse failure (`asset.vector.parse-failed`), or empty lowered output (`asset.vector.empty-output`). The decode-bomb scenario (small input, huge declared dimensions) is untested.

## Security

The trust boundary here is **untrusted asset bytes** (image/SVG/font payloads), *not* `Deserialize`-able input — in contrast to `hawk2ui-a11y`, this crate derives no Serde on its public types, so there is no deserialization attack surface. `#![forbid(unsafe_code)]` holds; there is no `unsafe`.

- **usvg local-file read, gated only by a load-bearing denylist** (`compile_vector` + `validate_vector`). usvg's `default_string_resolver` does `std::fs::read(path)` for `<image>` `href`/`xlink:href` targets (its own docs say local-file access "is allowed by default"). The crate uses `usvg::Options::default()`, where `resources_dir = None`, so `get_abs_path` returns the href verbatim — an **absolute** href such as `/etc/passwd` would be read if it reached the parser. The *only* thing preventing this is `validate_vector` blocking the substrings `<image`, `href=`, `xlink:href`, and `data:text/html` before parse. That denylist is therefore a security control, and it is a fragile one: it is a case-folded `contains` over raw text with no XML/entity awareness, so any spelling that evades the substring set but is still accepted by usvg's parser (entity-encoded attribute names, namespace-prefixed variants the parser normalizes, whitespace tricks) would re-open file read. **Recommend defense-in-depth:** install a custom `ImageHrefResolver` that refuses `resolve_string` (and only allows vetted `data:` images) rather than relying on the denylist alone. **Medium.**
- **Decode bomb — pixel limit is post-decode** (`compile_image`, `lib.rs:324`). `image::load_from_memory` decodes fully *before* `verify_pixels` runs. `load_from_memory` uses `ImageReader` with `Limits::default()`: `max_alloc = Some(512 MiB)` but **`max_image_width`/`max_image_height = None`**. So decode is bounded only by image's 512 MiB single-allocation cap, not by the crate's 16M-pixel limit, which only rejects the already-materialized buffer. A ≤16 MiB compressed input (passes `verify_bytes`) declaring large dimensions can drive an allocation up to image's 512 MiB ceiling per allocation before the crate's limit ever runs. **Recommend** constructing `ImageReader` with explicit `max_image_width`/`max_image_height` derived from `AssetLimits` so the dimension check happens *before* decode. Bounded (~512 MiB), so **Medium**, not High.
- **Unbounded SVG group recursion** (`count_vector_paths`, `lib.rs:591`). Recurses over nested `usvg::Group`s with no depth bound; nesting depth is attacker-influenced via nested `<g>` in a ≤16 MiB SVG. Unlike a11y's High (recursion over a `Deserialize` tree with no upstream bound), depth here is bounded by usvg's own parser limits, so stack-overflow risk is constrained. Worth a depth cap or iterative walk for defense-in-depth. **Low / verify.**
- **Unbounded growth of `manifest` and `generations`** (`AssetBackend`). Both `BTreeMap`s grow with distinct asset IDs and are never drained; a long-lived backend fed many distinct IDs is a slow memory-growth vector. Parallels a11y's unbounded `events`. **Low.**
- **Font bytes accepted and stored verbatim, stamped `sanitized`** (gap #3). Non-font / malformed bytes are not rejected and flow into `fontdb` (downstream `ttf-parser`/shaping consumes them) while the asset is advertised as sanitized. Not a memory-safety issue in this crate (no `unsafe`), but it misrepresents the trust state to downstream renderer/text code. **Medium.**
- **Good:** hashing is a real SHA-256 over the exact bytes with constant-time-irrelevant but correct `verify_hash` (full digest equality before any decode of vectors/fonts); input byte-size limit is enforced first on every path; the WebP re-encode genuinely strips image metadata (decode → raw RGBA → re-encode discards EXIF/ICC/ancillary chunks).
