# Code Review — hawk2ui-cli

**Reviewed at:** `5a042c51` · 2026-05-28 · working tree clean at review time
**Scope:** `src/{main,lib,commands,executor,dev_loop,diagnostics}.rs` + `tests/cli_commands.rs` (6 src files ~3.3k LoC / 1 test file ~0.66k LoC)
**Purpose:** End-user CLI (binary `hawk2ui-cli`) over the Hawk2UI stack: subcommands `new`/`run`/`dev`/`validate`/`build-dev`/`build-release`/`verify-artifact`/`run-desktop`/`package-plugin`/`export-schemas`/`diagnostics`/`explain`, dispatched by `WorkspaceCommandRunner` rooted at a project directory.
**Note:** Codex is concurrently committing hardening/remediation work; HEAD drifts (git HEAD is `5fecf2c4`). Findings reflect the SHA above and may overlap with in-progress fixes.

## Summary

**This CLI is genuinely wired, not a stub** — the real execution path is `WorkspaceCommandRunner` in `executor.rs`, and it drives the actual workspace crates. The two `commands.rs` types the rest of the workspace mis-reads as the CLI (`BuildCommandRunner` + `BuildCommandScenario`) are **recording/test helpers** that return canned results off a 3-value scenario enum (`commands.rs:156-205`); `main.rs` never touches them — it calls `CommandCatalog::parse` then `WorkspaceCommandRunner::execute`. The genuinely-real surfaces are: **build/validate** (`build_workspace`, `executor.rs:822` → `BuildWorkspace::load(...).build(...)` — real TS/JS + style compilation via hawk2ui-build); **the dev file watcher** (`dev_loop.rs::NotifyFileSystemWatcher`, a real `notify::RecommendedWatcher` with parent-directory registration, debounce coalescing, and content-hash re-validation, falling back to hash polling — `change_classifier` maps manifest/style/asset/script/tree changes to patch kinds); **`run-desktop`/`dev --unbounded`** (`WinitDesktopRuntime::run_blocking`/`run_dev_blocking`, `executor.rs:530,637` — a real winit window with Skia software raster per the host-winit review); **schema export** (`schema_catalog_json`, real); **`new`** (writes 6 real scaffold files, `executor.rs:283-305`); and — the key anti-false-positive catch — **desktop entry-script execution** (`entry_script_mount_app_model`, `executor.rs:1330`) runs the compiled entry module through **hawk2ui-script's real boa-backed `ScriptBackend::execute_module`**, *bypassing* hawk2ui-runtime's record-only `RecordingScriptEngine`, and turns the returned JSON node tree into a real `RuntimeViewTree`. There are **no** `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no `unwrap`/`expect`/`panic!` in `src/` (test-only `expect`s aside), and no TODO/FIXME/HACK markers.

The substantive weaknesses cluster in the *gating/verification* subcommands and in how the CLI surfaces its dependencies' known limits. (1) **`verify-artifact` is not a verifier**: it takes no artifact-path argument, *rebuilds the artifact from CWD source*, then checks `ensure_compatible_with(1,0)` (the same version it just built with → always true) and compares `content_hash()` against `hashes.content` of the same in-memory object (tautological); it **never loads a sealed container and never verifies a signature** (`executor.rs:580-612`). (2) **`build-dev` and `build-release` are identical** apart from one output word — both call `build_workspace()` with `ArtifactSchemaVersion::new(1,0)`, **neither signs nor writes any artifact to disk** (output is stdout hashes/counts only) (`executor.rs:272-273,547-561`). (3) **The CLI reads neither `output.verification` nor `output.pipeline`** that `build_workspace` returns, so it inherits hawk2ui-build's decorative `is_release_ready()`/`ensure_release_ready()` gating *and adds no gate of its own* — no subcommand can block a release on a verification rule. (4) **`package-plugin` over-reports**: the adapter set is real, but `materialize()` emits source scaffolds + descriptors + `Info.plist` (per the plugin-adapters review the VST3 factory is a null pointer and even CLAP is an un-compiled scaffold); the CLI prints `verification-status: passed` and the help text claims it packages "CLAP, VST3, AU, and standalone" without surfacing that these are layout scaffolds, not host-loadable binaries (`executor.rs:653-746`). It also discards every real planning/materialization diagnostic message, keeping only the rule (`executor.rs:712-718,993-1005`). No correctness blocker on the build/run-desktop happy path; the defects are in the verification/gating subcommands being modeled-or-tautological and in honesty of the package/verify surface.

## Completeness & implementation gaps

1. **`verify-artifact` does not verify a sealed artifact** (`executor.rs::verify_artifact`, `580-612`). The subcommand name and help ("Verify a sealed artifact") promise verification of an existing artifact, but the implementation calls `build_workspace()` — it **re-compiles from the current working directory's source**, producing a fresh in-memory `SealedArtifact`, and then performs two non-checks against *that* object: `ensure_compatible_with(ArtifactSchemaVersion::new(1,0))` (the artifact was just built at schema `1.0`, so this is always `Ok`) and `expected_hash = output.artifact.content_hash()` compared to `output.artifact.hashes.content` (`content_hash()` recomputes from the same payload, so equality is tautological unless hawk2ui-build's own `from_manifest` is internally inconsistent). It **never reads a `.toml` artifact container, never calls `from_container_bytes`/`from_trusted_container_bytes`, and never invokes `ArtifactSignatureVerifier`** — i.e. the one real signature/integrity machinery in hawk2ui-build is not surfaced at all. There is no path/argument to point it at an artifact (see `commands.rs` arg-parsing below). → Accept an artifact path, load the container, and verify signature + recomputed content/manifest hashes against the *deserialized* bytes.
2. **`build-dev` ≡ `build-release`** (`executor.rs:272-273` dispatch; `547-561` body). Both map to `self.build(profile)` where `profile` is `"development"`/`"production"`, and `profile` is used **only** in the `built {profile} artifact …` output string. The same `BuildWorkspace::build(ArtifactSchemaVersion::new(1,0))` runs for both; there is no debug/release distinction (no optimization flag, no differing schema, no signing on release). **Neither persists an artifact** — the sealed artifact is built in memory and only its hashes/counts are printed; nothing is written to disk. The crate hint asks "does `build-release` actually produce a sealed artifact?" — it produces one *in memory* via hawk2ui-build (real compilation), but does not seal-to-disk or sign, and is byte-for-byte the same work as `build-dev`.
3. **The CLI ignores the build pipeline and verification report entirely** (`executor.rs::build_workspace`, `822-831`). `BuildWorkspaceOutput` carries `pipeline: BuildPipeline` and `verification: VerificationReport`, but **no subcommand reads them** — `build`, `verify_artifact`, `validate`, `diagnostics`, `explain`, `run`, and `dev` all use only `output.manifest` and/or `output.artifact`. `ensure_release_ready()` and `is_release_ready()` are never called anywhere in `src/`. The CLI therefore inherits hawk2ui-build's decorative gating (build review #3/#4: empty phases, vacuously-true report) **and surfaces no gate of its own**: a build that should be release-blocked produces a success exit. (`diagnostics` is "no diagnostics" whenever the build merely *compiles* — `executor.rs:748-753`.)
4. **`package-plugin` reports `verification-status: passed` for a non-loadable scaffold** (`executor.rs::package_plugin`, `731-745`). `PackageAdapterSet::new().plan(...).materialize()` and `plan.verify_materialized(...)` are real calls, but per the plugin-adapters review `materialize()` emits a bundle *layout* (source scaffold, descriptors, `Info.plist`, hash manifest) — the VST3 `GetPluginFactory()` returns `null_mut()`, and even CLAP is an un-compiled source scaffold. `verify_materialized` checks the emitted layout's hash manifest/coverage, **not** that any plugin loads in a host. The CLI prints `verification-status: passed` (`executor.rs:744`) and the help text advertises "Package CLAP, VST3, AU, and standalone targets" (`commands.rs:123`) with no indication that the output is a pre-binary scaffold. This is honest *relative to what materialization does*, but the CLI's wording overstates the artifact's host-readiness. → Qualify the output ("materialized package layout") or gate on a real load check.
5. **`run-desktop`/`dev` execute the project entry script with no execution timeout** (`executor.rs::entry_script_mount_app_model`, `1330-1360`; `entry_script_visible_title`, `1362-1374`). The compiled entry module is run through `ScriptBackend::execute_module` (real boa). The sandbox is good — `HostCallPolicy::deny_all()` + `TimerPolicy::deterministic()` + a fresh context — but per the hawk2ui-script review boa **cannot be interrupted mid-evaluation**, and the CLI sets no wall-clock budget, so a project whose entry script contains `while (true) {}` hangs `run-desktop`/`dev` indefinitely before any window opens. See Security.
6. **Dev error overlay is produced but never reaches the surface.** `DevErrorOverlay::to_desktop_overlay` (`dev_loop.rs:445`) builds a real `DesktopErrorOverlay`, and `DevLoop::run_once` produces overlays on validation failure (`dev_loop.rs:598-602`) — but the executor's live dev path (`dev_live_desktop`, `executor.rs:442-545`) only sends `WinitDesktopReload`s into the runtime; on a rebuild failure it does `eprintln!` and `continue`s (`executor.rs:491-502`), and per the host-winit review `WinitDesktopRuntime` has no channel to set an overlay anyway. So `DevErrorOverlay`/`DevLoopReport::error_overlay` and the bounded-loop `DevLoop` path are **modeled but inert in the live runtime** — the in-window error overlay capability the dev loop advertises does not render. The bounded dev loop (`dev_iteration_limit = Some(_)`) drives a `RecordingReloadTarget` (`executor.rs:416-420`), so even successful reloads in that path are recorded, not applied.
7. **`run` for a desktop+plugin manifest silently only runs desktop** (`executor.rs::run`, `317-335`). `run` checks `has_target(Desktop)` first and returns `run_desktop()`; a manifest with both targets (the default scaffold declares both — `executor.rs:1601-1607`) never reaches the plugin branch. Reasonable default, but undocumented; `explain` does list both follow-up commands.

## Code quality & smells

- **`commands.rs` recording runner is dead relative to the binary.** `BuildCommandRunner`/`BuildCommandScenario`/`BuildCommandResult` (`commands.rs:132-205`) are `pub`-exported (`lib.rs:9-12`) and exercised only by `build_commands_return_...` (tests:221). They are a legitimate recording/conformance fixture, but nothing in the real path constructs them, and their existence is precisely the batch-wide false-positive trap — worth a doc note that they are *not* the execution path. (Not a defect; flagged so a reader does not mistake them for the CLI.)
- **`desktop_runtime_config_from_manifest` is `#[cfg(test)]`-only** (`executor.rs:1084-1095`) yet the production build path uses `desktop_runtime_config_from_build_output`. Fine, but it means the manifest-fallback (no entry script) config-building branch is only ever covered under test, not by an integration run.
- **`runtime_dimension_to_f32` double-checks finiteness** (`executor.rs:1515-1536`): it validates `value.is_finite() && value > 0.0` on the `f64` input, parses to `f32`, then re-validates `is_finite() && > 0.0`. The second guard is defensible (parse can overflow to `inf`), but the duplicated error-construction is verbose; a single post-parse check would do.
- **`json_number_prop` parses via `Number::to_string().parse::<f32>()`** (`executor.rs:1461-1473`) rather than `as_f64()` → cast. Round-tripping through a string to get an `f32` is roundabout and allocates; `value.as_f64()` then a finite/range check is cleaner and avoids locale-free-but-still-stringly parsing.
- **Two path-traversal guards with different rigor.** `read_runtime_asset_bytes` (`executor.rs:1180-1217`) rejects absolute/`..` paths *then* canonicalizes root + target and checks `starts_with` (symlink-safe, reads the canonical `resolved`). hawk2ui-build's own `read_declared_file` (used by `build_workspace`) does its own containment check. The CLI thus validates asset paths twice along different code (manifest→build vs runtime-assets), with the runtime-asset guard being the stricter of the two. Not a bug, but two sources of truth.
- **`package_plugin` plan-error mapping loses information** (`executor.rs:712-718`). Every planning diagnostic is rewritten to the constant message `"plugin package planning failed"`, discarding the adapter's real `diagnostic.message()` and keeping only `rule()`. `package_materialization_diagnostic` (`993-998`) and `package_verification_diagnostic` (`1000-1005`) do the same. A user sees a rule code but not *why*. (Contrast the script/style error mappers at `938-966`, which preserve `diagnostic.message()`.)
- **`event_debug` formats events with `{event:?}`** (`executor.rs:1043-1045`) and `render_patch_plan`/`build_workspace_error_diagnostic` embed `{:?}`/`{error:?}` (`executor.rs:969,1065`, `1538-1542`) into user-facing stdout/stderr. Debug formatting in shipped CLI output is brittle (changes with struct layout) and not localized.

## Documentation

- **Adequate.** Crate-level `//!` on `lib.rs`/`main.rs`/each module; `CommandCatalog::parse` carries `# Errors`; `NotifyFileSystemWatcher::{new,next_changed_files}` and `DevLoop::run_once` carry `# Errors`. `CliCommand`/`CliExitCode`/`CliDiagnostic`/`DevPatchKind`/`DevWatchKind` and their public methods are documented.
- **Misleading where docs/names outrun behavior:** `CliCommand::VerifyArtifact` doc "Verify a sealed artifact" and the help line "verify-artifact  Verify a sealed artifact" describe verification that does not happen (gap #1) — it rebuilds and self-compares. The `package-plugin` help "Package CLAP, VST3, AU, and standalone targets" implies host-loadable outputs (gap #4). `build-dev`/`build-release` help distinguishes "development" vs "production" artifacts though they are identical (gap #2).
- **`executor.rs`'s many free functions are private** (no doc obligation), but `CommandExecution::{success,failure}` are `pub` and documented; the only public fallible item lacking `# Errors` is none observed — `CommandExecution` constructors are infallible.

Reasonable as a release gate, but it is unrelated to CLI behavior and will fail the CLI test suite on a docs reshuffle.

## Cross-cutting conventions (workspace-wide; noted once, not a per-crate defect)

- `crate_name()` plus the `exposes_crate_identity` test follow the workspace pattern (`lib.rs:21-38`).
- **Deviation (Low):** like several siblings, this crate does **not** carry a `*_workspace_filter_marker` test. If conformance gates enumerate per-crate markers, this crate is invisible to them.
- `#![forbid(unsafe_code)]` holds at crate root (`lib.rs:1`, `main.rs:1`). **Deviation (Low):** the crate's own error types are not bridged to `hawk2ui_api::Diagnostic` via `From` — there is no domain `Error` enum here; instead `executor.rs` maps each upstream error (`BuildWorkspaceError`, `ManifestError`, `AssetCompilationError`, `PackageMaterializationError`, `RuntimeSceneError`, …) into a `CliDiagnostic` by hand. `CliDiagnostic` itself does not implement `From<…>` for any upstream error and does not convert to `hawk2ui_api::Diagnostic`. Defensible for a leaf binary, but it means each new upstream error variant must be wired manually (and `build_workspace_error_diagnostic`/`manifest_error_diagnostic` are large hand-maintained matches that can fall out of sync).

## Security

The trust boundaries here are (a) the **project manifest TOML** and **declared source/style/asset files** read from the working directory, (b) the **project entry script**, which the CLI *executes*, and (c) **command-line arguments**. `#![forbid(unsafe_code)]` holds; there is no `unsafe`.

- **The CLI executes untrusted project code with no time budget.** `run-desktop`/`dev`/`run` call `entry_script_mount_app_model` / `entry_script_visible_title` (`executor.rs:1330,1362`), which run the project's compiled entry module through `ScriptBackend::execute_module`. The sandbox is sound: `HostCallPolicy::deny_all()` denies all host calls, `TimerPolicy::deterministic()` removes wall-clock timers, and each execution gets a fresh boa `Context` — so there is **no filesystem/network/ambient-authority escape**, and prototype pollution is per-execution. **But** per the hawk2ui-script review boa cannot be interrupted mid-evaluation and the CLI sets no execution deadline, so a malicious or buggy entry script (`while(true){}`, deep synchronous recursion) **hangs the CLI** before a window opens — a denial-of-service on the developer's own machine. **Medium.** Mitigation: run entry-script execution under a timeout/cancellation budget (or in a watchdog thread that aborts the run).
- **`verify-artifact` provides no integrity guarantee** (gap #1). Because it rebuilds from source and self-compares rather than loading and cryptographically verifying a sealed container, it **bypasses the only real signature/hash verification in the workspace** (`ArtifactSignatureVerifier`, `from_trusted_container_bytes` in hawk2ui-build). A user running `hawk2ui verify-artifact` to check a *received* artifact gets no assurance about that artifact — the command silently verifies a freshly-built local one instead. This both fails to use, and gives false confidence about, the build crate's security gate. **Medium.**
- **Runtime-asset path traversal is guarded** (`executor.rs::read_runtime_asset_bytes`, `1180-1217`). Absolute paths and any `..` component are rejected pre-resolution; the project root and the target are both `canonicalize()`d and `resolved.starts_with(&root)` rejects symlink escapes; the canonical `resolved` path is what is read. This is the stricter of the CLI's two asset-path checks. **Low** (good). The manifest-declared source/style files go through hawk2ui-build's own containment check (build review notes a TOCTOU/non-canonical-read nit there, not in this crate).
- **Node-tree recursion is bounded — not the High-severity class seen in the runtime crate.** `DesktopEntryNode::from_json` (`executor.rs:123`), `append_desktop_entry_children` (`1239`), and `desktop_entry_node_height` (`1296`) recurse over a node tree, but the tree originates from `serde_json::from_str::<serde_json::Value>` (`executor.rs:63`), and serde_json's default `from_str` enforces a 128-level recursion limit (the CLI does not call `disable_recursion_limit`). The JSON itself is the boa-execution result of the entry script, so it is doubly bounded (boa output depth, then serde_json's limit). A deeply-nested mount result is rejected at JSON parse before the CLI's own recursion runs, so this is **not** an unbounded-stack-overflow vector. **Low.** (Recommend an explicit node-tree depth cap regardless, for defense in depth and a clearer diagnostic than a JSON recursion error.)
- **No unbounded file-watch fan-out.** `NotifyFileSystemWatcher` registers only the **parent directories of explicitly watched files** (`dev_loop.rs:325,469-478`) in `NonRecursive` mode — it does not recursively watch the whole project tree, so a project with a huge subtree does not blow up the watch set. Watched files are derived from the manifest (`dev_watched_paths`, `executor.rs:1047-1062`), a bounded set. Snapshot reads (`FileSystemWatcher::snapshot`, `dev_loop.rs:246`) and runtime-asset reads (`fs::read`, `executor.rs:1211`) are **unbounded in size** — a very large declared/watched file is read fully into memory (DefaultHasher over the bytes for the snapshot). **Low** memory-pressure DoS for a dev tool.
- **Command-line argument parsing has no injection surface — and that is also a limitation.** `CommandCatalog::parse` (`commands.rs:90-106`) consumes only argv[1] (the subcommand) and **ignores all further arguments**; there are no flags, paths, or values parsed. So there is no arg-injection/path-from-argv vector — but it is also why `verify-artifact` cannot be pointed at a file and why every command operates on `std::env::current_dir()` (`main.rs:10`). **Low.**
- **No panics-as-DoS in the real path.** No `unwrap`/`expect`/`panic!`/unbounded-length indexing in `src/`; hex-color parsing is length-checked (`executor.rs:1425-1443`); numeric coercions are finiteness-checked. The process exits via `std::process::exit` with mapped codes (`main.rs`), not panics. (`u16::try_from(...).unwrap_or(u16::MAX)` at `executor.rs:1305` is saturating, not panicking.)
- **Package output path is derived from the manifest identity** (`bundle_name`, `executor.rs:1030-1041`) by replacing every non-`[A-Za-z0-9_-]` char with `-`, and outputs go under `self.root.join("target/hawk2ui")`. The sanitizer prevents path separators/traversal in the bundle name. **Low** (good); the underlying file writes are hawk2ui-plugin-adapters' responsibility (its review confirms `is_safe_relative_path` + symlink rejection there).
