# Code Review — hawk2ui-host-baseview

**Reviewed at:** `5a042c51` · 2026-05-28 · **Remediated (contained subset):** 2026-05-29
**Scope:** `src/lib.rs` (1 src file ~2036 LoC) + `tests/baseview_adapter.rs` (~1295 LoC) + `tests/native_parented_smoke.rs` (~157 LoC) + `Cargo.toml`
**Purpose:** Baseview-backed embedded plugin-editor host adapter. Validates DAW-owned parent window handles (Win32 / AppKit / Xlib / XCB / XWayland), bridges them to `raw-window-handle` 0.5 for `baseview::Window::open_parented`, translates native baseview events into `Hawk2UI` plugin-host events, renders runtime scenes through the Skia CPU-raster backend, and presents the resulting pixels into the native X11 child window. Also hosts the CLAP GUI lifecycle bridge (`create`/`set_parent`/`show`/`hide`/`destroy`/parameters/state/realtime visuals) and the text-ABI trampoline that mirrors the generated `hawk2ui_editor_dispatch` vocabulary.
**Note:** This is the only crate that relaxes the workspace `#![forbid(unsafe_code)]` to `unsafe_code = "deny"` (Cargo.toml) so it can implement `raw-window-handle` FFI traits. Findings reflect the SHA above. The High native-presentation bug (#1), the `unsafe`-contract honesty gap (#2), partial native-path coverage (#9), and a spotted dead false-assurance field were **remediated 2026-05-29** — see the Remediation section. The `Choice` state degradation (#3) is **bucket-(c)** (downstream of the plugin `StateValue::Choice` decision).

## Summary

This crate is **genuinely implemented, not a stub** — and the real vs. headless split is important to state up front. There is **one** native, behind-`cfg(target_os = "linux")` backend (`BaseviewX11SkiaFrameHandler` + `present_snapshot_to_x11_window`) that does real work: it opens a real parented child window via `Window::open_parented`, renders a `RuntimeSceneFrame` to a Skia CPU surface, converts the `0x00RRGGBB` snapshot to BGRX bytes, and pushes them into the child window with x11rb `put_image`. The rest of the crate (`BaseviewPluginAdapter`, `BaseviewClapRuntimeEditor`, `BaseviewClapRuntimeEditorHost`, the ABI bridge) is a **state-machine / lifecycle layer** that records events and renders Skia snapshots in-process — it is *not* a fake: `render_scene_frame` calls the real `SkiaRendererBackend`, and the CLAP host genuinely loads & verifies a sealed package via `ClapRuntimeEditorSession::load_from_clap_plugin_path`. So "no native window is opened" in the headless adapter is **by design**, not a stub. There are no `todo!`/`unimplemented!`/placeholder panics and no TODO/FIXME/HACK markers.

The substantive weaknesses are: (1) **a real correctness bug in the native presentation path** — `put_image` uses the *root* window depth, not the depth 32 that baseview actually creates the child with, which will produce an X11 `BadMatch` on the common modern-X-server case (masked because the only test that exercises it is env-gated and never runs in CI); (2) **two `unsafe impl HasRawWindowHandle/HasRawDisplayHandle` blocks** whose soundness rests entirely on prior validation — they are *mostly* sound but the validation has a gap (XCB `connection`/Xlib `display` are checked non-zero as `usize` but their *provenance/liveness* is never re-verified, so a parent destroyed by the DAW is a use-after-free that this crate cannot detect); (3) **lossy `Choice` parameter round-trip** through save/load state; (4) **two parallel event-translation surfaces** (`BaseviewEventTranslator` vs the `PluginHostAdapter` impl) that can diverge; (5) **a fresh X11 connection opened on every presented frame** (`present_snapshot_to_x11_window` calls `x11rb::connect`), which is both a per-frame cost and a second-connection-drawing-to-another-connection's-window design smell. No panic/`unwrap`/`expect` exists on the production paths (good); the `unreachable!`s are all provably unreachable.

## Completeness & implementation gaps

1. **`unreachable!` arms are real but load-bearing on the validator** (`lib.rs:238`, `lib.rs:325`, `lib.rs:357`). `try_from_handle` matches `LinuxWayland => unreachable!("validated above")` because `validate_baseview_parent` rejects Wayland first; the two `raw_window_handle`/`raw_display_handle` arms `unreachable!` for `MacOsNsView`/`MacOsNsWindow`/`LinuxWayland`. These are genuinely unreachable *given the constructor invariant* (the struct can only be built through `try_from_handle`), so they are not stubs. But they are panics reachable from the FFI trait methods if the invariant is ever broken (e.g. a future variant added to `HostPlatformHandle`, or a direct field mutation) — and a panic inside `raw_window_handle` unwinds through baseview's `open_parented` call. See Security. → Prefer returning the `empty()` handle or making the enum non-exhaustive-safe rather than `unreachable!` inside an `unsafe impl`.
2. **`Choice` parameter values do not round-trip through state** (`lib.rs:1711` `state_value_from_parameter` + `lib.rs:1719` `parameter_value_from_state`). Save maps `ParameterValue::Choice(u32)` → `StateValue::Float(f64::from(idx))`; load maps `StateValue::Float` → `ParameterValue::Float`. A `Choice(3)` saved and reloaded becomes `Float(3.0)`, **never** `Choice(3)`. `apply_parameter_value` accepts `Choice` (it is in the `Ok` arm of `validate_parameter_event`), so this is a reachable, silent type-degradation across a save/load cycle. The ABI `save_state`/`load_state` text path (`lib.rs:1662`, `lib.rs:1175`) only emits/parses `Float` bits and silently drops `Bool`/`String`/`Choice` entirely.
3. **`mouse_button_label` collapses all extra buttons** (`lib.rs:512`). `MouseButton::Other(_)` → `"other"` discards the numeric button code, and `Back`/`Forward` are distinct but any `Other(8)` vs `Other(9)` are indistinguishable downstream. Minor fidelity gap in pointer routing.
4. **`drain_realtime_visuals` rejects before draining even when packets are pending** (`lib.rs:1520`). It checks `self.editor … ok_or_else(not_attached_error)?` first; correct for lifecycle ordering, but note the reader is not drained on the error path, so packets pushed by the audio thread before attach are left buffered (acceptable, but undocumented).
5. **`save_state` emits only `Float` over the text ABI** (`lib.rs:1662`). `response_to_host_abi_text` for `StateSaved` iterates `parameter_state` and writes `param.<id>.bits=` **only** for `StateValue::Float`; `Bool` and `String` parameters are silently omitted from the serialized response, so an ABI client cannot observe boolean parameters at all. Combined with (2) this means the text-ABI state surface is float-only in practice despite the typed API accepting `Bool`/`Choice`.

## Code quality & smells

- **Two parallel, divergent event-translation surfaces.** `BaseviewEventTranslator::translate*` (`lib.rs:408`–502) converts *native* baseview events into `PluginHostEvent`s, while the `PluginHostAdapter` impl (`lib.rs:1973`–2025) re-implements host-driven routing (`route_focus`/`route_keyboard`/`route_pointer`/`schedule_repaint`). They share no code and can drift: e.g. the translator emits `HostResize` + conditional `DpiChanged` on resize, whereas `try_host_resize` emits only `HostResize` and `try_dpi_changed` only `DpiChanged`. There is no single source of truth for "a resize happened," so the native path and the host-command path can produce different event sequences for the same logical change.
- **Fresh X11 connection per presented frame** (`lib.rs:1855` inside `present_snapshot_to_x11_window`). Every `on_frame` calls `x11rb::connect(None)`, allocates a GC, `put_image`s, frees the GC, flushes, and drops the connection. This is drawing into a window owned by *baseview's* connection using a *different* connection — it works for `put_image` (server-side drawable) but is wasteful (a full X11 handshake per frame) and is a layering smell; the handler already has access to `window` and could reuse a cached connection/GC. See Security for the depth consequence.
- **`scale_factor_to_f32` double-validates** (`lib.rs:1778`). It checks finite/`> 0`, casts to f32, then re-checks finite/`> 0` on the result. The post-cast check is defensible (overflow → `inf`), but `validate_baseview_metrics` has already gated the same value at every call site, so this is a third validation of the same invariant.
- **`require_nonzero_handle` semantics are pointer-width-dependent** (`lib.rs:1945`). It rejects handles that do not fit `usize` (32-bit targets) — reasonable — but the check `usize::try_from(handle).ok().is_some_and(|v| v != 0)` conflates "fits pointer width" with "non-zero" under one diagnostic rule, so a 64-bit-only handle on a 32-bit build reports `native-parent.invalid` with a message about non-zero rather than width.
- **`BaseviewHostError` exposes `rule()` but not `message()`** publicly (`lib.rs:169`–184). The `message` field is private with no accessor, yet error construction everywhere passes a distinct human message; consumers that fold this into a diagnostic stream can read the rule but not the message without `Debug`. Asymmetric API.
- **`BaseviewClapRuntimeEditorHostAbiBridge` is a ZST with a hard-coded `&'static str` contract** (`lib.rs:1088`). The `abi_contract()` string duplicates the command/response vocabulary that `dispatch_text_inner` matches on; the two can drift (the contract advertises `command=load_state` etc., but nothing asserts the match arms and the string stay in sync).

## Documentation

- Strong: crate-level `//!`, every public type/method documented, and `# Errors` sections on all fallible public fns (`attach`, `try_from_handle`, `open_parented_window`, `try_host_resize`, `try_dpi_changed`, `render_scene_frame`, the whole CLAP host surface, the ABI bridge). No undocumented public items found.
- **`# Safety` is present but thin on the two `unsafe impl`s** (`lib.rs:290`, `lib.rs:331`). The `// SAFETY:` comments correctly state that the parent is validated and pointers are non-zero, but they do **not** address the central hazard for an embedded plugin host: the handles are *borrowed* from the DAW and may be destroyed while `BaseviewNativeParent` (a `Copy` value) still holds their numeric values. The safety contract for `HasRawWindowHandle` is "the handle is valid for as long as the type is alive" — this crate cannot uphold that, and the comment does not acknowledge it. Misleading by omission.
- The headless-vs-native distinction is **not documented anywhere**. A reader of `BaseviewPluginAdapter::render_scene_frame` cannot tell from the docs that it renders in-process without opening a window, whereas `open_parented_window` + `BaseviewX11SkiaFrameHandler` is the path that actually drives a native child. Worth a crate-level note.

## Security

This crate is the **highest memory-safety-risk surface in the workspace**: it implements `unsafe` `raw-window-handle` traits over numeric handles borrowed from an untrusted, separately-lived parent process (the DAW), and it runs editor code (rendering, event translation) inside that host. There are exactly **two `unsafe` blocks**, both `unsafe impl` of marker-ish RWH traits — there is no other `unsafe`, no raw deref, no transmute, no manual `Send`/`Sync` on the threaded handler. Cargo enforces `unsafe_code = "deny"` with `#[allow(unsafe_code)]` only at those two impls (and the crate root `#![deny(unsafe_code)]`).

**Enumeration of every `unsafe` / FFI-relevant site and its soundness verdict:**

1. **`unsafe impl HasRawWindowHandle for BaseviewNativeParent`** (`lib.rs:294`). Builds a `Win32WindowHandle`/`AppKitWindowHandle`/`XlibWindowHandle`/`XcbWindowHandle` from the stored handle. **Soundness: conditionally sound, with a lifetime gap.** The numeric values are correct and the variant selection matches what baseview consumes (verified against `baseview-0.1.1/src/x11/window.rs:129` which reads `h.window` from Xlib/Xcb parents). Construction is gated by `try_from_handle` → `require_nonzero_handle`/`require_xcb_window`, so no zero/oversized handle reaches the trait. **But** RWH's `unsafe` contract is that the handle be *valid for the lifetime of the value*; `BaseviewNativeParent` is `Copy` and holds only integers, so it cannot observe the parent window being destroyed by the DAW. If the DAW tears down the parent between `attach` and `open_parented_window`, baseview will `XReparentWindow`/`put_image` against a dead window — a **use-after-free at the X11/AppKit/Win32 level** that this crate's type system cannot prevent. This is inherent to the embedding model, but the SAFETY comment does not acknowledge it and there is no "parent still alive" revalidation. **Medium.**
2. **`unsafe impl HasRawDisplayHandle for BaseviewNativeParent`** (`lib.rs:334`). Same structure for display handles. **Soundness: same verdict as (1).** The Xlib `display`/Xcb `connection` pointers are reconstituted via `handle_to_ptr` (`handle as usize as *mut c_void`) from a `u64` that was only checked *non-zero and pointer-width-representable* — never checked to be a *live, valid* `Display*`/`xcb_connection_t*`. A caller that fabricates a `HostPlatformHandle::linux_x11(0xDEADBEEF, …)` through the public `BaseviewParentFixture::from_platform_handle` constructor and reaches `open_parented_window` on Linux would hand baseview a **garbage pointer it will dereference**. The non-zero check is necessary but nowhere near sufficient; pointer *provenance* is unverifiable here by construction. **Medium / inherent.**
3. **`unreachable!` inside both `unsafe impl`s** (`lib.rs:325`, `lib.rs:357`) and in `try_from_handle` (`lib.rs:238`). **Soundness: sound today, fragile.** They are unreachable given the constructor invariant, but a `panic!` raised inside `raw_window_handle()`/`raw_display_handle()` would **unwind through baseview's `open_parented`** (a Rust→Rust boundary here, so not immediate C UB, but baseview spawns/owns OS resources and an unwind mid-`open` can leak the colormap/window or poison the event-loop thread). Because these live in the FFI-trait methods, a panic-as-DoS or panic-during-window-construction is the failure mode if the enum invariant is ever violated. **Low (today) / would be High if the invariant breaks.**
4. **X11 `put_image` depth mismatch — runtime `BadMatch`** (`lib.rs:1861`, `present_snapshot_to_x11_window`). `depth` is taken from `connection.setup().roots[screen_number].root_depth` (the **root** window's depth, typically 24). But baseview creates the child window with `visual_depth = 32` whenever the screen exposes a 32-bit TrueColor visual (verified: `baseview-0.1.1/src/x11/visual_info.rs:38` `find_best_visual_config` tries depth 32 first and only falls back to `COPY_FROM_PARENT` if none exists). `PutImage` requires its `depth` argument to equal the target drawable's depth or the server returns a `BadMatch` error → this crate maps it to `baseview.x11-present.put-image-failed` and closes the window. **On the common modern-X case the native presentation path fails at runtime.** Not memory-unsafe (x11rb is checked), but it is a correctness defect on the crate's headline native path, shipped green because the only covering test is env-gated. The correct depth is the child's, obtainable from `Window::raw_window_handle` → `GetGeometry`, or from baseview's negotiated visual. **High (correctness on the real path).**
5. **`screen_number` indexing** (`lib.rs:1861`). `x11rb::connect(None)` returns the *preferred* screen for the **presentation** connection, used to index `roots[screen_number]`. x11rb guarantees `screen_number` is in-range for *that* connection's setup, so the index does not panic — but it is the wrong screen if the parent lives on a different screen than `$DISPLAY`'s default, compounding (4). **Low.**
6. **Audio-thread vs UI-thread discipline.** `WindowHandler::on_frame`/`on_event` run **only** on baseview's event-loop (UI) thread (verified: `baseview-0.1.1/src/x11/event_loop.rs` calls `self.handler.on_frame`/`on_event` inline; `WindowHandler` is **not** `Send`, and `Window`/`WindowHandle` are `!Send`). Realtime data crosses via `RealtimeVisualUiReader` drained by `drain_realtime_visuals`, which is invoked from the host/UI side, not the audio thread. The `Arc<Mutex<Vec<PluginHostEvent>>>` / `Arc<AtomicU64>` in `BaseviewX11SkiaFrameHandler` are the sanctioned cross-thread channel to the *test* thread; the lock is taken on the UI thread only and is never held across a render or an FFI call. **No realtime-thread violation found** — the design correctly keeps all baseview interaction on one thread and never calls a blocking lock or allocator from an audio context within this crate. **Sound.**
7. **`open_parented_window` closure `Send` bound** (`lib.rs:764`). Matches baseview exactly: `B: FnOnce(&mut Window) -> H + Send + 'static`, `H: WindowHandler + 'static`. The `build` closure runs on the freshly-spawned window thread; requiring `Send` on the *builder* (not on `H`) is correct and the crate does not weaken it. **Sound.**
8. **x11rb resource handling in the native path** (`create_x11_gc` / `present_snapshot_to_x11_window`). GC is allocated with `generate_id`, created, used, then `free_gc`'d and `flush`ed. On the **error path** (`put_image` fails) the function returns early **without** `free_gc` — the GC id leaks on that connection. Because the connection is dropped immediately after (per-frame connection, smell #2), the leak is bounded to the dying connection, so it is benign in practice but is a resource-handling gap that would matter if the connection were cached. **Low.**
9. **`handle_to_ptr` truncation on 32-bit** (`lib.rs:1967`). `handle as usize` truncates a 64-bit handle on a 32-bit target; `#[allow(clippy::cast_possible_truncation)]` suppresses the lint. `require_nonzero_handle` already rejects non-`usize`-representable handles before this is reached on the validated path, so the truncation is unreachable for validated parents — but `handle_to_ptr` is also called for the Win32/AppKit arms, which are guarded by `require_nonzero_handle` too, so it is consistent. **Sound given validation.**
10. **Input validation / DoS surface.** The text-ABI parser (`parse_host_abi_*`) is robust: it rejects malformed lines, empty keys, empty commands, non-finite floats, and unknown commands/APIs with structured errors — no `unwrap`. `validate_baseview_metrics` rejects non-finite/non-positive dimensions before they reach Skia or baseview `Size`. `u16::try_from` guards the `put_image` width/height. **No unbounded recursion** (no recursive types here). **Unbounded growth:** `parameter_values` (`BTreeMap`) is bounded by distinct parameter IDs and cleared on create/destroy; `latest_realtime_packets` is replaced (not appended) each drain; `repaint_reasons`/`events` grow until drained but are drained by the host loop. The clearest unbounded item is `repaint_reasons` (`lib.rs:1991` pushes on every `schedule_repaint` and is never auto-capped), a slow growth vector if the host never reads it. **Low.**
11. **Panic-as-DoS in the editor.** Beyond the `unreachable!`s (3), the production paths use `Result` end-to-end with no `unwrap`/`expect`/`panic!` reachable from `on_frame`/`on_event` or the CLAP callbacks. A panic in user scene-rendering would unwind on baseview's window thread; baseview does not install a catch, so a render panic would propagate to that thread's boundary. The crate itself introduces no new panic on these paths (good). **Low.**

**Good, explicitly:** all FFI handle construction is validation-gated; metrics are sanitized before reaching baseview/Skia; the threading model correctly confines all baseview interaction to one non-`Send` thread and crosses to other threads only through `Arc<Mutex>`/atomics that are never held across renders or FFI; the ABI parser is panic-free and rejects malformed input; no `unsafe` beyond the two sanctioned RWH impls; size casts into the X11 protocol are checked.
