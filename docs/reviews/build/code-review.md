# Code Review — hawk2ui-build

**Reviewed at:** `5a042c51` · 2026-05-28 · working tree clean at review time
**Scope:** `src/{lib,artifact,assets,diagnostic,manifest,pipeline,report,workspace}.rs` + `tests/build_contracts.rs` (8 src files ~2.4k LoC / 1 test file ~1.1k LoC)
**Purpose:** Manifest TOML validation, build-pipeline orchestration records, sealed artifacts (ed25519-sha256 signing + schema-versioned containers), asset/package metadata, and verification reports for release gating.
**Note:** Codex is concurrently committing hardening/remediation work; HEAD drifts (git HEAD is `5fecf2c4`). Findings reflect the SHA above and may overlap with in-progress fixes.

## Summary

This crate is **genuinely implemented, not a stub**, and its security-critical core is real. `ArtifactSignatureVerifier::verify` performs **real Ed25519 verification** via `ed25519-dalek` 2.2.0 (`VerifyingKey::from_bytes` + `Verifier::verify`) over a domain-separated `signature_payload_bytes()`; the round-trip test signs with a live `SigningKey` and the tamper test (mutating a signed payload) correctly fails. `ArtifactHash::from_bytes` is a real SHA-256 digest; `SealedArtifact::from_container_bytes` recomputes and checks the content hash; `validate_json`/`json_schema` compile a real `jsonschema::Validator` from a `schemars`-generated schema; `HawkManifest::parse` does real TOML parse + schema validation + semantic validation. **The real build path is also real on two of three compile legs**: `BuildWorkspace::build` drives genuine TypeScript/JS compilation (`hawk2ui_script::ScriptBackend::compile_module_source`) and genuine style compilation (`hawk2ui_style::compile_style_source`), with a canonicalize-based path-traversal guard (symlink-escape test included). There are **no** `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no `unwrap`/`expect`/`panic!` in `src/`, and no TODO/FIXME markers. (The batch-wide `BuildCommandRunner`/`BuildCommandScenario` recording trap does **not** exist in this crate — there is no canned-result runner here at all.)

The substantive weaknesses cluster in three places. (1) **The third compile leg — asset compilation — is record-only**: the crate has no `hawk2ui-assets` dependency, never decodes/sanitizes anything, hardcodes `safe: true`/`sanitization: Clean`/`cache_generation: 1`, and the entire "unsafe asset" rejection branch is **unreachable** on the integrated build path. (2) **The pipeline and verification subsystems are inert/decorative**: `BuildPipeline::production()` builds empty phase records, `build()` calls `ensure_release_ready()` on that empty pipeline *before* doing any work (so it always passes), and the `VerificationReport` it returns only carries package-target rows — no phase ever attaches a diagnostic and no verification rule ever runs, so `is_release_ready()` is *vacuously* true. (3) **An integrity gap**: the signed/content-hashed payload binds only the manifest snapshot **hash field** (`manifest={…hash…}`), never the raw `manifest_snapshot` string, and `from_container_bytes` never re-derives that hash from the string — so the `pub manifest_snapshot` (and `hashes.manifest`) fields are attacker-malleable on a fully signed, verifying artifact. No correctness blocker on the desktop happy path; the defects are in asset-pipeline completeness, the decorative gating subsystems, and snapshot-field integrity.

## Completeness & implementation gaps

1. **Asset compilation is record-only — no decode, no sanitize, no real safety check** (`assets.rs::AssetCompilationPlan::compile_manifest`, `workspace.rs::asset_sources`). On the integrated build path, `asset_sources()` (`workspace.rs:168`) builds every `AssetSource` via `AssetSource::new`, which unconditionally sets `safe: true` and `dimensions: None` (`assets.rs:116-123`). `compile_manifest` then (a) parses the kind, (b) hashes the raw bytes, (c) formats a `cache_key`, (d) derives a `.pack` path, and (e) stamps **constants** `sanitization: AssetSanitizationStatus::Clean` and `cache_generation: 1` (`assets.rs:217,221`). It never decodes the image/vector/font, never validates content, and never strips metadata. Crucially the `if !source.safe { … UnsafeAsset … }` guard (`assets.rs:198`) is **unreachable in any real build** because the only producer of sources (`asset_sources`) always yields `safe: true`; `AssetSource::unsafe_asset()` and `with_dimensions()` exist solely for external adapters/tests. The crate has **no `hawk2ui-assets` dependency** (`Cargo.toml`), so the real decode/sanitize backend reviewed elsewhere in the workspace is simply never invoked here. This is the "records intent, does no real work" pattern sitting on a headline build capability. → Either depend on and call the real asset backend, or document that build-time "asset compilation" is content-hash + path derivation only.
2. **`AssetSanitizationStatus::Sanitized` is a dead variant** (`assets.rs:71`). It is defined but **never constructed** anywhere in `src/`; every compiled asset is `Clean`. It advertises a sanitization capability the build does not perform (a direct corollary of gap #1).
3. **The build pipeline is decorative** (`pipeline.rs`, `workspace.rs::build`). `BuildPipeline::production()` produces ten phase records each with an **empty** `diagnostics` vec. Nothing in `src/` ever calls `with_diagnostic` (grep: only tests do). `build()` calls `pipeline.ensure_release_ready()` (`workspace.rs:72-74`) on the freshly-constructed empty pipeline **before** compiling anything, so it is a guaranteed `Ok(())` — and the pipeline is then handed to the output unchanged. Real failures surface only as `BuildWorkspaceError` returned from the compile helpers; the phase/diagnostic machinery records nothing about them. The pipeline is a static phase-name list, not an orchestrator.
4. **The verification report performs no verification** (`workspace.rs:109-114`). `build()` constructs the `VerificationReport` by folding only `PackageTargetRecord`s over `manifest.targets`. None of the report's `with_invalid_manifest`/`with_unsupported_style`/`with_unsafe_asset`/`with_missing_asset`/`with_undeclared_capability`/`with_target_incompatibility` builders are ever called by `build()`. Consequently the returned report has zero diagnostics and `is_release_ready()` is **always true** by construction — it is a target-listing record, not a release gate. The rich diagnostic surface in `report.rs` is exercised only by a hand-built unit test (see Testing).
5. **`manifest_snapshot` integrity hole** (`artifact.rs::stable_payload_with_signature`, `from_container_bytes`). The hashed/signed payload binds the manifest only as `manifest={self.manifest_snapshot_hash.0}` (`artifact.rs:805-808`) — i.e. the *hash string*, never the raw `manifest_snapshot`. On load, `from_container_bytes` (`artifact.rs:604-641`) recomputes `content_hash()` and checks it, but **never re-derives** `manifest_snapshot_hash` from `manifest_snapshot`, and never checks `hashes.manifest` against the snapshot either. Because both `manifest_snapshot: String` and `hashes.manifest` are `pub` and documented as "the validated manifest snapshot," a tampered artifact can carry an arbitrary snapshot string (and an arbitrary `hashes.manifest`) while still verifying its signature and content hash. Any runtime consumer that reads `artifact.manifest_snapshot` rather than re-validating against the hash trusts attacker-controlled data on a signed artifact. (Capabilities and targets, by contrast, *are* bound directly — `artifact.rs:812-826` — so this is narrowly the snapshot string, not a general payload-integrity failure.) See Security.
6. **`RequireVerifiedSignature` accepts self-asserted "verified" status with no crypto** (`artifact.rs::satisfies_release_policy`, `ensure_signature_policy`). `to_container_bytes(RequireVerifiedSignature)` and `from_container_bytes(…, RequireVerifiedSignature)` only check the signature is *structurally* a 128-char ASCII-hex string with `status == Verified` and the right algorithm label — they perform **no signature verification**. A hand-authored artifact with `ArtifactSignature::verified("ed25519-sha256-v1", "k", <128 hex chars>)` and zero cryptographic validity passes the "release" policy. This is *documented* (`artifact.rs:418-422` tells callers to use `from_trusted_container_bytes`/a verifier for real trust), so it is a **footgun/naming** issue rather than a bypass: the enum variant name `RequireVerifiedSignature` and the `ArtifactSignatureStatus::Verified` label both overstate what was checked, and a caller who reaches for the policy expecting it to mean "verified" gets structural-only enforcement.

## Code quality & smells

- **`read_declared_file` TOCTOU / non-canonical read** (`workspace.rs:180-193`). It canonicalizes `absolute` and checks `resolved.starts_with(&self.root)` for containment, but then reads the **non-canonical** `absolute` path with `fs::read(&absolute)`. The containment decision is made on `resolved` while the read targets `absolute`; between the `is_file()` check, the `canonicalize()`, and the `read()` the path could change (classic time-of-check/time-of-use). Reading `resolved` would at least make the read target match the path that was validated. Low (local-filesystem build tool), but worth tightening in a security-critical crate.
- **Schema is regenerated and recompiled on every call** (`manifest.rs::validate_manifest_schema`/`json_schema`, `artifact.rs::validate_json`/`json_schema`). Each `HawkManifest::parse` rebuilds the schemars schema *and* constructs a fresh `jsonschema::Validator`; `parse` additionally parses the TOML **twice** (once as `toml::Value` for schema validation at `manifest.rs:348`, once as `RawManifest` at `manifest.rs:178`). Correct but wasteful; a `OnceLock`-cached validator and a single parse would be cleaner.
- **No input size bounds anywhere** (`workspace.rs:51` `read_to_string`, `workspace.rs:192`/`asset_sources` `fs::read`). Manifest and asset reads are unbounded; an arbitrarily large declared file is read fully into memory. DoS-adjacent for a build tool (see Security).
- **`cache_generation: 1` is a hardcoded constant** (`assets.rs:221`) labelled "monotonic cache generation format version." It never varies, so it conveys no cache-invalidation signal; only `cache_key` (which embeds the source hash) actually changes with content. Either drop the field or make it load-bearing. (Mirrors the inert-generation smell flagged in the `hawk2ui-assets` sibling review.)
- **`hex_nibble` double-masks** (`artifact.rs:63-66`). `HEX[usize::from(value & 0x0f)]` masks again although `push_hex` already passes `byte >> 4` / `byte & 0x0f`. Safe by construction, but the raw-index-into-array form reads as fragile in a `#![forbid(unsafe_code)]` crate. (Identical smell noted in the assets sibling.)
- **Two hex codecs in the crate.** `artifact.rs` has `push_hex`/`hex_value`/`decode_hex_array`; the test file re-implements `encode_hex` (`tests/build_contracts.rs:38`). Minor duplication; the encoder could be `pub(crate)` and shared.
- **`PackageTarget::as_str` is duplicated** across `report.rs:204-209` and the inline `match` in `artifact.rs:819-822`. Two sources of truth for the same desktop/plugin label.

## Testing

- **Good breadth on the genuinely-real surfaces.** Manifest accept/reject (missing identity, unknown-field schema rejection, duplicate targets/assets/presets, invalid plugin parameters), artifact hashing stability, JSON-schema generation+validation, container serialize/verify/tamper, **real Ed25519 sign→verify round-trip and untrusted-key + post-sign-tamper rejection** (`tests/build_contracts.rs:448-558`), and the real `BuildWorkspace` file→artifact path including TS compilation evidence, unsupported-extension/invalid-TS/unsupported-CSS rejection, missing-source, and a unix symlink-escape `UnsafePath` test. These are real assertions on real behavior.
- **False-confidence around the inert subsystems (mirrors gaps #3/#4).** `pipeline_phases_collect_release_blocking_diagnostics_by_phase` and `build_pipeline_propagates_phase_diagnostics` (`tests:624-660`) **manually inject** diagnostics via `with_diagnostic` — diagnostics the real `build()` never produces — then assert the pipeline reacts. They test the data structure, not the orchestration. `build_workspace_reads_project_files…` (`tests:927-928`) asserts `output.pipeline.ensure_release_ready().is_ok()` and `output.verification.is_release_ready()`; both are **true by construction** (empty pipeline, empty report), so these assertions can never fail and give false assurance that "the pipeline gated the build" and "verification passed." A build that *should* be blocked would still satisfy them.
- **Asset tests assert the record-only behavior as if it were compilation (mirrors gap #1).** `asset_compilation_records_metadata_for_supported_asset_kinds` (`tests:662`) feeds 4-byte non-asset payloads (`b"hero"`, `b"logo"`, `b"font"`) and asserts they "compile" with `sanitization == Clean` — i.e. it asserts that no decoding/validation happens. `asset_compilation_cache_metadata_changes_when_source_changes` only checks `cache_key` differs (driven by the source hash); nothing tests `cache_generation`, and nothing constructs/asserts `Sanitized`. The `UnsafeAsset` path is reachable only because the test calls `AssetSource::unsafe_asset()` directly — it never proves the *build* can reject an unsafe asset.
- **Untested error/integrity paths:** the `manifest_snapshot`/`hashes.manifest` malleability (gap #5) is not probed (no test edits the snapshot string post-sign while preserving its hash); the structural-only `RequireVerifiedSignature` acceptance of a bogus 128-hex signature (gap #6) is not asserted; `validate_json` failure, `json_schema`/schema-compile failure, container `invalid-format`, `decode_hex_array` odd-length/non-hex inputs, and `unsupported-algorithm`/`invalid-public-key` signature branches are uncovered.

## Security

The trust boundaries here are (a) **untrusted artifact-container bytes** subject to signature/hash verification, (b) **untrusted manifest TOML**, and (c) **the local project filesystem** during source/asset discovery. `#![forbid(unsafe_code)]` holds; there is no `unsafe`.

- **Signing/verification is real and correct.** `ArtifactSignatureVerifier::verify` (`artifact.rs:157-202`) checks algorithm, finds the trusted key by `(algorithm, key_id)`, hex-decodes 32-byte key + 64-byte signature with strict length/charset (`decode_hex_array`), builds a `VerifyingKey`, and calls `ed25519_dalek::Verifier::verify` over `signature_payload_bytes()` — a domain-separated payload (`HAWK2UI-ARTIFACT-SIGNATURE-V1\n` magic) computed **without** the signature field, so signing and loading agree. The signing payload binds schema, manifest hash, generator/profile, capabilities, targets, all compiled-script/style/asset records (scripts include a hash of `compiled_source`), and the runtime-scene hash. The post-sign-tamper test (adding a compiled script) correctly fails verification. **No "modeled" or canned crypto** — this is genuine Ed25519. (`signature_payload_bytes` allocates the full payload string; fine at artifact sizes.)
- **Tampered-artifact integrity is mostly enforced, with one hole.** `from_container_bytes` recomputes the content hash and rejects mismatches (the flip-a-bit test passes), and the trusted path additionally verifies the signature. **However**, neither the content hash nor the signature binds the raw `manifest_snapshot` string or the `hashes.manifest` field — both bind only `manifest_snapshot_hash.0` — and `from_container_bytes` never re-derives `manifest_snapshot_hash` from the snapshot (gap #5). A signed, fully-verifying artifact can therefore carry an **attacker-chosen `manifest_snapshot`/`hashes.manifest`**. Whether this is exploitable depends on downstream consumers (not visible from this crate); if any runtime reads `manifest_snapshot` instead of re-validating against the hash, it consumes untrusted data from a "verified" artifact. **Medium.** Mitigation: on load, recompute `manifest_snapshot_hash` from `manifest_snapshot` and reject mismatch (and likewise tie `hashes.manifest`), or bind the raw snapshot into the signed payload.
- **Structural-only release policy is confusable for cryptographic** (`satisfies_release_policy`, gap #6). `RequireVerifiedSignature` enforces only that the signature *looks* like 128 hex chars with `status: Verified`; it does not verify it. Documented, but the naming invites misuse (a caller who serializes/loads with `RequireVerifiedSignature` and skips the verifier ships unverified artifacts that self-report as verified). **Low–Medium.**
- **Manifest TOML parsing of untrusted input is reasonably hardened.** `#[serde(deny_unknown_fields)]` throughout plus a JSON-Schema pass reject unknown sections; semantic validation enforces non-empty fields, stable IDs, duplicate detection, and finite normalized parameter defaults. `toml`/`serde_json`/`schemars`/`jsonschema` carry their own depth/recursion bounds. No custom recursive descent over untrusted manifest data in this crate.
- **Path traversal is guarded** (`workspace.rs::validate_workspace_relative_path` + canonicalize containment). Absolute paths, `..`, and Windows prefixes are rejected pre-resolution; `canonicalize()` + `starts_with(root)` then rejects symlink escapes (covered by the unix symlink test → `UnsafePath`). The residual nit is the TOCTOU / non-canonical read noted in Code Quality (read uses `absolute`, not the validated `resolved`). **Low.**
- **No decompression/size-bomb surface here** — the crate does not decode images/SVG/fonts (gap #1 means asset bytes are only hashed), so the image-decode-bomb class that affects `hawk2ui-assets` does not apply. **But** reads are **unbounded**: `fs::read_to_string` for the manifest and `fs::read` per asset have no size cap, so a large declared file is a memory-pressure vector for the build tool. **Low.** Recommend a configurable max read size.
- **No unbounded recursion or `Deserialize`-driven stack-overflow surface** in this crate's own code: traversals over `phases`, `targets`, `assets`, compiled records, and the keyring are flat iterations. (`runtime_scene: Option<serde_json::Value>` is hashed via `to_string()`, which is deterministic here because serde_json 1.0.150 is built without `preserve_order`, so object keys serialize in sorted `BTreeMap` order — not a determinism bug.)
- **No panics-as-DoS.** No `unwrap`/`expect`/`panic!`/indexing-into-untrusted-length in `src/`; hex decode is length-checked and slice access is bounded by construction.
