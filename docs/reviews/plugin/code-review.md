# Code Review — hawk2ui-plugin

**Reviewed at:** `5a042c51` · 2026-05-28 · **Remediated (contained subset):** 2026-05-29
**Scope:** `src/{lib,parameter,state,automation,editor,format,realtime}.rs` + `tests/plugin_behavior.rs` (7 src files ~1500 LoC / 1 test file ~480 LoC)
**Purpose:** Format-neutral plugin model shared by the VST3/CLAP/AU adapters — typed parameters with range normalization, automation gesture sequencing, editor-embedding lifecycle records, package-format metadata + JSON-schema validation, versioned state/preset envelopes with migrations, and a preallocated realtime visual-data transport (audio-thread → UI-thread).
**Note:** Findings reflect the SHA above. The **High #1 (RT audio-thread allocation)** and the inert RT metrics (#5) were **remediated 2026-05-29** — the realtime transport now carries heap-free POD packets (see the Remediation section). The remaining **Choice/Bool fidelity cluster (#2/#3)** is **bucket-(c)** — it requires the parameter-type/state-format-model decision the project has not made — so it is surfaced for decision, not unilaterally fixed. The earlier contained subset (#4 duplicate-id, #7 group-recursion) was also remediated.

## Summary

This crate is **genuinely implemented, not a stub**: there are no `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, and no `TODO`/`FIXME`/`HACK` markers. The format module performs real `schemars` schema generation + `jsonschema` validation (`format.rs::validate_json`); the automation sequence enforces real gesture-pairing invariants (`automation.rs::push`); the realtime transport is a real `rtrb` lock-free SPSC ring buffer with genuine drop-policy handling; state migrations actually rename parameter keys (`state.rs::migrate`).

The substantive weaknesses cluster in the two areas the crate exists to get right — the **parameter value model** and **realtime audio-thread safety**:

1. The realtime transport advertises "**preallocated non-blocking**" writes, but the packet payload is `Vec<f32>` and the `meter`/`modulation` constructors `vec![value]`, so **every** audio-thread write allocates, and every full/drop path **deallocates a `Vec` on the audio (realtime) thread** — a realtime-safety violation. The `allocation_count`/`blocking_wait_count` accessors that were evidently meant to *prove* this safety are **hardcoded `0`, never incremented** (inert metrics).
2. `ParameterValue::Choice` **cannot be normalized** — `normalize` has no `Choice` match arm (always errors), and `denormalize` **always returns `Float`**, so `Bool`/`Choice` parameters do not survive the host normalize↔denormalize boundary. This — together with `StateValue` having **no `Choice` variant** — is the in-crate root cause behind the sibling host-baseview review's `Choice`→`Float` state degradation.
3. `ParameterModel::validate` checks id *format* but never **duplicate ids**, and `ParameterGroup::find` recurses unbounded over a `Deserialize`-able recursive type.

No correctness blocker on the developer-authored happy path; the defects are in RT-safety honesty, parameter type fidelity, id-uniqueness, and untrusted-input validation.

## Remediation (2026-05-29) — contained subset

Fixed the two findings that are genuine correctness/robustness bugs in **settled** code (no bucket-(c) decision reworks them); surfaced the rest.

- **#4 — parameter-id uniqueness (FIXED).** `ParameterModel::validate` checked id *format* but never *uniqueness*, so two records sharing an id both passed while host automation and `parameter_state` (a `BTreeMap` keyed by id) silently collapsed them — one parameter's value aliasing onto another on load. `validate` now reports a `parameter.id-duplicate` error (once per duplicated id, at its second occurrence). Test: `parameter_model_rejects_duplicate_parameter_ids`.
- **#7 — `ParameterGroup::find` recursion (FIXED, defense-in-depth).** Rewrote the recursive search as an iterative pre-order walk over an explicit work stack (children pushed reversed to preserve order), so a deeply nested group tree cannot overflow the call stack on the search path. Same DoS class bounded in `hawk2ui-runtime`/`-a11y`/`-script`. **Honest scope:** the trust boundary here is developer-authored plugin metadata (not a disk/DAW artifact — the untrusted-from-disk `PluginPreset`/`PluginStateEnvelope` are not recursive), and `serde` deserialize/drop of a `ParameterGroup` tree still recurses; this closes the search-path site the review named, not the whole class, which is proportionate to the Low severity. Existing `parameter_model_validates_stable_ids_and_group_nesting` confirms the rewrite preserves find behavior.

**Surfaced as bucket-(c) (NOT fixed — require a project decision):**
- **#1 (High) RT allocation + #5 inert metrics + #8 split-writer policy.** `RealtimeVisualPacket { values: Vec<f32>, channel_id: String }` heap-owns per packet, and `analyzer`/`scope` payloads are arbitrary-length (FFT bins / scope samples), so this is **not** a trivial `Vec`→array swap. RT-safety requires a bounded packet representation, a **max-sample-count capacity decision**, and a write-into-preallocated-slot API (replacing push-by-value) — plus deciding the `channel_id` representation (interned index vs fixed buffer). The inert `allocation_count`/`blocking_wait_count` (#5) become unnecessary once allocation is impossible by construction, and the split-writer `DropOldest` degradation (#8) is resolved by the same redesign. This is the crate's headline finding and the right thing to build — but it is a realtime-architecture decision, not a contained edit.
- **#2 / #3 (Medium) Choice/Bool round-trip fidelity.** `Choice` is half-wired (no `ParameterRecord::choice()` constructor, no `StateValue::Choice` variant, no choice-label model), and `denormalize` is type-blind (always returns `Float`). Making `Bool`/`Choice` round-trip requires extending the parameter-type model (choice cardinality, a value-kind discriminator) and the **state/preset wire format** (`StateValue::Choice`), which ripples into the `hawk2ui-host-baseview` adapter's `Choice(v) => StateValue::Float(...)` coercion (`lib.rs:1714`). That is a model + format-compat decision, deferred to the same batch.

**Deferred (Low, unchanged):** #6 `Deserialize` bypasses constructor clamps (NaN/out-of-range; defense-in-depth via `deserialize_with` or post-deserialize `validate`); #10 cross-cutting (inconsistent id rules `is_stable_id` vs `is_reverse_dns_id`; only `AutomationEventError` bridges to `Diagnostic`; no `*_workspace_filter_marker` test).

## Completeness & implementation gaps

1. **`Choice` parameters cannot be normalized** (`parameter.rs:298` `ParameterRecord::normalize`). The match covers only `(Some(range), Float)` and `(None, Bool)`; `ParameterValue::Choice(_)` falls into the `_ => Err("parameter value type is incompatible")` arm. A discrete-choice parameter (the natural use for `Choice`) can therefore **never** be converted to a host-normalized value. `Choice` is in fact a half-wired variant: there is **no `ParameterRecord::choice()` constructor** (only `numeric`/`boolean` exist, `parameter.rs:194,216`), so `Choice` appears only in the enum def (`parameter.rs:13`) and in `display_value` (`parameter.rs:322`) — never produced by `denormalize`, never accepted by `normalize`, and (per gap #3) with no `StateValue` representation.
2. **`denormalize` collapses every parameter to `Float`** (`parameter.rs:275`). It returns `Ok(ParameterValue::Float(value))` unconditionally — a boolean or choice parameter denormalized from the host yields `Float`, not `Bool`/`Choice`. Worse, it requires `self.range` (`ok_or_else("parameter has no numeric range")`), and `ParameterRecord::boolean` sets `range: None` (`parameter.rs:226`) — so **boolean parameters cannot denormalize at all** (they error), while `normalize` *accepts* them via the `(None, Bool)` arm. The pair is asymmetric: `Bool` normalizes but cannot denormalize; `Choice` does neither. A `Bool → normalize → denormalize` round-trip is impossible; this is the type-degradation root the crate hint points at.
3. **`StateValue` has no `Choice`/integer variant** (`state.rs:9`: `Float | Bool | String`). The state/preset model cannot represent a choice index, so any adapter persisting a `Choice` parameter is *forced* to coerce it to `Float` (confirmed downstream at `hawk2ui-host-baseview/src/lib.rs:1714` `Choice(v) => StateValue::Float(f64::from(v))`). The `Choice`→`Float` state degradation the sibling review found is rooted in this missing variant. (The `Bool`-dropped-on-save in that review is the *adapter's* serializer bug at baseview:1664, not this crate — but the model offers no `Choice` round-trip path either way.) Note: the coercion is not a *precision* loss — every `u32` is exactly representable in `f64` — it is a **type/semantic-identity** loss.
4. **No parameter-id uniqueness check** (`parameter.rs:424` `ParameterModel::validate`). It validates id *format* (`is_stable_id`) and group references per-parameter but never detects **duplicate ids**. Two records sharing an `id` both pass validation, yet host automation and `parameter_state` (a `BTreeMap` keyed by id, `state.rs:78`) collapse them — silent state/automation aliasing. The crate's job is "parameter ID stability/uniqueness"; uniqueness is unenforced.
5. **`allocation_count` / `blocking_wait_count` are inert** (`realtime.rs:186-187,263-264`). Initialized to `0`, exposed via `const fn` accessors (`realtime.rs:208,214,349,355`), and **never incremented anywhere** in the crate. The docs call them "allocation count *observed* in audio-thread writes" / "blocking wait count *observed*" — they observe nothing; they are canned `0`. They appear designed to demonstrate the RT-safety guarantee and instead assert it by fiat. Tests assert `== 0`, which is trivially true and masks that nothing is measured.
6. **Split-writer `DropOldest` silently degrades to `DropNewest`** (`realtime.rs:360` `push_without_waiting`). A `RealtimeVisualAudioWriter` created with `FrameDropPolicy::DropOldest` cannot pop (it does not own the consumer), so both policy arms `=> rejected_with_drop()`. The `drop_policy` field is stored and accepted but ignored for split writers; the doc comment (`realtime.rs:193`) acknowledges the limitation, but the API still lets callers request a policy it cannot honor rather than rejecting it at construction.

## Code quality & smells

- **`denormalize` step math is safe but opaque** (`parameter.rs:285-289`). It computes `index / max_index.max(1.0)`. The `.max(1.0)` guards division: for `steps == 1` (and the validate-rejected `steps == 0`), `saturating_sub(1)` gives `max_index == 0.0`, so the divisor is `1.0` and the result is `range.min` — no division by zero. The behavior is correct, but the interaction of `saturating_sub(1)`, `round()`, and `.max(1.0)` is unobvious and is **untested at the boundaries** (`steps == 1`); a direct `steps`-boundary test is absent. Readability note, not a correctness bug.
- **Inconsistent id rules across modules.** `is_stable_id` (`parameter.rs:484`) requires ASCII *lowercase*; `is_reverse_dns_id` (`format.rs:288`) permits mixed-case alphanumerics. Two different "stable identifier" notions in one crate; neither is documented as the canonical rule.
- **`display_value` for `Choice` emits the raw index** (`parameter.rs:322`): `Choice(3)` → `"3"`. There is no choice-label model anywhere, so generated editors/hosts show numeric indices instead of names for discrete parameters.
- **`denormalize` `# Errors` is incomplete** (`parameter.rs:271-274`). Doc says it errors only "when the parameter has no numeric range," but it also errors on non-finite `normalized` (`parameter.rs:280`) and on `range.validate()` failure (`parameter.rs:279`). Two of three error conditions are undocumented.
- **`StateMigration` only supports `RenameParameter`** (`state.rs:160-163`). `StateMigrationKind` is a private single-variant enum; type/format migrations (e.g. a parameter that changed from `Bool` to `Choice`) cannot be expressed. Adequate for today, but the migration framework is thinner than the "versioned state envelope" framing implies.
- **No monotonicity check on migration `to_version`** (`state.rs:154`: `self.version = migration.to_version`). The caller-supplied `to_version` is trusted; a migration may set a *lower* `to_version`, after which the loop's `from_version != self.version` guard (`state.rs:138`) misfires on the next migration. Minor; migrations are developer-authored.

- Misleading in three places tied to gaps above: `denormalize`'s `# Errors` (gap, see smells); the realtime `allocation_count`/`blocking_wait_count` docs claim *observed* counts they never compute (#5); and the `RealtimeVisualAudioWriter::audio_thread_push` doc describes drop behavior that contradicts the `DropOldest` policy a caller may have set (#6).
- `denormalize`/`normalize` carry no note that `Bool`/`Choice` are not round-trippable (#1, #2) — the docs read as if all `ParameterValue` variants are supported.

## Security

The trust boundaries here are (a) **untrusted preset/state bytes** — `PluginPreset`, `PluginStateEnvelope`, `ParameterModel`, `AutomationEvent`, etc. all derive `Deserialize` and are the artifacts a DAW/disk hands back; and (b) the **audio (realtime) thread**, where allocation/deallocation and panics are correctness hazards. `#![forbid(unsafe_code)]` holds; there is no `unsafe`.

- **Allocation and deallocation on the audio thread** (`realtime.rs`). `RealtimeVisualPacket.values: Vec<f32>` (`realtime.rs:36`); `meter`/`modulation` build packets via `vec![value]` (`realtime.rs:46,76`). The audio-thread write path therefore **allocates per packet**, and on a full ring the `DropOldest` branch pops and **drops a `Vec` on the audio thread** (`realtime.rs:308`), as do the `Full(_)`/`Full(packet)` paths (`realtime.rs:311,314,367`) when the returned/rejected packet is dropped by the caller on that thread. This directly violates the crate's stated "preallocated non-blocking" guarantee (allocator calls can block / are not realtime-safe). The inert `allocation_count`/`blocking_wait_count` (#5) were the intended proof of this property and instead conceal its absence. **This is the highest-severity item.** Mitigation: a packet payload that is itself preallocated/inline (e.g. fixed-capacity buffer or an arena owned outside the RT thread), and never dropping `Vec`-bearing packets on the audio thread. *(Affirmative: the RT path has no `panic!`/`unwrap`/`expect` — the hazard is allocation, not a panic-DoS.)*
- **`Deserialize` bypasses constructor clamps** (`automation.rs:31-41`, `parameter.rs:6-14`). `AutomationEvent.normalized_value` is a `pub Option<f64>` and the struct derives `Deserialize`, so a value deserialized from disk/DAW can carry `Some(NaN)` or `Some(5.0)` despite `value_change`/`host_update` clamping to `0..=1`. Likewise `ParameterValue::Float(f64)` accepts `NaN`/`Inf` on deserialize; `denormalize`/`normalize` guard finiteness, but any consumer reading `normalized_value`/`Float` directly gets the unclamped/non-finite value. Constructors validate; the deserialize path does not. Recommend `#[serde(deserialize_with = …)]` clamping or a post-deserialize `validate()`.
- **Unbounded recursion over a `Deserialize`-able recursive type** (`parameter.rs:367` `ParameterGroup::find`; type `parameter.rs:339-347`, `children: Vec<ParameterGroup>`). Same *class* as `hawk2ui-a11y`'s High. `ParameterModel::group_path` → `find` recurses with no depth cap; `ParameterGroup` derives `Deserialize`, so a deeply nested group tree from untrusted input overflows the stack. **Lower severity than a11y's**, because a `ParameterModel` is developer-authored plugin metadata, not a DAW/disk artifact (the untrusted-from-disk types — `PluginPreset`/`PluginStateEnvelope` — are *not* recursive). Still worth a depth bound or iterative walk for defense-in-depth. **Low / verify trust boundary.**
- **`HostStateChunk.bytes: Vec<u8>` and `RealtimeVisualPacket.values: Vec<f32>` are unbounded on deserialize** (`state.rs:58`, `realtime.rs:36`). A hostile preset/state blob can declare arbitrarily large vectors; there is no length cap before allocation. Bounded in practice by the outer JSON size, so **Low**, but pairs with the RT-allocation theme.
- **No id-uniqueness enforcement** (#4) is also a state-integrity issue: duplicate parameter ids alias silently in `parameter_state`, so a crafted model + state can cause one parameter's value to overwrite another's on load. **Low/Medium** depending on whether models are ever sourced from untrusted input.
- **Good input validation where present:** `ParameterRange::validate` rejects non-finite/inverted/out-of-range defaults; `ParameterSmoothing::validate` rejects negative/non-finite durations; `RealtimeVisualFrameGate::new` bounds `target_hz` to `1..=240`; `scaled_physical_dimension` (`editor.rs:48`) clamps non-finite/overflow to safe `u32`; `format` validation is real schema + field checks. `migrate` rejects version mismatch. Serde round-trips are derive-correct (no custom (de)serializers to get wrong).
