# Code Review — hawk2ui-style

**Reviewed at:** `5a042c51` · 2026-05-28 · working tree clean at review time
**Scope:** `src/{lib,compile,property,runtime,selector,token}.rs` (6 src files ~2.5k LoC) + `tests/style_compile.rs` (~855 LoC)
**Purpose:** Typed style subsystem for `Hawk2UI` — a typed property registry with per-property value-type/unit/inheritance metadata, a supported selector subset, design tokens (color/spacing/radius/typography/motion/preference-hook) with theme variants, a CSS→typed-record compiler over `lightningcss`, and a runtime style table that performs selector matching, the cascade (specificity + source order), inheritance, token/theme/preference resolution, and table-diff invalidation.
**Note:** Codex is concurrently committing hardening/remediation work; HEAD drifts (git HEAD is `5fecf2c4`). Findings reflect the SHA above and may overlap with in-progress fixes.

## Summary

This crate is **genuinely implemented, not a stub**, and it is materially different from the framework adapters that were found to be substring scanners. There is no `todo!`/`unimplemented!`/`unreachable!`, no placeholder panic, and no TODO/FIXME/HACK marker anywhere in `src/`.

**Is the CSS compiler a real parser? Mostly — it is a hybrid.** Structural parsing is real: `compile_style_source` (`compile.rs:240`) calls `lightningcss::stylesheet::StyleSheet::parse` with `ParserOptions::default()`. I confirmed against lightningcss 1.0.0-alpha.71 that `error_recovery` defaults to `false` (`parser.rs:71`, bool default), so a malformed rule or declaration makes `StyleSheet::parse` return `Err` (`stylesheet.rs:195`, `declaration.rs:86`) — invalid CSS is genuinely rejected (`style.syntax.invalid`), not scanned. Unknown property *names* parse into lightningcss's `Property::Custom`/`Unparsed` variants (`properties/mod.rs:715`/`724`), round-trip through `to_css_string`, and are then rejected by the typed registry's `metadata()` lookup (`style.property.unknown`). Selectors are serialized back from the parsed AST and re-parsed by a hand-written subset parser. So tokenization, rule/at-rule structure, comment handling, and selector structure are all real.

**Where it stops being a real parser: value-level parsing.** After lightningcss parses each declaration, the compiler serializes the *value* back to a string (`Property::to_css_string`) and re-parses it with hand-written `strip_prefix`/`split`/`contains` helpers (`parse_px`, `parse_color`, `parse_token_ref`, `parse_expression`, the grid parsers). This is where the "silently accepts unsupported values" defects live: keyword properties (`display`, `overflow`) accept **any** `[a-zA-Z-]` string (`is_keyword`, `compile.rs:443`), and `box-shadow`/`transform` accept **any** non-empty string without `{`/`}`/`;` (`parse_expression`, `compile.rs:609`). These two value families are effectively unvalidated beyond a character-class gate.

The runtime side is real and reasonably careful: `compute_for_tree` (`runtime.rs:338`) materializes every registered property on every node via specificity+source-order cascade, inheritance, and registry initials; `resolve_token_reference` (`runtime.rs:540`) follows preference-hook chains with a depth-16 cycle guard; `diff_from` (`runtime.rs:374`) produces a real per-node invalidation set. Token cycles cannot stack-overflow.

## Completeness & implementation gaps

1. **Keyword properties accept any well-formed identifier** (`is_keyword`/`parse_value`, `compile.rs:427`,`443`). `display` and `overflow` are `ValueType::Keyword`. `parse_value` accepts the value if every char is ASCII-alphabetic or `-`, builds `StyleValue::Keyword(raw)`, and `registry.validate` only checks the value *type* matches (`Keyword == Keyword`) — there is **no enumerated keyword set**. So `display: wobble`, `overflow: banana`, `display: inline-grid` all compile to valid typed declarations and flow into the runtime table and on to layout/render. The registry tracks `unit_handling`/`group`/`requirements` per property but never an allowed-keyword list. This is the canonical "CSS subset that silently accepts unsupported values" defect, on two layout/render-driving properties.
2. **`box-shadow` and `transform` values are essentially unvalidated** (`parse_expression`, `compile.rs:609`). The only checks are non-empty and absence of `{`, `}`, `;`. `transform: not-a-transform`, `box-shadow: 0 0 lol`, `transform: rotate(())` all compile to `StyleValue::Transform`/`Shadow` carrying the raw string verbatim. There is no grammar for transform functions or shadow components; the typed value is a stringly-typed passthrough that defers all meaning to a downstream consumer. For a crate whose job is "typed style properties," two render-critical properties are typed only as opaque strings.
3. **`from_style_refs*` silently resolves class selectors only** (`runtime.rs:398`, `from_style_refs_with_value_map`). Each ref is looked up as `format!("class({style_ref})")`. The public API is named/documented as "style references" with no hint that element/id/state/combinator rules are unreachable through it. A ref naming an element or id rule yields `runtime-style.ref.missing` even though the rule compiled successfully — a silent capability gap, not an error in the rule.
4. **Preference-hook resolution is asymmetric across the three resolver entry points** (`runtime.rs:502`,`515` vs `540`). `compute_for_tree` (env path) follows `PreferenceHook → target` recursively and returns the concrete value. But `from_style_refs_with_tokens` / `from_style_refs_for_theme` call `resolve_runtime_value`/`_for_theme`, which do **one** hop and then `token_to_style_value(PreferenceHook(target))` returns `StyleValue::TokenRef(target)` — an **unresolved** token reference left sitting in a table that is documented to contain "renderer-ready typed runtime values." Same token, two different runtime representations depending on which API the caller used.
5. **`resolve_for_theme` theme-name validation is misordered / near-dead** (`token.rs:303`). It finds the variant by name *first* (returning `theme.missing` if absent), and only *then* runs `is_valid_identifier(theme)`. Because `with_theme`/`with_token` never validate the variant name at insertion, the `theme.name.invalid` branch is reachable only if a variant with an invalid name was already inserted (and then queried by that same invalid name) — otherwise an invalid theme name falls through to `theme.missing`. The validation is both out of order relative to the lookup and effectively unreachable on the normal path.

## Code quality & smells

- **Serialize-then-substring-reparse is the core architectural smell** (`compile_declarations`, `compile.rs:323`). The compiler has a fully parsed lightningcss `Property` in hand and discards it: `property.to_css_string(false, …)`, then `split_once(':')`, then hand-rolled value parsing. lightningcss already has typed `Property`/value ASTs (e.g. `Property::Opacity`, `Property::Color`, length/`grid-*` values) that would give exact, spec-correct value parsing for free. Re-deriving units/colors/grid from the serialized string is the source of findings #1 and #2 and is fragile against lightningcss serialization changes (e.g. the shadow test already asserts a *normalized* `"0 8px 24px #00000059"` string — proving the value is taken post-serialization, not as authored).
- **Duplicated diagnostic boilerplate across five modules.** `StyleCompileDiagnostic`, `SelectorDiagnostic`, `TokenDiagnostic`, `RuntimeStyleDiagnostic` are byte-for-byte identical `{rule, message}` structs with identical `new`/`rule`/`message`. Only `SelectorParseError` bridges to `hawk2ui_api::Diagnostic`; `Token`/`RuntimeStyle`/`StyleCompile` errors do **not** (see conventions). A single shared diagnostic type would remove ~120 lines and unify the `From<…> for Diagnostic` story.
- **`contains_unsupported_function` mixes `starts_with` against an already-trimmed value** (`compile.rs:407`). It guards `rgb(`/`rgba(` by prefix but is only a *diagnostic-classification* helper (the real accept/reject already happened in `parse_value`); a value like `rgb (…)` or leading whitespace would misclassify the error rule. Cosmetic (affects diagnostic `rule` only), but it is logic that exists solely to label an already-decided failure.
- **`has_unsupported_unit` for `Length` keys off "contains any alphabetic char"** (`compile.rs:419`). `0` is special-cased; anything else with a letter is "unit". This is again only error-classification, but it means `font-size: abc` is reported as `style.unit.unsupported` rather than `style.value.unsupported` — a slightly misleading rule code.
- **Magic depth limit `16`** (`resolve_token_reference`, `runtime.rs:546`) is undocumented and emits `runtime-style.token.cycle` for any chain deeper than 16, conflating "genuine cycle" with "legitimately deep preference chain." Low impact (deep hook chains are unusual) but the rule name overstates the cause.
- **`compute_for_tree` is O(nodes × properties × rules)** with linear `find` for every node/property/parent lookup (`runtime.rs:347`, `RuntimeStyleTable::set_value`/`typed_value` are `Vec` scans). Fine for editor-sized trees; not a correctness issue, but the "runtime style table" is a `Vec<(PropertyId, StyleValue)>` with string-compare lookups rather than a map, so hot-path resolution is quadratic-ish. Worth noting given the crate is positioned for live runtime use.
- **`try_with_raw_value` always errors** (`runtime.rs:444`). This is intentional (a typed-only boundary that documents itself and is tested), so it is **not** an inert stub — it is a deliberate rejection API. Called out here only to record that I confirmed it is by-design, not an unfinished method.

## Documentation

- Strong overall: crate-level `//!`, every public type/method documented, `# Errors` on every fallible public fn (`compile_style_source`, `PropertyRegistry::validate`, `TokenSet::resolve`/`resolve_for_theme`, all `RuntimeStyleTable::from_*`/`compute_for_tree`, `RuntimeStyleTree::with_child`). No undocumented public items.
- **Misleading docs tied to gaps above:** `from_style_refs*` docs say "ordered style references" with no mention that only class selectors resolve (#3); the `_with_tokens`/`_for_theme` docs promise "renderer-ready typed runtime values" but can leave an unresolved `TokenRef` for preference hooks (#4). `StyleSubsetReference::production` advertises an exact, machine-readable subset (`functions() == ["rgb()","rgba()","token()"]`, etc.) yet the compiler accepts arbitrary `transform()`/`box-shadow` content and arbitrary keywords — the advertised subset is narrower than what actually compiles (#1, #2).

## Testing

- **Good breadth on the happy path and structural rejection.** Tests cover: registry families/defaults/inheritance/units/requirements; selector accept + reject with exact diagnostic rules; token resolution incl. invalid name/length and theme override + missing; CSS lowering of font-size/color/duration/shadow/transform; unitless-zero; the full grid longhand set; rejection of shorthands, `1rem`, `var()`, `@keyframes`, `@media`, unknown property, negative length, and `repeat(3,1fr)`; runtime ref precedence, token/theme resolution, missing ref/token, cascade+inheritance+initials across a real tree, preference override + invalidation diff, and the raw-value rejection.
- **False-confidence / coverage gaps that mask the findings above:**
  - **No test rejects a bogus keyword.** `display`/`overflow` are only ever fed valid keywords; nothing asserts that `display: wobble` fails — and it does **not** fail (#1). The suite would pass identically if keyword validation were a no-op, which it essentially is.
  - **No test rejects a bogus `transform`/`box-shadow`.** Only well-formed values are exercised; `transform: garbage` compiling (#2) is never probed.
  - **Preference-hook asymmetry untested.** `from_style_refs_with_tokens` is never given a preference-hook-backed declaration, so the unresolved-`TokenRef` leak (#4) is invisible; the only preference resolution test goes through `compute_for_tree`.
  - **`from_style_refs` class-only limitation untested** (#3): refs are always class names, so the silent inability to reference element/id rules is never surfaced.
  - **Theme-name validation untested** (#5): no test resolves a theme with a syntactically invalid name, so the misordered/dead `theme.name.invalid` branch is never hit.
  - No test for the token depth/cycle guard (`runtime-style.token.cycle`) — the one genuinely security-relevant guard in the crate has zero coverage.

## Cross-cutting conventions (workspace-wide; noted once)

- `crate_name()` + the `exposes_crate_identity` test follow the workspace pattern; `#![forbid(unsafe_code)]` is present. (Per instructions, not reported as issues.)
- **Deviation (Low):** the crate carries no `*_workspace_filter_marker` test (same deviation noted in the assets review). If conformance gates enumerate per-crate markers, this crate is invisible to them.
- **Deviation (Low):** only `SelectorParseError` implements `From<_> for hawk2ui_api::Diagnostic` (`selector.rs:57`). `StyleCompileError`, `TokenError`, and `RuntimeStyleError` carry the same `{rule,message}` shape but provide **no** bridge to `hawk2ui_api::Diagnostic`, so compile/token/runtime failures cannot be folded into the unified diagnostic stream without a manual adapter — inconsistent with the workspace's error→`Diagnostic` convention and with this crate's own selector path.

## Security

Trust boundary: **author-provided CSS source and token/selector strings** parsed at build/edit time (`compile_style_source`, `Selector::parse`, `TokenSet::*`). There is **no `Deserialize` surface** in this crate — all inputs arrive as `&str` or via builder calls, so there is no Serde attack surface (contrast the a11y crate). `#![forbid(unsafe_code)]` holds; no `unsafe`.

- **Unbounded recursion — bounded in practice (verify).** The only recursive paths are `resolve_token_reference` (preference-hook chains, `runtime.rs:540`) and `RuntimeStyleTree::ancestors`/`parent_entry` (`runtime.rs:170`). The token recursion is explicitly depth-capped at 16, so a preference-hook **cycle** (`a→b→a`) terminates with `runtime-style.token.cycle` rather than overflowing — I traced this and it holds; the other two resolver entry points do a single hop and cannot loop. `ancestors` walks parent links iteratively (a `while let` loop, not recursion) but has **no cycle/visited guard**; today `with_child` only attaches to existing parents and forbids duplicate IDs, so the parent graph is acyclic by construction and the loop is bounded by node count. Still, `ancestors` would infinite-loop if a parent cycle were ever introduced (e.g. a future mutation API). **Low / verify** — add a visited-set or depth cap for defense-in-depth.
- **Parser robustness delegated to lightningcss.** Tokenization and structural parsing of untrusted CSS run through lightningcss; deeply nested selectors/blocks are bounded by lightningcss's own recursion limits, and `error_recovery=false` means malformed input errors out rather than being scanned. No raw-string DoS vector was found in this crate's own parsing (the hand-written value parsers are all single-pass `strip_prefix`/`split`, no backtracking, no regex).
- **Numeric parsing is NaN/inf-safe where it is validated.** `parse_px` → `f32::parse` then `registry.validate` rejects non-finite/negative lengths (`property.rs:292`); `"NaNpx"`/`"infpx"` are rejected. `opacity` is range-checked to `0.0..=1.0` (`property.rs:299`). `parse_seconds`/`parse_ms` clamp through `u32::parse` so out-of-range durations return `None` rather than overflowing or panicking. **No panic-as-DoS found in numeric parsing.** Minor gap: a finite-but-absurd `font-size: 1e30px` passes validation (finite, ≥0) and flows downstream as `LengthPx(1e30)`; bounding is left to layout.
- **Unbounded allocation is input-proportional, not amplifying.** `parse_grid_track_list` (`compile.rs:466`) and the runtime tables grow with input size but do not amplify it; `RuntimeStyleTable`/`RuntimeStyleTree` are `Vec`s with no eviction, so a very large authored stylesheet/tree yields proportional memory. **Low** (build/edit-time, author-controlled input).
- **No untyped escape into the runtime table.** `try_with_raw_value` deliberately rejects raw strings (`runtime.rs:444`), and `compute_for_tree`/`from_style_refs*` only insert values that passed compile-time typing — the runtime boundary is genuinely typed-only. Good.
