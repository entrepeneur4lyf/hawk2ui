# Code Review — hawk2ui-plugin-adapters

**Reviewed at:** `5a042c51` · 2026-05-28
**Scope:** `src/lib.rs` (1 src file, ~3615 LoC, of which the two generated-source string templates are ~1060 + ~90 LoC) + `tests/plugin_adapters.rs` (~1524 LoC) + `tests/vst3_safe_bindings.rs` (~38 LoC) + `Cargo.toml`
**Purpose:** Emit the concrete plugin-format outputs (CLAP, VST3, AU, standalone, desktop, sealed-artifact) from the format-neutral `hawk2ui-plugin` model. Two distinct layers live here: (1) a **packaging / materialization engine** that lays out bundle directories, writes metadata/descriptor/`Info.plist`/launch manifests, and seals every package with a SHA-256 hash manifest plus tamper/coverage verification; and (2) **format code generation** — string templates that are written to disk as a buildable Cargo `cdylib` project carrying the real `extern "C"` ABI for each format.
**Note:** Codex is concurrently committing CLAP-ABI hardening/remediation; the CLAP editor dispatch ABI is recent and active, so HEAD drifts (git HEAD is `5fecf2c4`). Findings reflect the SHA above and may overlap with in-progress fixes.

## Summary

This crate's **ABI-without-`unsafe`** trick is real and clean: the workspace `#![forbid(unsafe_code)]` holds (`lib.rs:1`) because the C ABI lives inside a `&'static str` template (`CLAP_CDYLIB_SOURCE_TEMPLATE`, `lib.rs:895`) that is *emitted as source code* and compiled by a downstream `cdylib` build — the forbid-unsafe crate only ever produces text. The maturity differs sharply per format and must be stated precisely:

- **CLAP — real, and proven host-loadable.** The generated template is a complete CLAP plugin: `clap_entry` (`lib.rs:1719`), factory → descriptor → `create_plugin`, all eleven `clap_plugin` vtable fns, and the `audio-ports`/`params`/`state`/`gui` extensions, plus a text dispatch ABI (`hawk2ui_editor_dispatch`, `lib.rs:1759`). The test `plugin_adapters_generate_compilable_clap_cdylib_scaffold` (`plugin_adapters.rs:577`) actually `cargo build --release`s the scaffold into a real shared library and then **loads it with `libloading`**, walking factory→create→activate→process→extensions and round-tripping params/state through *both* the CLAP `state` extension and the dispatch ABI. This is a genuine callable boundary, not a described contract.
- **VST3 — modeled, not functional.** `GetPluginFactory()` — the single mandatory VST3 entry point — returns `std::ptr::null_mut()` (`lib.rs:2139`). The `factory_info`/`processor_class_info`/`controller_class_info` builders exist but are consumed only by `let _ = (...)` in the module-entry stubs to suppress dead-code lints (`lib.rs:2101`, `:2114`, `:2127`). The dependency `hawk2ui-vst3` supplies only *safe record types* (`Vst3FactoryInfo`, `Vst3ClassId`, …); there is **no `IPluginFactory` / COM vtable anywhere in the workspace**, so a working factory cannot be produced from current building blocks. The VST3 scaffold is never compiled or loaded by any test.
- **AU / Standalone / DesktopBundle — bundle-layout model only.** These write a directory tree, an `Info.plist`, and (standalone/desktop) a launch manifest, then write a **plain-text descriptor file in the executable slot** (`entry_descriptor`, `lib.rs:2484`, placed at `Contents/MacOS/<name>` / the `.vst3` / `.component` path). No code is generated and no entry point exists. These are the least complete.
- **SealedArtifact** writes a single descriptor file; it is a layout stub by intent.

Critically, even on the working CLAP path, `PackagePlan::materialize` emits a **source scaffold + descriptors**, never a compiled binary — the `.clap` file written at the bundle top (`lib.rs:2399`) is itself a text stub (`entry_descriptor`). "CLAP is real" means the generated *code* is real and loadable *once a separate build compiles it*, not that `materialize()` ships a loadable plugin.

The packaging/verification engine is the most mature and best-tested part: `is_safe_relative_path` (`lib.rs:3478`), symlink rejection, full hash-manifest round-trip with exact file-set equality (`hash_manifest_matches`, `lib.rs:3413`), and stale-output cleanup are all real and covered by tamper/coverage tests. There are no `todo!`/`unimplemented!`/`unreachable!`/placeholder panics anywhere, and no TODO/FIXME/HACK markers.

The substantive weaknesses are: (1) **the working CLAP ABI keeps all plugin state in process-global `static`s**, so two instances of the plugin (the normal DAW case — same plugin on two tracks) alias each other's parameters and editor lifecycle; (2) **VST3 ships a null factory under a "Production" label** → loads but exposes zero classes; (3) **the realtime-safety guard is decorative** — it advertises enforcement it does not perform; (4) **AU/standalone emit text stubs as binaries**; and (5) **misleading "Production" docs** over the three non-functional formats.

## Completeness & implementation gaps

1. **Process-global editor/parameter state in the CLAP ABI** (`CLAP_CDYLIB_SOURCE_TEMPLATE`: `EDITOR_CREATED/ATTACHED/VISIBLE/WIDTH/HEIGHT`, `lib.rs:933`–937; `PARAMETER_VALUES`, `lib.rs:967`). `create_plugin` returns a shared `&PLUGIN` with `plugin_data: std::ptr::null_mut()` (`lib.rs:984`, `:1085`), and every callback reads/writes the file-level `static`s rather than per-instance data. A DAW that instantiates the plugin twice gets **two handles sharing one editor state and one parameter bank** — `gui_set_size`, `gui_create`, `store_parameter_value`, save/load and the dispatch ABI all mutate global cells, so the instances corrupt each other. The atomics make this data-race-free (no UB/UAF), but it is a real user-visible **correctness** defect on the one functional path. Per-instance state belongs behind `plugin_data`. See Testing — the loader test only ever creates one instance, so this is invisible.
2. **VST3 `GetPluginFactory` returns null** (`lib.rs:2139`). The generated VST3 library loads (`ModuleEntry`/`BundleEntry`/`InitDll` return `true`) but exposes **no plugin classes** to the host. There is no factory/COM layer to call into; the metadata builders are dead-ended through `let _ = (...)`. Functionally the VST3 output is a no-op that advertises itself as a plugin.
3. **AU / Standalone / DesktopBundle write a text descriptor in the binary slot** (`write_format_layout`, `lib.rs:2428`–2446; `entry_descriptor`, `lib.rs:2484`). The `Contents/MacOS/<name>` file contains `"hawk2ui package entry\nformat=…\n"`, not an executable. No scaffold, no entry point, no codegen — purely a bundle skeleton. AU in particular has no AUv2/v3 component entry, `AudioComponents` plist registration, or factory.
4. **Realtime-safety guard is inert / decorative** (`realtime_guard_allows`, `lib.rs:1138`). It is a per-variant constant (`matches!(operation, PreallocatedWrite)`), so the gate in `plugin_process` (`lib.rs:1126`–1131) reduces to `!true || false || false` — a compile-time `false` that can **never** reject. The exported `REALTIME_SAFETY_POLICY_BYTES` (`lib.rs:932`) advertises `process_callback=guarded_preallocated_copy` / `forbidden=allocation` / `lock_policy=no_blocking_locks`, but the code performs no such enforcement. (The process body itself — `copy_nonoverlapping` over preallocated host buffers, `lib.rs:1142`–1202 — *is* allocation-free and genuinely RT-safe, so this is misleading advertising, not a live RT violation.)
5. **`gui_create` opens no window; "frame presented" is a counter.** The entire CLAP GUI extension is a state machine over atomics: `gui_create` flips `EDITOR_CREATED` (`lib.rs:1543`), and the dispatch ABI's `dispatch_show` increments `EDITOR_PRESENTED_FRAME_COUNT` and returns `response=frame_presented` (`lib.rs:1827`–1841) without rendering anything. The runtime-editor descriptor names `baseview`+`skia`, but the generated CLAP library does not link or drive them — actual rendering would require the separately-reviewed `hawk2ui-host-baseview`. By design for a scaffold, but the GUI surface is modeled, not live.
6. **`Choice` parameters lose their default and type** (`parameter_default_value`, `lib.rs:3122`: `Choice(_) => 0.0`). A choice/enum parameter is generated into the CLAP table with default `0.0` regardless of its real default index, and the `STEPPED` flag is only set when `steps.is_some()` (`lib.rs:3132`) — `Choice` without explicit steps is emitted as a continuous param. Echoes the `Choice`-degradation theme flagged in the baseview sibling review.
7. **Two parallel CLAP GUI surfaces share one global state** (`gui_*` vtable, `lib.rs:1543`–1671, vs the `hawk2ui_editor_dispatch` text ABI, `lib.rs:1759`–1908). Both mutate the same `EDITOR_*` atomics. They are kept in lock-step today, but they are independent code paths over shared mutable globals with no single source of truth, and the test even asserts cross-effects between them — a drift hazard analogous to baseview's dual event surfaces.

## Code quality & smells

- **macOS bundle conventions applied to every format.** All formats nest under `Contents/Resources` and emit an `Info.plist` (`materialize`, `lib.rs:2255`; `write_format_layout`, `lib.rs:2416`–2436), and VST3 hard-codes a single `Contents/x86_64-linux/<name>.vst3` binary dir (`lib.rs:2419`). This is a hawk2ui-internal layout, not a host-loadable Linux CLAP (a bare `.so`) or a portable VST3 bundle (`x86_64-linux`/`aarch64-linux`/`x86_64-win`/`MacOS` per platform). Consistent with "pre-binary scaffold," but it is not a host-installable layout as-is.
- **`clap_parameter_flags` uses raw bit literals** (`lib.rs:3130`: `1 << 0`, `1 << 2`, `1 << 3`, `1 << 5`). Verified against `clap-sys-0.5.0/src/ext/params.rs`: these **correctly** equal `CLAP_PARAM_IS_STEPPED`/`HIDDEN`/`READONLY`/`AUTOMATABLE`, so this is *not* an ABI bug — but the named `clap_sys` constants are in scope and unused, and nothing static-asserts the literals against them, so a future `clap-sys` change would silently desync. Readability/maintainability smell only.
- **`with_parameters` is dead on the materialization path.** `PackageTargetPlan` carries pre-computed `clap_parameter_source`/`clap_parameter_value_source` (`lib.rs:2208`–2211, filled in `plan`, `lib.rs:2778`) and feeds them via `with_parameter_sources` (`lib.rs:803`). The public `ClapCdylibScaffold::with_parameters` (`lib.rs:796`) is only reachable by direct scaffold callers/tests; the two parameter-source code paths can diverge.
- **`Hawk2uiEditorState` is duplicated by hand in the test** (`plugin_adapters.rs:728`). The `#[repr(C)]` struct returned by-value across the `extern "C"` boundary (`lib.rs:1942`) is re-declared field-for-field in the host-check binary with no shared header; field reordering would be an undetected ABI break.
- **`EDITOR_HOST_ABI_BYTES` / `REALTIME_SAFETY_POLICY_BYTES` are hand-written `&'static str` contracts** (`lib.rs:931`–932) that duplicate the command/response vocabulary the `match` in `hawk2ui_editor_dispatch` actually implements (`lib.rs:1776`–1786). Nothing asserts the advertised contract and the dispatch arms stay in sync — same drift smell the baseview review flagged for its ABI contract string.
- **Skip-serialized fields on a `Serialize`/`JsonSchema` type** (`PackageTargetPlan`, `lib.rs:2206`–2211): `clap_parameter_source`/`clap_parameter_value_source` are `#[serde(skip)]`, so a `PackageTargetPlan` round-tripped through JSON silently loses its generated parameter sources and would regenerate empty CLAP params. The schema-validation tests never round-trip *through* the plan back into materialization, so this is uncovered.

## Documentation

- Strong at the item level: crate-level `//!`, every public type/fn documented, and `# Errors` sections on all fallible public fns (`from_raw_parts`, `to_host_platform_handle`, `ClapRuntimeEditorDescriptor::new`, the whole `ClapRuntimeEditorSession` surface, `write_to`, schema/validate fns, `materialize`). No undocumented public items found.
- **Misleading "Production" claim** (`lib.rs:2` and `Cargo.toml` `description`): both state "**Production** plugin and package adapters for … CLAP, VST3, AU, standalone, and desktop outputs." VST3 ships a null factory, and AU/standalone/desktop ship text-stub binaries — three of the five advertised "production" outputs are non-functional. The doc overstates maturity across formats.
- **No doc states the maturity split.** Nothing in the source tells a reader that CLAP is the only functional ABI, that `materialize()` emits source-not-binary, or that the GUI/realtime surfaces are modeled. Given how convincingly the CLAP template reads, a per-format maturity note (and a "scaffold, not compiled artifact" note on `materialize`) is warranted.
- **`REALTIME_SAFETY_POLICY_BYTES` documents enforcement that does not happen** (see gap #4) — a misleading machine-readable "doc."

## Testing

- **Excellent on the two mature areas.** The CLAP loader test (`plugin_adapters.rs:577`) is the standout: it compiles the generated scaffold and exercises the real ABI end-to-end through `libloading`, including null-handle rejection, lifecycle ordering (`show` before `set_parent` fails), param automation via a synthetic `clap_input_events`, and state round-trips through both the CLAP `state` stream and the dispatch ABI. The packaging engine is well covered: format-layout assertions, hash-manifest presence, stale-payload cleanup (`:1287`), tamper rejection (`:1324`), and incomplete/extra hash-coverage rejection (`:1362`). Metadata escaping is tested across TOML/JSON/XML (`:1414`).
- **The global-state multi-instance bug is masked** (gap #1). Every test creates exactly one plugin instance and treats `hawk2ui_editor_state()` (a no-arg free function, `:920`–922) as global truth; the dispatch and GUI paths mutate the same globals. A two-instance test would expose the aliasing, and none exists.
- **The realtime guard is not meaningfully exercised** (gap #4). The loader's `process` call uses `frames_count: 0` with null audio buffers (`:774`–784) and only checks `CLAP_PROCESS_CONTINUE`; the guard is a constant `false`, so no test asserts it can *reject* anything.
- **VST3 codegen is asserted by substring only** (`:1259`–1260): the test checks the generated source *contains* `"Vst3ClassId"` and `"GetPluginFactory"`, never compiles or loads it, and **never asserts the factory is non-null** — so the null-factory defect (gap #2) ships green. `vst3_safe_bindings.rs` tests the `hawk2ui-vst3` record types, not this crate's VST3 output.
- **AU/standalone have no functional assertions** — only that the bundle dir/plist/text-stub files exist (`:1265`–1278). Nothing asserts (because nothing produces) an executable or component entry.
- Test helpers use `SystemTime::now()` nanos for temp-dir uniqueness with `.expect(...)` — fine for tests.

## Cross-cutting conventions (workspace-wide; noted once, not a per-crate defect)

- `crate_name()` plus the `exposes_crate_identity` test (`lib.rs:3611`) follow the workspace pattern. **Deviation (Low):** like `hawk2ui-assets` and the baseview sibling, this crate carries **no** `*_workspace_filter_marker` test; if the conformance filter gates enumerate per-crate markers, this crate is invisible to them.
- **Deviation (Low):** errors do **not** bridge to `hawk2ui_api::Diagnostic` via `From` — the crate does not depend on `hawk2ui-api`. It defines its own `PackageDiagnostic`/`PackageMaterializationError`/`PackagePlanningError` (`lib.rs:2880`, `:2738`, `:2910`), so callers cannot fold these into the unified diagnostic stream without an adapter. Same deviation the baseview sibling flagged.
- `#![forbid(unsafe_code)]` is held at crate root and is the central design constraint (the C ABI is emitted as text). Consistent and good.

## Security

The plugin ABI is a trust boundary with an untrusted DAW host, and — on the **functional CLAP path** — the generated ABI actually validates that boundary. Stated explicitly because it is real:

- **Every `extern "C"` entry null-checks its pointer arguments before deref**: `entry_get_factory`/`create_plugin` (`lib.rs:1046`, `:1074`), `plugin_process` (`lib.rs:1123`), all `params_*`/`state_*`/`gui_*` fns, and `hawk2ui_editor_dispatch` (`lib.rs:1766`). Host strings are read through `CStr` + `to_str()`/`to_bytes()` with UTF-8 validation (`cstr_matches`, `lib.rs:1685`; `params_text_to_value`, `lib.rs:1344`).
- **Event dispatch validates the host-supplied event before the cast**: `params_flush` checks `space_id`, `type_`, **and `header.size >= size_of::<clap_event_param_value>()`** before reinterpreting the header (`lib.rs:1381`–1390) — the correct guard against a short/forged event.
- **State bytes from the host are bounded**: `read_state_payload` caps accumulation at `MAX_STATE_BYTES = 64 * 1024` and aborts on overflow or negative read (`lib.rs:1474`–1490); `restore_state_payload` validates the magic header and parses defensively (`lib.rs:1494`). Parameter writes clamp to `[min,max]` and reject non-finite values (`store_parameter_value`, `lib.rs:1405`).
- **The dispatch response writer checks capacity before copying** and reports the required length without writing on overflow (`write_dispatch_response`, `lib.rs:1924`–1939) — no buffer overrun from an undersized host buffer.
- **No panic/`unwrap`/allocation is reachable on the audio path.** `plugin_process` and its `copy_*_channels` helpers are panic-free and allocation-free, so nothing unwinds across the `extern "C"` boundary from the realtime callback (the key UB-into-C hazard). `String`/`format!` allocation appears only on the cold GUI/dispatch/state paths, never in `process`.
- **Packaging-side path safety is genuinely hardened**: `is_safe_relative_path` rejects absolute paths and any non-`Normal` component (`..`, root) (`lib.rs:3478`); `package_regular_files` returns `None` on any non-file/non-dir entry, **rejecting symlinks** (`lib.rs:3466`); `hash_manifest_matches` requires the on-disk file set to *exactly equal* the manifest set (no missing, no extra) and re-hashes every file (`lib.rs:3437`–3445). `vst3_class_id_hex` derives a deterministic 128-bit TUID via SHA-256 (`lib.rs:3558`).

**Residual / unaddressed:**

1. **Process-global mutable state shared across instances** (gap #1). Not memory-unsafe (atomics), but a cross-instance state-confusion bug: one plugin instance can observe/alter another's parameters and editor lifecycle. On a real DAW host loading N instances, this is the highest-impact issue on the working path. **High (correctness).**
2. **Decorative realtime-safety guard** (gap #4). The exported policy claims allocation/blocking-lock enforcement the code never performs (`realtime_guard_allows` is a constant). A host trusting the advertised contract is misled; the guard provides no actual protection if the process body ever grew an allocation. **Low (today, given the body is RT-safe; misleading).**
3. **Non-loadable VST3 / AU / standalone outputs** (gaps #2, #3). A host that installs these gets a library exposing no classes (VST3) or a bundle whose "binary" is text (AU/standalone). Availability/correctness, not a memory-safety issue — but shipped under a "Production" label. **High for VST3** (silent zero-class load), **Medium for AU/standalone**.
4. **No upper bound on generated parameter count.** `clap_parameter_source` emits one entry per model parameter into a fixed-size `static [AtomicU64; N]` (`lib.rs:967`, `:3097`); a pathological model would generate a very large static, but the input is first-party (the plugin author's model), not host-controlled, so this is a generation-side concern only. **Low.**
5. **Unverified pointer provenance is inherent to the embedding model**, but note this crate's CLAP ABI never *dereferences* the host window handle — `gui_set_parent` only null-checks `window.specific.ptr` and records attachment (`lib.rs:1629`–1645); actual use of the handle happens in `hawk2ui-host-baseview`, where the sibling review covers the use-after-free surface. Here the boundary is conservative. **Informational.**

No `unsafe` exists in this crate (the C ABI is emitted as generated source); the generated template's `unsafe` is `#[allow(unsafe_code)]`-scoped inside the string.
