# Code Review — hawk2ui-text

**Reviewed at:** `5a042c51` · 2026-05-28 · working tree clean at review time
**Scope:** `src/lib.rs` + `tests/text_backend.rs` (1 src file ~737 LoC / 1 test file ~162 LoC)
**Purpose:** Production text backend for Hawk2UI — font discovery (`fontdb` 0.23), shaping (`parley` 0.7 / `swash` 0.2), line breaking, bidi (`unicode-bidi`), grapheme segmentation (`unicode-segmentation`), glyph cache keying, and high-DPI metrics. Resolves a font family (or fallback), produces a measured `TextLayout` (lines, width/height/baseline, cluster count, emoji/bidi/truncation flags), and emits stable glyph-cache keys.
**Note:** Codex is concurrently committing hardening/remediation work; HEAD drifts (git HEAD is `5fecf2c4`). Findings reflect the SHA above and may overlap with in-progress fixes.

## Summary

Shaping is **real, but wired to the wrong font.** `layout_with_parley` (`lib.rs:548`) genuinely runs Parley: it builds a `RangedBuilder`, calls `break_all_lines`, iterates `layout.lines()`, and reads per-line `metrics().advance`/`baseline`/`trailing_whitespace` plus `layout.width()`/`height()`. Width is `advance - trailing_whitespace`, matching Parley's own internal computation (`line_break.rs:694`). This is **not** a `char_count * constant` fake — line breaking, cluster measurement, and metrics are produced by Parley's real pipeline, and the layout-crate adapter (`hawk2ui-layout/src/text.rs:197`) consumes `layout.width_px()` as the production measurement. So on the main path there is no fake-width measure/render divergence: the measurement is real shaping. Grapheme segmentation via `unicode-segmentation` is also real (`graphemes(true)` drives `cluster_count` and truncation).

The defect is that **the resolved font family never reaches the shaper.** The only style pushed is `StyleProperty::FontSize` (`lib.rs:567`); no `FontStack`/`FontFamily` is ever pushed. `resolve_family` computes a family, stores it in `TextLayout::resolved_family` and the cache key — then Parley shapes in its **default system font stack**, ignoring it. Compounding this, the loaded `fontdb::Database` is **write-only dead state**: `with_app_font` calls `load_font_data` (`lib.rs:59`) but nothing ever queries it, and those bytes never reach Parley's `FontContext` (which discovers its own system fonts). So the crate's headline capabilities are largely inert *as wired here*: **fontdb font discovery is unused** (resolution is plain `Vec<String>` string-matching), **swash is constructed and never called** (`_scale_context`, `lib.rs:423` — the underscore admits it), and there is **no glyph cache store** behind `GlyphCacheKey` (it is a bare key string; nothing rasterizes or caches glyphs). Bidi is a special case: the crate's **direct `unicode-bidi` dependency is dead** (it builds a `BidiInfo` and discards it, `lib.rs:498`) and the `bidi_resolved` flag is a coarse heuristic — but **bidi in the output is correct**, because Parley runs its *own* bidi resolver inside `build` (`parley/src/context.rs:178`, levels feeding run/line reordering) so measured widths and line breaks are bidi-aware. Net: Parley does real, bidi-aware work but in the wrong font; fontdb and swash do no work, and the direct `unicode-bidi` use is redundant. Determinism suffers because metrics come from whatever font the *host* happens to have.

No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME markers; error handling on the Parley path is careful (poisoned-lock, non-finite, empty-layout, out-of-range all return structured diagnostics rather than panicking).

## Completeness & implementation gaps

1. **Resolved font family is discarded at the shaper boundary** (`layout_with_parley`, `lib.rs:565`–`568`). `resolve_family` (`lib.rs:451`) does real work to pick a family/fallback, and that string is threaded into `TextLayout::resolved_family` and the glyph-cache key — but the only `push_default` on the Parley builder is `StyleProperty::FontSize`. **No `FontStack`/`FontFamily`/`GenericFamily` is ever pushed.** Parley therefore shapes every layout in its default font stack regardless of the requested or resolved family. Measured width/height/baseline are **not a function of the family** the caller asked for: `resolve_family("Display")` and `resolve_family("Serif")` yield identical metrics. The crate advertises "shaping" keyed on a resolved family, but the family resolution and the shaping are disconnected. This is the crate's central defect and nothing downstream catches it (render-skia is record-only — see Cross-cutting). → Push a `FontStack`/`StyleProperty::FontStack(...)` built from `resolved_family` (and the fallback chain) before `build`.
2. **`fontdb::Database` is loaded but never queried — font discovery is inert** (`FontCatalog`, `lib.rs:22`–`106`). `with_app_font` stores bytes into `self.database` via `load_font_data` (`lib.rs:59`), but the only use of `self.database` in the entire crate is that one call. `contains_family` (`lib.rs:96`) resolves purely by matching the `system_families`/`app_fonts` `Vec<String>` lists; nothing calls `database.query`/`faces`/`load_font_source`. So the headline "font discovery (`fontdb`)" capability does no discovery: it is string equality over caller-supplied family names. The loaded font *bytes* are dead — they are not queried here and (gap #1) never reach Parley's `FontContext` either, so an app font registered via `with_app_font` cannot actually be used to shape text. → Either drive resolution + the Parley font stack from `fontdb` query results, or drop the database and document that resolution is name-only.
3. **No glyph cache exists; `GlyphCacheKey` is a key with no store** (`lib.rs:354`–`366`, `glyph_cache_key` `lib.rs:530`). The crate's stated job includes a "glyph cache," but `GlyphCacheKey` wraps a single `String` and there is no `HashMap`/`BTreeMap`/glyph storage, no rasterization, and no eviction anywhere in the crate. `glyph_cache_key` formats a key; nothing consumes it to memoize glyphs. This is "records intent, does no work" at the data-structure level: the API surface implies caching that is not implemented. (Upside: no unbounded-growth risk — but also no cache.) → Implement a keyed store with eviction, or rename/document this as "produces cache keys for an external glyph cache."
4. **`swash::ScaleContext` is constructed and never used** (`TextBackend::new`, `lib.rs:434`; field `_scale_context`, `lib.rs:423`). Swash is the glyph rasterizer that would turn shaped glyphs into outlines/bitmaps; the crate holds a `ScaleContext` but never calls `.builder(...)`. The `_` prefix concedes it is dead. Swash — one of the five headline dependencies — does no work. → Use it to rasterize glyphs (feeding the absent cache in #3) or remove the dependency.
5. **The direct `unicode-bidi` dependency is dead code; the `bidi_resolved` flag is decorative** (`layout`, `lib.rs:498`, `lib.rs:491`). `let _bidi_info = BidiInfo::new(&display_text, None);` constructs the full bidi analysis and immediately discards it — the dependency does no work in the output. The reported `bidi_resolved` flag is **not** derived from that analysis; it is `input.bidi && display_text.chars().any(is_rtl)` (`lib.rs:491`), a coarse codepoint-range heuristic that misreports edge cases (Arabic presentation forms outside the `is_rtl` range read as non-bidi; a bidi-control-only run with no strong RTL char reads as non-bidi). **Bidi in the layout is nonetheless correct:** Parley runs its own `BidiResolver` inside `build` (`parley/src/context.rs:178`; resolved levels flow into run/line `bidi_level` and reordering, `parley/src/layout/data.rs`), so the line advances and breaks this crate extracts are bidi-aware. The defect is thus a wasted dependency plus a misleading public flag, not broken bidi. → Remove the dead `BidiInfo` (and likely the `unicode-bidi` dep), and either derive `bidi_resolved` from `layout.data.has_bidi`/`base_level` (not currently exposed by Parley's public API) or document the flag as a heuristic.

## Code quality & smells

- **Truncation decides cut points with fake width constants, then Parley measures the result** (`truncate_text` `lib.rs:674` → `measure_clusters` `lib.rs:691` → `cluster_width_factor` `lib.rs:697`). `cluster_width_factor` returns hard-coded per-cluster factors (whitespace `0.35`, emoji `1.0`, CJK/RTL `0.8`, else `0.55`) times `size_px * dpi_scale`. This is exactly the `char_count * constant` fake the brief warns about — but it is confined to choosing *how many graphemes precede the ellipsis*. The final `width_px` is still real Parley. The consequence is an **internal measure/decision divergence**: the truncation cut is computed from fake advances while the reported width is real, so for `EndEllipsis { max_width_px }` the returned `width_px` can exceed `max_width_px` (factors underestimate a wide font) or cut too early (factors overestimate). The two notions of "width" inside one `layout()` call disagree. → Truncate using a Parley measurement (binary-search grapheme prefixes against a real layout) rather than the constant table.
- **Glyph-cache key omits `line_break` and `truncation`** (`glyph_cache_key`, `lib.rs:536`–`544`). The key is `text|font|size|dpi|bidi|font-generation`. Two inputs with identical text/font/size/dpi/bidi but **different wrap widths or truncation** produce the **same** key — yet `layout()` yields different `display_text`, line counts, and per-line geometry. An external cache keyed on this would return stale glyphs/lines for a different wrap or truncation. Wrong key → stale results. (Also omits `font_family` raw input, though `resolved_family` is folded in.) → Include line-break and truncation discriminants in the key.
- **`is_emoji` / `is_rtl` / `is_cjk_or_rtl` are coarse single-range approximations** (`lib.rs:709`–`719`). `is_emoji` covers only `U+1F000..=U+1FAFF`, missing common emoji in `U+2600..U+27BF` (e.g. ❤ U+2764, ☀, ✂ dingbats) and regional indicators/flags; `is_rtl` covers `U+0590..=U+08FF` (Hebrew/Arabic/Syriac block run) but misses Arabic Presentation Forms (`U+FB50..`, `U+FE70..`). These feed `contains_emoji`, the `bidi_resolved` heuristic, and the truncation width factor — so misclassification skews both flags and cut points. Range checks over Unicode blocks are inherently incomplete; a property-based check (e.g. `unicode-properties`) would be correct.
- **`generation` counts builder calls, not content changes** (`with_system_family`/`with_app_font`/`with_fallback_family`, `lib.rs:47`,`65`,`73`). Each registration `saturating_add(1)`s `generation`, which flows into the cache key as `font-generation`. Registering the *same* family twice still bumps it, so the "cache invalidation" generation is a registration counter, not a content hash — identical catalogs built via different call counts get different keys. Minor (catalogs are typically built once), but the doc "generation for cache invalidation" overstates it.
- **`contains_family` re-validates family strings on every lookup** (`lib.rs:96`). It calls `is_valid_font_family` on each stored candidate during resolution even though invalid entries could have been rejected at registration. `with_system_family`/`with_app_font` accept empty/blank families and empty byte vectors silently (the test `text_backend_rejects_invalid_font_catalog_entries` relies on this), pushing validation to read time. Builder-time rejection (or `Result`-returning builders) would be cleaner than storing then filtering junk.
- **`TextDiagnostic`/`TextBackendError` are a private parallel diagnostic type** (`lib.rs:368`–`418`). Same shape as sibling crates' diagnostics but with no `From`/bridge to `hawk2ui_api::Diagnostic`, and the crate does not depend on `hawk2ui-api`. See Cross-cutting.

## Documentation

- Strong surface: crate-level `//!`, every public type/method documented, `# Errors` on all three fallible entry points (`resolve_family`, `layout`, `glyph_cache_key`) and they accurately describe the validation/resolution failures.
- **Misleading vs. behavior:** the crate doc and `TextBackend` doc bill "font discovery," "glyph cache," and "shaping … bidi" as delivered capabilities. Per gaps #1–#5: discovery via fontdb is unused, there is no glyph cache store, bidi is discarded, and shaping ignores the resolved family. None of these are flagged as partial/external. `font_generation`'s "cache invalidation" doc and `parley_processed()`'s wording ("passed through Parley's layout pipeline" — true, but in the default font) read as stronger guarantees than the code provides.

## Testing

- The three behavioral tests genuinely exercise the Parley path (not just constructors): line counts, monotonically increasing per-line baselines, `width_px <= max_width` for wrapped lines, high-DPI width/baseline scaling, truncation suffix. Input-validation rejections are covered well (empty text, invalid family, non-positive wrap, NaN truncation width, zero DPI), as is fallback resolution and catalog junk-rejection.
- **Determinism / environment dependence (False confidence):** because shaping uses Parley's `FontContext::new()`, which "discover[s] system fonts if available" (parley `font.rs:18`), all metric assertions — `baseline_px() > 0`, `width_px <= 96.0`, `high_dpi.width > wrapped.width`, `lines()[1].baseline > lines()[0].baseline` — depend on the **host** having a usable default font. On a headless/minimal CI image with no system fonts, Parley may produce zero-advance or empty layouts and these tests can fail or the layout can hit `text.parley.empty-layout`. The suite never registers real font bytes that reach the shaper (app fonts go only into the dead `fontdb`), so it cannot pin metrics deterministically.
- **Tests assert around the disconnect, not against it.** `text_backend_shapes_latin_emoji_combining_and_bidi_text` registers families `"Display"`/`"EmojiFallback"` and asserts `resolved_family() == "Display"` and `bidi_resolved()` — both pass while Parley shapes in the default font and `BidiInfo` is discarded (gaps #1, #5). No test asserts that two *different* requested families yield *different* metrics, which would expose gap #1. No test recompiles identical inputs to check cache-key stability, nor varies wrap/truncation to expose the key-omission bug. `assert_close` uses `< f32::EPSILON` (`tests:91`) — far too tight for `round_tenth`-quantized f32s that merely "should be near," though it happens to pass because the two values are the same rounded baseline.
- Coverage gaps: no test for the Parley error paths (`empty-layout`, `invalid-metrics`, `invalid-line-range`, poisoned locks), no adversarial-Unicode input (combining bombs, bidi-override controls, zalgo), no test that emoji outside `U+1F000..` are detected (they are not — gap-adjacent), and no test that truncation's reported `width_px` actually respects `max_width_px`.

## Cross-cutting conventions (workspace-wide; noted once)

- `crate_name()` plus the `exposes_crate_identity` test follow the workspace pattern. `#![forbid(unsafe_code)]` holds.
- **Deviation (Low):** no `*_workspace_filter_marker` test (matching `hawk2ui-assets`'s same deviation). If conformance gates enumerate per-crate markers, this crate is invisible to them.
- **Deviation (Low):** `TextDiagnostic`/`TextBackendError` have **no** bridge to `hawk2ui_api::Diagnostic` and the crate does not depend on `hawk2ui-api`. Callers cannot fold text errors into the unified diagnostic stream without an adapter; the layout-crate consumer (`text.rs:198`) re-wraps rule+message by hand into its own `TextMeasureError`.
- **Cross-ref (not this crate's bug):** the render side, `hawk2ui-render-skia::draw_text_layout`, is **record-only** — it pushes `format!("text-at:…")`/`format!("text-layout:…")` command strings and never rasterizes glyphs (no swash, no `draw_str`). Combined with this crate measuring in the default font and holding no glyph cache, the end-to-end consequence is that *nothing in the pipeline rasterizes text in the requested font*. The measurement defect here (gap #1) is invisible because the renderer that would reveal it does not draw.

## Security

The trust boundary is **untrusted text input** (arbitrary `&str` to `layout`/`glyph_cache_key`) plus **untrusted font bytes** (via `with_app_font`). `#![forbid(unsafe_code)]` holds; there is no `unsafe`. The public types derive no Serde, so there is no deserialization attack surface.

- **Unbounded work proportional to input length; no input-size cap** (`layout`, `lib.rs:484`). There is no maximum on `input.text` length, on any path. A multi-megabyte string always incurs `display_text.graphemes(true).collect::<Vec<_>>()` (full materialization, `lib.rs:488`), a discarded `BidiInfo::new` allocation over the whole string (`lib.rs:498`), and Parley shaping + line breaking over the entire text — linear but unbounded, with no length guard or timeout. Pathological Unicode amplifies the constant factor: a combining-mark "zalgo" run packs many `char`s per grapheme. Separately, `truncate_text` is **O(n²)** in the narrower case where `EndEllipsis { max_width_px }` is large/caller-influenced: for each grapheme it builds `format!("{display}{cluster}…")` and re-segments the whole accumulated string (`lib.rs:679`–`682`); the `break` when `measure_clusters > max_width_px` bounds iterations by the width budget, so the quadratic blow-up needs a generous `max_width_px`. Net: CPU/memory DoS on attacker-controlled text, plus a quadratic amplifier under wide truncation. **Medium.**
- **Pathological-Unicode robustness rests on Parley/swash not panicking** (`layout_with_parley`). The crate guards Parley's *outputs* (non-finite metrics, empty layout, out-of-range line ranges all → diagnostics) and slices line text safely via `display_text.get(range)` with a `None` check (`lib.rs:589`), which is good. But any *panic* inside Parley/swash on adversarial input (deeply nested bidi overrides `U+202A..U+202E`/`U+2066..U+2069`, malformed combining sequences) would propagate as an unwinding panic, not a `TextBackendError` — there is no `catch_unwind`. Bounded by Parley's own robustness; flagged for defense-in-depth. **Low / verify.**
- **Untrusted font bytes are stored but never parsed here** (`with_app_font`, `lib.rs:59`). `load_font_data` hands bytes to `fontdb`; because the database is never queried and the bytes never reach the shaper (gaps #1–#2), no font-table parsing of attacker bytes happens *in this crate's active paths*. The parsing-trust risk is therefore latent rather than live — it would activate if gaps #1–#2 are fixed by wiring fontdb/parley to these bytes (ttf-parser/swash would then parse them). Note for the remediation. **Low.**
- **No glyph-cache growth vector** — because there is no cache (gap #3). Unlike sibling crates with unbounded `BTreeMap`s, `TextBackend` holds only the catalog and Parley contexts; per-call layout state is dropped. The `FontCatalog` `Vec`s grow only with explicit builder calls (bounded by the app). No unbounded-growth finding.
- **Good:** all numeric inputs are validated finite-and-positive before use (`validate_input`, `lib.rs:630`); `line_count` uses `u32::try_from(...).unwrap_or(u32::MAX)` rather than panicking; lock poisoning is handled, not `unwrap`ped; line-text slicing is bounds-checked.
