# Code Review — hawk2ui-perf

**Reviewed at:** `5a042c51` · 2026-05-28 · working tree clean at review time
**Scope:** `src/{lib,budgets,harness,realtime,stability}.rs` + `benches/{startup,layout,style,render,render_baseline,script,assets,runtime,package,desktop_host,plugin_realtime}.rs` + `Cargo.toml` (5 src files: `harness.rs` 365, `realtime.rs` 194, `budgets.rs` 132, `stability.rs` 73, `lib.rs` 289 incl. ~270 LoC inline tests; 11 bench binaries ~25 LoC each; no `tests/` dir)
**Purpose:** Performance budgets (parse + validate `performance/budgets.toml`), a deterministic benchmark suite (case → budget mapping, pass/fail vs `maximum`, release-evidence TOML), a runtime stability fixture, and a realtime audio-thread safety guard.
**Note:** Codex is concurrently committing hardening/remediation work; HEAD drifts. Findings reflect the SHA above and may overlap with in-progress fixes.

## Summary

The validation machinery in this crate is **genuinely implemented, not a stub**, and its comparators **can fail**: `PerformanceBudgets::parse` does real TOML deserialization + duplicate-name and target-≤-maximum validation; `BenchmarkSuite::validate_against`/`evaluate_against` perform a real `observed <= maximum` comparison and return `BudgetExceeded`/`MissingMeasurement`/`MissingBudget`; the inline test `benchmark_suite_rejects_measurements_above_budget_maximum` (observed 17 vs max 16) proves the comparator rejects an over-budget value. `RealtimeGuard` is a correct, real policy table. `RuntimeStabilityFixture::validate` is a real `failures > allowed` check. No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME markers.

The crate's central defect is **false stability assurance**, and it is structural, not incidental. **The comparator is live but the only values it ever sees are hardcoded literals.** Every benchmark in `benches/*.rs` feeds `BenchmarkMeasurement::new(N)` where `N` is a source constant chosen to sit under the budget `maximum` (e.g. `frame-render` → `new(7)` vs maximum 16; `cold-start` → `new(200)` vs maximum 500). **The crate exposes no timing primitive at all** — `BenchmarkMeasurement::new(observed: u64)` is the only constructor, and there is **zero** `Instant`/`Duration`/`elapsed`/clock anywhere in `src/` or `benches/` (confirmed by grep). The helpers *structure* recorded numbers; they never *measure*. So the gate can catch a typo'd constant or a deleted budget row, but it can **never** catch a real performance regression — the literals pass forever regardless of how the framework actually performs. The same self-reported pattern holds for the stability gate (`with_failures(0)`, hardcoded) and the realtime allocation budget (`plugin-audio-allocation`, max 0, satisfied by `new(0)` — nobody counts real allocations). This collides directly with `docs/development/performance.md`, which asserts "Performance gates are release gates, not advisory notes" and "a measurement above the configured `maximum` fails release readiness." The claim describes a gate keyed on observed performance; the code implements a gate keyed on constants the author picked.

A charitable reading is that these are *deterministic recorded baselines* and determinism is intentional (the harness docstring says "Deterministic benchmark suite"). That reading does not survive: nothing in the repo refreshes the literals from a real run, no harness reads a measured value from any source, and the documentation explicitly frames them as live release gates rather than fixtures. The gap between that claim and `BenchmarkMeasurement::new(7)` is the finding.

## Completeness & implementation gaps

1. **No measurement source exists; benches feed hardcoded literals** (`benches/render_baseline.rs:18,26`, and identically across all 11 benches). The CI-gated `render_baseline` bench constructs `scene-export → new(3)` (max 8) and `frame-render → new(7)` (max 16), calls `validate_against(...).expect(...)`, and exits 0. No bench times anything; `BenchmarkMeasurement::new(u64)` is the sole way to produce a measurement and it takes a literal. This is the crate's headline capability ("benchmark helpers, stability gates") implemented as record-only. → Either wire each case to a real measured value (time/size/count the referenced fixture) or stop documenting the suite as a performance regression gate.
2. **`--quick` is accepted by CI but never parsed** (all benches). These are `harness = false` binaries whose `main()` ignores `std::env::args()`. CI runs `cargo bench --bench render_baseline -- --quick` (`.github/workflows/ci.yml:79`; mirrored in `crates/hawk2ui-conformance/tests/verification_gates.rs:47` and `scripts/check-performance.sh`), but `--quick` is inert — the binary does the same fixed work regardless. Harmless given (1), but it reinforces the illusion of a tunable benchmark run.
3. **Stability gate is self-reported** (`benches/runtime.rs:20`). `RuntimeStabilityFixture::new("runtime-event-dispatch", 10_000).with_failures(0).with_allowed_failures(0)` — the `10_000` iterations are never executed and the `0` failures are never observed; both are constants. `validate()` is a real check, but over fabricated inputs. Same record-only pattern as the benchmarks.
4. **Realtime allocation budget is self-reported** (`benches/plugin_realtime.rs:18`). `plugin-audio-allocation` (target/maximum 0) is satisfied by `BenchmarkMeasurement::new(0)`; no code counts real audio-thread allocations. The `RealtimeGuard` policy table itself (`realtime.rs`) is real and correct — it is the *allocation count budget* that is canned.
5. **Two `release_gate = true` budgets have no bench case at all** — `memory-working-set` and `package-size` (`performance/budgets.toml`). 14 of 16 release-gating budgets are referenced by some bench; these two are referenced by none, so they are never evaluated even by the vacuous harness. A release gate that is never read cannot gate. → Add cases or remove the `release_gate` flag.
6. **`BenchmarkKind` and `PerformanceCategory` are never cross-checked.** `validate_against`/`evaluate_against` match on `budget_name` only (`harness.rs:245,271`); the `kind` field is decorative (it is stringified into evidence but never validated against `budget.category`). `BenchmarkKind` also has no `Memory` variant despite a `memory-working-set` budget, so a memory case cannot even be categorized correctly.

## Code quality & smells

- **`evaluate_against(...).artifact_payload()` result is discarded** in `style.rs`/`script.rs`/`assets.rs`/`package.rs`/`desktop_host.rs` (e.g. `style.rs:23`). The benches `black_box` the payload string but never inspect `report.accepted()` / `report.failed_count()`. Only `validate_against`'s `expect()` actually gates; `evaluate_against` runs purely for its (`black_box`'d) side-effect-free string. The two code paths (`validate_against` early-return errors vs `evaluate_against` per-row `failure` strings) duplicate the same `observed <= maximum` logic.
- **Hand-rolled TOML serialization** (`harness.rs:351` `escape_toml_string`, `:137` `artifact_payload`). The crate depends on `toml` (a real serializer) yet emits release evidence by string `format!` with a manual escaper. It is correct for the trusted budget names used here, but it is not a real serializer (no handling of e.g. control chars beyond `\n\r\t`, no key quoting), and it can silently drift from valid TOML if a name ever contains an unexpected character. Prefer serializing a `#[derive(Serialize)]` struct via `toml`.
- **`RuntimeStabilityFixture.iterations` is stored but never used in `validate()`** (`stability.rs:8,47`). The check is `failures > allowed_failures`; `iterations` is write-only state — there is no failure-*rate* computation despite the field implying one. The inline test name `..._detects_failure_rate_above_limit` overstates it (it is an absolute-count check, not a rate).
- **`BenchmarkMeasurement` is a single-field `u64` newtype with a `new`/field both public** (`harness.rs:74`). Minor; the public `observed` field makes the `new` constructor redundant.
- No dead code beyond the above write-only fields; modules are small and cohesive.

## Documentation

- Strong at the item level: crate-level `//!`, every public type/enum/method documented, and `# Errors` sections on every fallible fn (`parse`, `validate_against`, `write_artifact`, `write_report_artifact`, `check`, `RuntimeStabilityFixture::validate`). No undocumented public items.
- **Misleading in terminology, tied to the central finding.** The harness is documented as a "Deterministic benchmark suite" with a "Deterministic benchmark measurement" (`harness.rs:1,73`) and `BenchmarkCase.measurement` as an "Optional deterministic measurement supplied by a benchmark gate" — language that reads as *observed* values when they are author-chosen constants. Combined with `docs/development/performance.md`'s "release gates, not advisory notes," the surface advertises a measured gate that the code does not implement. Nothing documents that the published numbers are fixed literals rather than benchmark output.

## Testing

- Good breadth over the *validation logic*: budget parse + required-domain coverage, duplicate-name rejection, target-above-maximum rejection, missing-budget / missing-measurement / budget-exceeded rejection, an end-to-end evidence-artifact write + read-back, stability failure-limit rejection, and realtime guard allow/deny + telemetry. These genuinely exercise the comparators and error variants.
- **The entire suite tests the validator against literals, never against a measurement** — which is exactly the production usage, so the tests faithfully reproduce (and thereby normalize) the false-assurance gap rather than catching it. There is **no** test that any value is *derived from running anything*, because no such code exists to test.
- **False-confidence by omission:** `benchmark_suite_writes_release_evidence_report` asserts `failed_count() == 1` for a deliberately-over-budget literal (25 vs `js-evaluate` max 24) — proving the comparator works on a hand-picked failing constant, which is then never how the real benches are wired (they pick passing constants). The reader is left believing the gate is exercised against real numbers.
- Coverage gaps: no test for `memory-working-set`/`package-size` having no bench case (#5); no test that `kind` matches `category` (#6); no round-trip test that `artifact_payload` is parseable TOML (given the hand-rolled serializer).

## Cross-cutting conventions (workspace-wide; noted once)

- **Deviation (Low):** this crate has **no** `crate_name()` accessor and **no** `*_workspace_filter_marker` / `exposes_crate_identity` test (absent from `lib.rs`), unlike `hawk2ui-a11y`. If the conformance filter gates enumerate per-crate identity markers, this crate is invisible to them.
- **Deviation (Low):** `Cargo.toml` depends only on `serde` + `toml` — **not** on `hawk2ui-api`. The four error enums (`PerformanceError`, `BenchmarkError`, `StabilityError`, `RealtimeGuardError`) therefore have **no** `From` bridge into `hawk2ui_api::Diagnostic`; callers cannot fold perf-gate failures into the unified diagnostic stream without an adapter.
- `#![forbid(unsafe_code)]` holds.

## Security

The threat model here is **measurement/gate integrity** — a correctness-as-security concern, and the dominant one for a perf-budget crate.

- **Gate is trivially satisfiable / gameable → false stability assurance (primary).** Because every observed value (`BenchmarkMeasurement::new(N)`, `RuntimeStabilityFixture::with_failures(N)`) is a self-reported constant, the release gate passes by construction and stays green through any real-world regression — a frame-render that ballooned to 100 ms still reports `7`. The gate's pass condition is effectively vacuous with respect to actual performance; the system advertises a stability guarantee (`docs/development/performance.md`: "release gates") it does not enforce. This is the highest-severity item in the crate. → Bind measurements to a real source so the comparator (which already works) has something true to compare.
- **No `unsafe`** anywhere; `#![forbid(unsafe_code)]` holds.
- **`Deserialize` attack surface is narrow and trusted.** `PerformanceBudget`/`RawBudgets`/`BudgetUnit`/`PerformanceCategory` derive `Deserialize`, but `parse` is only ever fed the **compile-time-embedded** `include_str!("../../../performance/budgets.toml")` (a trusted, in-repo file). `parse` is `pub`, so untrusted TOML *could* be passed, but parsing is flat (a `Vec<PerformanceBudget>` — no recursion, no nesting), so there is no stack-overflow/decode-bomb exposure. Far milder than `hawk2ui-a11y`'s recursive-tree DoS. The realtime types also derive `Serialize`/`Deserialize` but carry only fixed-size scalars/enums and small `Vec`s populated internally.
- **No unbounded allocation of concern.** Report `entries` and `RealtimeSafetyReport` vectors are bounded by the (constant) number of cases/operations supplied at the call site.
- **Hand-rolled `escape_toml_string` is not a hardening boundary** — inputs are trusted budget/suite names, so it is not an injection vector, but see the code-quality note: it is not a substitute for a real serializer.
- **Panics are bench-only.** The `expect()` calls live in `benches/*.rs` `main()` functions, not in library APIs, so they are not a library-level panic-as-DoS surface; the library returns `Result` throughout.
