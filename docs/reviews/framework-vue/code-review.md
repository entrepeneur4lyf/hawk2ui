# Code Review — hawk2ui-framework-vue

**Reviewed at:** `5a042c51` · 2026-05-28 · working tree clean at review time
**Scope:** `src/lib.rs` + `tests/vue_integration.rs` (1 src file ~698 LoC / 1 test file ~304 LoC) + `Cargo.toml`
**Purpose:** Vue 3.5+ integration adapter. Scans author single-file-component (SFC) source (or accepts explicit native-compiler output via `from_native_program`) and emits typed `Hawk2UI` records — root `ElementNode`, keyed children, refs, style/asset refs, event + lifecycle bindings, and a custom-renderer operation key list — then bridges to a runtime view tree via `hawk2ui-authoring`'s `NativeRuntimeBridge`. One of four near-identical siblings (react/solid/svelte/vue); React is the structural reference.
**Note:** Codex is concurrently committing hardening/remediation work; HEAD drifts (git HEAD is `5fecf2c4`). Findings reflect the SHA above and may overlap with in-progress fixes.

## Summary

This crate is **genuinely wired, not a declarative stub** — but it is **structurally weaker than its React sibling on one axis** (the source-path renderer-operation list), so the real-vs-record boundary must be stated precisely. Two real lowerings exist and are exercised end-to-end:

- **`render_to_runtime()` lowers to a real `RuntimeViewTree`** via `NativeAuthoringRuntime` → `NativeRuntimeBridge::bridge_artifact` (`native_artifact_from_vue_with_defaults`, lib.rs:405). The tests prove this is real: `vue_35_renderer_preserves_static_text_children` builds an actual `RuntimeDrawCommand::Text` skia command (`"Static Title"`); `_with_styles`/`_with_theme` assert resolved `Color::rgba` fills (e.g. `240,88,40,255` and a themed `245,243,238,255`). This path is **not** record-only.
- **The `from_native_program` path drives the real validated `CustomRendererProtocol`.** `vue_artifact_from_native_program` (lib.rs:475) calls `custom_renderer_operation_keys("vue")` (authoring `adapter.rs:212`), which applies `CreateNode`/`SetStyleRef`/…/`Commit` through `CustomRendererProtocol::apply` → `validate_operation` (authoring `adapter.rs:482`) with **real** duplicate-node and reference-before-create checks. The native-path operation list is derived, not canned.

No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no `unwrap`/`expect`/`panic!`, no TODO/FIXME/HACK markers.

What **is** canned/fabricated is scoped to three things, all on the **source-scan** path: (1) **`renderer_operations` is a canned skeleton** — `render()` (lib.rs:296-300) emits `create:root` + `patch-props:root` as unconditional bookends with the keyed `insert:{child}` entries spliced between, **never touching `CustomRendererProtocol`** (the crate does not even import it) and performing **zero** node-identity validation — whereas React's source path runs the real protocol; (2) **`lifecycle_handlers` is unconditional canned data** — always `["mounted:onMounted","unmounted:onUnmounted"]` regardless of source, and inconsistent with the conditionally-built `events`; (3) **handler identifiers are hardcoded, not parsed** (`@pointerdown`→`handlePress`, `@mounted`→`onMounted`, `@unmounted`→`onUnmounted`). There is one **genuine Vue improvement** over the siblings: the `:id=`/`v-bind:id=` guards (lib.rs:628-629, 645-646) correctly skip dynamically-bound text-node ids. No correctness blocker on the desktop happy path; the defects are record-fidelity and a public-API-consistency latent issue.

## Completeness & implementation gaps

1. **`renderer_operations` is a canned skeleton with derived inserts and no validation (source path)** (lib.rs:296-300). `render()` builds `renderer_operations` as `push("create:root")` → `extend(keyed_children → "insert:{child}")` → `push("patch-props:root")`. The two bookends are unconditional literals (emitted even for an empty component with no props and no children); only the `insert:{child}` entries are derived (from the keyed-children scan). Crucially this path **never constructs a `CustomRendererProtocol`** — the crate imports only `CustomRendererError` (lib.rs:567), not `CustomRendererProtocol`/`CustomRendererOperation` — so it cannot catch the duplicate-node / reference-before-create errors that React's `react_protocol_operations` (react `lib.rs:584`) catches via `validate_operation`. This is the crate's central real-vs-record divergence from React. Vue is **not unique** here — Solid's `fine_grained_updates` is likewise canned and Svelte exposes no operation list at all (see Code quality); React is the lone sibling running the real protocol in its source path. → Either route the source path through `CustomRendererProtocol` (as React does) or document `renderer_operations()` as an advisory sketch on the source path.

2. **`renderer_operations()` returns a *different vocabulary* on the two construction paths, untested** (lib.rs:296-300 vs lib.rs:480-482). The same public accessor returns canned `["create:root","insert:title",…,"patch-props:root"]` on the source path, but on the `from_native_program` path returns the **raw, untransformed** protocol stable keys — e.g. `create-node:root:view`, `set-style:root:surface.card`, `set-asset:root:…`, `set-ref:root:root_ref`, `bind-event:root:pointer.press`, `bind-lifecycle:root:mounted:onMount`, `set-prop:title:…`, `append-child:root:title:key:title`, `commit:root` (vocabulary confirmed in authoring `adapter.rs:357`; exact ordering follows `emit_node_operations`, authoring `adapter.rs:602`). A consumer comparing the two will see total drift. This is Vue's analog of React's reconciler-key issues — but note it is the **inverse** of React's bug: React applies a `react_public_operation_key` transform that *mis-fires* off the happy path (react `lib.rs:719`), whereas Vue applies **no** normalization at all, so the raw internal keys leak verbatim into the public API on the native path. **No test pins the native-path `renderer_operations()`** (the native-program test, vue_integration.rs:80-94, asserts root/children/refs/styles/events/lifecycle/`operation_keys` but never `renderer_operations()`), so the inconsistency is invisible. → Normalize both paths to one public vocabulary, or document the asymmetry.

3. **`lifecycle_handlers` is unconditional canned data (source path)** (lib.rs:313). The source-scan branch always sets `lifecycle_handlers: vec!["mounted:onMounted".into(), "unmounted:onUnmounted".into()]` with no dependence on `component.source`. Render `<hawk-view id="root"></hawk-view>` (no `@mounted`/`@unmounted`): `events()` correctly contains **no** lifecycle bindings (those *are* gated on `source.contains("@mounted")`/`"@unmounted"`, lib.rs:280/287), yet `lifecycle_handlers()` still reports both `mounted:onMounted` and `unmounted:onUnmounted`. The two fields disagree for the same input — `events` conditional, `lifecycle_handlers` not — marking this an oversight, not intent. No test asserts `lifecycle_handlers` on a no-lifecycle source (the only source-path test, vue_integration.rs:46-49, uses a source containing both hooks), so the canned output is invisible. The native-program branch (lib.rs:498-503) derives `lifecycle_handlers` correctly from `native_program.root().lifecycle()`; only the source-scan branch is canned. Direct parallel to React #1. → Gate the labels on the same `source.contains(…)` checks that gate `events`, or derive both from one source of truth.

4. **Handler identifiers are fabricated, not parsed** (lib.rs:270-293, repeated lib.rs:435-447). `@pointerdown` unconditionally records `HandlerRef::new("handlePress")`; `@mounted`/`@unmounted` record the literal `"onMounted"`/`"onUnmounted"`. The authored handler expression (`@pointerdown="handleX"`) is never extracted — two components with different handlers produce byte-identical artifacts. The source-path test uses exactly these names (vue_integration.rs:22 authors `@pointerdown="handlePress"` etc.), so it asserts the fabricated constants rather than catching the gap (false confidence). Shared with React/Solid/Svelte. → Parse the `="…"` binding expression, or document handler names as placeholders.

5. **Source scanner is single-element / root-only** (lib.rs:581-681). The "render" path is attribute-substring scanning, not a parse: `extract_attribute` finds the first `name="…"` occurrence; the root is always `ElementKind::View`; children are always `ElementKind::Text`; there is no nested element tree, no arbitrary component nesting, no non-text leaf kinds. This is an intentional thin author-source heuristic feeding the typed-record layer (the real fidelity path is `from_native_program`), but the limitation is undocumented at `render()`. **Vue-specific sub-case (Low, fold here):** Vue's `:id=`/`v-bind:id=` guard (lib.rs:628-629, 645-646) correctly excludes a dynamically-bound `<hawk-text :id="item.id">` from `static_hawk_text_ids`/`static_hawk_text_content`. The consequence is that for the canonical `v-for` SFC (vue_integration.rs:23), keyed ids come solely from `declared_item_ids` (the `:key="item.id"` → `id: 'title'` script scan), and the per-child `text` prop falls back to the child id rather than extracted content (lib.rs:456-459, `static_hawk_text_content` returns `None` for the dynamic node). Correct for Vue idiom, but the fallback is silent. → Document the source-grammar limits, or route real authoring through the native-program boundary.

## Code quality & smells

- **Four-way copy-paste with near-zero shared code.** `extract_attribute`, `extract_number_attribute`, `style_refs_from_attribute`, `keyed_children`, `static_hawk_text_ids`, `static_hawk_text_content`, `declared_item_ids`, `push_unique`, `framework_program_events`, `lifecycle_event_kind`, `lifecycle_handler_label`, `bridge_error`, `custom_renderer_error`, and the entire `native_artifact_from_*` / `*_with_defaults` lowering are duplicated **near-verbatim** across react/solid/svelte/vue (only framework-name strings, the event-token table, and the attribute syntax differ). A bug fixed in one (e.g. gap #3) must be fixed in four files; there is no shared `hawk2ui-framework-core`. Dominant maintainability risk for the family.
- **The public renderer-op surface has diverged across all four siblings.** React → `reconciler_operations()` built from a real validated `CustomRendererProtocol`; Vue → `renderer_operations()` canned skeleton (this crate); Solid → `fine_grained_updates()` canned (`signal:items`/`for-each:keyed`/`effect:root-props`, solid `lib.rs:313`+`:504`); Svelte → **no operation list at all** (carries a `diagnostics` field instead, svelte `lib.rs:82`). Four crates that are supposed to be parallel adapters expose four different (and three non-validated) operation contracts. Family-level inconsistency; **do not read it as a Vue-specific defect** beyond gaps #1/#2.
- **The one genuine Vue improvement: dynamic-id guards.** The `:id=`/`v-bind:id=` checks (lib.rs:628-629, 645-646) are present **only** in Vue (4 occurrences; 0 in react/solid/svelte). They are correct: without them, `extract_attribute(segment, "id")` would pull `item.id` out of `:id="item.id"` and emit a spurious literal child id. This is the lone case where Vue is *more* correct than the reference sibling. (Noted positively per the anti-false-positive guidance.)
- **Asset `name` is a constant namespace, not a Vue attribute** (lib.rs:310). `AssetRef::new("vue.asset", path)` hardcodes the name; only the path is author-derived. Matches siblings (`react.asset`/`solid.asset`); intentional namespacing, noted for completeness.
- **Magic visual defaults baked into the adapter** (lib.rs:424, 460-463): root `background "#080a0e"`, text `color "#ffffff"`, `width 160.0`, `height 32.0`, default `font_size 18.0`. Leaky presentation constants in an integration adapter (sourced from neither style nor tokens); they match test expectations and the authoring adapter's own `#080a0e` default, but a real theme should own them. Low; shared with siblings.
- **`framework_version_requirement()` returns a hardcoded `">=3.5"` string** (lib.rs:130) never used for any actual version check — purely advisory metadata. Fine, but it implies enforcement that does not exist.

## Documentation

- Strong: crate-level `//!`, every public type and method documented, and `# Errors` sections on all four fallible entry points (`render`, `render_to_runtime`, `render_to_runtime_with_styles`, `render_to_runtime_with_theme`). No undocumented public items.
- Misleading/under-documented tied to the gaps above: nothing documents that `renderer_operations()` is a canned skeleton on the source path (gap #1) nor that it returns a different vocabulary on the native path (gap #2); nothing documents that `lifecycle_handlers()` is unconditional on the source path (gap #3), that handler names are placeholders (gap #4), or that `render()` models only a root + flat text children (gap #5). The `# Errors` text itself is accurate.

- **False-confidence (masks #3/#4):** the only source-path record test (vue_integration.rs:13) feeds a source containing **both** `@mounted` and `@unmounted`, so the unconditional canned `lifecycle_handlers` (gap #3) is never exposed; a test rendering a no-lifecycle source and asserting `lifecycle_handlers().is_empty()` would catch it. Handler-name assertions (`handlePress`, `onMounted`, `onUnmounted`) assert the fabricated constants (gap #4) rather than parsed values.
- Coverage gaps: no test pins the **native-path `renderer_operations()`** (would surface the dual-vocabulary inconsistency, gap #2); no test for `vue.event.unsupported` (the `@click`/`@hover`/`@mouseenter`/`@keydown` denylist, lib.rs:602, is entirely untested); no test for `vue.runtime-bridge.failed` or `vue.custom-renderer.failed`; **no test with a non-`"root"` root id**; no test asserting the canned `renderer_operations()` skeleton stays consistent with the bridge `operation_keys()`.

## Security

The trust boundary is the **untrusted author `&str` source** (and a caller-supplied `FrameworkNativeProgram`), *not* `Deserialize`-able input. **This crate derives no Serde on any public type and contains no recursion**, so — unlike `hawk2ui-a11y` — there is no deserialization attack surface and no in-crate stack-overflow vector. `#![forbid(unsafe_code)]` holds; there is no `unsafe`. The attack surface is identical to the React sibling — no new surface is introduced.

- **No panics-as-DoS.** There are no `unwrap()`/`expect()`/`panic!`. The `unwrap_or`/`unwrap_or_else`/`unwrap_or(18.0)` sites (lib.rs:268, 448, 458, 627) are all infallible-default forms. String slicing is on ASCII byte literals (`"<hawk-text"`, `>`, `"`, `</hawk-text>`) or `find`-computed offsets, and UTF-8 multibyte quote handling in `declared_item_ids` uses `quote.len_utf8()` (lib.rs:672, 678), so no char-boundary panic. Confirmed safe.
- **Source scanners are bounded by input length, not attacker-controlled depth.** `static_hawk_text_ids`, `static_hawk_text_content`, and `declared_item_ids` (lib.rs:622-681) are iterative `while let Some(index) = rest.find(…)` loops that advance `rest` monotonically — linear in source length, no recursion, no unbounded allocation beyond the (input-bounded) id vectors. No DoS here.
- **Recursion / stack-overflow risk is downstream, reachable via `from_native_program`** (lib.rs:411-413). `to_native_authoring_artifact` and (via the native path) `custom_renderer_operation_keys`/`NativeRuntimeBridge::bridge_artifact` recurse over the element/child tree inside `hawk2ui-authoring` (`emit_node_operations`, authoring `adapter.rs:602`, recurses over children). A caller-supplied `FrameworkNativeProgram` with deeply nested children flows straight into those recursive traversals. The unbounded-depth concern is **real but belongs to `hawk2ui-authoring`**, not this adapter — this crate is the entry point, not the recursion site. **Verify/Low (attributed downstream).**
- **Path/asset validation is shallow but present** (lib.rs:237-245). The `vue.asset.path-invalid` guard rejects `://`, leading `/`, and `..` in `data-asset`, blocking absolute/traversal/scheme paths from reaching downstream asset loading. It only checks the *first* `data-asset` occurrence (single-element scanner) and is a substring check, not path normalization, but it is a reasonable workspace-relative gate at the boundary.
- **Good:** on the `from_native_program` path the protocol's `validate_operation` (authoring) rejects duplicate nodes and reference-before-create, so malformed native programs cannot silently corrupt the operation list; bridge/protocol/native-finalization failures all convert to source-mapped `AuthoringDiagnostic`s rather than panicking. **Caveat:** the **source path** does not run this validation (gap #1), so a source-scan that produced a colliding id would not be caught by the renderer-op layer (it would still be caught downstream at `runtime.finish()`/`bridge_artifact`).
