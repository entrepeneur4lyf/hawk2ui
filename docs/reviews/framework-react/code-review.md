# Code Review — hawk2ui-framework-react

**Reviewed at:** `5a042c51` · 2026-05-28 · **Remediated (contained subset):** 2026-05-29
**Scope:** `src/lib.rs` + `tests/react_integration.rs` (1 src file ~851 LoC / 1 test file ~330 LoC)
**Purpose:** React 19+ integration adapter. Scans author TSX source (or accepts explicit native-compiler output) and emits typed `Hawk2UI` records — root `ElementNode`, keyed children, refs, style/asset refs, event + lifecycle bindings, and a custom-renderer reconciler-operation key list — then bridges to a runtime view tree via `hawk2ui-authoring`'s `NativeRuntimeBridge`. One of four near-identical siblings (react/solid/svelte/vue).
**Note:** Codex is concurrently committing hardening/remediation work; HEAD drifts (git HEAD is `5fecf2c4`). Findings reflect the SHA above and may overlap with in-progress fixes.

## Remediation (2026-05-29) — contained subset

Fixed the two findings that are bugs *within the scanner's existing design* (a public field that lies, and a latent key-leak) plus the honest documentation of the heuristic's limits; surfaced the one finding that would prejudge an open design decision. Verified: `cargo test -p hawk2ui-framework-react` (12 passed, +3) + `cargo clippy -p hawk2ui-framework-react --all-targets -- -D warnings` (clean) + `check-fast` (green).

**Reachability context (informs severity):** the raw-source `render()` / `render_to_runtime()` path has **no build-pipeline or CLI caller** — every `render_to_runtime` call site is in `hawk2ui-framework-conformance` (which uses `from_native_program`, `lib.rs:665`) or the crates' own integration tests. So production fidelity is expected to flow through the `from_native_program` boundary (explicit native-compiler output), and the source-scan path is a heuristic/conformance surface. The two fixes below still matter because they harden **public accessors** (`lifecycle_handlers()`, `reconciler_operations()`) that the conformance and test surfaces read.

- **#1 — `lifecycle_handlers` was unconditional canned data (FIXED, Medium).** `render()` always set `lifecycle_handlers: vec!["mounted:onMount","unmounted:onUnmount"]` regardless of source, while `events` were gated on `source.contains("onMount")`/`("onUnmount")` — the two public surfaces disagreed for the same input (a no-lifecycle source reported zero lifecycle `events` but two `lifecycle_handlers`). This is a bug *within* the design (not a fidelity decision): the `from_native_program` path already derives the field correctly from `root().lifecycle()`. Now both labels are gated on the same `source.contains(…)` checks as the events, so they agree by construction. Locked by `react_source_path_lifecycle_handlers_track_declared_hooks` (no-hooks source → empty + no lifecycle events; `onMount`-only source → `["mounted:onMount"]`).
- **#3 — `react_public_operation_key` leaked raw internal keys off the happy path (FIXED, Medium).** It did `strip_prefix("append-child:root:")`, hardcoding the parent as `"root"`. A custom root id (`id="app"`) **or** a nested `from_native_program` tree (whose grandchildren are parented at a non-root id — confirmed: authoring `emit_node_operations` recurses with the child as parent, `adapter.rs:706`) caused the strip to mis-fire, leaking the raw `append-child:{parent}:{child}:key:{key}` shape unchanged into the public `reconciler_operations()`. Rewrote it parent-agnostic: strip `append-child:`, take the segment before `:key:`, and lower its final `:`-segment to `append:{child}`. This now covers every parent (root, custom-root, grandchild) and needs no signature/call-site change. Locked by `react_public_operation_keys_use_actual_root_id` (`id="app"` → `append:title`, asserts no `append-child:` prefix survives).
- **#4 — undocumented source-grammar limits (FIXED-by-doc, Low).** Added a `# Source grammar (raw-source path)` section to `render()` stating it is a substring heuristic, not a TSX parser: single root `View` + flat `<hawk-text>`/keyed children only, no nested trees, and **handler identifiers on this path are fixed labels** (`onPointerDown` → `handlePress`), not parsed — pointing authors to `from_native_program` for fidelity. This honestly discloses the #2 limitation (below) at the API surface, pending the design decision.
- **#9 (real subset) — added the tests that observe #1/#3 and fill the `react.event.unsupported` gap.** The three tests above + `react_reports_unsupported_event` (the `onClick`/`onHover`/… denylist was entirely untested).

**Surfaced / deferred (NOT fixed — would prejudge an open decision or has no in-crate fix):**
- **#2 — handler identifiers are fabricated, not parsed (SURFACED → `frameworks-real-compiler`, Medium).** `onPointerDown={handleX}` always records `handlePress`; the authored expression is never read. This is *not* a bug within the design — it is "how much should the source-scan path parse," which is a miniature of the open frameworks-real-compiler decision. A partial fix (extract a bare identifier, fall back otherwise) is worst-of-both: it turns a uniformly-visible fabrication into a **silent mix** of real and fabricated handlers, lowering detectability while prejudging the decision 4×. Honest disclosure added to the `render()` doc instead; real fix belongs to the compiler decision (or: fail loudly on a non-bare expression). Shared family-wide.
- **#6 — four-way verbatim copy-paste, no `hawk2ui-framework-core` (SURFACED, Low/architecture).** A fix here (e.g. this #3 rewrite) must be applied in up to four files. Extracting a shared core is an architecture decision; surfaced, not unilaterally done.
- **#7 — magic visual defaults (`#080a0e`/`#ffffff`/160×32/font 18) baked into the adapter (deferred, Low).** A real theme should own them; moving them to style/tokens is a design decision and they currently match test + authoring-adapter defaults. Deferred.
- **#5 — `reconciler_operations()` vs `operation_keys()` independently lowered (deferred, Low).** Low value; "lower once" is a refactor, and the asymmetry is intended (different layers). Not churned.
- **#8 — unbounded child-tree recursion via `from_native_program` (attributed downstream).** The recursion site is `hawk2ui-authoring` (`to_native_authoring_artifact`/`bridge_artifact`), which already bounds depth (`MAX_AUTHORING_TREE_DEPTH`, `adapter.rs:642`). Not this crate's fix.

## Summary

This crate is **genuinely wired, not a declarative stub** — and on the structural axis it is the **most complete of the four framework siblings**. Two real pipelines exist and are exercised end-to-end:

- **`render()` builds a real `CustomRendererProtocol`** (`react_protocol_operations`, lib.rs:584): it issues `CreateNode`/`SetStyleRef`/`SetAssetRef`/`SetRef`/`BindEvent`/`BindLifecycle`/`AppendChild`/`Commit` through `CustomRendererProtocol::apply`, whose `validate_operation` (authoring `adapter.rs:482`) performs **real** duplicate-node, reference-before-create, and parent/child-existence checks. The reconciler-operation list is derived, not canned.
- **`render_to_runtime()` lowers to a real `RuntimeViewTree`** via `NativeAuthoringRuntime` → `NativeRuntimeBridge::bridge_artifact` (authoring `runtime_bridge.rs:32`). The tests prove this is real: `react_19_renderer_preserves_static_text_children` builds actual `RuntimeDrawCommand::Text` skia commands; the `_with_styles`/`_with_theme` tests assert resolved `Color::rgba` fills. No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no `unwrap`/`expect`, no TODO/FIXME/HACK markers.

The substantive weaknesses are in the **per-field record contents of the source-scanning path**, where several fields are fabricated rather than parsed: (1) **`lifecycle_handlers` is unconditional canned data** — `render()` always returns `["mounted:onMount","unmounted:onUnmount"]` regardless of whether the source declares any lifecycle hook; (2) **handler identifiers are hardcoded, not read from source** (`onPointerDown` always → `handlePress`, lifecycle always → `onMount`/`onUnmount`); (3) `react_public_operation_key` **hardcodes the `append-child:root:` prefix**, so any non-`"root"` root id leaks raw internal keys into the public API; (4) the source scanner is a single-element, attribute-substring matcher (root-only; no nested element tree). No correctness blocker on the desktop happy path; the defects are record-fidelity and a root-id-fragility latent bug.

## Completeness & implementation gaps

1. **`lifecycle_handlers` is unconditional canned data** (lib.rs:317). The source-scan branch of `render()` always sets `lifecycle_handlers: vec!["mounted:onMount".into(), "unmounted:onUnmount".into()]` — with no dependence on `tree.source`. Render `<hawk-view id="root"></hawk-view>` (no `onMount`/`onUnmount`): `events()` correctly contains **no** lifecycle bindings (those *are* gated on `source.contains("onMount")`, lib.rs:277/284), yet `lifecycle_handlers()` still reports both `mounted:onMount` and `unmounted:onUnmount`. The two fields disagree for the same input — `events` is conditional, `lifecycle_handlers` is not — which marks this as an oversight, not intent. No test asserts `lifecycle_handlers` on a no-lifecycle source (every test that checks it uses a source containing both hooks), so the canned output is invisible. Note: the native-program branch (`react_artifact_from_native_program`, lib.rs:505) derives `lifecycle_handlers` correctly from `native_program.root().lifecycle()`; only the source-scan branch is canned. → Gate the labels on the same `source.contains(…)` checks that gate `events`, or derive both from one source of truth.
2. **Handler identifiers are fabricated, not parsed** (lib.rs:267-289, repeated at lib.rs:439-451). `onPointerDown={…}` unconditionally records `HandlerRef::new("handlePress")`; `onMount`/`onUnmount` record the literal handler names `"onMount"`/`"onUnmount"`. The actual authored handler expression (`onPointerDown={handleX}`) is never extracted — two components with different handlers produce byte-identical artifacts. The tests use exactly these names (`handlePress`, `onMount`, `onUnmount`), so they assert the fabricated values rather than catching the gap (false confidence). Shared with Vue/Solid (also hardcode), so a family-wide pattern, not a React divergence. → Parse the `={…}` binding expression, or document handler names as placeholders.
3. **`react_public_operation_key` hardcodes the `"append-child:root:"` prefix** (lib.rs:719-723). It does `key.strip_prefix("append-child:root:")` then `format!("append:{child}")`. The authoring layer emits `append-child:{parent}:{child}:key:{key}` (authoring `adapter.rs:385`). When the root id is literally `"root"` (the only id any test uses) this strips correctly to `append:{child}`. But when the author sets `id="app"` (root id is taken from the `id=` attribute, lib.rs:265) **or** a `from_native_program` root is not named `"root"`, the prefix never matches and the **raw** `append-child:app:title:key:title` leaks unchanged into the public `reconciler_operations()`. Vue (the other `CustomRendererProtocol` user) applies **no** such transform at all, so the public key shapes already diverge between the two; React's transform additionally mis-fires off the happy path. → Strip `append-child:{root_id}:` using the actual root id, or split on `":key:"` without assuming the parent.
4. **Source scanner is single-element / root-only** (lib.rs:741-835). The "render" path is attribute-substring scanning, not a parse: `extract_attribute` finds the first `name="…"` occurrence; the root is always `ElementKind::View`; children are always `ElementKind::Text`; there is no nested element tree, no arbitrary component nesting, no non-text leaf kinds. This is an intentional thin author-source heuristic feeding the typed-record layer (the real fidelity path is `from_native_program`), but the limitation is undocumented at `render()`, so authors cannot see that only the root element and a flat list of `<hawk-text>`/keyed children are modeled. → Document the source-grammar limits, or route real authoring through the native-program boundary.
5. **`reconciler_operations` and `operation_keys` are independently lowered** (lib.rs:330-343). `render_to_runtime` calls `render()` (which builds reconciler keys via `CustomRendererProtocol`) **and** `native_artifact_from_react` (which separately builds a `NativeAuthoringRuntime` tree whose `operation_keys()` come from `bridge_artifact`). The two key lists are derived from two independent lowerings of the same source; nothing guarantees they stay consistent (e.g. the protocol path emits `set-asset`/`set-ref`, the bridge path emits `mount-element:*`). They are *intended* to describe different layers, but a consumer comparing them will see drift, and a source change that updates one path but not the other would not be caught. Low. → Note the asymmetry or lower once.

## Code quality & smells

- **Four-way copy-paste with near-zero shared code.** `extract_attribute`, `extract_number_attribute`, `style_refs_from_attribute`, `keyed_children`, `static_hawk_text_ids`, `static_hawk_text_content`, `declared_item_ids`, `push_unique`, `framework_program_events`, `lifecycle_event_kind`, `lifecycle_handler_label`, `bridge_error`, and the entire `native_artifact_from_*` / `*_with_defaults` lowering are duplicated **verbatim** across react/solid/svelte/vue (only framework-name strings and the event-token table differ). A bug fixed in one (e.g. the root-id strip in #3) must be fixed in four files; there is no shared `hawk2ui-framework-core`. This is the dominant maintainability risk for the family.
- **Divergence (informational, not a React defect): React is the reference; Vue/Solid are more canned.** Vue's source-path `renderer_operations` is three canned strings — `create:root`, `insert:{child}`, `patch-props:root` (vue `lib.rs`), not a validated protocol. Solid's `fine_grained_updates` is three hardcoded strings — `signal:items`, `for-each:keyed`, `effect:root-props` — emitted **unconditionally regardless of source** (solid `lib.rs:313` and again at :504), the clearest record-only stand-in in the family. React alone runs a real `CustomRendererProtocol` with validation in its source path. Do **not** read React's richer behavior as a defect; the *siblings* are the weaker implementations.
- **Asset `name` is a constant namespace, not the React attribute** (lib.rs:297). `AssetRef::new("react.asset", path)` hardcodes the name; only the path is author-derived. Matches siblings (`solid.asset`/`vue.asset`); intentional namespacing, noted for completeness.
- **Magic visual defaults baked into the adapter** (lib.rs:428,465-467): root `background "#080a0e"`, text `color "#ffffff"`, `width 160.0`, `height 32.0`, default `font_size 18.0`. These are leaky presentation constants in an integration adapter (sourced from neither style nor tokens); they match test expectations and the authoring adapter's own `#080a0e` default, but a real theme should own them. Low; shared with siblings.
- **`framework_version_requirement()` returns a hardcoded `">=19"` string** (lib.rs:131) that is never used for any actual version check — purely advisory metadata. Fine, but it implies enforcement that does not exist.

## Security

The trust boundary is the **untrusted author `&str` source** (and a caller-supplied `FrameworkNativeProgram`), *not* `Deserialize`-able input. **This crate derives no Serde on any public type and contains no recursion**, so — unlike `hawk2ui-a11y` — there is no deserialization attack surface and no in-crate stack-overflow vector. `#![forbid(unsafe_code)]` holds; there is no `unsafe`.

- **No panics-as-DoS.** There are no `unwrap()`/`expect()`/`panic!`. The four `unwrap_or`/`unwrap_or_else` sites (lib.rs:265,452,461,787) are all infallible-default forms. All string slicing is on ASCII byte literals (`"<hawk-text"`, `>`, `"`, `</hawk-text>`) or computed via `find`, and UTF-8 multibyte quote handling in `declared_item_ids` uses `quote.len_utf8()` (lib.rs:826,832), so no char-boundary panic. Confirmed safe.
- **Source scanners are bounded by input length, not attacker-controlled depth.** `static_hawk_text_ids`, `static_hawk_text_content`, and `declared_item_ids` (lib.rs:782-835) are iterative `while let Some(index) = rest.find(…)` loops that advance `rest` monotonically — linear in source length, no recursion, no unbounded allocation beyond the (input-bounded) id vectors. No DoS here.
- **Recursion / stack-overflow risk is downstream, reachable via `from_native_program`** (lib.rs:415-417). `to_native_authoring_artifact` and `NativeRuntimeBridge::bridge_artifact` recurse over the element/child tree inside `hawk2ui-authoring` (already documented in that crate's review). A caller-supplied `FrameworkNativeProgram` with deeply nested children flows straight into those recursive traversals. The unbounded-depth concern is **real but belongs to `hawk2ui-authoring`**, not this adapter — this crate is the entry point, not the recursion site. **Verify/Low (attributed downstream).**
- **Path/asset validation is shallow but present** (lib.rs:235-243). The `react.asset.path-invalid` guard rejects `://`, leading `/`, and `..` in `data-asset`, blocking absolute/traversal/scheme paths from reaching downstream asset loading. It only checks the *first* `data-asset` occurrence (single-element scanner) and is a substring check, not a path-normalization, but it is a reasonable workspace-relative gate at the boundary.
- **Good:** the reconciler protocol's `validate_operation` (authoring) rejects duplicate nodes and reference-before-create, so malformed operation sequences cannot silently corrupt the runtime tree; bridge/protocol/native-finalization failures all convert to source-mapped `AuthoringDiagnostic`s rather than panicking.
