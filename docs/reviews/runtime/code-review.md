# Code Review — hawk2ui-runtime

**Reviewed at:** `5a042c51` · 2026-05-28 · **Remediated at:** `e7918972` · 2026-05-28
**Scope:** `src/{lib,bindings,events,lifecycle,safety,scene_payload,scheduler,script,view,persistence}.rs` + `tests/runtime_behavior.rs` (10 src files ~1.6k LoC / 1 test file ~1.3k LoC)
**Purpose:** Runtime core — script-module records and a script-engine boundary, capability-scoped host bindings, deterministic event dispatch, work/animation scheduling, lifecycle-hook registry, runtime safety guard, state persistence, and the retained view tree that bridges into `hawk2ui-layout`/`hawk2ui-render`.
**Note:** The High recursion-DoS finding (#1) and the capability-overreach doc (#2) were **remediated** at `e7918972`; a **follow-up** fixed a High nested-node coordinate bug in the view→render bridge that the original review had mislabeled "real and correct" — see the Remediation sections. The findings text below reflects the original review at `5a042c51`; the remaining items are unaddressed quality/design notes.

## Summary

This crate is a mix of **genuinely-implemented machinery** and **record-only models**, and the distinction is load-bearing for judging it honestly:

**Real (state this plainly):**
- **The view→render bridge is real.** `view.rs::RuntimeSceneBridge::build` does actual work: `to_layout_tree` builds a `hawk2ui_layout::LayoutTree` and computes layout (including text measurement), `to_scene_graph` builds a real `SceneGraph`, `to_layers_and_draw_commands` emits `PaintLayer`s and `RuntimeDrawCommand`s, and `export_paint_commands` produces stable paint commands. The Skia test (`runtime_scene_bridge_output_renders_visible_pixels_with_skia`) renders real pixels. This is the crate's substantive engine. **Correction (follow-up remediation):** it was real but not correct — it emitted parent-relative geometry for nested nodes (dropping ancestor offsets), so any depth-≥3 subtree mis-rendered. The original review missed this because the existing Skia/smoke tests assert pixel *presence*, not nested *position*. Fixed — see Remediation.
- **Event dispatch is real routing.** `events.rs::RuntimeEventDispatcher::dispatch_pending` / `delivery_targets` filter deliveries by `(target, kind)` listener membership and append the bubble path; **all five** `RuntimeEventKind` variants route uniformly — none fall through to a no-op. Teardown cancellation is enforced.
- **Host-binding gating is real (as validation).** `bindings.rs::HostBindingRegistry::call` enforces unknown-binding, lifecycle-availability, capability, and schema-label checks *before* returning. It returns a validated descriptor (`HostBindingCall`), not an invocation.
- **The safety guard, scheduler, persistence, and animation cadence are real** deterministic logic with no stubs.

**Record-only by design (not `todo!()` stubs, but the crate does not perform the action its docs imply):**
- **Scripts are never loaded or executed.** There is no `hawk2ui-script`/boa dependency (`Cargo.toml` deps are api/layout/render + serde only). `script.rs` defines a `ScriptEngine` *trait boundary* and one impl — `RecordingScriptEngine` — that pushes every operation onto a `Vec<ScriptEngineOperation>` and returns `Ok(())`. It models the lifecycle of script interaction; it does not run JS/TS. The crate-level doc ("Script loading…") overstates this.
- **Lifecycle hooks are never invoked.** `lifecycle.rs::LifecycleRegistry` is a phase-filtered list (`hooks_for`); nothing in the crate calls a hook or sequences mount/unmount. There is no mount/unmount *ordering* logic at all — only registration order within a phase.

No `todo!`/`unimplemented!`/`unreachable!`, no placeholder panics, no TODO/FIXME/HACK markers anywhere. The substantive weaknesses are: (1) **unbounded recursion over a `Deserialize`-able, untrusted scene payload** (`scene_payload.rs`) — stack-overflow DoS, the same class a11y rated High; (2) **doc/capability overreach** — the crate advertises script loading/execution and lifecycle handling it does not perform; (3) a recursive `StructuredValue` that crosses every untrusted surface with no depth bound; and (4) a partial `Diagnostic` bridge and a path-key validation inconsistency.

## Remediation (2026-05-28 · `e7918972`)

Fixed the one High finding (#1, recursion DoS) and corrected the capability-overreach doc (#2/#4-doc); added coverage for the untrusted-input boundary (#9).

- **#1 — unbounded recursion over an untrusted scene payload (FIXED).** Scene payloads arrive as caller-supplied JSON carried by sealed artifacts, and the consumer does not verify the artifact signature at the call site (`hawk2ui-plugin-adapters::…::runtime_scene_frame` — its own finding), so a tampered artifact can deliver an arbitrarily deep payload. All three recursion sites are now bounded to `RUNTIME_SCENE_MAX_DEPTH` (256): an **iterative** `enforce_value_depth` pre-scan runs in `from_json` *before* `serde_json::from_value` / the recursive `Value::clone` (explicit work stack, so the check itself cannot overflow), and `validate`/`append_children` carry depth bounds (covering programmatic construction). Mirrors the a11y/script depth-bound pattern. Tests: `runtime_scene_payload_rejects_deeply_nested_input_before_overflow`, `…builds_a_well_formed_frame`, `…rejects_unknown_fields`.
- **#2 / #4-doc — capability + doc overreach (doc FIXED; capability deferred).** The crate-level `//!` no longer claims "script loading" or "lifecycle" handling that the crate does not perform; it now states that script engines and lifecycle hooks are **modeled boundaries** (the recording engine + hook registry), with execution/sequencing supplied by the host. **Capability decision surfaced for the bucket-(c) round:** wiring a *real* script engine + lifecycle invocation into the runtime is a feature, not remediation — and note the CLI already executes entry scripts via `hawk2ui-script` directly (`executor.rs` `entry_script_*`), not through this crate's `ScriptEngine` seam, so whether the runtime should own script execution is an architecture decision.

**Coverage added (#9).** `scene_payload.rs` had zero tests; it now has depth-rejection, happy-path build, and unknown-field rejection.

**Not addressed here** (deferred Low items, unchanged from below): #3 recursive `StructuredValue` deserialize (no in-crate recursion today — bound it if a consumer recurses), #4 `with_child` O(n²) (needs a `RuntimeViewId`→index map in `view.rs`, a separable refactor), #5 partial `Diagnostic` bridge (~8 mechanical `From` impls), #6 `is_stable_key` permits `..`, #7 unbounded queue/history growth, #8 bubble double-delivery.

## Remediation follow-up (2026-05-28) — nested-node coordinate bug (High, FIXED)

A finding the original review *missed* and the `hawk2ui-layout` review (`0113eef`) only *documented*: the bridge produced **parent-relative** geometry for every node and never accumulated ancestor offsets, so the wired render path drew nested nodes at the wrong absolute position.

- **Mechanism (traced end-to-end).** Taffy reports each node's `Layout::location` relative to its parent's border box; `hawk2ui-layout` faithfully preserves that (its `ComputedGeometry` is documented parent-relative, and the layout test `computed_geometry_is_parent_relative_not_absolute` pins it). The runtime bridge copied those coordinates **verbatim** into both outputs — `collect_geometry`/`to_layers_and_draw_commands` → `RuntimeDrawCommand`/`PaintLayer`, and `scene_node_for` → `SceneNode` layout/hit-test rects — with no accumulation. The **only** wired renderer, `hawk2ui_render_skia::SkiaRendererBackend::draw_runtime_scene_frame_with_options`, iterates the *flat* `draw_commands()` and blits each at its stored geometry under a single global DPI transform; it never walks the scene graph to compose offsets. `SceneGraph::accessibility_geometry` likewise applies only the node's *own* (identity) transform. Net: a node at depth ≥ 3 (any node whose parent is not the root) renders, hit-tests, and reports a11y geometry offset by the sum of its ancestors' positions. Both host surfaces are affected — desktop (`host-winit` `present_frame` → `render_scene_frame`) and plugin (`host-baseview` `render_scene_to_skia_snapshot`) both funnel through the same backend call.
- **Severity: High, latent-but-live.** It is on the real, shipped render path for both surfaces, and triggers for essentially any non-trivial nested UI (a container holding a row holding a label). It had not surfaced because (a) the shipped examples are trivially shallow — `examples/desktop-basic` returns a single root node — and (b) every Skia/smoke/visual test asserts pixel *presence*/color, which a *position* error survives. No test or fixture caught it; the regression test below is the first depth-3 assertion in the suite.
- **Fix (consumer-side, `view.rs`).** Added `resolve_absolute_geometry`, which accumulates `absolute(node) = location(node) + absolute(parent)` (root at the origin) in one pass over the parent-before-child `entries` (`RuntimeViewTree::with_child` guarantees that order; an unresolved parent surfaces as `MissingParent`). Both `collect_geometry` (→ draw commands, layers, paint commands) and `scene_node_for` (→ scene layout, hit-test, scroll clips) now consume the resolved absolute geometry. `LayoutOutput` is left **unchanged and parent-relative** — the layout contract is correct; the bridge was the sole wired consumer that mishandled it (`SceneGeometryAttachment::from_layout` shares the same latent trap but has no wired consumer — test-only — so it is left as a documented hazard, not a live bug). `RuntimeSceneFrame::layout()` still exposes the raw parent-relative `LayoutOutput`; the `geometry`/`draw_commands`/`scene` outputs are now absolute.
- **Test.** `runtime_scene_bridge_resolves_absolute_geometry_for_nested_nodes` builds a depth-3 tree (`root → {spacer, panel → dot}`) where `panel` stacks at y=150 and `dot` sits at `panel`'s content origin; it asserts `dot`'s absolute geometry `(0, 150)` on the draw-command path (`geometry_for` + the matching `RuntimeDrawCommand`) and on the scene-graph hit-test path. It failed at the parent-relative `(0, 0)` before the fix and passes after. Full workspace suite stays green (627 tests) — confirming no existing fixture depended on the buggy relative coordinates.
- **Supersedes** the `hawk2ui-layout` doc-only remediation (`0113eef`): that change correctly documented the parent-relative contract and pinned it with a test, but left the actual defect (an unaccumulating consumer) live. This fixes it at the consumer. The layout review is annotated accordingly.

## Completeness & implementation gaps

1. **No script loading or execution; `RecordingScriptEngine` is the only `ScriptEngine`** (`script.rs:362` `RecordingScriptEngine`). Every trait method (`load_module`, `call_export`, `resolve_promise`, `set_timer`, `call_host`, `interrupt`, `teardown`) records its argument into `operations` and returns `Ok(())`. This is a legitimate test/conformance fixture and a clean trait seam for a future engine — but no engine exists in-tree, so the headline capability named in `lib.rs` (`//! Script loading … for Hawk2UI`) is not realized here. → Either document the crate as the runtime *model/boundary* (engine supplied elsewhere) or land a real adapter. Do not read this as a stub-with-`todo!`; it is record-only by construction.
2. **Lifecycle hooks are registered but never run; no mount/unmount ordering** (`lifecycle.rs`). `LifecycleRegistry::hooks_for(phase)` returns hooks filtered by phase in insertion order. Nothing invokes them, sequences `Mount`→`Update`→`Teardown`, or enforces the Shutdown-before-Teardown intent encoded by the `LifecyclePhase` enum. The crate doc claims "lifecycle" handling; in practice it is a record. (Contrast: `BindingLifecycleAvailability::allows` *does* consume the phase to gate bindings — that part is real.)
3. **`HostBindingCall` is a validated descriptor, not a performed call** (`bindings.rs:128`). `call()` returns a struct describing an authorized call; nothing in this crate dispatches it to a host. Consistent with the record-layer theme — worth stating so a reader does not assume the binding executes.
4. **Crate-level documentation overreach** (`lib.rs:2`). `//! Script loading, host bindings, event dispatch, scheduling, lifecycle, and runtime safety` — of these, *script loading* and *lifecycle* (hook invocation/ordering) are not performed. Event dispatch, scheduling, safety, and binding validation are. The doc should distinguish "models/records" from "performs."

## Code quality & smells

- **`RuntimeViewTree::with_child` is O(n²)** (`view.rs:585`). Each insert calls `index_of` twice (duplicate check + parent lookup), each a linear scan of `entries`. Building an `n`-node tree is `O(n²)`. This is the per-insert cost behind the recursive `scene_payload::append_children` (see Security: a deep/wide untrusted payload is a CPU-amplification vector on top of the stack-depth one). `entry`/`index_of`/`node`/`children_of`/`geometry_for` are all linear scans; a `BTreeMap<RuntimeViewId, usize>` index would remove the quadratic behavior.
- **Bubble delivery has no dedup** (`events.rs:223` `delivery_targets`). `targets = [event.target] + bubble_path`, then filtered by listener membership. If `event.target` also appears in `bubble_path`, that listener is delivered the event **twice**. The bubble test uses disjoint targets, so this is invisible. Minor, but a handler-side surprise.
- **Partial `Diagnostic` bridge** (`bindings.rs:170`). Only `HostBindingError` implements `From<…> for hawk2ui_api::Diagnostic`. The other error types — `RuntimeError`, `RuntimeEventError`, `RuntimeScheduleError`, `ScriptEngineError`, `RuntimeGuardDenial`, `RuntimeStatePersistenceError`, `RuntimeScenePayloadError`, `RuntimeSceneError` — carry a `code`/`message` shape but have **no** bridge to the unified diagnostic stream. The workspace convention is that domain errors fold into `hawk2ui_api::Diagnostic`; here only 1 of ~9 does. → Add `From` impls (most are mechanical) or document why these stay private.
- **`is_stable_key` permits `.` and `..`; inconsistent with `is_valid_storage_root`** (`persistence.rs:318`). `is_stable_key` allows `-`/`_`/`.`, so `".."` is an accepted key. `user_preset_path` interpolates `plugin_id`/`preset_id` into `"{root}/presets/{plugin_id}/{preset_id}.hawkstate"`. Keys cannot contain `/`, so a single `..` segment escapes `presets/` into the store root only (not arbitrary traversal), and the function returns a `String` (no FS I/O in this crate). But `is_valid_storage_root` deliberately rejects `Component::ParentDir`, so the two validators disagree about `..`. → Reject `.`/`..`-only keys in `is_stable_key` for consistency. **Low.**
- **`RuntimeViewId`/view types are not `Serialize`/`Deserialize`** while almost everything else in the crate is. This is *good* (the view tree is built programmatically, not deserialized) and is the reason `view.rs` is not a deserialization-recursion vector — noted here so the asymmetry isn't mistaken for an oversight.
- **`RecordingScriptEngine` derives `Deserialize`** with private `operations`/`torn_down` — it can be reconstituted with fabricated history. Benign (snapshot fixtures), same pattern as a11y's dispatcher.

## Security

`#![forbid(unsafe_code)]` holds; there is no `unsafe`. The crate's trust boundaries are (a) **`Deserialize`-able runtime/view/state trees from untrusted input** and (b) **script-provided binding payloads**. The gating story is otherwise good: capability/lifecycle/schema enforcement happens before a binding call is authorized, and the audio-thread guard denies script/render/fs/network/blocking operations.

- **Unbounded recursion over a `Deserialize`-able scene payload → stack-overflow DoS** (`scene_payload.rs`). `RuntimeScenePayloadNode` derives `Deserialize` with a self-referential `children: Vec<RuntimeScenePayloadNode>` (line 79). `from_json` (line 26) accepts **any** caller-supplied `serde_json::Value`; `validate()` recurses over `children` (lines 108–110), and `append_children` recurses (line 227) — both with **no depth bound of their own**. A deeply-nested payload overflows the stack and crashes the host/editor process. **Mitigating context (state it):** these payloads are carried in `hawk2ui-build` *sealed artifacts* that *can* be Ed25519-signature-verified (`hawk2ui-build/src/artifact.rs::TrustedArtifactKeyring::verify`). **But that verification lives in another crate and is not coupled to `from_json`**, which is public API. The actual consumer confirms the gap: `hawk2ui-plugin-adapters::…::runtime_scene_frame` (lib.rs:615) reads `sealed_artifact.runtime_scene` (a `serde_json::Value`) and calls `RuntimeScenePayload::from_json(...).build_frame()` **with no signature verification at the call site** (the method doc says "verified," the code path does not verify). A crate cannot assume its callers verified; `from_json` accepts any `Value`. Because `from_value` runs on an already-materialized `Value` (serde_json's 128-deep read limit may not have applied if the `Value` was built programmatically) and the crate imposes no cap, the airtight defect is the **absence of a crate-side depth bound**. Consistent with a11y's High for the same class. → Add an explicit depth limit in `validate`/`append_children` (and/or a `RecursionLimited` deserializer). **High.**
- **`StructuredValue` is recursive-`Deserialize` and crosses every untrusted surface** (`script.rs:55`). `Array(Vec<StructuredValue>)` / `Object(BTreeMap<String, StructuredValue>)` are self-referential and `Deserialize`. `StructuredValue` flows through event payloads (`events.rs`), persistence entries/snapshots (`persistence.rs`), and host-binding payloads (`bindings.rs`) — all `Deserialize`-able. No operation in this crate recurses over it today, so it is not an *active* overflow path here, but any consumer that recurses (or a deeply-nested literal in a deserialized snapshot/payload) inherits the same DoS class as the scene payload. Note it so the omission isn't conspicuous; bound on deserialize. **Low / verify.**
- **CPU-amplification on the untrusted append path** (`view.rs:585` + `scene_payload.rs:217`). `append_children` calls `with_child` per node, and `with_child` is `O(n)` per insert → `O(n²)` to build an `n`-node payload. A wide (not just deep) untrusted scene payload is a quadratic CPU sink on top of the stack-depth concern. Pairs with the High above. **Low.**
- **Path-key validator inconsistency** (`persistence.rs:318` `is_stable_key`). Permits `..`; `user_preset_path` would emit a `presets/../…` segment (escapes into the store root only; returns a string, no FS I/O in-crate). `is_valid_storage_root` rejects `ParentDir`, so the validators disagree. Low blast radius, but a real inconsistency on a path-construction boundary. **Low.**
- **Unbounded queue/history growth (memory DoS).** `RecordingScriptEngine.operations` (`script.rs`), `RuntimeEventDispatcher.queue`/`listeners` (`events.rs`), every `RuntimeScheduler` queue (`scheduler.rs`), and `RuntimePersistenceStore.snapshots` (`persistence.rs`) grow without cap or drain-on-error budget. A runaway or hostile producer (event/timer injection) is a slow memory-exhaustion vector — the same theme as a11y's unbounded `events`. Note `enqueue`/`schedule_*` accept events unconditionally; teardown/shutdown clear queues but only on the next drain. **Low.**
- **No panic-as-DoS surface found.** Arithmetic uses `saturating_*`/`div_ceil`; `checked_order` uses `try_from(...).unwrap_or(i32::MAX)`; float validation rejects non-finite/≤0 text metrics and viewport/node dimensions (`view.rs::validate_runtime_node`, `scene_payload.rs::validate_positive_f32`). No indexing/`unwrap` on untrusted data in the hot paths.
- **Good:** the audio-thread guard (`safety.rs`) denies script/render/fs/network/blocking ops and is exercised by tests; binding gating is enforced before authorization; `deny_unknown_fields` is set on every scene-payload struct; storage-root validation rejects relative/`..`/`./`/backslash/NUL roots.
