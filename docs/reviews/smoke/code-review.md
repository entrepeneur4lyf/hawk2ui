# Code Review — hawk2ui-smoke

**Reviewed at:** `5a042c51` · 2026-05-28
**Scope:** `src/lib.rs` (~915 LoC — the runner *and* the result types live here) + `tests/smoke_apps.rs` (~195 LoC, the CI-gated `--test smoke_apps`) + `Cargo.toml`. Fixtures live under workspace `examples/{desktop-basic,desktop-dashboard,plugin-synth-editor,plugin-meter-analyzer,style-gallery,security-denials,frameworks/*}`.
**Purpose:** "Smoke application runner and fixtures for `Hawk2UI` desktop, plugin, visual, and security validation." Seven `SmokeRunner` methods each drive one fixture and return a typed result the test asserts on, across the four claimed domains: desktop, plugin, visual, security (plus a cross-framework example sweep).
**Note:** Codex is concurrently committing hardening/remediation work; HEAD drifts. Findings reflect the SHA above and may overlap with in-progress fixes.

## Summary

The crate splits into two tiers, and the split *is* the review. The decisive structural fact is the **dependency set**: `Cargo.toml:19-31` pulls in `authoring`, the four framework crates, `host`, `host-baseview`, `layout`, `plugin`, `render`, `runtime` — and **deliberately omits `hawk2ui-build`, `hawk2ui-style`, `hawk2ui-script`, and `hawk2ui-host-winit`**. Those are exactly the crates that implement manifest parsing/validation (`HawkManifest::parse`, `manifest.rs:176`), asset/style/script compilation, and the real desktop CPU renderer (`SoftwareFrameRenderer::render_scene_frame`, `host-winit/software_frame.rs:208`). So the desktop and security runners *physically cannot* drive a real build, validation, or render path — they are limited to reading a pre-written fixture file and asserting on substrings. This is not a tactical shortcut; the dep graph is incompatible with the package's own promise of "desktop … and security **validation**."

- **Genuinely real (keep — real end-to-end paths).** Two runners reach real engine code. `run_plugin_synth_editor` (`lib.rs:336`) calls `BaseviewPluginAdapter::attach` → `try_host_resize` → `try_dpi_changed` → `render_scene_frame`, and the latter rasterizes through a real `SkiaRendererBackend` (`host-baseview/lib.rs:1803` `render_scene_to_skia_snapshot`: `create_surface_with_config`/`begin_frame`/`clear`/`draw_runtime_scene_frame`/`end_frame`/`frame_snapshot`). The asserted pixel `0x001a_6f4a` (`lib.rs:879`) is the **actual rendered fill** of `Color::rgba(26,111,74,255)` (`lib.rs:872`), and `baseview_surface_size == [960,540]` is `640×360 × 1.5` computed by `metrics.physical_size()`. **This is the only real Skia output in the crate** — and it lives in the *plugin* path, not the "visual" path. `run_framework_examples` (`lib.rs:534`) compiles four real frameworks (`SvelteIntegration::compile_to_runtime`, React/Vue/Solid `render_to_runtime`) through `NativeRuntimeBridge::bridge_artifact` into a real `RuntimeViewTree`. The realtime drop/drain in `run_plugin_meter_analyzer` is real (real `rtrb::RingBuffer` producer/consumer, `realtime.rs:258`).
- **Modeled / canned (false confidence — the central risk).** `run_desktop_basic`, `run_desktop_dashboard`, `run_style_gallery`, and `run_security_denials` each `require_file(...)` some inputs, then read **one answer-key artifact** (`artifacts/scene.json`, `artifacts/visual.snap`, `artifacts/snapshots.txt`, `fixtures/denials.txt`), `.contains()`-check expected substrings, and return a **hardcoded struct literal**. No layout solve, no style compile, no asset sanitization, no manifest parse, no render. The asserted numbers (`layout_nodes=18`, `style_rules=12`, `snapshot_count=13`) are typed into both the fixture and the runner.
- **The circularity is tighter than the sibling conformance crate.** There, presence-checks at least guarded *real product files* (scripts, manuals) for drift. Here the checked files are **answer keys co-authored with the assertion**: `fixtures/denials.txt` literally contains the line `runtime_surface_launched=false`, which the runner reads and then the result hardcodes to `false` (`lib.rs:643-648`), which the test then asserts (`smoke_apps.rs:164`). The fixture, the runner return, and the assertion are three copies of the same constant.

No compile/correctness blocker: the suite builds and the two real-tier runners are sound. The defect is that four of seven runners — including the entire **security** domain and both **visual** snapshot assertions — assert on fabricated text, and the **test names oversell** what the real runners exercise.

## Completeness & implementation gaps

1. **Security domain is fully modeled, and structurally so** (`run_security_denials`, `lib.rs:620`). The runner reads `fixtures/denials.txt` (seven hand-written denial codes + a `runtime_surface_launched=false` line), asserts each line is present, and returns those same seven strings with `runtime_surface_launched: false`. **No manifest is parsed, no capability is evaluated, no script/asset is rejected.** `examples/security-denials/manifest.hawk.toml` and `fixtures/denied.ts` are only `require_file`'d (existence), never fed to any validator. Because the crate does not depend on `hawk2ui-build`/`-style`/`-script`, it *cannot* call `HawkManifest::parse` or the asset/style sanitizers without a new dependency. A regression that stopped denying an undeclared-filesystem capability, an unsafe asset, or a malformed manifest would leave this test green. This is the single highest-impact item — detailed in **Security**.
2. **Both "visual" snapshot assertions are canned text, not pixels** (`run_desktop_dashboard` `lib.rs:295`, `run_style_gallery` `lib.rs:485`). `visual.snap` and `snapshots.txt` are static files; the runner substring/line-matches them and returns literals. `deterministic=true` (`lib.rs:519`) is asserted from a string in the fixture, not by rendering twice and diffing. The dashboard's `layout_nodes=18`/`style_rules=12` are never computed by `hawk2ui-layout`/`hawk2ui-style` (both available as deps — so here the omission is a *choice*, not a dep limitation). The task's "is the visual smoke real Skia?" question resolves to **no** for the visual domain; the only real raster is `baseview_visible_pixel` in the plugin path.
3. **`run_desktop_basic` exercises no desktop runtime** (`lib.rs:245`). It checks six fixture files exist, reads `scene.json`/`first-frame.snap`, substring-matches `"desktop-basic-root"` and `desktop-basic:first-frame`, and returns a struct with hardcoded `window_events: ["created","focused","repainted","closed"]`. The window lifecycle is a literal vector — no window is created, focused, repainted, or closed. The desktop renderer (`SoftwareFrameRenderer`) is in `host-winit`, which is **not a dependency**, so the real path is unreachable.
4. **Native framework "example" is canned, unlike the other four** (`native_contract`, `lib.rs:679`). svelte/react/vue/solid compile their *actual source files* (`App.svelte`/`App.tsx`/`App.vue`) through real integrations. Native instead substring-checks `app.ts` for five tokens and then builds the contract from a **hardcoded `native_root()` tree** (`lib.rs:722`), ignoring `app.ts` entirely. So `conformance_equivalent` (`lib.rs:596`) is genuine for four frameworks and **tautological for native** (it compares a hand-built tree against the constants the same function hardcodes).
5. **Realtime non-blocking / zero-allocation assertions are vacuous** (`run_plugin_meter_analyzer`, `lib.rs:472-473`; `smoke_apps.rs:101-102`). `RealtimeVisualTransport::allocation_count`/`blocking_wait_count` (`realtime.rs:349,355`) are initialized to `0` and **never incremented anywhere** in `realtime.rs` (confirmed: no `+=`/`saturating_add` writes them). Asserting `blocking_waits == 0` and `allocations_on_audio_thread == 0` therefore asserts that two inert fields equal their construction value — it proves nothing about runtime behavior. The *real* non-blocking guarantee comes from the lock-free `rtrb::RingBuffer` type, not from these counters. (The `channels`, `dropped_frames`, `transport_capacity` assertions on the same result **are** real — they reflect the actual push/drain.)
6. **Plugin synth editor test name claims three things it does not run** (`smoke_apps.rs:49`, `plugin_synth_editor_exercises_editor_parameters_automation_state_and_destroy`). Parameters, automation, and state-roundtrip are read as substrings from the canned `editor.trace` and returned as literals (`lib.rs:388-403`); no parameter is set, no automation event is dispatched, no state is saved/loaded. Only `attach`/`resize`/`dpi`/`render→Skia`/`destroy` is real. The name should reflect that only the lifecycle + render is exercised.
7. **`examples/plugin-basic` is an orphan fixture** (no runner references it; `grep` finds it only in conformance/build crates). The smoke crate's own doc string claims "plugin … validation," but the basic plugin fixture is never smoke-run here — only `plugin-synth-editor` and `plugin-meter-analyzer` are. Either wire a `run_plugin_basic` or note that "plugin basic" coverage lives in conformance, not smoke.
8. **No negative/error-path coverage anywhere.** Every test is happy-path. There is no test that a *missing* fixture file produces the `require_file` error, that a target-kind mismatch returns the guard error (`lib.rs:246,299,340,420,489`), or that a malformed artifact fails. The error branches (`Err(...)` returns and the `format!` mismatch messages) are entirely unexercised — including the unreachable `_ => Err(...)` arm in `framework_contract` (`lib.rs:675`), which is dead because `run_framework_examples` only ever passes the five known names.

## Code quality & smells

- **Result types are over-engineered relative to use.** Every result struct (`DesktopSmokeResult`, `DashboardSmokeResult`, …, `SecurityDenialSmokeResult`) derives `Deserialize` + `Serialize` (`lib.rs:100,115,134,…`), but nothing in the crate ever serializes or deserializes them — the tests construct them via the runner and assert field-by-field. The `Serialize`/`Deserialize` surface is inert (see Security for the `Deserialize` note). Likewise `SmokeFixture`/`SmokeTargetKind`/`SmokeBuildResult` carry `Deserialize` with no loader.
- **`SmokeBuildResult { built, artifact_verified }` is always `{ true, true }`** (`lib.rs:270-273`). Both fields are hardcoded `true` whenever the file-existence checks pass; there is no path that sets either to `false`. The struct models a build/verify outcome that is never actually false — pure record-only state.
- **`audio_writes` is a redundant recomputation** (`lib.rs:469`: `accepted_writes + dropped_frames`). With `DropNewest` + capacity 4, packets 1-4 are accepted (dropped=0) and packet 5 ("overflow") is `rejected_with_drop` (accepted=false, dropped=1), so `4 + 1 == 5` — correct, but it reconstructs the input count by summing accepted and dropped rather than measuring a distinct quantity. Mildly misleading as "writes."
- **`SmokeFixture::name()` swallows a missing filename to the literal `"fixture"`** (`lib.rs:65-71`) via `unwrap_or("fixture")`. Harmless for the fixed fixtures, but it means a malformed `relative_path` silently produces a fixture named `"fixture"` rather than an error — another inert fallback.
- **Six near-identical runner bodies.** Each `run_*` repeats the same shape: target-kind guard → `require_file` list → `fs::read_to_string` → substring loop → hardcoded struct. The substring-loop-over-required-tokens pattern is copy-pasted five times with different literal arrays. A single `assert_fixture_contains(path, &[...])` helper would remove the duplication.
- **`#[lib] name`/`path` are redundant** (`Cargo.toml:12-14`) — restate the default `src/lib.rs` and the derived lib name. Cosmetic; matches the sibling conformance crate's same minor smell.

## Documentation

- Crate-level `//!` is present and matches the manifest description (`lib.rs:2`). Every public type, field, and runner method is documented, and each fallible `run_*` carries an accurate `# Errors` section (`lib.rs:241-244`, etc.). `CRATE_NAME`/`crate_name()` documented (`lib.rs:909,912`). No *undocumented* public items.
- The documentation is, however, **optimistic to the point of being misleading**. Method docs say "Runs the basic desktop smoke fixture" / "Runs the security denial smoke fixtures" without disclosing that these read a canned artifact and assert substrings rather than running a desktop app or denying anything. Given the false-confidence risk, each modeled runner should carry a one-line caveat ("asserts recorded fixture evidence; does not drive the live build/render/validation path") so future readers do not over-trust the green check — the same recommendation the conformance review made for its presence-only tests.
- Test functions carry no comment distinguishing real vs modeled. `plugin_meter_analyzer_proves_non_blocking_transport_and_ui_consumption` (`smoke_apps.rs:85`) "proves" non-blocking via two never-incremented counters — the name asserts a guarantee the body does not establish.

## Testing

The crate *is* a test harness; the meta-question is whether each scenario drives a real path. Per-runner verdict:

- **Real behavior (keep):** `run_plugin_synth_editor`'s baseview half — real attach/resize/dpi + **real Skia raster** with a pixel assertion on rendered output (`lib.rs:362-407`). `run_framework_examples` for svelte/react/vue/solid — real source compile → real `RuntimeViewTree` (`lib.rs:755-861`). `run_plugin_meter_analyzer`'s drop/drain/capacity/channels — real lock-free transport (`lib.rs:440-466`).
- **Modeled (false confidence):** `run_desktop_basic`, `run_desktop_dashboard`, `run_style_gallery`, `run_security_denials` — all four read an answer-key fixture and return literals (`lib.rs:257-287`, `306-328`, `497-526`, `627-648`). The "visual" snapshot domain is entirely in this tier.
- **Vacuous within an otherwise-real test:** the zero-alloc / non-blocking asserts in meter-analyzer (inert counters, see gap #5); the native contract in framework-examples (hardcoded tree, see gap #4); the parameter/automation/state asserts in synth-editor (canned `editor.trace`, see gap #6).
- **Coverage gaps:** zero negative tests — no missing-file, no target-kind-mismatch, no malformed-fixture, no rejected-input. The `require_file` error path, the six guard-error branches, and the `framework_contract` fallback arm are never exercised. No test ever asserts a runner *fails*, so the suite cannot catch a fixture that has been silently neutered (e.g. `denials.txt` edited to remove a denial — caught only if the *string* disappears, never if the *behavior* would now allow it).

## Cross-cutting conventions (workspace-wide; noted once, not a per-crate defect)

- `CRATE_NAME` / `crate_name()` plus `exposes_crate_identity` and `smoke_workspace_filter_marker` (`lib.rs:909-930`) — the standard package-identity + filter markers; consistent with the workspace. Not a defect.
- `#![forbid(unsafe_code)]` at crate root (`lib.rs:1`). No domain error type here (runners return `String`, not a `Diagnostic`-convertible error), so there are no `From<…> for Diagnostic` conversions to assess — see the `String`-error note below. Consistent otherwise.

## Security

The crate holds no `unsafe`, allocates/recurses negligibly, and only reads workspace files under a `CARGO_MANIFEST_DIR`-derived root (`lib.rs:901`), so it is not itself a meaningful attack surface. The security findings are about **the assurance it falsely projects** — and here that is acute, because "security" is one of its four advertised domains.

- **The security smoke provides *no* real assurance — and is structurally incapable of it (false assurance, High).** `run_security_denials` (`lib.rs:620`) asserts that `fixtures/denials.txt` *contains* seven denial-code strings and a `runtime_surface_launched=false` line, then returns those same constants. It never parses `manifest.hawk.toml`, never evaluates a capability grant, never sanitizes `denied.ts` or any asset, and never denies anything. Worse, the crate **does not depend on** `hawk2ui-build`/`hawk2ui-style`/`hawk2ui-script` (`Cargo.toml:19-31`), so it *cannot* invoke `HawkManifest::parse` (`manifest.rs:176`) or the asset/style validators that actually implement denial — the string-match is not a shortcut, it is the only thing the dep graph permits. The fixture is an **answer key**: it contains the literal `runtime_surface_launched=false`, the runner hardcodes `false`, the test asserts `false`. A real regression that began *allowing* an undeclared-filesystem capability, an unsafe SVG, a hash-mismatched manifest, or an unsupported style would not flip this test. The crate's name implies it guards security properties; it only guards that a hand-written text file still contains the expected words.
- **No malicious input is ever exercised.** The seven denial categories (`filesystem.undeclared`, `network.denied`, `clipboard.denied`, `secret.redacted`, `asset.unsafe`, `style.unsupported`, `manifest.invalid`) name precisely the denial paths a security smoke *should* drive end-to-end. None is driven. The sibling crates *do* implement these (e.g. `HawkManifest::parse` validates and rejects; the asset compiler has `AssetSanitizationStatus`), so the gap is purely that this crate asserts strings instead of feeding a hostile fixture through a validator and asserting the rejection diagnostic — the identical "documentational-only security" failure the conformance review flagged, one rung worse (text the crate authored itself, not a product file).
- **`Deserialize` on every result/fixture struct is an unused, inert surface.** `SmokeFixture`, `SmokeTargetKind`, and all eight result structs derive `Deserialize` (`lib.rs:34,43,75,…`) but nothing in the crate ever deserializes them — there is no fixture-loading-from-untrusted-input path. So it is **not** a live attack surface today, but it is a latent one: if a future change starts loading these from a fixture file, the derives are already present and would accept arbitrary input. Note and drop the derives unless a loader is planned.
- **Panic-as-DoS in test helpers (minor).** The tests use `.expect(...)` on every runner call (`smoke_apps.rs:9,30,55,…`); a missing/edited fixture aborts the test rather than reporting a denial outcome. Acceptable in a test binary (test failure is the intended signal), noted only for completeness.
- **Security-relevant behavior is claimed-covered but unexercised.** The package description asserts "security validation"; the desktop and visual domains likewise claim "validation." On the evidence above, *security* validation is entirely unexercised here, and *desktop/visual* validation is reduced to string-matching. The only domain where the crate's claim is backed by real execution is the plugin baseview render and the realtime transport drop/drain.
